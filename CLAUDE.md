# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is the overview: the project, how to build and run it, the one data structure everything turns on, the repo-wide conventions, and **which document covers what**. The detail lives in `docs/` — see "Where the rest is documented" below, and read the relevant document before working on that area.

## Project

BS3D is a 3D Puzzle-Bobble-style game (shoot balls at a hanging 3D cluster of balls) built with MonoGame and BepuPhysics 2. Repo: https://github.com/AntoninPrazsky/BS3D — tasks are tracked in GitHub issues.

**Finished work lands on main immediately** (the owner's standing instruction): once a task is done and verified, its branch is merged to main right away — work sitting on a side branch is work the owner cannot see. This said "its PR is merged" until 2026-08-14, which contradicted the branch rule below and had two agents working two different ways at once; the owner's ruling is that the branch rule below stands, so **the merge is a direct `--no-ff` merge into main and there is still no PR anywhere in this repo**. The point of the sentence is the *immediacy*, not the mechanism.

There are **three executables**: the **Testbed** (**the development instrument** — where the shot, the gun and the cameras were built, and today the rig every colour, cost and shading judgement in this project is framed through), the **MapEditor**, and **Game** — the shipping product, founded deliberately small on top of the libraries the other two already share (see `docs/game-session.md`).

**The Testbed is kept and developed deliberately, and its role is narrowed** (#100): it is an instrument, not a second game, and must never grow a menu, a HUD or a level flow — every step towards the game takes away what it is used for. It is the only executable that can hold a camera still (`campos`/`camtarget`, and `C` prints one back), isolate a pass (`arena=`, `capprobe=`), sweep variants inside one process (`alt=`), drive itself without a keyboard, the mouse included (`at=`, `hold=`, `aim=`, `rmb=`) and photograph itself (`shot=`, `shotframe=`); the Game's camera orbits and its levels override the scene they were launched with, and the MapEditor has no simulation, gun or shot at all. See `docs/testbed.md`.

All three run on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0). MapEditor used to be on **DesktopGL**, where MojoShader capped shaders at Shader Model 3.0 and everything 5.0-only in the shared `InstancedModel.fx` had to sit behind `#if OPENGL` — it was moved to WindowsDX so it can render the balls exactly as the game does (full linear + tonemap parity, see "The map editor's render pipeline" in `docs/formats-and-tools.md`). There is no OPENGL build of any shader now, and the `#if OPENGL` branches are gone. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers, and each executable brings its own reference (all now the same WindowsDX package). MapEditor and Game build `Testbed/Content/Shaders/InstancedModel.fx` (and `Tonemap.fx`, `Glare.fx`, the scene shaders, …) out of the Testbed content directory, so there is one copy of each shader and a change reaches every executable at once. **`Sky.fx` is the one exception and it is the Game's only**: the MapEditor's content project has no entry for it at all, so the editor draws the dome through its own `BasicEffect` and gets no cloud deck and no sun disc — which is what `Sky.fx`'s own header says, and is why a scene wanting a per-scene sky feature cannot put it there (see "The storm" in `docs/scenes.md`).

## Build and run

```powershell
# From the repository root: the paths below are relative to it (#594)
# Build everything (libraries + Testbed game)
dotnet build Testbed.sln

# Run the game testbed / the map editor / the game
dotnet run --project Testbed\Testbed.csproj
dotnet run --project MapEditor\MapEditor.csproj
dotnet run --project Game\Game.csproj

# Testbed can load a map right at startup (useful for testing)
Testbed.exe Testbed\Maps\Full.json
```

There are four solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln`, `MapEditor.sln` and `Game.sln` (each executable plus the libraries it uses). There is one test project, `Tests/BS3D.Tests` (xUnit, plain `net10.0`, in `Game.sln` and `BS3DLibs.sln`, #586). It checks the invariants the libraries state "by construction": the neighbour rule, one constraint per pair, the legacy padding's parity, the level round-trip, the save outcomes, the scoring mechanics and the top-level ceiling anchor. Run it with `dotnet test Tests\BS3D.Tests`; `build.yml` runs it on every push (see "The logic tests" in `docs/formats-and-tools.md`). There is no lint configuration. **Three root files configure every project at once** (#587): `global.json` names the SDK band (`10.0.200`, `rollForward: latestFeature` — a floor, so a newer band still builds; both workflows install `10.0.2xx` so CI and the release compile with the band the owner does), `Directory.Packages.props` holds **every NuGet package version** (central package management — a `PackageReference` names the package and nothing else, so MonoGame, Bepu and NVorbis cannot drift apart between projects; bump a version there, never in a `.csproj`), and `.editorconfig` the indentation and LF. `Prazsky.Core` references no Bepu: `Prazsky.BS3D.Physics` is the one library that does, so a `using BepuPhysics;` in Core or `Prazsky.BS3D` no longer compiles and the MapEditor no longer carries `BepuPhysics.dll`. Every executable's Debug build writes `bin\net10.0-windows\` and its Release build `bin\Release\net10.0-windows\` (the MapEditor's Release wrote over its Debug exe until #587).

**Two GitHub Actions workflows run on `windows-latest`** (`.github/workflows/`), and both are free because this repository is **public** — GitHub bills neither standard-runner minutes nor release storage on a public repo. `build.yml` (#387) fires on every push (except one touching only the agent journal or `Research/`), builds all four solutions and `Game.sln` once more in Release — the configuration players get — runs both gates (the level regeneration check refuses an untracked level file too) and, since #588, the three "seen to fire" self-checks every push rather than by hand (`ScoreSim --ceiling-scale 0.25` must refuse, `WindingCheck --selftest`, the destructive-git guard's test); it is what says `main` compiles on a machine that is not the author's. `release.yml` (#453) makes the download a player runs: a pushed tag `v*` publishes `Game` self-contained for `win-x64` (`dotnet publish -r win-x64 --self-contained`), asserts the published folder really carries the runtime, the compiled shaders, the levels and the music, zips it (one top-level folder; **218.1 MB** zipped from a 320.6 MB publish, re-measured locally 2026-09-23 after #486 — **162.3 MB of that is `Music/`**, the twelve families of generated recordings, so three quarters of the download is now audio. It was 70.9 MB with the logo and 68.3 without before those tracks landed, and the runner's zip came out 1.7 MB larger than the local one at that size) and creates a **GitHub Release** with the zip attached (and, since #549, ScoreSim's score ceiling table beside it; since #588 a `SHA256SUMS` of both, and the level gate and ScoreSim run in the release job itself, so a tag on a commit whose gate fails publishes nothing) — nothing for the player to install, no .NET, no MonoGame, no DirectX redistributable. The "Run workflow" button does the same build and leaves the zip as a workflow artifact **without** publishing anything, which is how the pipeline is rehearsed. Only the Game ships; the Testbed is the instrument and the MapEditor an authoring tool. Deliberately **not** trimmed and **not** single-file (Myra, FontStashSharp and the content pipeline all reflect, and `Content/`, `Levels/` and `Music/` sit beside the exe anyway), and the exe is **unsigned** — a certificate is the one part of this that costs money, so SmartScreen warns on a player's first launch and the release notes say so.

Besides the three executables there are seven **tools**, all in `Game.sln` and all but the last two plain `net10.0` console apps with no graphics device. `Tools/LevelGen` is the generator that writes the game's pattern levels and the checks that say a generated level is playable before anyone plays it. `Tools/ScoreSim` plays every shipped level several ways through the real `ScoreKeeper`/`StarRating` and refuses a scoring rule that rates them wrongly — it exists because #173 found the star rating ordered backwards against skill on every level, a fault no individual number showed; since #549 it also refuses a score ceiling a simulated clear reaches and, with `--ceilings`, writes the table the online boards whitelist levels against, keyed by `LevelIdentity`. Those two exit non-zero on a failure so they can go in front of a commit; see "The level generator" and "The scoring simulator" in `docs/formats-and-tools.md`. `Tools/MusicBake` renders the game's six procedural pieces of music to .wav and prints what they measure (length, loudness, channel balance, where the energy sits, and a two-second envelope that says when a piece arrives) — it is not a gate but an ear (though since #464 it does refuse a limiter drive or a streamed render that drifted from the one-shot piece, exit 3 and 4, and since #467 a loudness meter off its standard, exit 5 — every table carries a K-weighted LUFS column beside the RMS, and `--shipped` prints it for every track in `Game/Music` without the masters): music is the one part of this game that cannot be judged from a screenshot, and hearing a piece in the game means playing a level of the right chapter for two minutes. It compiles `Game/Audio/ProceduralMusic.cs` straight into itself, so what it writes is the same arithmetic the About page's player plays. **Since #443 the music a level plays is generated recordings** (`Game/Music/*.ogg`, grouped into families by the name before the first dash and decoded to PCM when a family is first asked for, played by `GameMusic`), and `MusicBake --tracks` is what writes them — every master named `theme-<track>.wav` in `Research/AI-Music` (or in a `--masters` folder outside the repository, where the generated families' masters live since #486) brought to the themes' loudness, its peaks held under full scale, encoded as Ogg Vorbis (#444) and decoded straight back through the game's own decoder to check that every loop still has its exact length. `MusicBake --sfx <wav> <name>` does the same for one generated **sound effect** (#482): `Game/Sfx/<name>.ogg`, mono, decoded back to prove its length — the shot, a landing, a release, the firework's burst, the victory fanfare, the ceiling's step (#500) and the line's cut (#434) are such renders since #482 (`--music` keeps a piece stereo and writes the key and tempo tags the star chime tunes to), and `ProceduralAudio` bakes any one whose file is missing ("The sound" in `docs/game-feedback.md`). `Tools/SemanticSearch` ranks the GitHub issues (and, with `--journal`, the agent journal; with `--docs`, the sections of the documents listed below, #490) by what they *mean* rather than by the words they share, through a local embedding model in LM Studio — run it before filing an issue, because #319 was filed an hour after #316 and #317 described the same levels in other words. It needs LM Studio running with `text-embedding-qwen3-embedding-0.6b` loaded — the default since #439, which measured it never worse than nomic on the English issues and far better on the Czech journal (see "The semantic search" in `docs/formats-and-tools.md`). Ask it before reading a whole document: on fifteen questions with a known section it put that section first twelve times and second twice. `--ask` then answers from those results through Gemma 4, citing them — a lead into the entry it names, never a source (#494). `Tools/DocDrift` lists the figures `docs/` and this file quote beside a name the code defines with another value — a hand-run triage sweep that always exits 0, never a gate: `dotnet run --project Tools\DocDrift` (`-- --all` adds the ones set aside as history; see "The number-drift sweep" in `docs/formats-and-tools.md`, #525). The last two check a convention below rather than a number (#400), and neither is a gate: `Tools/WindingCheck` (`net10.0-windows`, on DirectX's software rasteriser, no GPU and no window) builds every procedural mesh through its own constructor and judges every triangle's winding against its normals and by signed volume, and `Tools/VectorBoundary` is a Roslyn analyzer a build is pointed at to list every Xna/Numerics crossing through a conversion operator (see "The winding check" and "The vector boundary scan" in `docs/formats-and-tools.md`).

MonoGame content (`Content/Content.mgcb` in each executable) is compiled automatically during build by `MonoGame.Content.Builder.Task`; editing the .mgcb itself is normally done with the MonoGame Pipeline Tool. **Each executable needs its own `.config/dotnet-tools.json`** pinning the `mgcb` tool — the content build shells out to `dotnet mgcb`, and the manifest search walks up from the *project* directory, so a new executable without one fails the content build with "Nenašel se soubor manifestu" even though its siblings build fine (`dotnet tool restore` once after adding it). All three executables target `net10.0-windows` and pull in WinForms (WindowsDX hosts its window on it), so they are Windows-only; the libraries target plain `net10.0`.

It loads and saves whole **levels** (map + scene name + sky; the scenes' parameters are fixed in code since the format-2 refactor). It has no GUI of its own since #522: the live scene-config panel that once tuned those fixed looks is gone, because a scene's look is programmed, not configured. See `docs/formats-and-tools.md`.

### The ball grid

The central data structure is a 3D array `[x, z, level]` where **level is the vertical (Y) axis**. Odd levels are shifted by +0.5 in X and Z (hexagonal-like packing); vertical spacing between levels is `1/√2`. `BallsMap.GetRealPosition` maps array coordinates to world positions, and `Center()`/`ComputeCentered` translate between the raw grid frame and the centered world frame. A cell has 4 neighbors on its own level and up to 4 on each adjacent level; which diagonal offsets are the true neighbors depends on level parity (`GetNeighboringCells` encodes this).

`BallsMap` holds the logical state (`StaticBall`s); `BallsConstraintsBuilder.BuildBallsStructure` mirrors it into a parallel `PhysicsBall[,,]` of dynamic Bepu bodies connected by `BallSocket` constraints to their neighbors, with the top level constrained to a kinematic ceiling body. The whole cluster hangs from the ceiling and jiggles physically.

The play field is larger than the initial ball layout: map JSON stores field dimensions (`sx`/`sz`/`l`) separately from the layout array, the layout is placed at the **top** of the field and the empty bottom levels are room for shot balls to attach into. Legacy map files without field dimensions get 6 extra bottom levels on load (an even number, to preserve level parity). The Testbed ceiling repositions/resizes itself to the loaded map (`FitCeilingToMap`).

### Constraint handle bookkeeping

Each constraint is shared by two balls, so `PhysicsBall` stores handles in three slot groups (`HandlesBottom`/`HandlesMiddle`/`HandlesTop` = balls below / same level / above + ceiling; four slots each, filled via `TryStore` in no particular order — a ball touches at most four neighbors per group). Every pair gets exactly one constraint by construction: the build pass connects same-level pairs only towards +X/+Z from each ball, and cross-level pairs only from the **even** (unshifted) level of each pair — adjacent levels always differ in parity, and neighbor index offsets depend on it (`diagonalShift`). The runtime attach path for a newly shot ball (`AttachBallToStructure`) instead connects all four same-level directions plus both adjacent levels, since the new ball has no constraints yet. Anchor offsets must be rotated into body-local space (`WorldToLocalOffset`) since bodies no longer have identity orientation once the simulation has run.

## Conventions

- **Triangle winding**: procedural meshes (`BoxMesh`, `SphereMesh`, `CannonMesh`, `LatheMesh`) wind their triangles **clockwise seen from outside**, which is what MonoGame's default `CullCounterClockwiseFace` treats as the front face — the viewport transform flips Y, so a triangle whose `(b - a) × (c - a)` points at the viewer comes out counter-clockwise in window space and is culled. Both classes had it backwards for a long time and it is a nasty bug to spot: nothing disappears, the far side of the object is drawn instead. A box reads as a hollow shell seen from inside; a sphere keeps its exact silhouette and only its shading is wrong, so the balls just looked washed out. Loaded models are wound the normal way — the opposite — so the two cannot be reconciled by picking a cull mode; flipping the mesh is the fix. `Tools/WindingCheck` checks every procedural mesh against this rule without a frame and names the deliberate exceptions (the dome, the editor's wire box, the drain's `CullNone` rims). (The sky domes carried that loaded winding until #113 made them procedural, and their captured triangle order keeps it deliberately: a dome shows front faces to a camera *inside* it, and the Testbed and the editor draw the sky under an inherited rasterizer state that is frequently `CullCounterClockwiseFace`. The last loaded model anywhere is the MapEditor's GUI `Selector.x`.) The Testbed **states** `RasterizerState` before the scene rather than inheriting it: the tonemap pass leaves `CullNone` and the overlay's `SpriteBatch` leaves its own, so what the scene culled used to depend on which of them ran last.
- Two vector types coexist: `Microsoft.Xna.Framework.Vector3` in game/render code and `System.Numerics.Vector3` in Bepu code, with **named** conversions at the boundary — the framework's own `ToNumerics()` outbound, `Prazsky.Core.Tools.NumericsExtensions`' `ToXna()` inbound. MonoGame 3.8.5 declares an implicit conversion for the inbound direction, so such a crossing compiles with nothing on the line to mark it; the named call is used anyway, deliberately, so the boundary is visible where it is crossed rather than inferred. Reading cannot find a crossing that has no call on it; `Tools/VectorBoundary` finds them with the compiler, and found five a reading pass had missed (#400).
- **Per-frame render hygiene** — the full discipline, each rule with the incident that taught it, is in `BestPractices.md`; hold all new code to it. The short form: cache `EffectParameter`/`EffectTechnique` references at load (the by-name indexers are linear scans; `InstancedModelRenderer` and `CloudField` are the patterns) and set never-changing parameters once; never `new` a GPU state object per frame (framework statics); no per-frame managed allocations (iterators included), no console I/O on load/gameplay paths, one `GetState()` per input device per frame; write a translation into `M41–M43` instead of multiplying `R × CreateTranslation` in per-ball loops; in shaders, scene-gated work goes behind a `[branch]` on a uniform (non-divergent, derivative-safe with no gradient ops inside). And comments are load-bearing: update them in the same change as the behaviour, reference constants instead of repeating values, never leave a wrong "why" standing.
- **The documents in `docs/` are held to the same standard as the comments**, and for the same reason: a measured figure that is quietly wrong is worse than no figure. When behaviour changes, change the document in the same commit; when a number is stated, it is because it was measured, so do not carry one over from a test rig into the record without re-measuring it on the real thing.
- **`git clean` and `git reset --hard` are refused in this repository**, by a `PreToolUse` hook (`.claude/hooks/guard-destructive-git.sh`, wired in `.claude/settings.json`) and by matching `permissions.deny` rules. Untracked files here are **data**: a level saved out of the MapEditor lands in `Game/Levels` as a `??`, and the editor's save dialog defaults to the working directory. A `git reset --hard origin/main && git clean -fd` once deleted three hand-built levels outright — no blob in the object database, nothing in the Recycle Bin, noticed four days later. `git add` a new level the moment it exists: a staged blob survives even a hard reset. The hook's own header carries the incident.
- **Line endings are LF, everywhere, and `.gitattributes` says so** — in the stored blob and in the working tree alike (`* text=auto eol=lf`). Until 2026-09-21 there was no `.gitattributes` at all, so the ending was decided by each machine's `core.autocrlf` and by whichever tool last wrote the file; the repository carried **470 blobs stored LF against 28 stored CRLF** (the 2023-era library sources, the `.sln`/`.csproj` set, the agent journal). The cost never landed at the edit, it landed at the **merge**: a file whose every line differs from `main`'s conflicts *whole*, so the two or three real changes had to be dug back out of a conflict spanning the entire file — which is what had been happening on nearly every merge. It had also produced a defect nothing reported: `GameplayScreen.Session.cs` carried two `\r\r\n` sequences from a script that wrote one ending into a file using the other, and **a lone CR makes git classify a file as binary** — it was the only `.cs` in the repository git would neither diff nor merge by line. LF was the choice because it was already the de facto standard, because every tool writes it unless told otherwise, and because `.claude/hooks/*.sh` must be LF or bash refuses the shebang — and one of those hooks is what refuses `git reset --hard` here. **Do not hand-write CRLF back in**, and after any script has touched a tracked file run `git diff -w --numstat` before committing: if it disagrees with `git diff --numstat`, the file was re-ended and the commit is whole-file churn. The one renormalization commit is listed in `.git-blame-ignore-revs` (GitHub honours the name; locally `git config blame.ignoreRevsFile .git-blame-ignore-revs`, once per clone) — though **measured afterwards, blame had barely suffered**: `git blame` re-attributes a re-ended line to the commit that wrote its content, so of the lines the renormalization still owns, **every one is blank** (91 of 91 in `SkyDome.cs`). Those are also the lines `--ignore-revs-file` cannot rescue, since one blank line is indistinguishable from another. The file is therefore insurance for the *next* reformatting commit rather than a repair of this one.
- **Branches are the unit of work, and there are no pull requests.** Commit a change to a feature branch off `origin/main` and push the branch; the branch is then **merged into `main` with a merge commit** as soon as the work is done and verified (the standing instruction at the top of this file; this said "when the author asks" until #594, which contradicted it) — `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`, which is what every merge in the log is. This said `--ff-only` until 2026-08-12 and the history had never done that: it matters because **two branches off the same `main` cannot both fast-forward**, so an `--ff-only` rule refuses the second one and invites a rebase and a force-push of a branch that is already pushed — on the one repository whose whole point is that several machines share `main`. The merge commit also keeps the branch's name and its one-line summary in the log, so the history reads as a list of named changes rather than a flat run of commits. Never open a PR and never offer one — a sole author reviewing their own work gains nothing from the round-trip. The branch is not a review artefact: it exists because several machines are active on this repo at once (a laptop and a desktop), so `main` is shared between them and a direct push to it from one machine is the one action that can leave another machine's checkout diverged. Name a branch `<issue-number>-<slug>` when there is a GitHub issue, a plain descriptive slug otherwise. One change per branch — the working tree here often carries several unrelated threads at once, so stage only the files belonging to the change at hand.
- **A merged branch is deleted immediately, on the remote and locally, in the same breath as the merge.** `git push origin --delete <branch>` and `git branch -d <branch>` (the safe `-d`, never `-D`: it refuses anything not actually merged, which is the check, not a formality). The merge commit already carries the branch's name and its one-line summary, so once it has landed **the branch ref holds nothing the history does not** — what it still does is *say something*, and what it says is "this is in flight". That is the whole cost of leaving it: on a repository whose point is that several machines share `main`, the list of branches is how one machine asks what the other is in the middle of, and a list of finished work reads as a list of unfinished work. Left unenforced until 2026-09-10, when it had grown to **eighteen merged branches on GitHub and about a hundred and thirty locally** — every one of them merged, so the answer to "what is actually being worked on?" had to be computed rather than read. Two exceptions, and both are temporary rather than permitted: a branch checked out in a worktree cannot be deleted until that worktree moves off it (`git worktree list` says which), and a branch the **other machine** has not fetched since the merge simply loses its upstream there, which is harmless — the work is in `main`.

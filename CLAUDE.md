# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BS3D is a 3D Puzzle-Bobble-style game (shoot balls at a hanging 3D cluster of balls) built with MonoGame and BepuPhysics 2. Repo: https://github.com/AntoninPrazsky/BS3D — tasks are tracked in GitHub issues.

There are **three executables**: the **Testbed** (where every system was built and is still tuned), the **MapEditor**, and **Game** — the shipping product, founded deliberately small on top of the libraries the other two already share (see "The game (Game)").

All three run on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0). MapEditor used to be on **DesktopGL**, where MojoShader capped shaders at Shader Model 3.0 and everything 5.0-only in the shared `InstancedModel.fx` had to sit behind `#if OPENGL` — it was moved to WindowsDX so it can render the balls exactly as the game does (full linear + tonemap parity, see "The map editor's render pipeline"). There is no OPENGL build of any shader now, and the `#if OPENGL` branches are gone. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers, and each executable brings its own reference (all now the same WindowsDX package). MapEditor and Game build `Testbed/Content/Shaders/InstancedModel.fx` (and `Tonemap.fx`, `Glare.fx`, the scene shaders, the sky domes, …) out of the Testbed content directory, so there is one copy of each shader and a change reaches every executable at once.

## Build and run

```powershell
# Build everything (libraries + Testbed game)
dotnet build C:\Projects\Testbed.sln

# Run the game testbed / the map editor / the game
dotnet run --project C:\Projects\Testbed\Testbed.csproj
dotnet run --project C:\Projects\MapEditor\MapEditor.csproj
dotnet run --project C:\Projects\Game\Game.csproj

# Testbed can load a map right at startup (useful for testing)
Testbed.exe C:\Projects\Testbed\Maps\Full.json
```

There are four solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln`, `MapEditor.sln` and `Game.sln` (each executable plus the libraries it uses). There are no test projects and no lint configuration.

MonoGame content (`Content/Content.mgcb` in each executable) is compiled automatically during build by `MonoGame.Content.Builder.Task`; editing the .mgcb itself is normally done with the MonoGame Pipeline Tool. **Each executable needs its own `.config/dotnet-tools.json`** pinning the `mgcb` tool — the content build shells out to `dotnet mgcb`, and the manifest search walks up from the *project* directory, so a new executable without one fails the content build with "Nenašel se soubor manifestu" even though its siblings build fine (`dotnet tool restore` once after adding it). All three executables target `net10.0-windows` and pull in WinForms (WindowsDX hosts its window on it), so they are Windows-only; the libraries target plain `net10.0`.

## Architecture

Three layered libraries under `BS3DLibs/`, consumed by two executables:

- **Prazsky.Core** — game-agnostic 3D infrastructure: `BasicCamera3D`/`ICamera`, `CameraShake` (a camera's recoil-and-rattle response to a violent event, offsets only — see "Recoil and camera shake"), model/bitmap/info renderers, `InstancedModelRenderer` (GPU instancing), `SkyDome`, and `Tools/Constants.cs` (named float constants like `HALF`, `SQRT_TWO` used throughout).
- **Prazsky.BS3D** — game logic without physics: the ball grid (`GameStructure/BallsMap.cs`), `StaticBall`, `BallType`, JSON map (de)serialization (System.Text.Json), the `Levels/Level` file format, input helpers, `Cannon`. (See "Levels, scene config and serialization".)
- **Prazsky.BS3D.Physics** — BepuPhysics representation: `PhysicsBall` (body reference + constraint handle slots + array position) and `BallsConstraintsBuilder` (builds the constrained ball structure).
- **Testbed** — the actual playable game loop: simulation setup, shooting, contact handling, backdrops, HUD. Test maps live in `Testbed\Maps\*.json`.
- **Game** — the shipping product (`Game/`, assembly `BS3D.exe`). Founded small and deliberately **not** a copy of `Testbed.cs`: a hanging cluster over the island in any of the seven shared scenes, the gun with its visible magazine, the fast shot with its launch smear, a real Bepu simulation, and a camera that is hit every time the gun fires — behind a Myra front end (main menu, pause, settings, scene picker) over a slowly orbiting camera. No map or level files yet. See "The game (Game)" and "The front end (Game)".
- **MapEditor** — visual editor for those map JSON files (supports drag-and-drop of a map file onto the window). It draws the balls and the sky the same way the game does, so a map looks in the editor the way it will play: the same instanced procedural spheres, the same shader, the same sky-derived lighting and now the same full render pipeline — linear radiance into an HDR target, glare, then the ACES tonemap (see "Ball rendering" and "The map editor's render pipeline"). It builds `Shaders/InstancedModel.fx`, `Shaders/Tonemap.fx`, `Shaders/Glare.fx`, the scene shaders (`Sea`/`Savanna`/`Desert`/`Acacia`/`Flame`/`Birds`/`Mountain`/`Snow`/`Spray`/`Meadow`) and all eighteen `Skyes/SkyDome*.dae` straight out of the Testbed content directory (`/build:../../Testbed/Content/…;<asset name>` in its own .mgcb), so there is one copy of each; B cycles the domes (the game's NumPad1, which the editor uses for ball types) and **V cycles the seven scenes** (the game's NumPad2), so a map can be previewed against every backdrop it might play in — the same shared `SceneRenderer` and city the game uses (see "The shared scene backdrops"). It has no ground, castle, cannon or shadows, and no arena platform (the AABB replaces it); the play field is marked by a translucent procedural outline (`GUI/AABB.cs` + `WireBoxMesh`) instead of the game's glass ceiling, and only the selector gizmo still draws through `ModelRenderer`/`BasicEffect`. It loads and saves not just plain map files but whole **levels** (map + scene + sky), F2/drag-drop/F1/F4, and carries a **live scene-config editor** — a Myra `PropertyGrid` over the active scene's config (see "Levels, scene config and serialization" and "The scene-config editor").

### The ball grid

The central data structure is a 3D array `[x, z, level]` where **level is the vertical (Y) axis**. Odd levels are shifted by +0.5 in X and Z (hexagonal-like packing); vertical spacing between levels is `1/√2`. `BallsMap.GetRealPosition` maps array coordinates to world positions, and `Center()`/`ComputeCentered` translate between the raw grid frame and the centered world frame. A cell has 4 neighbors on its own level and up to 4 on each adjacent level; which diagonal offsets are the true neighbors depends on level parity (`GetNeighboringCells` encodes this).

`BallsMap` holds the logical state (`StaticBall`s); `BallsConstraintsBuilder.BuildBallsStructure` mirrors it into a parallel `PhysicsBall[,,]` of dynamic Bepu bodies connected by `BallSocket` constraints to their neighbors, with the top level constrained to a kinematic ceiling body. The whole cluster hangs from the ceiling and jiggles physically.

The play field is larger than the initial ball layout: map JSON stores field dimensions (`sx`/`sz`/`l`) separately from the layout array, the layout is placed at the **top** of the field and the empty bottom levels are room for shot balls to attach into. Legacy map files without field dimensions get 6 extra bottom levels on load (an even number, to preserve level parity). The Testbed ceiling repositions/resizes itself to the loaded map (`FitCeilingToMap`).

### Constraint handle bookkeeping

Each constraint is shared by two balls, so `PhysicsBall` stores handles in three slot groups (`HandlesBottom`/`HandlesMiddle`/`HandlesTop` = balls below / same level / above + ceiling; four slots each, filled via `TryStore` in no particular order — a ball touches at most four neighbors per group). Every pair gets exactly one constraint by construction: the build pass connects same-level pairs only towards +X/+Z from each ball, and cross-level pairs only from the **even** (unshifted) level of each pair — adjacent levels always differ in parity, and neighbor index offsets depend on it (`diagonalShift`). The runtime attach path for a newly shot ball (`AttachBallToStructure`) instead connects all four same-level directions plus both adjacent levels, since the new ball has no constraints yet. Anchor offsets must be rotated into body-local space (`WorldToLocalOffset`) since bodies no longer have identity orientation once the simulation has run.

### Shooting flow (Testbed)

Contact detection uses `Testbed/Contacts/ContactEvents.cs` (adapted from the Bepu demo); Bepu callbacks fire on worker threads, so contact events are queued and processed on the main thread. When a shot ball hits the structure, it is snapped into the nearest free neighboring cell (`BallsMap.PutBallAtClosestEmptyPositionNextTo`) and then wired into the physics structure with `AttachBallToStructure`.

### The launch smear (Testbed)

A ball leaves the cannon at `SHOOT_MULTIPLIER` (200 u/s) — several ball diameters a frame — so a colour streak is drawn on firing to sell the launch (`Shaders/ShotTrail.fx`, modelled on `Flame.fx`). It is **anchored at the muzzle, not following the ball**: at 200 u/s the ball attaches in ~0.075 s, far too brief to read, so instead `ShootBall` records a `ShotTrail` (muzzle position, shot direction, type colour) that lives its own `TRAIL_LIFETIME` (~0.45 s) and fades — held near-full for most of that (a `1 - t²` curve, not `(1 - t)²`, so it does not dim the instant it appears and get missed), then the ball is crisp. `DrawShotTrails` draws one camera-facing billboard per live smear, stretched `TRAIL_LENGTH` (7) along the shot; the trap learned here is that the **bright, wide end must be the leading (far) end, not the muzzle** — the muzzle end is hidden behind the barrel, so a muzzle-bright streak shows only its faint tapering tip and reads as a thin thread. It is drawn additively and depth-read like the campfire flame (so the cluster/cannon in front still hide it), in linear radiance boosted over 1 (`TRAIL_BRIGHTNESS`) so it glows and blooms through the glare. The colour is the ball type's diffuse tint decoded to linear, its hue kept but its peak lifted to `TRAIL_COLOR_FLOOR` so even the near-black 8-ball leaves a faint grey smear. The whole thing is Testbed-only (the editor never shoots) and costs a handful of quads; the smear ages/culls inside the `if (_simulate)` block, so a paused sim freezes it. Dials (`TRAIL_*`) sit with the other shooting constants in `Testbed.cs`.

### The city and the glass arena

The default of the seven settings (NumPad2 cycles through the sea, the savanna, the desert, the mountains, the meadow and the neon city, below) — no flag: a **small round stone island** (the drain funnel ringed by a disc of marble, below) in a clearing between the towers of a procedural city (`Prazsky.Core.Render.City`, shared with the map editor; see "The shared scene backdrops"). The arena used to be a big square marble-and-glass plaza sized to the ground blocks, but it ate the whole lower frame and hid the scene it stood in; it is now the round island in **every** scene, so the sea, the dunes or the city fill the frame rather than a plaza. The castle backdrop and the shadow overlay are gone, and so are the marble ground blocks — the island's only physics floor is the funnel's own mesh (see "The drain funnel").

The city stands **over** the arena and falls away **underneath** it at the same time, and both halves of that took a correction. The first version cleared the blocks under the glass, which left nothing to look through the glass at; the city now continues underneath, cut off far below so the drop reads as a drop. The second version put the roofline below the floor, so no tower was ever seen against the sky — only bright roofs with dark canyons beside them, which the eye reads as holes punched in a white plain rather than as buildings (it was reported as inverted normals, and it was not). `ROOFLINE_Y` therefore sits well above the play surface.

The island is one procedural mesh (`Prazsky.Core.Render.DiscMesh`): a solid stone annulus — a flat top the fallen balls rest on, an outer **vertical wall** that is the hard edge the scene falls away past, and an inner wall around the central hole the funnel sits in. Its top is `ARENA_Y`, derived from `GROUND_PLATEAU_Y` so the drawn floor sits exactly on the physics plateau where the balls rest; the stone runs from the funnel's rim (`FUNNEL_TOP_RADIUS`) out to `ARENA_DISC_RADIUS` and drops `ARENA_EDGE_HEIGHT`. It is drawn opaque with `CullNone` (a solid ring — the nearest face wins on depth, so the winding is moot, exactly like the funnel rims), so `DiscMesh` imposes no winding convention. The stone is the `GroundMarble` model's texture projected triplanar with coursed slab relief (a `DetailTexture` on the renderer — **without** one the renderer falls through to the plain technique and every `SlabSize`/`CavityStrength`/relief setting is silently dead). The old marble-and-glass panel mosaic, its four marble bands, its mullions and the recessed centre "bath" are all gone, and with them the whole square-plaza machinery (`ARENA_HALF_EXTENT`/`ARENA_PANEL_SIZE`/the panel loop).

### The drain funnel (Testbed)

Where the recessed square used to be, the centre of the arena is a **glass funnel** the shot balls fall into: they run down the cone to a hole at the bottom and drop through it, below the platform, into the drop — where the kill plane removes them. It is what replaced the flat bath that just let balls pile up.

- **Rendering** is `Prazsky.Core.Render.FunnelMesh` — a single-sided truncated-cone wall (round rim at `FUNNEL_TOP_Y`, flush with the island top, down to a small hole at `FUNNEL_BOTTOM_Y`) with inward-and-up normals, and **no collar** now (`squareHalf` 0): the round stone disc meets the round rim directly, so there are no square corners to fill. It is drawn translucent through its own `InstancedModelRenderer` at `FUNNEL_GLASS_ALPHA` (~0.55, more opaque than plain glass, so the funnel reads clearly as a frosted-glass drain). Because it is one open surface it is drawn with `RasterizerState.CullNone` (set around the draw, restored to `CullCounterClockwise` after) so it reads both looking down into it and up through the hole, and it joins `SkyLitRenderers` so its sheen takes the dome.
- The rim (radius `FUNNEL_TOP_RADIUS`, 14) meets the stone disc's inner hole exactly, and the gold top-rim bead rings that stone-meets-glass junction — the drain reads at a glance where the two materials meet. (The old square-collar machinery that filled the corner gaps between the round funnel and the square pit is gone with the square plaza.)
- **Gold rims.** A polished-gold metal bead runs around **both circles** — the wide top rim and the small bottom hole — which is what makes the glass drain read at a glance (`FunnelRimsMesh`: two tori in one mesh, at the funnel's own local y = 0 and y = -height, so they share `_funnelWorld`; one gold `InstancedModelRenderer` draws them). They are **opaque**, so they draw with the opaque scene *before* the glass, and `CullNone` (a closed convex-tube torus, so the nearest face wins on depth and the winding is moot — one less thing to get wrong unseen). They are drawn **metallic**, which needed a shader addition: `InstancedModel.fx` now has a `Metalness` uniform (a renderer property, set unconditionally every `Draw` like `SpecularAmbientStrength`, **0 for every other surface** so nothing else changes) that makes the environment-reflection F0 the material's specular color itself rather than the 4 % dielectric `DielectricF0 * tint` — so gold reflects the sky *in gold*. The gold specular (`FUNNEL_RIM_SPECULAR`) is passed as a per-draw `BasicEffectParams` override; the gold diffuse (`FUNNEL_RIM_COLOR`) keeps the bead visible even under a dark dome. The rims are visual only — no physics; the stone disc is the floor.
- **Physics** is a Bepu triangle-`Mesh` (`BuildFunnelPhysics`) — the island's whole physics floor now that the wide grid of ground blocks is gone (`BuildGroundAndCeiling` only calls this and builds the ceiling): the sloped cone wall plus the flat **round stone ring** from the rim out to `ARENA_DISC_RADIUS`, all **double-sided** — every quad's two triangles added in both windings — deliberately, so a ball collides with the surface regardless of Bepu's one-sided-triangle normal convention rather than depending on getting the winding right. Balls rest on the ring; within the rim they run down the cone to the hole (wider than a ball) and fall through; past the ring they drop off the island's edge into the drop and the kill plane takes them. `KILL_PLANE_Y` sits below `FUNNEL_BOTTOM_Y` so a ball that drops through falls a visible distance into the drop before `RemoveFallenBalls` culls it. Steep walls (~55°) keep balls running down to the hole rather than resting (a ball that did come to rest would be sleep-culled, i.e. vanish where it sits). Dumping a very large cluster all at once (the `End` debug release of a full map) briefly floods the funnel and spikes the physics until it drains; ordinary matched clusters are small and drain smoothly.
- **The terrain hole and the dark pit shaft (solid-ground scenes).** In the city the funnel drains into the canyon that falls away below the arena, and in the sea into the water; but the **solid-terrain** scenes (mountains, meadow, savanna, desert) are a flat clearing at the island's foot, and the flat ground plane sliced across the glass funnel just below its rim — the drain read as a shallow bowl and balls falling through vanished into the ground. The fix is in two halves. First, the terrain shaders `clip()` the island's footprint out of the ground (`IslandHoleRadius`, set from `SceneRenderer.TerrainHoleRadius` = `TERRAIN_HOLE_RADIUS`, a couple of units inside the disc's rim so the terrain tucks under the stone edge with no gap; **0 in the map editor**, which draws no island, so its terrain stays whole under the field AABB). But a hole alone made it worse — the ~55 %-opaque glass then showed the bright sky-haze straight through it, reading as a glass ring on the ground. So second, a **dark pit shaft** (`_pitMesh`/`_pitRenderer`, drawn in the four `IsSolidTerrainScene`s only, opaque and `CullNone` before the glass, which composites over it) backs the glass: a near-black `FunnelMesh` cone that **hugs** the glass funnel — it *shares the funnel's mouth* (`FUNNEL_TOP_RADIUS`) and descends just outside it past the kill plane, so a ball runs down the glass into darkness and is culled inside the pit rather than against the bright sky. A wide cone would hide behind the disc's stone ring and leave the bright hole showing through the narrow (radius 14) aperture — the pit **must** stay just outside the funnel at every depth. It is near-matte (`SpecularAmbientStrength` 0.03) so no dome bleaches the well, and the gold rim bead hides the mouth it shares with the funnel. Purely visual — no physics; the funnel mesh is still the only floor.

Windows are not lit once and for all: each keeps its own rhythm off `CityWindowTime` (wall clock, like the balls' pulse — a city's lamps do not stop when the simulation is paused), holding a state for an interval of its own length and then deciding again, with a short fade rather than a cut. `CITY_WINDOW_BRIGHTNESS` stays **under** `GLARE_THRESHOLD`: a window that glares veils the tower behind it, and a thousand of them turn the skyline into one white haze.

Everything about the buildings is procedural and there are no assets. One 1×1×1 `BoxMesh` serves every building — each is that cube under a different instance matrix, so the whole city is a single instanced draw call (the marble floor is no longer part of it; that is the separate `DiscMesh` island, above). Non-uniform scale is safe here because the boxes are axis-aligned in object space: a diagonal scale maps each face normal onto itself, so `normalize` in the pixel shader recovers it without an inverse transpose. The `InstancedCity` technique lays the window grid out **relative to each building**, not on a raw world grid. A raw world grid (what it used to do) put the pattern at a random phase against every tower's edges, so windows landed jammed into corners or clipped — which reads as unreal. Now a dedicated `CityVS` hands the pixel shader the pixel's offset from the building's centre and the building's world size (the box is the 1×1×1 unit cube, so a transformed unit axis is the world size and the transform of the object origin is the centre; all Bone-agnostic), and `CityPS` holds a fixed wall margin (`WindowMargin`, world units) clear of glass at **every** edge and spreads the windows evenly across the interior — so no window touches a corner and every tower carries the same border. The floor/column **count** is still solved from the building's world size against the target pitch (`WindowPitchX/Y`), so a hundred-storey tower still gets more floors than a low one and a wide one more columns; only the phase is now the building's rather than the world's. The per-building cell pitch is the target pitch nudged so a whole number of windows fills the interior exactly (kept near the target, so it still reads natural), and the `buildingId` — for the neon per-tower hue and the lit-window pattern — is taken from the tower's own centre so it is one value across the whole facade. Windows band-limit to their own average coverage against that per-building pitch, so a distant tower is a dim glowing block rather than a moire of floors.

Two things learned tuning it, both worth keeping in mind elsewhere. The **specular ambient is not multiplied by albedo** (a reflection does not care how dark the surface under it is), which is physically right but washes a whole skyline in sky color at grazing angles. Almost every facade of a city seen from inside it, and almost every square metre of a floor beyond your own feet, is at a grazing angle where Fresnel is near 1 — so the city runs the term at 0.07 and the marble floor at 0.4, and both were bleached white before that. And a translucent sheet over a lit city reads as *no floor at all*; the mullions dividing the glass into panels are what make the eye accept there is glass there.

### The shared scene backdrops

The seven settings are **shared between the game and the map editor** so a map looks in the editor the way it will play. The split:

- The five self-lit backdrops — sea, savanna (with its acacias and birds), desert (with the same flock of birds), mountains (with its snow) and meadow — live in `Prazsky.Core.Render.SceneRenderer`, which owns their effects, meshes, particle buffers and every tuning constant. Each is a dedicated shader that computes its own lighting from a `SceneFrame` handed over per frame (camera, sun direction, the sky palette in linear radiance, the sun's tinted radiance, the wall-clock time, and an optional cloud-apply hook). `DrawEnvironment` draws the terrain/water (plus the savanna's acacias and the savanna's and desert's birds); `DrawOverlays` draws the foreground weather last — the mountain's snow, the sea's spray, the savanna's campfire flame. The Testbed passes `_clouds.ApplyTo` as the hook; the editor passes null, so its scenes get full sun with no cloud shadow (the cloud uniforms stay zero and `CloudSunlight` returns 1). Both build the scene shaders out of the one Testbed content directory.
- The **city** (and its neon relight) is `Prazsky.Core.Render.City` — a seeded generator of one instanced box per building — drawn through the shared `InstancedModel` city technique by an `InstancedModelRenderer` each executable owns and sky-lights like the balls (`CityWindowBrightness > 0` selects the technique; `CityNeon` flips it to neon). The arena floor (marble/glass panels) is **not** shared: it is tied to the physics ground blocks and stays in `Testbed.cs`, which is why the editor draws no platform and marks the field with the AABB instead.

So a change to any scene reaches both executables at once, exactly as the shared shaders do. The per-scene sections below describe what each one is doing; the tuning dials named in them now live on `SceneRenderer` (or `City`) rather than at the top of `Testbed.cs`.

### Levels, scene config and serialization

The designer-meaningful tuning of every scene lives in serializable **`SceneConfig`** POCOs (issue #44), one concrete subclass per `SceneKind` in `Prazsky.Core/Render/Config/` (`SeaSceneConfig`, `DesertSceneConfig`, `SavannaSceneConfig`, `MountainSceneConfig`, `MeadowSceneConfig`, `CitySceneConfig`). **Every default reproduces the original hard-coded look byte-for-byte**, so a fresh config renders exactly as before; only look/mood dials and particle/tree/building counts are exposed — mesh grid density and other hard limits stay as constants in `SceneRenderer`. `SceneRenderer` holds one config per scene and reads its values in `Apply*Parameters`/`Build*Buffers`; `SceneRenderer.Apply(SceneConfig)` re-pushes a scene's effect parameters and rebuilds the scatter/particle buffers it sizes (acacias, birds, snow, spray) at runtime — the path a loaded level or a live editor edit takes. A `CitySceneConfig` is a no-op in `Apply` (the city lives outside `SceneRenderer`, in `City` + the instanced city technique), so its caller rebuilds the `City`. The shared savanna/desert bird flock is sized to the **larger** of the two configs' counts, or a desert level's flock would be silently capped to the savanna's. Colours are `Rgb`, 2D/3D vectors `Vec2`/`Vec3` — all **reference types** (see "The scene-config editor" for why), holding linear values that may exceed 1.

A **level** (issue #32, `Levels/Level.cs`) bundles a ball map with the `SceneConfig` and sky dome that reproduce its look — everything needed to make a map play (and preview) as authored. It is a JSON object marked by `"format": "bs3d-level"`; `Level.IsLevelFile` is a cheap probe that tells it from a plain map file (both use `.json`), robust to a directory or unreadable path (returns false rather than throwing). The ceiling, physics statics and cannon/camera placement are **not** stored — they are all derived from the map size at load (`FitCeilingToMap` / `FitCannonAndGameCameraToMap`), so a level only carries what cannot be re-derived. The format is versioned. Both executables **load** levels — the Testbed's `DeserializeMapFromFile` and the editor's `DeserializeMapFromJsonFile` probe and route a level through the scene/sky apply, a plain map through the layout-only path; the whole dispatch is wrapped so a broken or hand-edited file logs and leaves the running program untouched instead of crashing. The Testbed's startup `sky=` still pins the dome over a startup level's own dome. The **editor saves** levels (F4): it reads the active config from `SceneRenderer.GetSceneConfig` (or its own `CitySceneConfig`) and the map from `BallsMap.ToBallPositionTypes`, so a level authored in the editor plays in the game — the loop is closed.

A **`LevelSet`** (`Levels/LevelSet.cs`) is the tier above: a `"format": "bs3d-levels"` file listing level files **in play order**, so which level is first and which is second lives in one place rather than in a directory listing. Entries are objects (`file`, optional `name`, and the level's **rules** — `shots`, `minScore`, `ceilingStep`) whose paths are relative to the set's own directory. The rules live on the entry rather than in the level file because this is the only place that can annotate a **plain map file**, which has nowhere to put metadata of its own. All three are **nullable, and null means "no rule" rather than zero** — a set authored before rules existed has to keep playing exactly as it did, and a sentinel cannot say the difference between "unlimited" and "none"; what each null falls back to is documented where it is *read*, not where it is declared. `Load` rejects a rule that is present but meaningless (a zero budget, a zero ceiling step, a negative score gate) rather than letting it surface as an unplayable level. The game reads one set; the Testbed and the editor do not (they open whatever file they are handed). See "Levels in the game (Game)".

Serialization is **System.Text.Json** throughout (issue #38; Newtonsoft is gone). STJ has no native multidimensional-array support, so `Balls3DArrayJsonConverter` reads and writes the exact nested `[x][z][level]` shape the legacy map files use (they were written by Newtonsoft, which does it natively) — a plain map file and a level's embedded map stay byte-shape-compatible, and legacy maps that omit the field dimensions still load (STJ defaults them to zero, and `BallsMap` then adds the extra bottom levels). `SceneConfig` is serialized polymorphically on a `"kind"` discriminator. `BallPositionType`/`BallPositionTypes` carry `[JsonPropertyName]` only.

### The sea (Testbed)

The second setting, reached with NumPad2 the way NumPad1 cycles the sky domes (or `scene=sea` on the command line, since a synthetic NumPad press never reaches the SDL window). Only the environment swaps: the round stone island stays as it is, now floating a little above open water instead of standing among city towers. It is `Testbed/Content/Shaders/Sea.fx` with its switch and draw plumbing in `Testbed.cs` (`SceneKind`, `SwitchScene`, `DrawSea`), and it borrows the scene's whole toolkit rather than inventing its own.

The water is **real geometry** now, not a flat quad: a camera-centred grid (the shared `CreateGridMesh`, the same machinery the desert, mountains and meadow use), snapped to a cell each frame so it does not swim, displaced by a sum of **Gerstner (trochoidal) waves** in the vertex shader — sharp crests, rounded troughs, the horizontal pinch that sells a wave over a plain height field. The analytic normal and the horizontal **Jacobian fold** (which drops below 1 as a crest pinches and negative where it overhangs — the whitecap generator) come free from the same per-vertex evaluation. The wavelengths are kept **short relative to the scene** (a ball is ~1 unit) so several crests fall inside the visible water and it reads as waves rather than one flat tilt — a 100-unit swell only ever shows a corner of one wave at this scale, which is why the first flat-quad version, whose whole "wave" was a normal-only slope, read as a low-res mirror. The mean level (`SEA_LEVEL_Y`) is dropped well below the island so the crests have headroom without poking up through it, and the waves **fade to flat** between `WAVE_FADE_START`/`WAVE_FADE_END` so the far sea settles into a clean hazed horizon rather than a jagged fringe. Everything runs off the wall clock, so the sea keeps moving while the simulation is paused, like the clouds and the balls' pulse.

On the wave geometry the pixel shader piles the rest. Fine **wind chop** — a few band-limited octaves tilting the normal through the ground relief's `PerturbNormalFromHeight`, scrolled downwind — breaks the surface so it is rough rather than a mirror between the crests. **Whitecap foam** appears where the Jacobian folds and where a crest rises past `FOAM_CREST_START`, broken up by the shared cloud noise into flecks and streaks rather than a painted band, and lit as a matte cap by sun and sky. **Subsurface scattering** glows the crests when the sun is low behind them and the eye looks into the water. A Fresnel **sky reflection** samples the dome's two-color gradient in closed form (`SkyRadiance`'s trick, so the water takes the mood of whichever of the eighteen skies is up), a sharp **sun glint** sparks where the reflected ray points at the sun, and the **cloud shadow** is the same one line the rest of the scene gets (`CloudSunlight` off `Clouds.fxh`), so the water darkens under the very cloud overhead. A horizon haze fades the finite grid into the skyline. Because the water mirrors the sky, its whole mood follows the dome — a bright sunny sky gives a bright, breezy sea, not a stormy one — so **the sea scene defaults to a darker dome** (`SEA_DEFAULT_SKY_DOME`, a violet/teal dusk) on entry, whether from `scene=sea` at startup or a NumPad2 switch into it, unless a command-line `sky=` overrode the startup default; NumPad1 still cycles domes freely from there (`SetSkyDome` is the shared runtime dome-change, used by both). The dials (`WAVE_*`, `CHOP_*`, `FOAM_*`, `SSS_*`, `WATER_COLOR_*`, `SEA_LEVEL_Y`) live on the shared `SceneRenderer`, so the map editor draws the same water. It is drawn opaque, first in the scene block where the city would be, `CullNone` (one open surface, read from above and through the crests), so the arena glass composites over it unchanged. Shader Model 5.0, like every scene shader.

The free camera can dive **below the surface**, and there the sea alone gets an **underwater murk** so being submerged reads as underwater rather than showing the world unchanged with a water plane cutting through it. It is a post-resolve tint in `Tonemap.fx`, applied in **linear light before the ACES curve** (so the submerged scene rolls through the same highlight response as everything above it): the frame is absorbed towards a blue-green (`UNDERWATER_ABSORB`, a multiplier under 1 — red goes first, so it blues and dims) and the water's own in-scattered glow is added (`UNDERWATER_INSCATTER`), both by `UnderwaterAmount`. That amount is set on the CPU only in the sea scene and ramps `0→1` over `UNDERWATER_FADE_DEPTH` world units below the mean surface (`SceneRenderer.SeaLevelY`, a touch above it so partial submersion already tints), and is **0 (a shader no-op) in every other scene** — the terrain scenes have solid ground, not water, to get under. The tint itself is uniform (no per-pixel depth in that pass, so no distance fog — good enough, and it fades in smoothly as you dive; the spray billboards double as suspended bubbles down there). On top of it the same pass adds a **peripheral blur** — a diver's vision goes soft at the edges: a cheap 8-tap golden-angle spiral disc whose radius and blend both grow from **0 at the frame centre** (which stays crisp) out to the corners, as `edge² · UnderwaterAmount`, so it is stronger towards the edges and off entirely above water. It is inside a branch on the `UnderwaterAmount` **uniform**, so the whole frame takes the same path (no cost above water, no divergence). The overlay and aimer draw after the resolve, so they stay sharp. Above water the whole block is byte-for-byte the old resolve.

Blown spray and spindrift ride over the waves (`Spray.fx`, drawn by `SceneRenderer.DrawOverlays` in the sea scene exactly as the mountain's snow is): a static buffer of billboards animated entirely in the vertex shader, like the snow, but in a **thin slab that follows the camera in XZ while clinging to the sea surface in Y** (`SPRAY_LEVEL_Y`, just above the mean), whipped fast downwind (`SPRAY_WIND`, aligned with the waves' own wind) with a turbulent per-particle sway. One buffer carries two reads split per particle — fine **droplets** and larger, fainter **mist wisps** (the spindrift). It feathers towards the slab's top and edges so it has no hard boundary, is depth-read (the waves and platform occlude it) and runs off the wall clock, so the storm keeps blowing while the simulation is paused. The one trap, worth remembering for any water/light particle here: `GLARE_THRESHOLD` is only **0.38** (on linear luminance), and at a grazing angle the view ray threads hundreds of particles through the thin slab which **stack to full opacity** — so any spray colour above the threshold blooms into a starfield once it accumulates, *however low the per-particle alpha*. The spray colour (`SPRAY_COLOR`) is therefore kept a cool grey-blue **under** 0.38: it reads as cold storm haze/spindrift rather than white foam-spray, but it never glares. Making it a brighter, whiter spray would need a raised glare threshold (globally, or per-scene) or drawing it in a post-resolve pass — which would forgo the depth occlusion that keeps it behind the platform and cluster. The spray dials (`SPRAY_*`) sit with the sea's on the shared `SceneRenderer`, so the map editor draws the same spray.

### The savanna (Testbed)

The third setting, next in the NumPad2 cycle after the sea (or `scene=savanna`; the enum slot is `SceneKind.Savanna`). It **grew out of the old Sahara dunes** — which are now back as their own [Desert](#the-desert-testbed) scene, below — into open golden grassland rolling gently to a wide horizon, dotted with acacia trees, the island standing in a flat clearing. The rework was prompted by the dunes showing a **grid** — the coarse displaced mesh's per-vertex normal left a faint facet / Mach-band pattern across the sand — and the per-pixel-normal fix is the one thing the savanna terrain does differently from its siblings (and the fix the reborn desert now shares).

`Savanna.fx` displaces a camera-centred grid (`SAVANNA_GRID_N` a side over `SAVANNA_EXTENT`, snapped to its cell so it does not swim) by a smooth rolling field — flat in a clearing around the origin and rising into low rises with distance, flatter than the meadow's hills since a savanna is open. Its **normal is taken per pixel** from the height field's own gradient (three cheap `TerrainHeight` taps in the pixel shader), not interpolated from per-vertex normals: interpolating a coarse mesh's per-vertex normal is exactly what made the grid show (a normal discontinuity, i.e. a Mach band, at every cell edge), and evaluating the gradient per pixel makes the shading smooth regardless of tessellation, so the grid is gone. The grid is also finer than the old dunes (400 vs 200) so the silhouette is smooth too. The meadow and mountains still take their normal per vertex; they get away with it because their per-pixel relief and detail hide the seams, but the per-pixel approach here is the clean fix and the one to reach for if either of them ever shows the same grid.

The grass is dry gold-green, varied in patches at two noise scales so the field is patchy gold and green rather than one flat tone, combed by travelling wind bands and tilted by a fine footprint-band-limited relief. It is matte — sun plus the sky hemisphere, dimmed by the shared cloud shadow — and melts into the skyline over `SAVANNA_HORIZON_HAZE_DISTANCE`, so it takes the mood of every dome. Like the sea's dusk default, the savanna **enters under a warm golden dome** (`SAVANNA_DEFAULT_SKY_DOME`, the set's warmest gold horizon) on `scene=savanna` or a NumPad2 switch into it, unless `sky=` overrode it; NumPad1 still cycles freely. Drawn opaque, first in the scene block, CullNone; the grass, wind, relief and terrain dials (`SAVANNA_*`, `GRASS_COLOR_*`) sit on the shared `SceneRenderer`. Shader Model 5.0, drawn in both executables.

Scattered over it are **acacia trees** — the flat-topped umbrella tree that reads as savanna at a glance (`Acacia.fx`). Each is one upright (cylindrical) billboard from a static buffer the C# side plants on the ground (`SavannaTerrainHeight` mirrors the shader's `TerrainHeight`, so a tree sits where the terrain is), and the pixel shader *is* the tree: a thin trunk under a wide, vertically-flattened, flat-topped green crown. They are **alpha-tested** (`clip`) rather than alpha-blended, so they **write depth** and occlude the terrain and each other correctly (the hard cutout edge is softened by the scene's supersampling); the crown takes the dome's ambient and a flat sun term, so it too follows the mood. `ACACIA_COUNT` of them are scattered in a ring clear of the island (`ACACIA_MIN/MAX_RADIUS`), each at its own size off a packed random. Drawn after the terrain, before the birds.

A flock of birds circles overhead — the only moving creature in the whole world, and still no sprite sheet; the savanna and the desert **share the one flock** (the buffer, the shader and the orbits live once in `SceneRenderer`, drawn in both those scenes). `Birds.fx` draws each bird as a camera-facing billboard whose pixel shader *is* the bird: a dark flapping-wing silhouette, a resting dihedral plus a `sin` beat with the wing tips travelling furthest, wings tapering out, a rounder body at the centre, softened a pixel wide on the footprint so distant birds do not crawl. The C# side circles the quads — `BIRD_COUNT` of them orbit `BIRD_FLOCK_CENTER` over the field, each at its own radius, altitude, phase and unhurried speed with its own flap phase, all off the wall clock, so the kettle wheels slowly and never beats in time. They draw alpha-blended and depth-read (the terrain or the platform in front hides one) writing no depth, in the savanna and desert scenes; the flock's count, size and place sit with the other dials in `SceneRenderer`.

### The desert (Testbed)

The fourth setting, next in the NumPad2 cycle after the savanna (or `scene=desert`; the enum slot is `SceneKind.Desert`). A Sahara: rolling sand dunes stretching to a hazed horizon, the round island standing in the sand exactly as it floats on the sea and stands in the grass. It was the third scene originally, was **turned into the savanna** to fix a grid artefact, and is now **back as its own scene alongside the savanna** — the two arid siblings adjacent in the cycle — because the fix that killed it (the per-pixel terrain normal) means it can come back clean. `Desert.fx` with its dials, mesh and `DrawDesert` on the shared `SceneRenderer`, so the map editor draws the same dunes.

The dunes are **real geometry**, not a flat plane: the shared `CreateGridMesh` grid (`DESERT_GRID_N` a side over `DESERT_EXTENT`), snapped to its cell each frame so it does not swim, displaced in the vertex shader by a low-frequency **direction-mixed sine sum** (`DuneSum`) — a dune with no silhouette against the sky is just a lit patch of floor. Like every terrain scene since the arena became the small round island, it is **flat in a clearing** around the origin (the island's foot, `DESERT_LEVEL_Y`, the same level the savanna's grass sits at) and **rises into dunes with distance** (`DESERT_CLEARING_RADIUS`/`_TRANSITION`, `DUNE_AMPLITUDE` the peak height out in the far field), so the sand fills the frame and the dunes read against the horizon rather than crowding the platform.

The one thing it does deliberately, and the whole reason it can return: the base **normal is taken per pixel** from the height field's gradient (three cheap `DesertHeight` taps in the pixel shader), *not* interpolated from a per-vertex normal. Interpolating a coarse displaced mesh's per-vertex normal is exactly what left the old dunes' faint facet / Mach-band grid; evaluating the gradient per pixel makes the shading smooth regardless of tessellation — the same fix the savanna taught, applied here (the grid is finer too, 360 vs the old 200, for a smooth crest silhouette). On top of the smooth dune normal, fine **wind ripples** (footprint-band-limited octaves through `PerturbNormalFromHeight`, scrolled downwind) crawl the sand, and a veil of **blown dust** (the shared `Clouds.fxh` noise) drifts across it and thickens towards the horizon into a windblown murk. The sand is matte — sun raking the dunes, the sky hemisphere filling the rest, dimmed by the shared cloud shadow — and melts into the skyline over `DESERT_HORIZON_HAZE_DISTANCE`, so it takes the mood of every dome. Drawn opaque, first in the scene block where the city would be, `CullNone` (the winding is moot on a heightfield); the dune, ripple, dust and sand dials (`DUNE_AMPLITUDE`, `DESERT_LEVEL_Y`, `DESERT_RIPPLE_*`, `DESERT_DUST_*`, `SAND_COLOR`) sit on the shared `SceneRenderer`. Shader Model 5.0, drawn in both executables. It carries **no point lights** (no campfire), so unlike the savanna its draw sets `SceneLightCount` to nothing, and it forces **no default dome** — like the mountains and the meadow, it keeps whatever dome is up. It shares the savanna's [flock of birds](#the-savanna-testbed) circling overhead (drawn from the one buffer in both scenes), the one moving creature over the empty sand.

### The mountains (Testbed)

The fifth setting in the NumPad2 cycle (or `scene=mountain`). A snow basin the arena sits in, ringed by tall snow-capped peaks that rise with distance and fade into an alpine haze — the city's clearing-among-towers rebuilt in rock and snow, the platform standing in the basin as it stands anywhere.

The terrain is the desert's machinery with a different field: a camera-centred grid (they share `CreateGridMesh`), snapped to its cell on the CPU so it does not swim, displaced by a heightfield that is *ridged* — octaves of `1 - |sin|`, whose sharp maxima are ridge lines — rather than the dunes' smooth sines. It is low and gentle around the arena (world origin) and rises into peaks with distance (`ClearingRadius`/`ClearingTransition`), so the play surface sits in a clearing the way it does in the city, and the basin stays below the platform glass. Its base normal is taken by finite differences — three field taps per vertex — because the ridge folds and the distance ramp would make a closed-form gradient more trouble than it saves; a fine `RockRelief` (band-limited against the footprint) then perturbs it per pixel so the near rock reads as rough stone. Snow lies where the surface faces up (a `smoothstep` on `normal.y`) *and* above an irregular, noise-broken altitude snowline, so the range reads as rock with snow on it rather than one white blanket; rock varies between a dark and a lighter grey-brown in patches; the blue zenith fills the shadows so the snow reads cold where the sun misses it, and the range dissolves into the skyline over `MOUNTAIN_HORIZON_HAZE_DISTANCE` — the strong aerial perspective that says a lot of cold air.

`MOUNTAIN_GRID_N` was raised from 240 to 360 for craggier detail, and **that is what forced `CreateGridMesh` onto a 32-bit index buffer**: a grid over ~255 a side has more than 65 536 vertices, and the old 16-bit index silently wrapped, so far triangles referenced the wrong vertices and stretched into garbage. On the near-flat sea (380) and savanna (400) that garbage stayed down at the surface and never showed — but the mountain's tall peaks stretched it into strong, regular *dark horizontal bands across the whole sky*, which read exactly like a glare/shading artifact and cost a long hunt down the wrong path (glare threshold, snow brightness, normal band-limiting — none of it). The lesson is in the code: **any `CreateGridMesh` grid over 255 a side must use 32-bit indices**; the sea and savanna were silently over the line already and are now correct too.

And it snows. `Snow.fx` is a static buffer of billboard flakes — one quad each, its base a fixed point in a unit cube — animated entirely in the vertex shader: each flake falls, drifts on the wind and sways, wrapping with `frac` inside a box that follows the camera, so the snowfall is endless and always around you. Following the camera rather than the world trades a little translational parallax for never popping at a box edge, the right trade for a uniform veil of small flakes. The pixel shader is a soft round speck; they draw last, alpha-blended and depth-read (the terrain and the cluster hide the flakes behind them) writing no depth, in the mountain scene alone. Their color's luminance (~0.76) actually sits *over* `GLARE_THRESHOLD` (0.55); what keeps a near flake from blooming into a glowing orb — which reads as a bug rather than a snowflake — is the feathered speck alpha and the quarter-resolution glare downsample diluting its few pixels. Dim the colour, not the opacity, if flakes ever glow. Count, size, fall speed and wind sit with the other dials in `Testbed.cs`.

### The meadow (Testbed)

The sixth setting in the NumPad2 cycle (or `scene=meadow`). The Windows XP *Bliss* hill: vivid green rolling to a crisp horizon under a blue cloudy sky, a flat flowering clearing where the arena stands rolling up into hills with distance. It is the desert's and mountains' displaced-grid machinery again (shared `CreateGridMesh`), but the field is smooth rolling sines rather than dunes or ridges, low around the arena (world origin) and rising with distance, its normal by finite differences. The grass is matte, varied in broad patches so it is not one flat green, and the whole field takes the mood of the dome like everything else.

The motion is the wind and the weather, with no particle system: bands of wind comb through the grass — bright and dark travelling downwind — while the shared cloud shadows drift across the hills, and a fine wind-animated relief tilts the grass normal so the light plays over it. And it is in bloom: wildflowers are scattered through it, little rosettes rather than dots — a ring of petals around a warm golden eye, `|cos(N * angle / 2)|` cutting N rounded lobes (even in the angle, so it survives the `atan2` seam), with a per-cell petal count, size, rotation and colour (white daisies, yellow buttercups, the odd pink one). Each flower's centre is held within `[size, 1 - size]` of its grid cell so the whole rosette fits inside and no petal is clipped by the cell edge, and the lot fades against the pixel footprint so the distant meadow stays clean green rather than a shimmer of dots. Grass, hill, wind and flower dials sit at the top of `Testbed.cs`.

### The neon city (Testbed)

The last of the seven, at the end of the NumPad2 cycle (or `scene=neon`). Not a new place but the same procedural city relit: the `CityNeon` switch on `InstancedModelRenderer` flips `InstancedModel.fx`'s city technique from warm-and-cool lamps to a neon night — near-black facades and windows glowing pink and blue, the magenta and cyan of a neon street, one dominant hue per tower with the odd off-colour accent, about one window in six sparking the opposite hue, big sign bands wrapping some towers in the contrast colour, and a fraction of it all buzzing. The window brightness is driven well over `GLARE_THRESHOLD` (`NEON_WINDOW_BRIGHTNESS`), so every lit pane blooms into a sign; the facades stay dark under any dome, so the neon carries whatever the sky, but it reads best under a dark or dusk one. The `#if !OPENGL` guard the neon path used to sit behind is gone now that both executables build the file for Shader Model 5.0 — the map editor draws the city, and its neon, through the same shared technique, so V reaches the neon scene there too. It is the heaviest scene — the whole city plus the extra sign/flicker work and the bloom it feeds — so it runs the lowest frame rate.

### Scene point lights (Testbed)

Beyond the sun and the dome-derived ambient, a scene can carry its own **point lights that exist under every sky dome** — real lights that illuminate, not emissive surfaces that only glow (the city windows and neon glow but light nothing). `InstancedModel.fx` (`AddSceneLights`, called in `ShadePixel`) and `Savanna.fx` both loop over a fixed set of slots — `SceneLight{Position,Color,Range}[MAX_SCENE_LIGHTS]` and `SceneLightCount` — summing each light's Blinn-Phong contribution with a quadratic distance falloff on top of the sun and sky. Colours are linear radiance (bright, over 1) so they cast real colour. The Testbed sets them on the **shared** `_instancingEffect` once a frame (`ApplySceneLights` — the balls, island, cannon and city all get them since they share that one effect); the savanna grass shader gets its own copy in `SceneRenderer.DrawSavanna`. Scenes without lights leave `SceneLightCount` at 0 (the uniform default), so the map editor — which never sets it — lights no balls, and the shader loop does nothing at runtime.

Two are live:
- **The savanna campfire** (`SceneRenderer.SavannaCampfirePosition` / `CampfireColor`): a warm point light on the grass just off the island, flickering off the wall clock, that warms the island's near edge, the grass around it and any balls near it. Its visible flame is a separate **additive** billboard (`Flame.fx`) at the same spot — a procedural flickering tongue, bright enough to bloom through the glare but with the blue kept low so it reads as fire, not a white spark. Light and flame flicker together off the one clock. The position is chosen to sit in the low game camera's view (it looks down `-Z` from about `(0,-3,30)`).
- **The neon city's neon** (`NEON_*` in `Testbed.cs`): a ring of alternating magenta/cyan point lights around the island, so the near towers, the platform, the cannon and the balls actually take the neon's colour instead of the windows merely glowing. Neon scene only.

Adding another is a slot: set a position/colour/range per scene in `ApplySceneLights` (up to `MAX_SCENE_LIGHTS`, matched in the shaders), and add the loop to any scene shader that should also catch it (the sea, desert, mountains and meadow do not yet — their terrain shaders have no scene-light loop).

### The weather (Testbed)

Procedural clouds that drift, shade the sky, throw shadows across the scene and flatten the light when they cover the sun. They live on **a flat plane at a finite altitude**, not as a texture on the dome, and that is the decision everything else follows from: a dome texture sits at infinity and casts no shadow anyone can derive from it, so what you look at and what shadows you would have to be two fields, and two fields drift apart. With a plane there is one field and three ray-plane intersections into it — the sky shader crosses it with the view ray, the scene shader with the sun ray, the CPU with the sun ray from the arena.

The field is defined **once**, in `Testbed/Content/Shaders/Clouds.fxh` (`#include` works in the MonoGame content pipeline, and `.fxh` edits *do* trigger a rebuild of the `.fx` that includes them — both verified). It is split in two, and the split is what removes the usual CPU/GPU noise-synchronisation problem:

- the **weather** layer is coarse, and mirrored in `Prazsky.Core.Render.CloudField` — the only part that exists twice. Its hash is built from `frac`/`dot`/multiply and no `sin`, because a sine-based hash is exactly where a C# and an HLSL copy would part company.
- the **detail** layer is fine, lives only in the sky shader, and nothing the shadow or the light rig looks at ever touches it.

`CloudField.ApplyTo(effect)` hands the shared parameters to both shaders, so the drawn cloud and the shadow it throws cannot be tuned apart by accident.

Things that took a while to get right:

- **Shading needs unclamped thickness, opacity needs the clamped one.** With one `saturate` for both, everything inside a cloud is exactly 1 and the interior comes out as a flat wash with a nice edge. `CloudThickness` runs past 1 on purpose.
- **The ACES curve eats cloud contrast.** Two linear values close together up in the highlights tonemap to the same white, so the shadowed underside has to be *well* below the sunlit top (0.18 against 1.7), not a shade under it.
- **Detail strength must be read against `CoverageGain`**, which is what the weather is multiplied by. At 0.55 against a gain of 2.8 the detail modulated the thickness by six percent and the clouds came out airbrushed.
- **Cloud shadows plug into the existing `keyShadow`** in `ShadePixel` — one line, and balls, city, floor and cannon all get them, because they all come through there. They use the coarse layer alone: a shadow thrown from that height has a penumbra hundreds of units wide, so the fine octaves would not survive the trip anyway. `SunDirection` is a separate uniform, not `KeyLightPosition`, which is a point forty units out whose direction fans across the scene.
- **The key light is dimmed per pixel by the shader, the ambient on the CPU, and never both.** Dimming the key on both sides counts the same cloud twice and darkens everything uniformly, which is the look this exists to avoid. Sun goes, sky stays: overcast reads *flat*, not dark.
- **Ambient reads an area, not a point** (`CoverAround`, five taps). "How much sky is over me" is an average by definition, and a single tap lurches between 0 and solid every time a cloud edge crosses it — smoothing afterwards does not turn that back into the quantity that was wanted.
- **Coverage is also the dial for whether the weather is noticeable at all**, which is a different question from whether it looks right: a handsome sky with a fifth of it covered leaves the arena in unbroken sun for minutes, because a shadow only lands when cloud happens to sit on the one patch its sun ray crosses.
- **Cloud color follows the dome** (`ApplyCloudPalette`, re-run on every dome switch). A cloud has no color of its own — its lit side is the color of the sun and its underside the color of the sky — so the lit side takes the same tint the scene's key light takes (`SKY_TINT_STRENGTH`, shared with the rig, so the clouds are lit by literally the same light as everything under them) and the underside takes the zenith, harder (`CLOUD_SHADOW_TINT_STRENGTH`), since it sees no sun at all. One fixed white cloud over all eighteen domes read as a grey smear pasted onto turquoise day, blood-red dusk and near-black night alike; checking a change like this means a launch per dome (`sky=<n>`), because synthetic NumPad presses do not reach the window.

Costs nothing measurable — 265–338 FPS on `Dense20x10x15` uncapped, the same CPU-physics ceiling as before. `SkyDome` takes an optional `Effect`; leave it null and it draws the plain gradient through `BasicEffect`, which is what the MapEditor does (it does not build `Sky.fx`, so it gets no drawn clouds). The cloud shadow in `InstancedModel.fx` is no longer stubbed: `Clouds.fxh` is always included, and the MapEditor simply never sets the cloud uniforms, so `CloudCoverageGain` stays zero and `CloudSunlight` returns a flat 1.0 — full sun, no shadow.

### Color management (Testbed)

The Testbed renders in **linear radiance** and leaves it exactly once. The scene always draws into a half-float HDR `RenderTarget2D` (`_sceneTarget`, `SurfaceFormat.HdrBlendable`, sized backbuffer × `_supersampleFactor`), and `Tonemap.fx` resolves it in one full-screen pass: box filter over the supersampled block, exposure (`DEFAULT_EXPOSURE`, `exposure=<f>` to override), the ACES filmic curve, then sRGB encode. The text overlay and aimer draw after it, in display space.

Between the scene and the tonemap sits **glare** (`Glare.fx`), two passes at a quarter of the *back buffer* resolution (not of the supersampled target — glare is blurry anyway, so the extra samples buy nothing; it costs ~0.03 ms and is independent of `ssaa`). A bright pass keeps each pixel's excess over `GLARE_THRESHOLD`, tinted with the pixel's own color so a red ball glares red; a streak pass smears it into a six-armed star. Each arm is normalized against **its own** weights and the arms are combined with `max` — summing all taps and dividing by the total weight of every arm collapses the star into a round blob. `Tonemap.fx` adds the result back **before** the ACES curve, so a glaring ball bleaches through the same highlight roll-off as everything else instead of looking like a decal. It is deliberately exaggerated: the point is to make it unmistakable that the balls emit light, not to model a lens. `GLARE_INTENSITY` was retuned from 2.6 to 1.3 when the procedural meshes' winding was fixed — the balls had been showing their far hemisphere, so everything above the threshold got brighter at once and the old number bleached a hole in the skyline.

Where a color is decoded depends on what it is. **Textures and model material colors** are sRGB data and are linearized in the shader at the point of use (`SrgbToLinear`, a cubic fit). **The light rig and the sky palette** are decoded on the CPU by `Prazsky.Core.Tools.ColorSpace`, because everything applied to them there — the `1.3`/`0.75` scales, the tint lerps — are multiplications, and `SrgbToLinear(a*b) != SrgbToLinear(a)*SrgbToLinear(b)`. `InstancedModelRenderer.SkyColor`/`GroundColor` therefore hold **linear** values and are not clamped to 1; `LinearLightRig` selects whether `SetLightTint` decodes the rig. Both executables now set it **true**: the map editor renders in linear and tonemaps like the game, so its `ApplySkyLighting` decodes the sky palette to linear too and its `SkyDome` is built with `linearVertexColors: true` (the dome's baked gradient is drawn through `BasicEffect` into the HDR target and has to be converted from sRGB once at load, or the tonemapper reads display values as radiance). `SrgbToLinear` in the shader always decodes now — the `#if OPENGL` no-op is gone. Adding a color to the frame without linearizing it is the recurring bug in this area: it has happened twice (the balls' sheen, the ambient scales).

Lighting is Blinn-Phong plus a **specular ambient**: `SkyRadiance` evaluates the dome analytically (the domes are two-color vertical gradients, so a prefiltered cubemap would only reproduce this at lower resolution), sampled along the normal for diffuse and along the reflection for specular, with roughness — derived from the Blinn-Phong exponent, so no material was re-authored — lerping towards the sky average. Fresnel is Schlick over a **dielectric F0 of 0.04** modulated by the material's specular color; handing `SpecularColor` to Schlick directly makes F ≈ 1 at every angle and veils the whole scene. A `Metalness` uniform (0 for every surface except the funnel's gold rims) lerps that F0 from the dielectric `0.04 * specular` up to the specular color itself, which is what a bare metal needs — its reflectance is high and colored, so a gold rim reflects the sky in gold rather than near-white. It must be set on **every** `Draw` (it is, alongside `SpecularAmbientStrength`), or a leftover 1 would turn the next surface to metal.

### Ball rendering (Testbed)

Balls are procedurally generated spheres (`SphereMesh` in Prazsky.Core) drawn with GPU instancing at three LOD resolutions picked by camera distance: `CollectBallInstances` fills one bucket per `BallType` × LOD (no camera culling — measurements showed it saved nothing on this scene) and `InstancedModelRenderer` issues one `DrawInstancedPrimitives` call per bucket. Per-instance data (`ModelInstance`, TEXCOORD1–5) carries the world matrix plus the ambient-occlusion vector (direction towards occupied neighbor cells + base factor, recomputed every frame from the grid). The shader (`Testbed/Content/Shaders/InstancedModel.fx`) does per-pixel Blinn-Phong with a positional key light ("sun"), hemisphere ambient tinted by the sky dome palette (`SkyDome` extracts zenith/horizon colors from the dome's vertex colors; `ApplySkyLighting` distributes them, `DefaultLighting` holds the base rig), directional AO, and a per-type diffuse tint (`GetDiffuseTintByType`). There are **eight ball types** — red/green/blue/white plus **cyan/magenta/yellow/black** (`BallType.Type1..Type8`, their tints and ambient in `BasicEffectParamsProvider`); `BALL_TYPE_COUNT` (`= (int)BallType.Type8`) sizes the instancing buckets in both executables, `RandomBallType` spans all eight, and the map editor's NumPad1–8 pick them. Two carry a deliberate quirk of the white-gore pattern: **white** is drawn beige and **yellow** a rich gold so their pattern reads against the white gores (a pure-white or pale-yellow primary would be patternless), and **black** is near-black with near-zero ambient — its form comes from the glossy highlight and its white gores, and since emission radiates the primary it is the one ball that stays dark while the rest pulse. Balls draw with the `InstancedModelPattern` technique: a procedural beach-ball pattern (gores alternating between the type tint and white, white discs at the poles) evaluated in object space so it turns with the ball and makes rotation readable; `PatternGoreCount` on the renderer enables it, the tint passed to `Draw` becomes the primary gore color, and `PatternGoreWidth` sets how much of each pair of segments the color takes. Balls are **emissive and alive**: they radiate the ball's own type tint — `primary`, not the blended pattern color, whose gores and polar discs are white and made half of every ball radiate white light (`EmissiveStrength`, `BALL_EMISSION`) on a `Heartbeat` curve — two gaussian bumps per cycle, lub-dub, not a sine — whose phase is offset by world position along `PulseDirection` so the beat travels up the cluster as a wave instead of every ball flashing together. `PulseTime` is driven from wall-clock time in `Update`, so the pulse survives a paused or slowed simulation. The emission is deliberately **not** occluded: a light source buried in the pile is the one that should still glow out. `TranslucencyStrength` adds light carried through the shell from a source behind. Note the ad-hoc Fresnel "vinyl sheen" that used to live here is gone — it was a sky reflection, which the specular ambient now does for every surface, and two Fresnel sky terms stacked on a sphere bleached the balls out.

The same technique gives the ball its inflatable-vinyl surface: a sine-sum height field (molded micro-relief plus a groove along every panel weld) tilts the normal through `PerturbNormalFromHeight`, breaking up the highlight, and a Fresnel term adds the grazing-angle sky sheen (`PatternReliefStrength`, `PatternSheenStrength`). Each relief octave band-limits itself against its own wavelength using the screen-space pixel footprint (not camera distance), because the perturbation is derivative-driven and turns into a checkerboard once a wave gets near pixel size. The scene therefore renders into a supersampled `RenderTarget2D` (`_supersampleFactor`, default 2, `ssaa=<n>` to override) that is box-filtered onto the back buffer: more samples shrink the footprint, which is what keeps the fine octaves alive and sharp. MSAA antialiases geometry edges but not shading, so it is switched off while supersampling is on. The text overlay and aimer draw after the resolve, at native resolution. The old ball shadows are gone with the drawn ground: the `InstancedDepth` shadow-map pass and the `ShadowOverlay.fx` ground overlay were dropped when the city became the scene (`DrawDepth` and the `InstancedDepth` technique still sit in `InstancedModelRenderer`, unused; the orphaned `ShadowOverlay.fx` file — no `.mgcb` referenced it — has been deleted). The scene objects — the ceiling and cannon as single-instance draws, the city and arena floor as instanced arrays — render through the same shader (`InstancedModelRenderer.Draw(...)` with per-part material colors/specular read from the model), so the whole scene shares one lighting model; `SkyLitRenderers()` enumerates every sky-lit renderer for `ApplySkyLighting`. The ceiling is a procedurally generated translucent glass box (`BoxMesh` in Prazsky.Core), regenerated at the exact field size whenever a map is loaded (`RecreateCeilingRenderer`) and drawn after the opaque scene. Models whose materials carry a texture use the `InstancedModelTextured` technique. Models without one can set `DetailTexture` on their renderer — a texture that only modulates the material colors — mapped either world-space (`DetailMapping.Triplanar` + optional procedural masonry joints, used by the arena's marble floor, whose boxes carry no UVs worth the name) or through the model's own UVs (`DetailMapping.ModelUVs`: moving objects must not use the world-space projection or the texture would swim across them — the cannon used this before it became procedural, and nothing uses it now). The UV path can add a `DetailNormalMap` for actual relief; its tangent frame comes from screen-space derivatives (`CotangentFrame` in the shader), so no model needs tangent vertex data. On top of any of these, `SurfaceReliefStrength`/`SurfaceReliefFrequency` add a procedural micro-relief (seven summed sines in world space) that tilts the normal through the same `PerturbNormalFromHeight` — no texture, no tiling, and it holds its grain to whatever the pixels can still resolve. The scene path band-limits each octave through `ReliefOctaveDirectional`, which measures the footprint **along that octave's own wave direction** (`abs(dot(dpdx, waveDirection)) + abs(dot(dpdy, waveDirection))`) rather than as one scalar: a pixel only fails to resolve a wave when it is wide across its crests, and on a surface seen at a grazing angle — a pixel covering meters along the view but millimeters across it — a scalar footprint reports the long axis and fades out every octave at once, leaving the surface geometrically perfect exactly where it should look roughest. The ball path still uses the scalar `ReliefOctave`, spheres being small enough that it does not show. `TextureSampler` is anisotropic for the same reason: isotropic mip selection blurs a textured surface into a smear at grazing angles. The arena's marble floor uses it (the cannon did too, before it became procedural). A model is rarely one material throughout, so `SetMeshSurfaceStyle(meshName, SurfaceStyle)` declares per mesh what it is made of — `Masonry` (coursed blocks with mortar cut in as real recesses), `Wood` (upright boards, seams between them, grain stretched along their length) or `Plain`; meshes left undeclared default to `Masonry`. Nothing calls it now that the multi-material castle model is gone, so it — and `MasonryStrength` — sit unused as library features. Testing CLI args: `autoshoot` (logs FPS + LOD distribution once per second), `aimcheck` (logs per-map aim reachability, PASS/FAIL), `aimshoot` (auto game-mode aim-and-shoot scan; see "Cannon controls"), `nocap` (no vsync), `sky=<n>`, `scene=<name>`, `ssaa=<n>`, `exposure=<f>`, `switchmap=<path>`, and `campos=x,y,z`/`camtarget=x,y,z` (place and aim the free camera at startup, so a screenshot can be framed from any vantage — e.g. `campos=0,-18,24` under the sea) — see `.claude/skills/verify/SKILL.md` and `.claude/skills/screenshot/SKILL.md`. `Maps/Dense20x10x15.json` (3000 balls) is the perf stress map; the frame budget ceiling there is the CPU physics (~300 FPS uncapped), not rendering.

### The cannon (Testbed)

The cannon is procedural now (`Prazsky.Core.Render.CannonMesh`) — the last modeled asset, `Cilinder.dae`, and its `CannonMetal`/`CannonMetalNormal` textures are gone from the content project. It is a thick-walled steel tube along the barrel axis with a **slot** running along the top (`CANNON_SLOT_HALF_ANGLE`, ~57°): a smooth-shaded outer and inner wall over the rest of the circumference, annular rims at the muzzle and breech, and rim faces closing the wall's thickness along the slot's cut edges so it does not read as paper-thin (wound clockwise-from-outside with the auto-winding helper described under Conventions). It has to stay a tube — a barrel — with only a slit on top, or it reads as an open trough; the balls nest in the bore and only a strip of each shows through the slit, which is enough to see its colour. The slot's width is not just a look, it is how much of the magazine reads: the balls sit **entirely inside** the bore (centres on the axis, radius 0.5 against a bore of 0.6), so nothing protrudes and the near rim occludes them as soon as the eye is off the slot's own axis. At the original ~41° the queue was invisible from anywhere but straight above. No UVs, so no detail texture — plain steel whose sheen is the specular ambient reflecting the sky.

The point of the slot is the **magazine**: the cannon loads a queue of `MAGAZINE_SIZE` (5) balls in a row inside the barrel, and they show through the slit so the player can see the colour that will fire and the ones queued behind it — you cannot aim a shot whose colour you cannot see. The queue is a plain `BallType[]`; `ShootBall` fires `_magazine[0]` (the ball at the muzzle) and `AdvanceMagazine` shifts the queue forward and drops a fresh random type in at the back, so it never empties. The loaded balls are drawn as **real balls** — added to the instanced ball buckets in `CollectBallInstances` at positions along the aim axis (`CannonMuzzlePosition() - dir * (i + slide) * MAGAZINE_SPACING`, index 0 at the muzzle = the spawn point), so they get the same pattern, emission and sky lighting as every other ball. The advance is **animated**, not a snap: `AdvanceMagazine` arms `_magazineSlide` at 1 (each ball drawn one slot back, so the muzzle slot is momentarily empty where the fired ball left) and Update eases it to 0 off the wall clock (`MAGAZINE_SLIDE_TAU`), so the queue glides forward into the freed slot.

The cannon is drawn with its own look-at matrix (`CannonWorld`) rather than `Cannon.World`: the mesh is modelled with its muzzle towards local -Z and its window towards local +Y, which `CreateWorld` maps to the aim direction and the up vector. `Cannon` keeps only the pose logic (orbit, aim, `Position`, `AimTarget`); its `Object3D` model slot is unused and its constructor no longer takes a `Model`.

That up vector is **world up**: `CannonOrientation()` points the barrel down the aim and pins the slot (local +Y) to world up, so the slit stays on the barrel's upper face and never rolls about the bore. An earlier version rolled the slot to face the **camera** so the loaded queue was always readable, but the roll looked wrong in motion — the gun is to sit on a stand that only **elevates and traverses**, and a barrel that spins about its own axis to track the eye reads as unreal. The cost is accepted: from the low game camera the player sees the barrel's underside and not always the queue (precise aim, whose camera rides over the barrel, still looks into the slot). `CreateWorld` orthogonalises world up against the aim, so the slit stays on top as the barrel elevates; the bore is clamped well off vertical (`Cannon`'s elevation clamp), so world up and the aim are never parallel and it never degenerates — and it no longer depends on the camera at all. The magazine balls take **the same basis**, which stops them skewing: drawn unrotated they would hold a fixed world orientation while the barrel tilts around them. They lie in the bore, so they are carried by it.

`Cannon.Position` is the **trunnions** — the pins a carriage holds a real gun by, at the barrel's point of balance — and not the muzzle. Aiming leaves `Position` alone and only moves `AimTarget`, so whatever `Position` means is what the barrel turns about: with it at the muzzle the whole tube and its loaded queue swung from the tip, which is the one place a gun does not pivot. The mesh is therefore modelled **about its midpoint** (`muzzleZ`/`breechZ` are laid symmetrically around `CANNON_PIVOT_TO_FRONT_BALL`, half the queue's length), so the world matrix's translation is the pivot. The muzzle becomes derived — `CannonMuzzlePosition()`, `CANNON_PIVOT_TO_FRONT_BALL` ahead of the pivot along the aim — and is what both the magazine layout and `ShootBall`'s spawn point hang off, so the shot leaves from the ball the player was watching rather than from the middle of the barrel. The aim direction is unchanged by this (the muzzle lies on the pivot→`AimTarget` line), so nothing about where a shot goes moved. `trunnionHeight` in the constructor is consequently an axle's height **above** whatever the gun stands on, not the floor — the room under the barrel is where the carriage and wheels will go.

### The game-mode camera (Testbed)

Third-person, behind the gun and **below** its trunnions, near the arena floor. The game is picking a cell out of a cluster hanging overhead and putting a ball of that colour into it, so the frame has one job: show the whole map, from underneath, square enough to read the layout — the gun is furniture in the foreground.

- `GetCannonDirection()` is **flattened to the horizontal**. Taken straight from `Position - OrbitCenter` it tilts down by however far the gun stands below the cluster (~30° here), so half of the camera's back-off went downwards and cancelled its height, putting the camera on the barrel's own axis. Flat, `GAME_CAMERA_HEIGHT` is the only thing setting the camera's height, which is the point of it.
- **How much of the angle on the map is actually the camera's to give is small, and worth knowing before tuning it.** It is `atan((clusterY - cameraY) / horizontal distance)`, and a camera behind the gun is always further out horizontally than the gun itself, so it always sees the cluster *flatter* than the ~30° the barrel has. On the floor it is ~25°; a true perpendicular from-below view would need the camera at y = -20, far under the world. What dropping it buys is 5° (edge-on, the map a strip at the top of the frame) to ~22°, which is the whole difference between reading the layout and not — but 40°+ is not on the table without moving the camera out from behind the gun or shrinking the orbit radius.
- **The view does not ride the aim.** `GetCannonOffsettedTarget()` is the field centre. The controls split cleanly: orbiting carries the camera around the field, aiming turns the barrel inside a frame that stays put. An earlier version aimed the view along the barrel, which swings the board the player is reading and, at full traverse or depression, swings it off the screen.
- `GAME_FOV` is **narrow** (`Pi/4.2`, ~43°) and that follows from the drop. From up behind the gun the barrel and the cluster were 57° apart and the FOV had to be wide enough to hold both, leaving the map a small patch in a very wide frame; from down here they are ~14° apart, so the frame can close in on the map.
- **The stand-off and the aim height are solved, not tuned** (`FitGameCameraToMap`, run on map load and on resize). Both inputs move under a fixed number: the field is sized per map, and the frustum per display. It bisects for the smallest camera distance at which the field's eight corners, the top of the glass ceiling and a box around the cannon all land inside both half-angles, then bisects that angular range to get the aim height. Measured: `Full.json` (10×10×16) and `Dense20x10x15` settle around distance 34, `20x20x20` pulls back to 44. Hand-tuned constants framed `Full.json` and cut the top clean off `20x20x20` — a fixed frame can only ever fit one field size.
- **The cannon is placed relative to the camera, not to the field** (`CANNON_CAMERA_STANDOFF`, 15 units in front of the lens). The queue showing through the barrel's slot is what the player reads the next colour off, so it is really a HUD element and has to keep its size on screen; anchoring the gun to the field instead lets a large map push the camera back and shrink the gun with it. Two lower bounds override the stand-off and **which one binds changes with the map**: clearing the field's corner (or the gun stands under the cluster) and staying far enough out that the resting aim sits comfortably inside `Cannon`'s elevation clamp (now strongly up-biased — see the clamp rework below). `Cannon.OrbitRadius` is settable for this and slides the gun along its current orbit angle.
- The two solves are **mutually dependent** — the camera frames the gun, the gun is placed off the camera — so `FitCannonAndGameCameraToMap` alternates them a few times. It converges immediately in practice: at a fixed distance from the lens the gun's angular footprint is the same whatever the radius, so the camera's solve barely moves after the first round.
- **Moving the cannon closer to the field does not close the empty ground between the gun and the map**, which is worth knowing before trying it again. It was tried: because the camera stands off from the *field centre*, a cannon closer to the field is a cannon *further from the camera* (20.3 units against 14.9 on `Full.json`), and since the camera sits only 1.5 below the trunnions the gun is near the horizon from it — pushing it away moves it *towards* 0°, i.e. down, not up. Its elevation went from 5.75° to 4.23° and it lost a quarter of its size. The gap is set by the vertical drop from the hanging map to the gun, and only moving one of those in Y changes it.

### Precise aim (ADS) (Testbed)

The complement to the overview above, and the deliberate inverse of its "the view does not ride the aim" rule: a hold-to-aim sub-mode of game mode that *does* ride the aim, the way a shooter's iron sights do. Held with the **right mouse button** (or the gamepad **left trigger**), it leans the camera in over the barrel and looks straight down the aim, so the whole map reads and the shot goes where a screen-centre crosshair points; releasing eases back to the overview. It only runs in game mode (free mode still shoots from the fly camera). The overview's "how much angle is the camera's to give is small (~25°)" limit is exactly what this dissolves: a camera that looks *along* the aim sees whatever the barrel points at, head-on.

- **The pose is an over-the-barrel scope.** `AdsCameraPosition()` sits the lens `ADS_BACK` (6) behind the muzzle along `-aim` and `ADS_RISE` (2) above the bore, so the barrel is a small sliver along the bottom of the frame — grounding, not obstruction — and `AdsCameraTarget()` looks at a point **on the shot ray** (`muzzle + aim·d`), so screen centre marks where the shot is directed (the shot leaves the muzzle along `aim`, so this is honest before gravity). `d` is the field's vertical midpoint projected onto the aim, clamped to `[ADS_CONVERGE_MIN, ADS_CONVERGE_MAX]` = `[6, 90]`; since the crosshair is on the ray at *any* `d`, this only *centres* the small over-the-barrel parallax over the depth range the impact face sweeps. **Aiming steeply up, `-aim` points down, so the set-back drops the lens below the stone island** (top at `ARENA_Y`) and it showed the disc from underneath — an artefact the widened elevation clamp (up to ~80°) exposed. `AdsCameraPosition` therefore floors the lens Y at `ADS_MIN_Y` (`ARENA_Y + 1`): at every clamped-steep aim the frame bottom still looks ≥13° up, so the island stays out of frame and the lens never sinks through it. (Only the ADS camera rides the aim; the overview camera holds a fixed pose, so it never needed this.)
- **Two different ups, on purpose.** The lens offset uses `AdsCamUp()` — world up made perpendicular to the bore (`Up - aim·dot(Up,aim)`) — so the lift is straight over the barrel at every pitch and yaw and the tube stays a *bottom-centre* sliver. The **view** up is plain world up, got for free by setting `_camera.Target` **last**: `BasicCamera3D`'s `Target` setter rebuilds the view with its fixed `Vector3.Up`, giving a level, roll-free horizon. Both are well-conditioned across `Cannon.EnsureAimInBounds`'s elevation clamp (`Cannon.MinElevation`/`MaxElevation`, ≈ `[-5.7°, +80°]` — see the clamp rework below): at the ~80° ceiling the bore is still ~10° off vertical, so `AdsCamUp`'s `up` keeps `|up|² ≈ 0.03`, far above the 1e-4 fallback threshold (which only trips within ~0.6° of straight up); the horizontal-perpendicular fallback stays dead code unless the clamp is pushed almost to vertical.
- **Modest zoom, not a tunnel.** `ADS_FOV` = π/5 (36°) against `GAME_FOV` π/4.2 (43°) — a 1.19× lean-in. It is the *vertical* FOV (`CreatePerspectiveFieldOfView`), so the sliver position and every parallax angle are aspect-independent; nothing here needs per-map or per-aspect solving (unlike the overview), because precise aim magnifies the aim region rather than framing the whole field — the overview owns full-field context.
- **One reversible blend scalar.** `_adsBlend` eases 0→1 while held with the same `MathF.Exp(-dt/τ)` idiom as `_magazineSlide` (`ADS_BLEND_TAU` 0.08 s), and the per-frame pose is `Lerp(overview, ADS, _adsBlend)` for FOV, position and target. At `_adsBlend == 0` the Lerps return the overview pose **bit-for-bit**, so disengaging re-asserts today's game mode exactly. It is C1-continuous through an interrupted hold/release (no state machine, no snap). The set order **FOV → Position → Target is mandatory** — the `Target` setter rebuilds the view last, with world up, from the freshest values; the FOV setter's own `Recalculate()` is a throwaway.
- **The mouse aims the cannon throughout game mode** — in the overview as well as in precise aim (the arrow keys are retired). The cursor is captured the whole time you play: hidden and recentred every frame off the **live** `GraphicsDevice.Viewport` centre (**not** `CameraInputHelper`'s cached `_widthHalf/_heightHalf`, which go stale after a resize). The pixel delta is divided by the frame time, which cancels *exactly* against the frame time `Aim` multiplies back in, so aim moves a fixed `0.001·MOUSE_AIM_SENSITIVITY` radians per pixel at any frame rate; `_adsMouseInitialized` skips the first captured frame so grabbing the cursor never yanks the aim. Non-inverted (mouse up = aim up, mouse left = yaw left); the gamepad right stick aims too, fed in as a rate (no `1/dt`). Precise aim changes nothing about the aiming itself — it only leans the camera in over the barrel (below).
- **The aim persists within a game-mode session; only the mouse moves it.** There is no auto-return to rest and no recentre-on-orbit — the whole aim-parking mechanism (`_aimParkingStarted`, `HoldAim`, `ReturnAimToRest`) was removed from `Cannon`. Releasing precise aim keeps the aim (it is just a zoom-out, so you stay pointed where you were), and orbiting with A/D turns the carriage without dragging the barrel to centre — like a turret keeping its aim as the base rotates. An earlier build returned the barrel to rest on precise-aim release and recentred it on orbit; both were dropped once the mouse became the aim everywhere in game mode, where they would have discarded the player's aim on a zoom-out or a reposition. **Leaving game mode does reset it**, though: `SwitchGameMode(false)` calls `Cannon.ResetAim()`, which *eases* the aim back to the rest direction over ~1 s (`Vector2.SmoothStep`, the same smooth return the old orbit parking had; orbit position left alone) — the gun swings back rather than snapping, and each game-mode session starts neutral. `Cannon.Update` advances the ease every frame regardless of mode (the cannon is a prop in free mode), and a mouse `Aim` interrupts it.
- **Cannon controls (game mode).** Aiming (elevation/traverse) is the **mouse**; firing is **LMB or Space**. Orbiting the gun around the field is on **A/D** (A left, D right), game-mode only — in the free fly camera the mouse and A/D belong to the fly camera instead. **W/S are unused** (the gun turns on a carriage; it does not rise or fall). The arrow-key aiming and the old NumPad4/6 orbit are both retired.
- **The elevation clamp is strongly up-biased** (`Cannon.MinElevation`/`MaxElevation`, ≈ `[-5.7°, +80°]`; traverse `MaxTraverse`, ±45°). The whole target cluster hangs overhead, so aiming down only wastes shots into the ground. The old near-symmetric range (`[-28.6°, +45°]`) did both wrong: it let the gun plunge into the ground, yet **could not lift onto a large map's top cells** — the clean shot at a cell is from the orbit angle that *faces* it (the ball rises over open ground; the opposite angle is shallower but fires across the cluster and is obstructed), and that facing elevation runs ~50-65° on the big maps, so a third of a wide map was unreachable and the level could not be finished. ~80° up covers the top corners of every supported map with margin, kept off vertical for the ADS up-vector; ~-6° down is a hair of feel with no more ground shots. `Cannon.CanAimAt`/`AimAt` aim the barrel at a world point within the clamp (used by the test tooling and any future auto-aim); `OrbitToFace` stands the carriage facing a target.
- **Testing the aim/shoot gameplay** (it is otherwise mouse-driven and hard to automate): `aimcheck` logs, per loaded map, the steepest *facing* elevation any cell needs against the clamp and a PASS/FAIL (`Testbed.LogAimReachability`); `aimshoot` (implies `aimcheck`) auto-enters game mode and fires a scan up the field's centre column then at its four top corners (orbiting to face each via `Cannon.OrbitToFace`, aiming via `AimAt`), logging the elevation each shot wanted vs what the clamp gave — a shot held short reads `CLAMPED SHORT`. Both run headless in a background window (the mouse aim is gated off under `aimshoot`).
- **LMB fires in game mode**, completing the hold-RMB-to-aim / click-to-shoot idiom (Space still fires). No shooting change was needed: `ShootBall` in game mode already spawns from `CannonMuzzlePosition()` towards `_cannon.AimTarget`, i.e. along `aim`, which is the very ray the crosshair converges on.
- **Two wiring fixes are load-bearing.** `CameraInputHelper.CameraMovement` gained an `allowMouseLook` argument, passed **false** in game mode, so its whole mouse region is gated off there — otherwise the right button would *also* toggle the fly camera's rotate/pan and call the stale-centre `CenterMouse`. And leaving game mode straight from ADS (F10 while holding) must not teleport: `SwitchGameMode(false)` captures the leaned pose and sets `_freeExitFromAds`, so the free-mode exit animation eases **position, target and FOV** together from the ADS close-up to the overview pose (a plain overview→free exit leaves the flag false and only widens the FOV, byte-identical to before).
- **Focus and edge-input hygiene.** `_adsBlend`'s target is gated on `IsActive`, so a held **gamepad left trigger** — which XInput reports even when the window is unfocused — does not keep an alt-tabbed window leaned in; losing focus eases ADS out and restores the cursor. And because the LMB now fires in game mode, edge-driven input (the button actions and the LMB shot) is skipped for one frame after focus returns (`_wasActive`): the input state is not registered while inactive, so the very click that refocuses a windowed game would otherwise read as a fresh press against a stale "released" and fire an unintended shot.
- **The honest limit is parallax.** Because the lens sits `ADS_RISE` above the shot ray, the crosshair is pixel-exact only at the convergence depth `d`; a nearer impact reads slightly low, a farther one slightly high — worst ~1.6° on the biggest map, and consistently *slightly low* since balls attach at the near face. It is fundamental to over-the-barrel framing; if pixel-perfect first-contact aiming is ever wanted, replace the `clusterCentre` dot-projection in `AdsCameraTarget` with a Bepu raycast of `(muzzle, aim)` against the ball bodies and set `d` to the hit distance, at the cost of one raycast per frame.

### Resolution and aspect (Testbed)

The game targets desktop and Xbox on large screens — 3840×2160 down to 3840×1600, i.e. **16:9 to 21:9**. The windowed default is 1600×900 so the development case is the narrowest targeted aspect rather than a wider-than-target one.

- `CreatePerspectiveFieldOfView` takes the **vertical** FOV, so a wider display adds width and leaves the vertical framing untouched (`Hor+`). That is the behaviour wanted here — the map keeps its size on an ultrawide and the extra width goes to city — and it means **vertical is the binding constraint at every targeted aspect**, so the frame is already as tight on the map as it can be at 21:9. `FitGameCameraToMap` still checks both axes, because a narrow display (or a tall window, which `AllowUserResizing` permits) flips which one binds.
- `InfoRenderer` scales its text and icon by `Viewport.Height / 2160`, i.e. it is authored for 2160p and scales down — it does not need changing for 4K.
- **Supersampling is the dominant frame cost at 4K, which it is not at 720p.** Measured on `Full.json` at 3840×1600 uncapped: `ssaa=2` gives ~118 FPS, `ssaa=1` ~362 — 8.5 ms against 2.8, so SSAA costs ~5.7 ms/frame. (At 1280×800 it costs nothing measurable, because CPU physics binds long first.) Comfortable for 60 Hz on a desktop GPU; worth knowing before assuming it on a console.
  - **That "costs nothing at 720p" is a statement about *this desktop*, not about the setting.** On an integrated GPU (Ryzen 7 2700U / Vega 10) SSAA is the biggest thing in the frame at any resolution: `ssaa=2` → `ssaa=1` on `Full.json` went ~8 → ~22 FPS, while *tripling* the ball count 1000 → 3000 moved it only ~8 → ~6-7. There the fixed per-frame scene cost dominates and the ball count barely registers — the exact opposite of the story here, and why the game measures rather than assumes (see "Adaptive quality"). Issues #62/#63/#64. Visually at native 4K, `ssaa=1` shows harder stair-stepping on the city's edges and slightly coarser shading on the balls, but the gap is much smaller than at 720p — the native pixel footprint is already ~3× finer, which is what the relief's band-limiting reads.

### The game (Game)

The shipping product, founded as a thin executable over the shared libraries rather than as a fork of the Testbed monolith. `Game/BS3DGame.cs` is the whole game: it owns the frame, the gun and the shot, and borrows the instanced ball shader, the procedural `City`, the shared `SceneRenderer`'s five self-lit backdrops, the `SkyDome`, the `CloudField` and the linear-radiance pipeline from `Prazsky.Core` exactly as the other two executables do. It builds `InstancedModel.fx`, `Sky.fx`, `Glare.fx`, `Tonemap.fx`, `ShotTrail.fx`, the ten scene shaders (`Sea`/`Savanna`/`Desert`/`Acacia`/`Flame`/`Birds`/`Mountain`/`Snow`/`Spray`/`Meadow`), **all eighteen** `Skyes/SkyDome*.dae`, the island's marble (`GameObjects/Ground_8.png`) and the overlay's `Fonts/segoeui.spritefont` out of the Testbed content directory. The only files it owns are the menu's two **Inter** TTFs, which are `EmbeddedResource`s rather than content (see "The front end").

What it is: the round stone island the gun stands on with the Testbed's **glass drain funnel** in its middle, standing in **any of the seven settings** — the same `SceneKind` set the Testbed and the map editor draw, picked at random each launch and switchable from the menu — under a sky of **drifting procedural clouds**, with a **hanging cluster** (a stepped square pyramid, apex down, in four colours) hanging from the Testbed's own **translucent glass ceiling**, the procedural cannon with its magazine showing through the barrel's slot, the shot at `SHOOT_SPEED` (200 u/s) with its launch smear, each scene's own point lights, and the recoil below — which moves the gun as well as the camera. Post-processing is the Testbed's own: supersampled HDR target → glare → ACES tonemap, with the same constants, so the two agree.

**The game runs a real Bepu simulation** — the founding slice's biggest deliberate omission, and it is gone. The cluster is bodies held to each other and to a kinematic glass ceiling by `BallSocket` constraints, so it sways and a shot shoves it; a shot is a dynamic body thrown down the bore; the island's drain is a collision mesh balls run down and fall through; and a group of three or more touching balls of one colour lets go and falls, taking anything it was the last anchor for with it. See "Physics in the game" below.

**The cluster is a level off disk**, read through the shared `Level`/`BallsMap` loaders from the files a `LevelSet` orders — see "Levels in the game" below.

**Clearing the field wins the level and advances through the set**, gated on the level's minimum score — see "Levels in the game" below.

What it still deliberately does **not** have: no aim feedback beyond precise aim's crosshair (#47), no audio, no way to *lose* (#58), and no HUD but the FPS line — the score, the streak and the level's outcome are all counted and none of them are shown (#59, #60).

The first pass over it after it was founded closed four gaps against the Testbed — the cluster hung from nothing, the island was a flat grey band, the sky was a flat purple wash, and shot balls stuck where they touched and chained into an icicle pointing at the camera. All four are above; the icicle is below, along with the traps each one turned out to carry.

- **Recoil and camera shake.** `Prazsky.Core.Camera.CameraShake` is the game-agnostic half: `Kick(strength)` on firing, and it produces **offsets only** — a rotation triple (pitch/yaw/roll), a lens displacement, a set-back along the view and an FOV punch — so a kick can never accumulate into the pose, and at rest every output is exactly zero. It models *two* things because a gun does two things: a **directional recoil** (thrown back along the view, muzzle rising — not random, which is what separates recoil from a generic wobble) that recovers quickly, and a **random rattle** that decays a little slower. Both decays are **linear in time, not exponential**, so the shake genuinely ends instead of leaving a permanent sub-pixel jitter; the amplitude is the trauma *squared*, because a linear decay spends most of its life in the middle amplitudes and reads as a lingering wobble rather than a jolt. The rattle's phase runs off accumulated seconds (two sines at incommensurable frequencies), never off a frame counter — a per-frame random would shake faster on a faster machine.
- **`RecoilCamera` is its own `ICamera`, and the reason is roll.** `BasicCamera3D` rebuilds its view with a fixed world up, which is exactly right for a level horizon and exactly wrong for a camera being knocked sideways; `RecoilCamera` keeps the base pose (which the game rewrites every frame from where the gun stands) separate from the shaken one, rotates the view basis by the shake and **rolls the up vector about the view axis**, so the whole frame tips. Rolling is what makes the eye read "the camera was hit" rather than "the aim moved a little", so `MaxRoll` is the largest of the three angles. Measured at full strength: 40 ms after a shot the mean frame difference is ~9 %, and by 200 ms it is back under 1 % — a hard jolt that is gone before the next shot.
- **The camera's ceiling was lowered, and the gun took over the difference.** At full strength the shake read as the *lens* being hit rather than as a gun going off, so every dial of `CameraShake` is scaled by one number in `Initialize` (`CAMERA_SHAKE_SCALE`, 0.45) — the shape of the response is kept, only its ceiling comes down, and that is the one number to turn. It is the **ceiling** that is scaled and not `RECOIL_KICK`, which stays 1: `Kick` accumulates and saturates at 1, so a fractional kick would let two shots in quick succession climb straight back to the response that was too strong. What replaces it is the gun's own recoil (`CANNON_RECOIL_BACK`/`_DECAY`): the barrel is thrown straight back along its bore and slides home over ~0.24 s, carrying the balls loaded in it, because `CannonWorld` and `CollectMagazineBalls` both add `CannonRecoilOffset`. Squared in the stroke, so the throw is instant and the return eases — the same reasoning as the shake's amplitude. It is **drawing only**: a shot leaves along the true aim on the frame it is fired, before the barrel moves, so nothing about where a ball goes depends on it (the trail stays anchored at the un-recoiled muzzle, ~1 unit from the drawn one at the peak, which is invisible against a 7-unit smear).
- **The camera pose** is the Testbed's game camera: back from the field centre along the gun's own bearing and just below its trunnions, looking at the cluster. The bearing is **flattened to the horizontal** for the same reason as in the Testbed — taken straight from the gun's offset it tilts down by however far the gun stands below the cluster and eats the camera's height. The stand-off and the aim height are solved per level and per display, not tuned; see "Levels in the game (Game)".
- **The shot is a swept sphere test, not a point test.** At 200 u/s a ball crosses several diameters per frame, so a point test at the end of the frame tunnels clean through the cluster; `TryHitCluster` solves for the **moment of contact** instead — the quadratic in the step parameter whose smaller root is where the two spheres first touch. It first ranked candidates by their *clamped closest approach*, which is wrong in exactly the case that matters: on the frame a ball first comes within reach it is still approaching, so every candidate's closest approach lies past the end of the step and clamps to 1. The whole field ties, and "first touched" then falls out of the array order rather than the geometry. Cheap either way — a few hundred quadratics per flying ball.
- **A landed ball snaps into the lattice; sticking it where it touched is what made the game read as broken.** `BallsMap.PutBallAtClosestEmptyPositionNextTo` puts it in the free cell touching the ball it hit that lies nearest the contact point, so it lands flush in the packing. Stuck at its raw contact point it stands off the surface — and since `_clusterBalls` is also what the next shot is tested against, each ball then sticks to the one before it and they chain into an **icicle pointing back down the line of fire**. Three things follow from doing it properly:
  - The `BallsMap` is now kept alive as the truth about the cluster (it was a local in `BuildCluster`), and `_clusterBalls` is a flattened copy of it — each ball carrying its cell — rebuilt by `RebuildClusterBalls` whenever a ball lands. Rebuilding the lot rather than appending is what keeps the **neighbours'** occlusion right: a ball that arrives also boxes in everything it arrived next to.
  - **The layout hangs at the top of a taller field**, exactly as a map file's does, so the empty levels underneath are room to grow downwards. Because a level's height is its index over √2, the layout would ride that many levels higher, so `CLUSTER_WORLD_Y` puts it back: the grid is the truth, and the offset is applied where the lattice frame meets the world and nowhere else (the general-purpose `MapToWorld`/`WorldToMap` pair this used to go through is gone — see "Physics in the game" for the two crossings that replaced it). What constrains `CLUSTER_EXTRA_LEVELS` is that **`FIELD_LEVELS` must come out even**, i.e. the field's topmost level must be one of the shifted (odd-index) ones. `BallsMap.Center()` centres the map on that top level and offsets by its bounding box's *half-extent* less a ball radius — on a shifted level, whose cells run from 0.5 to N−0.5, that lands exactly on the origin; on an unshifted one it lands half a unit off the axis the gun orbits and the camera looks down. (It was 12 + 6; it is 9 + 7 now that the layout is a nine-level pyramid.) The old rule of thumb that `CLUSTER_EXTRA_LEVELS` itself had to be even belonged to a layout whose shape was written in raw cell indices; `BuildCluster` measures each level's width against the *shifted* position of its cells instead, so the pyramid comes out the same at either parity. **Extra room in X/Z is *not* free the same way** — the same half-extent offset only lands on the origin when the top level's occupied cells start at index 0, so insetting the layout laterally would silently push the whole cluster off centre by the inset.
  - **The first level is a stepped square pyramid, apex down, in four colours.** Widest at the top level (the full `CLUSTER_X` × `CLUSTER_Z` base) and half a unit narrower on every side per level down, so the side count steps 9, 8, 7 … 1 — half a unit, not a whole cell, because consecutive levels are offset by +0.5 in X and Z and shrinking by a cell would put every second level off the axis and zig-zag the flank. `LEVEL_BALL_TYPES` holds four of the eight types and **the magazine draws from the same list**, since loading a colour that is nowhere in the cluster is a shot that cannot be spent; a fixed `LEVEL_SEED` makes it the same level every run, which until map files arrive is the whole of its authoring.
  - **The first ring is not always enough.** The ball a shot reaches first is on the cluster's outer face, and where that face is the field's own wall there is no cell beyond it — so the pocket around an edge ball fills after a handful of shots and every ball after that was silently eaten (measured: 12 of 21 shots on one fixed aim). `TryFindCellInSecondRing` widens the search to the free cells touching the balls that touch the one it hit, nearest the contact first: local by construction, so the ball never lands somewhere it could not have rolled to. That took the same test from 9 of 25 attaching to 25 of 25.
- **The ambient-occlusion direction is a sum of unit vectors and must be divided by `MAX_BALL_OCCLUDERS` before the shader sees it.** Handed over raw it is up to twelve times too long, the shader's dot against it saturates over most of the ball, and every surface ball wears a hard-edged black crescent instead of the soft inward shading that makes the cluster read as one body rather than a heap of spheres. The Testbed divides (`Testbed.cs`'s `occlusionSum / MAX_BALL_OCCLUDERS`); the game did not, and it cost the cluster its whole look.
- **The island is a washer again, because the drain arrived to fill it (#48).** `DiscMesh`'s inner radius came over from the Testbed's `FUNNEL_TOP_RADIUS` (14) before the funnel did, which left a 28-unit hole dead centre under the hanging cluster, open onto the city below; it was pinned to 0 until the funnel could fill it, and it is back at the rim radius now that it does. The glass cone, its two gold beads and every figure of them are the Testbed's unchanged — the game's island top is at the Testbed's own arena height, so the two drains are the same object — drawn the same way: the opaque rims with the opaque scene and the one-sided glass after them, both `CullNone`, before the glass ceiling. What did **not** come over is the physics (there is no simulation here, so nothing rests on the stone and nothing runs down the cone) and the dark pit shaft, which exists only for the Testbed's solid-terrain scenes; in the city the drain looks through onto the canyon below, exactly as it does there. Note the play camera sits 0.6 above the island, so the drain reads from it as a gold line across the bottom of the frame — it opens up as the camera moves, the same as in the Testbed's game mode. The marble is the Testbed's own coursed-slab relief over `Ground_8.png` projected triplanar; the trap CLAUDE.md flags elsewhere is real and was exactly what left it a flat grey band — **without a `DetailTexture` the renderer falls through to the plain technique and every `SlabSize`/`CavityStrength`/relief setting is silently dead**.
- **Precise aim (ADS) is the Testbed's, and so is the reason for it.** Held on the **right mouse button** (or the gamepad's left trigger), the lens leans in over the barrel — `ADS_BACK` behind the muzzle along `-aim`, `ADS_RISE` above the bore — and looks at a point *on the shot ray*, so the shot goes where the screen-centre crosshair points; `ADS_FOV` (36°) is a modest 1.19× lean-in on `GAME_FOV`. It exists because how much angle onto the map the overview can give is fixed by where the camera stands, and a lens looking *along* the aim sees whatever the barrel points at, head-on. One reversible scalar `_adsBlend` eases 0→1 with the `_magazineSlide` idiom and the pose is `Lerp(overview, ADS, blend)`, so at 0 the overview pose comes back bit for bit and an interrupted hold never snaps. One real difference from the Testbed: `RecoilCamera` takes a base pose rather than `BasicCamera3D`'s ordered setters, so the FOV → position → target ordering that file insists on has no counterpart here — the shake is applied on top of whatever base pose the frame set. The focus gate is the *same* rule by a different route, not a difference: the Testbed rebuilds `adsHeld` with an `IsActive` term every frame, while here `UpdateAim` simply does not run while the window is inactive, so `_adsHeld` is cleared in the inactive branch instead. Either way a gamepad trigger — which XInput reports to an unfocused window — cannot keep an alt-tabbed game leaned in. `ADS_MIN_Y` floors the lens a unit above the island: aiming steeply up, `-aim` points down and the set-back would otherwise drop it through the stone and show the island from underneath.
- **The FPS line and the crosshair.** `Prazsky.Core.Render.InfoRenderer` draws the FPS as a `DrawableGameComponent` (so `base.Draw` puts it out last, in display space, with its own `SpriteBatch`), off the Testbed's own `segoeui` font built out of the Testbed content directory; **F12** hides it, the key that hides the Testbed's text. It is authored for 2160p and scaled by `Viewport.Height / 2160`, so `RecomputeScale` has to be re-run on a resize *and* on a fullscreen switch. The crosshair is the game's own and needs no bitmap — four bars struck from a 1×1 white texel, scaled the same way — and it is drawn **only while precise aim is leaning in**, fading up with the blend, because that is the only pose whose lens looks along the shot; in the overview a screen-centre mark would point at nothing in particular.
- **The clouds are the Testbed's weather, minus its ambient half.** One `Sky.fx` entry, `_sky.Effect`, the ten cloud constants, and `_clouds.ApplyTo` on *both* the sky and the instanced effect each frame off the wall clock — which is what keeps the cloud the player looks at and the shadow it throws the same cloud. The cloud shadow on the balls, city and island then costs nothing extra: `CloudSunlight` is already called unconditionally in `InstancedModel.fx` and returns a flat 1 while `CloudCoverageGain` is 0. `ApplyCloudPalette` is **not** optional despite the fixed dome — the two cloud colours have no defaults, and unset means a black deck. The `_overcast` ambient flattening is deliberately left out: its palette is authored for daylight and is brighter than this dusk dome's own, so lerping towards it would *lighten* a night city as the weather thickened.
- **Controls.** Mouse aims (always — game mode is the only mode), LMB / Space / gamepad right trigger fire, **RMB / gamepad left trigger hold precise aim**, A/D traverse the carriage, F11 toggles fullscreen, F12 hides the FPS line, **Escape pauses** (quitting is a menu item now — a game that closes the instant Escape is tapped is one that loses a game). `ssaa=<n>`, `exposure=<f>`, `nocap`, `fullscreen` on the command line — the first two seed the settings screen, which then owns them. Every edge-driven input — Space, LMB **and** the gamepad trigger, which XInput reports whether the window has focus or not — is skipped for one frame after focus returns, or the click that refocuses the game arrives against a stale "released" and fires a shot the player did not ask for. `ssaa=1` falls back to 8× MSAA on the scene target the way the Testbed does (multisampling antialiases geometry edges but not shading, so it only earns its memory with supersampling off) — that is the setting a weak machine reaches for first, and it had no antialiasing of any kind. `SetGraphics` reads `GraphicsAdapter.DefaultAdapter.CurrentDisplayMode` rather than `GraphicsDevice`: it also runs from the constructor, before the device exists, and reading the device there made `fullscreen` mode-switch the display down to 1600×900 instead of filling it.
- **Two traps worth remembering when testing it.** The cursor is captured and recentred every frame, so **any external `SetCursorPos` reads as a huge aim delta** — the `screenshot.ps1` title-bar click yanks the aim to the elevation and traverse clamps, which is a test artefact, not a bug (a shot then flies 45° wide of the cluster). Compensate by setting the cursor a known offset from the viewport centre afterwards; the aim moves ~0.002 rad per pixel, and there is no auto-recentre to fight. And the keyboard is polled **once per frame**, so a `keybd_event` down+up sent back to back is never seen as a press and the shot silently does not happen — the key has to be *held* across a frame (~40 ms is plenty). Both cost a wasted round of screenshots before they were spotted.

### Levels in the game (Game)

The game builds its cluster from a **level file**, not from the procedural pyramid it shipped with. What orders those files is a **`LevelSet`** (`Prazsky.BS3D/Levels/LevelSet.cs`, beside `Level`): a JSON object marked `"format": "bs3d-levels"` listing entries **in play order**, the first entry being the first level. `Game/Levels/Levels.json` is the set; `Game/Levels/One.json` is the first level. Both are plain `Content` copied beside the exe (`CopyToOutputDirectory`), **not** MGCB assets — they are data read with System.Text.Json at runtime, and being editable next to the binary without a rebuild is the point.

- **The order lives in the set, never in the directory listing.** A filesystem has no order worth relying on, and reading the directory would silently promote whatever was dropped into it. Entries are objects rather than bare strings so a level can carry a display name now and par, unlock rules or a preview later without breaking a file that predates them; paths are relative to the set's own directory (captured in `LevelSet.Directory` at load), so a set and its levels move together and nothing depends on the working directory. `LevelSet.Load` validates and throws, mirroring `Level.Load`, and `IsLevelSetFile` is the same cheap marker probe `Level.IsLevelFile` is.
- **A level file or a plain map file, both `.json`, so the loader probes** — `InstallLevel` runs `Level.IsLevelFile` exactly as the Testbed's `DeserializeMapFromFile` does. A full level's scene and sky are applied; a plain map leaves whatever the player picked from the menu standing. `One.json` is a plain map (`sx`/`sz`/`l`/`b`), so it plays in whichever scene is up.
- **Clearing the field wins the level, and winning advances through the set.** The condition is `GetBallsCount() == 0`, tested **only on a landing** (`CheckLevelCleared`) — that is the one thing which can empty the field, and polling it per frame would declare a level authored with no balls won before a shot was fired, and keep declaring it. The end is then held for `LEVEL_CLEARED_BEAT`: balls leave the map at *release* time while their bodies are still falling, so ending the level the instant the last group is cut takes the collapse the player earned off the screen before they see it. The completion bonus is awarded at the moment of clearing, not at the end of that beat, so a shot fired into the empty field meanwhile cannot eat the balls they finished with.
- **`BuildLevel(index)` is the one path** a first Play, a New Game, a retry and an advance all take. `FinishLevel` picks between three outcomes: below the finished level's `minScore` the level is replayed (cleared but not passed); past the last entry the campaign is complete, said plainly and returned to the front end — the session is torn down so the main menu offers a new game rather than "Continue" into a level that is already over — and otherwise the next entry is built. It runs **last** in `Update`, because it may tear the session down and build another in its place, and anything above it that frame would then be working against a simulation that no longer exists.
- Every branch of `FinishLevel` is a placeholder for the result screen (#59), which is where the player will actually be *told* which of the three happened and choose what to do. Until then a missed gate simply replays, which without a screen is an unbroken loop — Escape → Main Menu is the way out, so it traps nobody, but it is the strongest argument for doing #59 next.
- **A level's rules ride on its set entry** — `shots` (the ball budget), `minScore` (what unlocks the *next* level) and `ceilingStep` (shots between descents of the glass), all optional. `LoadLevelSet` logs every entry's rules at startup, spelling each absent one out as what it means ("unlimited shots, no score gate, ceiling holds"), so an inconsistently authored set is obvious in one place before a level is played. Nothing consumes them yet — the budget, the gate and the descending ceiling are #55/#56/#58 — so today the log reports what the file says, not what the game does with it. `shots` and `ceilingStep` are **not independent**: the descent is driven by shots against a fixed death line, so the geometry implies a budget of its own, and `LevelSet` deliberately does not try to cross-check them (the implied limit is the game's geometry, not the set's data).
- **Nothing about a missing or broken level is fatal.** `LoadLevelSet` runs once in `LoadContent`, so a bad set is reported at startup rather than at the moment Play is pressed; the set staying null, or a level failing to parse, falls back to `BuildFallbackMap` — the procedural pyramid, kept for exactly this. Measured: with the set present, `One.json` gives 315 balls / 1088 constraints; with the `Levels` directory gone, the fallback gives 285 / 1377, which are the figures the pre-level build had.
- **The field's size and depth are no longer constants.** `FitFieldToMap` derives them per level: `FIELD_TOP_Y` pins the field's topmost level to a fixed world height whatever its depth (a cell's height is its level index over √2, so otherwise a map with more empty growth levels would hang that much higher than the camera frames), and `_ceilingY`, `_clusterCentreY` and the glass plate's footprint follow from it. `FitCeilingToMap` rebuilds the plate's mesh and renderer per level, which is why `SkyLitRenderers` tolerates a null ceiling renderer and `StartGame` runs `ApplySkyLighting` again afterwards — the same dance the Testbed does around its own `FitCeilingToMap`.
- **`_clusterWorldOffset` gained an X and a Z, and that is the parity trap finally handled rather than avoided.** `BallsMap.Center` offsets by the top level's bounding-box *half-extent* less a ball radius, which lands on the origin only when that level is a shifted (odd-index) one whose cells start at index 0. An **odd** field tops out on an unshifted level, whose cells run 0…N−1 rather than 0.5…N−0.5, and the whole cluster then hangs half a unit off the axis the gun orbits and the camera looks down. That used to be a rule the hard-coded field satisfied by hand; a level is authored elsewhere and cannot be held to it — `One.json` is fifteen levels deep — so the residual is measured off the centred top level through `GetRealCenteredPosition` and folded into the offset the physics builder and the contact handler already take. No new frame crossing, and it is exactly zero for the old even-field pyramid.
- **The magazine's colours come off the loaded map** (`CollectLevelBallTypes`), not from a fixed list: loading a colour that is nowhere in the cluster is a shot that cannot be spent, and an authored level picks its own palette (`One.json` uses eight). `RandomBallType` stopped being static for it. An empty map falls back to the default four.
- **The camera and the gun are solved to the field, not tuned to it** — the Testbed's `FitGameCameraToMap`/`FitCannonOrbitToMap` ported (`FitCannonAndGameCameraToLevel`, run on every level load and every aspect change). `_gameCameraDistance` and `_gameCameraTargetY` replaced the two constants: the stand-off is **bisected** for the smallest distance at which the field's eight corners, the top of the glass and a box around the gun all land inside *both* frustum half-angles, and the aim height comes from bisecting the resulting elevation range, which is what centres the subject. The gun is then placed `CANNON_CAMERA_STANDOFF` in front of the lens — off the *lens*, not the field, because the magazine showing through its slot is really a HUD element and has to keep its size on screen — held off by two lower bounds (clear the field's footprint; keep the resting aim inside the elevation clamp) whose binding one changes with the level. Each solve depends on the other, so they alternate three rounds; it converges on the first.
  - **The one thing that differs from the Testbed's copy is the Y frame.** There the lattice frame *is* the world frame, so the field's floor is `y = 0`; here level 0 sits at `_clusterWorldOffset.Y`. The empty growth levels are deliberately inside the fitted volume — the cluster grows down into them, so they have to be in frame before the first ball lands there.
  - Measured, all at the default window and 16:9 unless noted: 9×9×16 (the fallback) → 27.6 out; 10×10×15 (`One.json`) → 28.0; 20×20×20 → 32.9, aim Y 1.5, gun orbit 18.0. `One.json` at 21:9 gives **the same 28.0**, which is the vertical axis binding at every targeted aspect exactly as "Resolution and aspect" says it should — the extra width goes to scenery.

### Scoring (Game)

The rules for what a shot is worth live in **`Prazsky.BS3D/Scoring/ScoreKeeper.cs`** — no MonoGame, no Bepu, no map, no frame. It is fed three events and answers what a HUD and a result screen need. That placement is the point: the rules are the part of this game most likely to be argued about and retuned, and they have no business being another few hundred lines inside a `Game` subclass.

- **Two kinds of released ball, and the difference is the skill.** `BallsConstraintsBuilder.ReleaseSameTypeCluster` used to return `cluster.Count + disconnected.Count`, one number; it now returns a **`BallsReleased`** pair. *Matched* is the group the shot completed (10 points); *orphaned* is everything that fell afterwards because that group was its last anchor (**20** — double, because cutting a support and collapsing half the cluster is the shot worth learning). Orphans cannot happen without a match: the disconnected walk only runs once a group has actually been taken out.
- **The streak.** A scoring shot is awarded at the multiplier standing when it lands and *then* raises it, capped at ×5 — so the shot that starts a streak scores at ×1 and it is continuing that pays. `Multiplier` therefore reads **forward** (what the next scoring shot will get), which is why `Landed` returns a `ScoreAward` carrying the multiplier actually applied rather than leaving a popup to read the property after the fact. Any shot that drops nothing resets it to ×1.
- **The three events do not arrive together, and wiring any two to one place would be wrong.** A ball is spent the instant it leaves the barrel (`Shot()`, in `Shoot`); what it *did* takes a physics step or more to resolve (`Landed`); a shot that misses everything resolves later still (`Missed`).
- **Every shot resolves exactly once, and `ContactEvents.IsListener` is that guarantee for free.** A shot ball is a listener from `Shoot` until its shot is over — on attaching, on touching something it cannot attach to, or on being culled. So `BallContactEventHandler` reads *whether it was still listening* before the unregister that its own static-contact branch performs, and the kill-plane cull in `RemoveFallenBalls` reports a miss only for a ball that is still a listener. No per-ball state anywhere. **A miss is resolved at the moment the ball strikes the island, not when it is finally culled** — the player knows they missed instantly, so the streak has to break then, and it also closes the case of a shot that comes to rest *on* the stone and is therefore never culled at all.
- **The handler reports; it does not score.** `BallLanded` and `ShotSpent` are events on it, and the game routes them through methods that read the `_score` field rather than binding the instance — the scorer is replaced per level, and a handler holding a stale one would score into a keeper nothing reads.
- The budget comes from the level's set entry (`shots`, null = unlimited). `Shot()` clamps at zero and **refuses nothing**: ending a level when the budget is spent is the lose condition's job (#58), not the scorer's.
- `BaseScore` is what the score would have been at ×1 throughout, so `StreakBonus` is exactly the difference — the line a result screen wants. `CompletionBonus`/`AwardCompletionBonus` (unused shots × 50) exist for #56/#59 and are called by nothing yet; a failed level must never get them.
- Nothing displays any of this. A temporary `[score]` line logs each scoring shot until the HUD (#60) exists — a score that is counted but never seen is indistinguishable from one that is not counted.

**The magazine may only load a colour that is still hanging.** `RecountBallTypes` refills `_ballsOfType` off the map every time a shot lands, and `RandomBallType` draws evenly among the types whose count is above zero. Without it the queue goes on offering a colour the player has eliminated, and a ball of a colour that exists nowhere can never match anything — it can only be parked, which grows the cluster the player is shrinking, wastes a budgeted shot and in the limit makes a level **unwinnable**. Recounted rather than maintained incrementally on purpose: the walk is the field's cell count (1500 for `One.json`) and runs per landing, not per frame, while a running total would be three places to get wrong (release, attach, second-ring fallback) for microseconds nobody can measure. A colour with fewer than `MINIMUM_CLUSTER_SIZE` left is arguably dead weight already and is deliberately *not* dropped — that changes which levels are solvable, so it is a difficulty decision rather than this fix.

**A ball already in the barrel whose colour has just died is re-coloured where it sits** (`Transmute`), not left to be fired at nothing. Letting a stale queue play out costs the player up to `MAGAZINE_SIZE` shots on colours that cannot match, through no fault of their own; this is a game and not a simulation, so re-colouring a loaded ball is allowed. The colour changes **immediately** and the animation is cosmetic — firing mid-transition gives the new colour, never the dead one. The replacement is drawn at random from what survives; picking whichever colour would help most would quietly make the game easier, which is a difficulty decision and not a fix.

- **The transition is a dither cross-fade, and that is a technical choice before it is a stylistic one.** A ball's colour is a **per-draw uniform** (`GetDiffuseTintByType` selects the bucket), so there is nothing per-instance to lerp: blending two colours means drawing the ball **twice**, once in each bucket. Two coincident *translucent* spheres would need depth sorting and would come out muddy — a dither cut needs neither, and both draws stay in the opaque path.
- `ModelInstance` therefore grew a **`Dissolve`** float (TEXCOORD6, a `Single` rather than another `Vector4` — one scalar is all it is, and this rides on every instance in the scene, the city alone being over a thousand). **Zero draws the whole thing**, so nothing has to know it exists to opt out. Positive *goes* (keeps pixels whose noise is above it), negative *arrives* (keeps those below its magnitude); the two are exact complements, so `+t` and `-t` together cover every pixel exactly once. Only the ball pattern technique reads it; an unconsumed element in the vertex layout costs the other techniques nothing.
- **The noise is object-space, not screen-space, and this is the trap worth remembering.** A screen-space dither is laid down at the *supersampled* resolution and the box filter then averages it straight back into a smooth cross-fade — the pixelation the effect exists for would vanish at exactly the settings that make everything else look better. Cells in the ball's own space survive any resolution and turn with it. The hash has no `sin` in it, for the same reason the cloud field's has none.
- The cut is branchless (a select, not an `if`: `Dissolve` varies per instance and a branch would diverge inside one draw call) and sits at the top of `PatternPS`. At the settled zero it reduces to `clip(noise)`, and the hash is never negative.
- `_magazineTransmute` counts **down** from 1 to 0, so the dissolve's progress is its *complement*. Feeding the countdown straight in runs the effect backwards — the new colour arrives complete on the frame of the swap and the old one is never seen. That is exactly what the first build did, and only a zoomed screenshot showed it.
- `AdvanceMagazine` shifts `_magazineFrom` and `_magazineTransmute` alongside `_magazine`: the three are drawn in step, and shifting only the colours would leave a slot dissolving out of the ball behind it.

### The in-play HUD (Game)

What the scoring rules above look like while a level is being played (#60). It is drawn by `DrawHud` in one `SpriteBatch.Begin/End` **after the tonemap resolve**, in display space, like the crosshair and for the same reason — a HUD downsampled with the scene would be soft. It is deliberately small: a score, a streak, a ball count and the numbers floating up from where they were earned.

- **The corners, because they are the only space free in *both* poses.** The centre of the frame belongs to the cluster, the bottom to the gun, and precise aim leans the lens in over the barrel and fills more of it still. Score top **right** (the FPS line owns the top left, and `InfoRenderer` draws after this in `base.Draw`), balls left bottom **left**. Verified in the overview, in ADS and at 21:9 — everything is placed off `Viewport.Width/Height` and scaled by `Viewport.Height / 2160` through the menu's own `Scaled()`, so a wider display only moves the two columns apart.
- **Greyscale, and the distinct state is WEIGHT rather than colour.** The HUD sits over seven scene palettes exactly as the menu does, so a red "running low" number would be the one hue in the game (see the front end's palette note). Balls left switches to the **bold** font system at `HUD_LOW_BALLS` (5) instead. Legibility over a busy cluster or a neon skyline comes from a dark offset copy drawn behind every string (`DrawHudString`, `HUD_SHADOW`) — cheap, and it works against any backdrop, which a plate or an outline would not without adding furniture.
- **The streak is held back at ×1.** It appears only while it is actually running, so it reads as something the player is carrying rather than as part of the furniture — and its *disappearance* is the feedback that they just broke it.
- **No ceiling counter.** The glass coming down at the cluster is meant to be its own warning; a number counting to the next descent says a second time what the player can already see. (`ScoreKeeper.ShotsToNextCeiling` exists if that turns out to be wrong.)
- **The score chases rather than jumps** (`_hudScoreShown`, an exponential chase with a floor rate so a big award still lands promptly). A number that snaps 0 → 2,960 is not read as a number at all.
- **The floating awards are projected every frame, not fixed on screen when they are made.** The cluster sways and the recoil knocks the camera about, so a number pinned to a pixel comes adrift from the ball it belongs to within a few frames; `DrawScorePopups` runs `viewport.Project` per popup per frame against the live camera and skips anything whose `Z` leaves `[0,1]` (behind the lens, where `Project` still returns a point). They hold full opacity for the first half of their life and then fade — the launch smear's curve, for the launch smear's reason: a number that starts fading immediately is one the eye never gets to read.
- **Every figure is `CultureInfo.InvariantCulture`.** The machine's locale decides what `"N0"` groups with, and a popup reading "+2 960" beside a corner score reading "2,960" is one number written two ways in one frame. It happened.
- **Testing it needs the game actually running, and two harness traps cost a round of screenshots each.** A popup lives `POPUP_LIFETIME` (1.3 s) and is nearly transparent by the end of it, so a capture taken a second after the shot shows nothing and reads as "the popups do not work" — capture inside the first half. And a scripted `rmbdown` for the ADS pose that is never released leaves the **button held at the OS level** after the process is killed: Windows then treats every later click as part of a drag and the next run's menu clicks vanish silently, with the button still highlighting on hover. Release it in the harness's exit path.

### Adaptive quality (Game)

The default of 2× supersampling costs four times the shaded pixels, and on a weak GPU that is the single biggest thing in the frame. Measured on an integrated Vega 10, the **main menu** ran at 13 FPS — so the one setting that would nearly triple it sat behind a menu the player had to sit through at 13 FPS to reach. `TuneQualityToFrameRate` notices for them (#62).

- **It measures, it does not recognise the adapter.** A vendor/name list is wrong on the first machine nobody tested — plenty of AMD parts are discrete and plenty of Intel ones now are — and it cannot see the other reasons a frame is slow: a 4K display, a laptop on battery, something else on the GPU. This is the same "be universal, not hardcoded" rule the rest of the renderer follows.
- **The front end is its own probe.** It already draws the same city, clouds, glare and tonemap the game does, at the same factor, and on this class of hardware it is the *fixed scene cost* rather than the ball count that dominates (#64) — so no separate probe pass, no synthetic workload, and the player is sitting there anyway. The verdict lands about three seconds in.
- **Warm-up is counted in seconds, not frames.** The opening frames are shader compiles, the first touch of each render target and the window settling. A fixed frame count is itself a function of the frame rate, so on the slow hardware this exists for it would wait the longest — exactly backwards.
- **One step per verdict, never upwards, and it latches.** `_qualitySettled` is one-way: set when the player named `ssaa=` on the command line (`Program` passes `int?` — null means "nobody said"), when they touch Antialiasing in Settings, when the machine proves fast enough, or when there is nothing left to lower. A quality dial that keeps moving under the player is worse than one merely set too low once, and raising it again on a machine that recovered would put them back where they started.
- `QUALITY_MIN_FPS` (45) sits comfortably under any display's refresh, so a vsync-capped machine — the normal case — never trips it. A drop is explained on the main menu on its own dark plate, because that screen deliberately has no scrim and a line of small text over open water is otherwise unreadable.
- **Not persisted.** Nothing in this game is: there is no settings file yet, so every run re-measures. Cheap, and it means a machine that was busy once is not penalised for ever.

### The front end (Game)

The game's menus, built on **Myra** — the project's one GUI library, already carrying the map editor's scene-config panel, so the game's menus and the editor's tools are one stack. `Game/BS3DGame.cs` owns the lot; there is no separate screen class yet.

**`GameState { Menu, Playing, Paused }` is the seam the whole thing is built around**, and it is what kept the menu from having to fight the game for anything. `Update` returns into `UpdateMenu` for the two non-playing states, so no gameplay path runs at all — no aiming, no shooting, no physics, no game camera; `Draw` gates every *session* object (the gun, the cluster, the shot smears, the glass ceiling, the crosshair) behind `drawGameplay = _gameBuilt && _state != Menu`, while the *setting* (sky, backdrop, island, drain) is drawn unconditionally because the menu stands in it too. A pause therefore draws the game exactly as the player left it, camera shake and all — `UpdateMenuCamera` only runs in `Menu`.

- **The world is built on the first "Play", not at load** (`StartGame`/`TearDownGame`). The simulation, the ceiling body, the drain's collision mesh and the cluster are the expensive part of starting up and belong to a session; the menu comes up without paying for them. Two consequences worth knowing: the ceiling's **mesh and renderer** had to move out of `BuildCluster` into `BuildScene` (its kinematic *body* is still the simulation's), because `SkyLitRenderers` must be complete before the first `ApplySkyLighting`; and a rebuild disposes the whole `Simulation`/`ContactEvents`/`ThreadDispatcher`/`BufferPool` set rather than emptying the cluster ball by ball — same order as `UnloadContent`, for the same reason.
- **Returning to the main menu keeps the session.** The menu then offers **Continue** (visible only when `_gameBuilt`) and **New Game**, which is the difference between a mis-click costing a click and costing a game. It was very nearly the other way round; the flag that makes it cheap is the same one `Draw` already needed.
- **`EnterPlaying` is the one door into `Playing`, and it exists for the input state.** The cursor is captured and recentred every frame while playing and left alone in the menu, so the first frame back would read the distance from wherever the player clicked to the viewport centre as an aim delta and yank the barrel across the field — and the very click that pressed the button would arrive against a stale "released" and fire a shot nobody asked for. Clearing `_mouseAimInitialized` skips that first frame's aim **and** its shot test, since both live behind it; the gamepad is re-polled there so a held trigger or Back button has to be released first.
- **Escape hands over through the same `_previousKeyboard` the play loop uses.** `UpdateMenu` stores its snapshot into that very field, which is what makes the two states hand over cleanly: the Escape that paused the game is still down on the first menu frame and is correctly not seen as a second press, and the Escape that resumed it is not seen again by the play loop. `UpdateInput` **returns immediately** after pausing — firing or traversing on the way out would be an action asked of a game that has stopped.
- **`Desktop.Render()` also reads the input, so it only runs where the game's own input has stood down**, and **only while the window is focused**. `Mouse.GetState()` reports the button and a window-relative position whether the window has focus or not, so a click meant for another application that happened to land over a menu entry would press it — and "Quit" would close a game nobody was looking at. Unfocused, the desktop is laid out and drawn (`UpdateLayout` + `RenderVisual`) but not fed input.
- **The look is deliberately greyscale, and that is a constraint rather than a taste.** The menu sits over seven backdrops whose palettes are nothing alike — a magenta/cyan neon city, an ochre desert, a blue sea, white peaks, green meadow — so any accent colour that reads as the game's own over one of them fights the next. Emphasis is carried by **brightness and opacity**: dark slabs for entries, a step up the grey ramp for hover, white for the active item and grey for the inactive. There are **no drawn frames** either: a border is one more shape competing with every backdrop, and the tone step at a slab's edge already reads as a control. Myra's stylesheet supplies a framed grey tool button by default, so `Border` has to be explicitly cleared. Note each state brush **replaces** the one before it rather than compositing over it, so a translucent hover would show the scene through the very entry the pointer is on — they are all near-opaque.
- **Sizes are authored for 2160p and resolved at build time** (`MENU_DESIGN_HEIGHT`, `Scaled()`), exactly as `InfoRenderer`'s overlay is — Myra measures in pixels, so without this the menu keeps its pixel size and shrinks to a postage stamp at 4K. It is done by re-resolving the sizes and rebuilding the tree, **not** by `Desktop.Scale`: scaling the desktop also scales the full-screen scrim, which then stops covering the frame (tried, and it left the scrim as a rectangle in one corner). `EnsureMenuLayout` runs from `Draw` rather than off the resize event, so the one place it can be stale is the frame about to draw it, and the rebuild is quantized (`MENU_REBUILD_QUANTUM`) so a live window drag asks the font system for a couple of dozen sizes rather than hundreds.
- **The font is Inter (SIL OFL 1.1), embedded in the assembly.** Myra's own stylesheet carries a small bitmap font — fine for a tool panel, far too coarse for a title. It is an `EmbeddedResource` rather than content: no path to get wrong, nothing to install, and nothing through the MGCB pipeline. **Two `FontSystem`s, not two fonts in one** — FontStashSharp falls back through a system's fonts glyph by glyph, so a bold added beside the regular would never be reached, since the regular has every glyph. Picking a weight means picking a system.
- **The screens** are built once each and swapped into `_desktop.Root`; everything that must agree with the game's state (the resume entry, each setting's value, the marked scene) is refreshed in `ShowMenuScreen`, because a screen can only change while it is shown. **Main menu** (title, Continue/Play, Scene, Settings, About, Quit) · **Pause** (Resume, Settings, Scene, Main Menu, Quit) · **Settings** · **Scene** · **About**. Settings, Scene and About are reached from both the front end and a pause, so "Back" returns to whichever menu opened them and their scrim is set per showing — which is where the one asymmetry lives: **only a pause dims the frame.** The front end draws no scrim at all, because the rotating scene is the whole point of that screen and a full-screen wash over it throws away the only thing it exists to show; a pause dims hard, because what is behind it is a stopped game. Legibility on the front end therefore comes from the widgets: the entries are near-opaque slabs, and the three text-carrying screens sit on a dark **plate** (a slab alone cannot hold small text steady when every line lands on a different piece of moving scene). `CurrentScrim()` returns null outside a pause; a null `Background` simply draws nothing, and the root panel still stretches because it is what centres the column and what Myra hit-tests.
- **Every setting is a button that cycles its value** rather than a slider or a drop-down — one widget kind, one click, nothing that can be left half-dragged, and each change takes effect where it is made, so the scene behind the panel *is* the preview. Fullscreen, antialiasing (`_supersampleFactor`, which is what `EnsureSceneTarget` sizes the target from, so changing it is what recreates it), exposure, sky dome (all eighteen) and the FPS counter. `_supersampleFactor` and `_exposure` stopped being `readonly` for this; the command line still seeds them.
- **The menu camera** orbits the scene origin at `MENU_CAM_RADIUS` (44, well outside the island's 26) roughly level with its target, so the frame is a look *across* the scene rather than down onto it — which is what shows the most of a city, a sea or a mountain range at once. About one turn every 90 s, advanced by elapsed seconds so it takes the same time on any machine. It is the game's own `RecoilCamera` with the shake at rest.
- **The scene is a real setting, not a menu backdrop**: `SetScene` is the one place a scene changes, shared by the random pick at startup and the scene screen, and what the player picks is what they then play in. It switches the city's day/neon lighting (a flag and a brightness on the renderer — neither city goes through `SceneRenderer`), applies the sea's and savanna's default domes exactly as the Testbed does, and ends in `ApplySkyLighting`, which is why nothing derives the light rig before it. `ApplySceneLights` became per-frame for it (the savanna's campfire flickers), replacing the old set-once `ApplyNeonLights`, and the dark **pit shaft** behind the drain came over from the Testbed for the four solid-terrain scenes along with `TerrainHoleRadius`.
- **Testing it is mouse-driven, so it needs clicks, not keys.** The `screenshot` skill's script only sends keys; a scratch variant that clicks at a fraction of the *client* area is what drove the verification here. The two traps under "The game" still apply once you are in `Playing` — an external `SetCursorPos` reads as a huge aim delta, and a key has to be *held* across a frame to be seen.

### Physics in the game (Game)

The Testbed's simulation, ported into `Game` (its own decision, taken after the founding slice shipped without it). What made the port cheap is that `Prazsky.BS3D.Physics` was already complete: `BallsConstraintsBuilder` builds the constrained structure, attaches a newly landed ball, and — in `ReleaseSameTypeCluster` — **already implements the match rule** (`MINIMUM_CLUSTER_SIZE` 3) including the follow-up release of everything left unanchored, via `BallsMap.GetCellsDisconnectedFromCeiling`. Wiring Bepu therefore delivered "balls fall on a match" for free; it was never a separate job.

- **Three files moved out of the Testbed into `Prazsky.BS3D.Physics` rather than being copied**: `Callbacks.cs` (the narrow-phase and pose-integrator callback structs, in class `Simu`), `ContactEvents.cs` (adapted from Bepu's demo) and `KinematicBody.cs`, plus `IContactEventHandler`, which was a loose interface at the bottom of `Testbed.cs`. All four were pure Bepu infrastructure with **zero** coupling to Testbed types — they only happened to live in its namespace. Two divergent copies of the contact material (`FrictionCoefficient` 1, `MaximumRecoveryVelocity` 2, contact `SpringSettings(30, 1)`) would have been exactly the kind of silent drift this repository keeps one copy of shaders and scenes to avoid. `Prazsky.BS3D.Physics` needed `AllowUnsafeBlocks` for them.
- **The one place the game deliberately does not do what the Testbed does is the timestep.** The Testbed takes one `Timestep(min(frameTime, 1/60))` per rendered frame, which runs the simulation in **slow motion below 60 FPS** (at 30 FPS everything moves at half speed) and with a dt that varies with the display and the load above it — and Bepu's own guidance is to keep the step constant. The game accumulates the frame time and spends it in whole steps of `PHYSICS_TIMESTEP` (1/120 s), capped at `PHYSICS_MAX_STEPS_PER_FRAME` so a frame that hitched drops the remainder instead of spiralling. It runs `IsFixedTimeStep = false` and offers `nocap`, i.e. precisely the configuration the Testbed's approach breaks under.
- **The frame question is the one that would have silently wrecked the port.** `Game` has a lattice frame and a world frame, offset in Y by `CLUSTER_WORLD_Y` (−4.9497) so the empty field levels below the layout do not raise the cluster; the Testbed has no such offset. The simulation lives in **world**, because everything else it touches does — the funnel floor, the ceiling, the muzzle a shot leaves from, the kill plane — and only *one* thing is lattice-framed: the positions `BuildBallsStructure` reads out of the `BallsMap`. So `BuildBallsStructure` took an optional `worldOffset` (the Testbed passes nothing and is unchanged), and it is applied to the body positions **and to nothing else**: `ConnectBalls`'s anchors are *differences* of two grid positions, so a uniform translation cancels out of them, and `ConnectBallToCeiling` reads only X and Z from the grid (its Y is the ceiling body's own). Applying it twice tears the structure apart on the first step; forgetting it on the ceiling body yanks all 285 balls five units up into the glass. `MapToWorld`/`WorldToMap` were **deleted** rather than kept: the crossings are now countable — the builder's offset, and the offset the contact handler carries to take a world contact down into the grid frame.
- **The cluster does not settle on its lattice.** The ceiling `BallSocket` anchors a ball's top (local +0.5) to the plate's bottom face (local −0.5), so the top level comes to rest one unit below the plate's centre and the whole rigid structure with it — half the clearance `CEILING_Y`'s "+2" looks like it buys. It is the Testbed's own behaviour and is kept for parity, but it means the contact point a landing ball is ranked against sits a unit above the lattice cells it is compared with, which biases attachment towards same-level cells over cells below. `CEILING_Y` is the figure to change if the cluster should ever hang exactly on its grid.
- **`BallContactEventHandler` is its own file**, and the split inside it is the whole point: Bepu runs contact callbacks on worker threads from inside `Timestep`, so `OnContactAdded` only enqueues, and everything that touches the simulation, the map or the listener set happens in `ProcessQueuedContacts` on the main thread. The order `Timestep` → `_events.Flush()` → `ProcessQueuedContacts()` is mandatory — unregistering a listener is only safe once the per-worker adds collected during the step have been applied — and it runs **per step**, not per frame. The Testbed's version was ported with three fixes: no LINQ and no `Console.WriteLine` on the contact path, and the game's own second-ring fallback (`TryFindCellInSecondRing`) kept, since the first ring runs out where the cluster's face is the field's own wall.
- **A manifold offset is relative to the pair's *first* collidable**, not to either body's own, so the world contact is `pair.A`'s position plus the offset whichever of the two the shot ball happens to be. Both velocities are zeroed on attach, angular included: residual spin would drag the constraint anchors that are about to be created around with it.
- **The shot's collidable is built from the bare `TypedIndex`**, not from a `CollidableDescription` with a speculative margin, and that is load-bearing rather than sloppy: it is what gives the shot continuous detection. At `SHOOT_SPEED` a ball crosses several diameters in one step and a discrete test would let it pass clean through the cluster.
- **What is drawn is the simulation.** `CollectBallInstances` walks the `PhysicsBall[,,]` plus the shot and falling lists and takes each ball's world matrix from its body pose — **orientation included**, which is what makes the beach-ball pattern read as rotation. Two smoothings ride along: the occlusion is *eased* towards its target (a ball joins or leaves the lattice in one step while it has not moved, so taking it straight pops the shading of everything around a hole a released group left), and a landed ball is drawn *gliding* in from where it actually hit, since it is snapped to the nearest free cell and the constraints then drag its body several diameters. Each ball must be visited exactly once a frame — both advance state on the ball itself.
- **Falling below `KILL_PLANE_Y` is the only thing that removes a ball, and that is a deliberate parting from the Testbed.** The Testbed also culls any ball whose body has gone to sleep — cheap, and it keeps the scene tidy, but it means a ball that settles on the island's stone winks out in front of the player, which reads as a bug whatever it saves. Here a ball that comes to rest on the stone ring stays there and stays visible. The cost is that those accumulate over a session, and it is small: they fall asleep, and a sleeping body leaves Bepu's active set, so it is drawn but barely simulated — and most never rest at all, since anything inside the funnel's rim runs down its ~55° wall and out through the hole. `RemoveFallenBalls` is only ever handed the shot and falling lists; handing it the structure array would delete the cluster.
- Measured: 285 balls and 1377 constraints at startup, and the frame rate is unchanged from the pre-physics build (vsync-capped) — this cluster is two orders of magnitude smaller than the Testbed's 3000-ball stress map.

### The map editor's render pipeline

The map editor renders through the **same linear-radiance pipeline as the game**, so a map looks in the editor the way it will play — that is the whole point of moving it off DesktopGL. `MapEditor.Draw` binds the supersampled HDR `_sceneTarget` (`SUPERSAMPLE_FACTOR`, a fixed 2 — there is no `ssaa=` CLI here), clears it to the **current dome's horizon colour** (`_horizonLinear`), draws the sky, the chosen scene backdrop and the balls into it, then `ResolveSceneTarget` runs `Glare.fx` and `Tonemap.fx` exactly as `Testbed.cs` does (the post-processing methods were ported verbatim; the exposure and every glare figure are the game's own constants, so the two agree). The clear colour is the horizon rather than a fixed blue because the hemisphere dome covers only above the horizon and the finite scene only reaches its own edge, so at a wide aspect (21:9) the bottom corners look below the horizon past both — and a fixed clear colour showed through there as a blue band; clearing to the horizon makes that gap blend with the hazed skyline the dome and terrain both fade to. Both executables do this. `EnsureSceneTarget` is called from `LoadContent`, `Window_ClientSizeChanged` and `SetGraphics`, so the target tracks the back buffer through a resize or an F11 fullscreen switch; back-buffer MSAA is off because only the resolved full-screen quad ever touches the back buffer.

Two things do **not** go through the shared shader and needed handling for the linear target:

- **The sky dome** is drawn through `BasicEffect` (the editor builds no `Sky.fx`), so its baked vertex-colour gradient is sRGB. `SkyDome` is therefore built with `linearVertexColors: true`, which converts the gradient to linear once at load — otherwise the tonemapper reads a gradient of display values as radiance. `ApplySkyLighting` likewise decodes the palette to linear (`ColorSpace.SrgbToLinear`) before scaling and tinting it, and sets `LinearLightRig = true` on the ball renderers, mirroring the game.
- **The AABB field outline and the selector gizmo** are drawn through `BasicEffect`. The AABB is opaque-coloured and depth-tested against the balls, so it stays in the HDR pass and its one flat colour is linearised on the CPU (`ColorSpace.SrgbToLinear(COLOR)` in `AABB.cs`) — handed over raw it would tonemap too bright. The selector is additive and drawn with depth off (always on top), so it is drawn **after** the resolve, in display space, where `BasicEffect`'s gamma output is already correct — the same split the game makes for its aimer and text overlay, which also draw post-resolve (`base.Draw` runs last). The **axis gizmo** (`GUI/AxisGizmo.cs`) — a small X/Y/Z cross in the bottom-left corner showing how the world axes sit relative to the camera, to keep the user oriented while building a map — draws post-resolve too: it binds a small square viewport, draws the three coloured axes (X red, Y green, Z blue) through a rotation-only view of the camera under an orthographic projection, then labels the tips with `SpriteBatch`. It reflects only the camera's orientation, not the scene, so it needs no depth and no scene state.

Because both executables now build the shared shaders for DirectX/SM 5.0, `InstancedModel.fx` has no `#if OPENGL` branches left at all: `SrgbToLinear` always decodes, `Clouds.fxh` is always included (the editor just never sets the cloud uniforms), and the relief self-shadow / parallax marches are always compiled (guarded at runtime by their strength uniforms, which the editor leaves at zero).

### The scene-config editor (MapEditor)

The editor carries an in-engine GUI built on **Myra** (issue #45; the project's single GUI library, chosen over ImGui so the same stack could serve the game's menus — which it now does, see "The front end (Game)"). Myra's `Desktop` is rendered last in `MapEditor.Draw`, straight to the back buffer after the resolve and `base.Draw`; its default stylesheet is embedded, so no content pipeline change was needed. The panel is a right-docked `PropertyGrid` reflecting over the **active scene's `SceneConfig`** (issue #33's Level Editor skeleton, realized by extending the MapEditor rather than a separate tool): editing a value fires `PropertyChanged`, which re-applies the config through `SceneRenderer.Apply` (or rebuilds the city) so the backdrop **updates live**. The grid rebinds when the scene is switched (V) or a level is loaded; **G** toggles the panel.

Two integration points matter. First, **input arbitration**: the editor's own keys and camera stand down while a Myra widget has keyboard focus (`_desktop.FocusedKeyboardWidget`) or the mouse is over the panel (`_desktop.IsMouseOverGUI`), or typing "42" into a field would fire hotkeys and dragging would spin the camera; Myra processes its input in `Draw`, so those flags lag one frame (negligible). Second, **name clashes**: `PropertyGrid`, `Label` and `HorizontalAlignment` also exist in `System.Windows.Forms` (used for the file dialogs), so Myra's are aliased (`MyraPropertyGrid`, `MyraLabel`, `MyraHAlign`).

`Rgb`/`Vec2`/`Vec3` are **reference types** specifically for this editor: Myra's `PropertyGrid` edits a nested *value* type's sub-properties on a boxed copy it never writes back, so as structs a colour's channels could not be tuned live; as classes the grid holds the same instance the config exposes, so an R/G/B change reaches the config `SceneRenderer` reads. The channels are individual float fields rather than a 0–255 colour picker because the values are linear radiance and may exceed 1 (a proper HDR colour-swatch widget would need a custom Myra editor — Myra 1.6.3 exposes no public per-type editor hook).

### Conventions

- **Triangle winding**: procedural meshes (`BoxMesh`, `SphereMesh`, `CannonMesh`) wind their triangles **clockwise seen from outside**, which is what MonoGame's default `CullCounterClockwiseFace` treats as the front face — the viewport transform flips Y, so a triangle whose `(b - a) × (c - a)` points at the viewer comes out counter-clockwise in window space and is culled. Both classes had it backwards for a long time and it is a nasty bug to spot: nothing disappears, the far side of the object is drawn instead. A box reads as a hollow shell seen from inside; a sphere keeps its exact silhouette and only its shading is wrong, so the balls just looked washed out. Loaded models (the sky domes — the last other model, the cannon, is procedural now) are wound the normal way, so the two cannot be reconciled by picking a cull mode — flipping the mesh is the fix. The Testbed **states** `RasterizerState` before the scene rather than inheriting it: the tonemap pass leaves `CullNone` and the overlay's `SpriteBatch` leaves its own, so what the scene culled used to depend on which of them ran last.
- Two vector types coexist: `Microsoft.Xna.Framework.Vector3` in game/render code and `System.Numerics.Vector3` in Bepu code, with `ToNumerics()` conversions at the boundary.
- **Per-frame render hygiene** — the full discipline, each rule with the incident that taught it, is in `BestPractices.md`; hold all new code to it. The short form: cache `EffectParameter`/`EffectTechnique` references at load (the by-name indexers are linear scans; `InstancedModelRenderer` and `CloudField` are the patterns) and set never-changing parameters once; never `new` a GPU state object per frame (framework statics); no per-frame managed allocations (iterators included), no console I/O on load/gameplay paths, one `GetState()` per input device per frame; write a translation into `M41–M43` instead of multiplying `R × CreateTranslation` in per-ball loops; in shaders, scene-gated work goes behind a `[branch]` on a uniform (non-divergent, derivative-safe with no gradient ops inside). And comments are load-bearing: update them in the same change as the behaviour, reference constants instead of repeating values, never leave a wrong "why" standing.

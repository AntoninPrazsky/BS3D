# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is the overview: the project, how to build and run it, the one data structure everything turns on, the repo-wide conventions, and **which document covers what**. The detail lives in `docs/` — see "Where the rest is documented" below, and read the relevant document before working on that area. Since 2026-10-03 the long histories and measurements this file used to carry sit in `docs/build-and-release.md`, `docs/libraries.md` and `docs/repo-conventions.md`, word for word; **this file keeps the rules** and says where the reasons are.

## Project

BS3D is a 3D Puzzle-Bobble-style game (shoot balls at a hanging 3D cluster of balls) built with MonoGame and BepuPhysics 2. Repo: https://github.com/AntoninPrazsky/BS3D — tasks are tracked in GitHub issues.

**Finished work lands on main immediately** (the owner's standing instruction): once a task is done and verified, its branch is merged to main right away — work sitting on a side branch is work the owner cannot see. **The merge is a direct `--no-ff` merge into main and there is no PR anywhere in this repo**; the point of the sentence is the *immediacy*, not the mechanism (why it was reworded: `docs/repo-conventions.md`).

There are **three executables**: the **Testbed** (**the development instrument** — where the shot, the gun and the cameras were built, and today the rig every colour, cost and shading judgement in this project is framed through), the **MapEditor**, and **Game** — the shipping product, founded deliberately small on top of the libraries the other two already share (see `docs/game-session.md`).

**The Testbed is kept and developed deliberately, and its role is narrowed** (#100): it is an instrument, not a second game, and must never grow a menu, a HUD or a level flow — every step towards the game takes away what it is used for. It is the only executable that can hold a camera still (`campos`/`camtarget`, and `C` prints one back), isolate a pass (`arena=`, `capprobe=`), sweep variants inside one process (`alt=`), drive itself without a keyboard, the mouse included (`at=`, `hold=`, `aim=`, `rmb=`) and photograph itself (`shot=`, `shotframe=`); the Game's camera orbits and its levels override the scene they were launched with, and the MapEditor has no simulation, gun or shot at all. See `docs/testbed.md`.

All three run on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0); there is no OPENGL build of any shader. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers, and each executable brings its own reference. **Every shader lives and compiles once in the `Prazsky.Shaders` library** (`BS3DLibs/Prazsky.Shaders/Content/Shaders`, #618): its `Content/Shaders.mgcb` is built by the content task in that project, and the compiled `.xnb` files are Content items MSBuild copies into the output and the publish folder of every project that references it, at `Content/Shaders/<name>.xnb` where `Load<Effect>("Shaders/…")` looks. So there is one copy of each shader and one compilation, a change reaches every executable at once, and the executables' own `Content.mgcb` files carry no shaders. **`Sky.fx` is the one the MapEditor never loads**: the editor draws the dome through its own `BasicEffect` and gets no cloud deck and no sun disc, which is why a scene wanting a per-scene sky feature cannot put it there (see "The storm" in `docs/scenes.md`). The history (the MapEditor's move from DesktopGL, the shaders' move out of the Testbed) is in `docs/build-and-release.md`.

## Build and run

```powershell
# From the repository root: the paths below are relative to it (#594)
# Build everything (libraries + Testbed game)
dotnet build Testbed.sln

# Run the game testbed / the map editor / the game
dotnet run --project Testbed\Testbed.csproj
dotnet run --project MapEditor\MapEditor.csproj
dotnet run --project Game\Game.csproj

# Testbed can load a map right at startup (useful for testing)
Testbed.exe Testbed\Maps\Full.json

# Play the latest main: fetches, builds the Game in Release in a second checkout (..\BS3D-play) and starts it,
# so the folder you work in keeps its branch and its changes (-Ref <branch>, -NoRun, -NoFetch). The .cmd runs the
# script with the execution policy lifted for that run: a stock Windows refuses to load any .ps1
Tools\play-latest.cmd
```

There are five solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln`, `MapEditor.sln` and `Game.sln` (each executable plus the libraries it uses), and `GamePi.sln` (the Game's own sources built for Linux ARM64, below). There is one test project, `Tests/BS3D.Tests` (xUnit, plain `net10.0`, in `Game.sln` and `BS3DLibs.sln`): it checks the invariants the libraries state "by construction" and is run with `dotnet test Tests\BS3D.Tests` and by CI on every push. There is no lint configuration. **Four root files configure every project at once**: `global.json` (the SDK band — a floor, so a newer band still builds), `Directory.Packages.props` (**every NuGet package version** — a `PackageReference` names the package and nothing else; bump a version there, never in a `.csproj`), `.editorconfig` (indentation and LF) and `Directory.Build.props` (`GenerateDocumentationFile`, so a `cref` that does not resolve, a stale `<param>` or malformed doc XML is a compiler warning; **a project's own `<NoWarn>` must be `$(NoWarn);…`** or it drops the suppressions). `Prazsky.Core` references no Bepu: `Prazsky.BS3D.Physics` is the one library that does, so a `using BepuPhysics;` in Core or `Prazsky.BS3D` does not compile. Every executable's Debug build writes `bin\net10.0-windows\` and its Release build `bin\Release\net10.0-windows\`. Detail: `docs/build-and-release.md`.

**Two GitHub Actions workflows run on `windows-latest`** (`.github/workflows/`), free because this repository is **public**. `build.yml` fires on every push (except one touching only the agent journal or `Research/`): it builds all four solutions and `Game.sln` once more in Release, runs the logic tests, both gates (the level regeneration check, which refuses an untracked level file too, and ScoreSim) and the "seen to fire" self-checks, and in a second job on an `ubuntu-24.04-arm` runner builds `GamePi.sln`, runs the logic tests on ARM64 and checks a `linux-arm64` publish (#787) — it is what says `main` compiles on a machine that is not the author's, so **look at it after every merge**. `release.yml` runs on a pushed tag `v*`: it publishes `Game` self-contained for `win-x64` as a **single exe and four folders** (`Content`, `Levels`, `Music`, `Sfx`), asserts the published folder really carries them, zips it and creates a **GitHub Release** with the zip, ScoreSim's score ceiling table and a `SHA256SUMS`; a tag on a commit whose gate fails publishes nothing. "Run workflow" rehearses it without publishing. Only the Game ships, and the exe is **unsigned**. The release's measured size, why it is deliberately not trimmed, the screenshot the notes open with (`Tools/release-screenshot.ps1`) and the build's name shown in the corner are in `docs/build-and-release.md`.

Besides the three executables there are eight **tools**, all in `Game.sln` and all but two plain `net10.0` console apps with no graphics device. **`Tools/LevelGen`** writes the game's pattern levels and checks that a generated level is playable; **`Tools/ScoreSim`** plays every shipped level through the real `ScoreKeeper`/`StarRating` and refuses a scoring rule that rates them wrongly (`--ceilings` writes the table the online boards whitelist against) — **those two exit non-zero and go in front of a commit**. **`Tools/SemanticSearch`** ranks the GitHub issues (and, with `--journal`, the agent journal; with `--docs`, the sections of the documents) by what they *mean*, through a local embedding model in LM Studio — **run it before filing an issue**, and ask it before reading a whole document. `Tools/MusicBake` renders and encodes the game's music and sound effects (an ear, not a gate); `Tools/DocDrift` lists figures the docs quote beside a name the code defines with another value (a triage sweep, always exit 0); `Tools/LatticeProbe` measures whether a procedural field reads as a repeating grid (an instrument); `Tools/WindingCheck` and `Tools/VectorBoundary` check the two conventions below (neither is a gate). What each does, its arguments and what it measured: `docs/formats-and-tools.md`, and the commands in `docs/build-and-release.md`.

```powershell
# Regenerate the pattern levels and the level set
dotnet run --project Tools\LevelGen\LevelGen.csproj

# Check the scoring still rates the shipped levels the right way round
dotnet run --project Tools\ScoreSim\ScoreSim.csproj

# Render and encode the game's music and sound effects (MusicBake): the commands are in docs/build-and-release.md

# The issues most like #425, or like a drafted issue (--file draft.md), before filing one
dotnet run --project Tools\SemanticSearch -- --issue 425

# The sections of the documents most likely to answer a question, before reading a whole document
dotnet run --project Tools\SemanticSearch -- --docs "why are the shadow maps drawn before the scene target is bound"
```

MonoGame content (`Content/Content.mgcb` in each executable, and `Content/Shaders.mgcb` in `Prazsky.Shaders`) is compiled automatically during build by `MonoGame.Content.Builder.Task`; editing the .mgcb itself is normally done with the MonoGame Pipeline Tool. **Every project that runs the content build needs its own `.config/dotnet-tools.json`** pinning the `mgcb` tool — the three executables, `Prazsky.Shaders` and `GamePi` — because the content build shells out to `dotnet mgcb`, and the manifest search walks up from the *project* directory, so a new one without it fails the content build with "Nenašel se soubor manifestu" even though its siblings build fine (`dotnet tool restore` once after adding it). `Prazsky.Shaders.csproj` sets `MonoGamePlatform` to `Windows` itself: it references no MonoGame platform package, and the task's `/platform:$(MonoGamePlatform)` is what decides what the effects are compiled for. All three executables target `net10.0-windows` and pull in WinForms (WindowsDX hosts its window on it), so they are Windows-only; the libraries target plain `net10.0`. **`GamePi`** (`GamePi/`, plain `net10.0`, MonoGame **DesktopGL**) is not a fourth executable but the Game's own sources built for Linux ARM64 (a Raspberry Pi 5): it compiles everything under `Game/` except three Win32/WinForms files of `Game/Platform`, which it replaces with SDL namesakes in `GamePi/Platform`, and `Game.csproj` does not know it exists. Win32 calls inside shared logic are guarded with `OperatingSystem.IsWindows()`; WinForms added to a file under `Game/` fails GamePi's compile and so does any other Windows-only .NET API (CA1416, an error there), but a new `DllImport` into user32 passes both and fails only at run time on Linux. It has **no shaders yet** (the SM 5.0 effects cannot be compiled for OpenGL) and stops at the first `Load<Effect>`; see "GamePi" in `docs/build-and-release.md`.

## Architecture

Three layered libraries under `BS3DLibs/`, consumed by the three executables, plus `Prazsky.Shaders` beside them — no code, only every `.fx`/`.fxh` and the one content build that compiles them (#618; the executables reference it with `ReferenceOutputAssembly="false"`, so only its compiled effects reach them):

- **Prazsky.Core** — BS3D's shared 3D, rendering and scene library: cameras (`BasicCamera3D`, `RecoilCamera`, `CameraShake`), the procedural meshes, `InstancedModelRenderer` (GPU instancing), `PostProcessPipeline` (the HDR target, bloom, tonemap resolve, and the Game's defocus and motion blur), `ScreenshotWriter`, `SkyDome`, one `Backdrop` class per scene under `Render/Scenes` hosted by `SceneRenderer`, the setting no executable keeps a copy of (`ArenaIsland`, `CeilingPlate`, `SkyLightRig`, `SceneLights`, the forest and savanna scatter — "The setting, in one copy" in `docs/scenes.md`), the shot's visuals (`LaunchSmears`, `AimBeam`, `Crosshair`), the screen stack, `Tools/Constants.cs`, `Tools/AtomicFile.cs` (**every player file is written through it**) and `Tools/BuildStamp.cs` (the `[build]` lines every run opens with). **Every executable calls `SceneRenderer.DrawShadowMaps` before binding its scene target** ("Sun shadows" in `docs/rendering.md`). The full inventory, and which code an executable must not copy, is in `docs/libraries.md`.
- **Prazsky.BS3D** — game logic without physics: the ball grid (`GameStructure/BallsMap.cs`), `StaticBall`, `BallType`, `BallKind`, the map and `Level`/`LevelSet` (de)serialization, `PlayerProgress`, the scoring rules (`ScoreKeeper`, `StarRating`), and the gameplay hardware no executable keeps a copy of (#76): `Cannon`, `CannonRig`, `Magazine`, `WildcardCycle`, `GameCameraFit`, `DropFocus`, `PreciseAim`, `AimReachability`, `BallRenderSet`, `MouseAim`. See `docs/libraries.md` and `docs/formats-and-tools.md`.
- **Prazsky.BS3D.Physics** — BepuPhysics representation, and the one library that references Bepu: `PhysicsBall`, `BallsConstraintsBuilder` (builds the constrained ball structure and implements the match rule that releases a group), `FunnelPhysics`, `PhysicsWorld` (the dispatcher, the buffer pool, the simulation, the contact stream and the mandatory order inside one step — **the stepping policy deliberately stays with each executable**, #76), `ClusterCollector`, `ShotPlacement` (where a shot lands: one answer for the contact handler and the aim preview) and `BallContactEventHandler` (what happens when a shot touches something, in one copy since #68 — read its class doc before touching it).
- **Testbed** — the original playable game loop: simulation setup, shooting, contact handling, backdrops, HUD. Test maps live in `Testbed\Maps\*.json`. It is also the project's instrument, and the arguments that make it one are a **contract** the skills in `.claude/skills` drive it by: `campos`/`camtarget`/`fov` and `C`, `arena=`/`capprobe=`, `alt=`, `at=`/`hold=`/`aim=`/`rmb=`, `shot=`/`shotframe=`, `logfps`/`fpscap=`, `mirrorcheck` (see `docs/testbed.md`).
- **Game** — the shipping product (`Game/`, assembly `BS3D.exe`). Founded small and deliberately **not** a copy of `Testbed.cs`: a hanging cluster over the island in any of the twenty-one shared scenes, the gun with its visible magazine, a real Bepu simulation and a camera that is hit every time the gun fires, behind a Myra front end (main menu, pause, settings, scene picker) over a slowly orbiting camera. It opens on the logo bitmap, plays levels off disk ordered by a level set and — opted in by the nickname the first launch asks for, or in Settings — submits every cleared level to the online score service off the frame through an outbox that survives the service being away (#542, #546, #763); `userdata=<dir>` keeps a scripted run's save, settings and identity out of the player's profile. See `docs/game-session.md` and `docs/game-shell.md`.
- **MapEditor** — visual editor for the map JSON files (supports drag-and-drop of a file onto the window). It draws the balls and the sky the way the game does — the same instanced procedural spheres, shader and sky-derived light, and the full HDR → glare → ACES tonemap pipeline — from the same compiled shaders in `Prazsky.Shaders`; B cycles the sky domes and V all twenty-one scenes. It loads and saves whole **levels** (map + scene name + sky) and has no GUI of its own since #522. See `docs/formats-and-tools.md`.

### The ball grid

The central data structure is a 3D array `[x, z, level]` where **level is the vertical (Y) axis**. Odd levels are shifted by +0.5 in X and Z (hexagonal-like packing); vertical spacing between levels is `1/√2`. `BallsMap.GetRealPosition` maps array coordinates to world positions, and `Center()`/`ComputeCentered` translate between the raw grid frame and the centered world frame. A cell has 4 neighbors on its own level and up to 4 on each adjacent level; which diagonal offsets are the true neighbors depends on level parity (`GetNeighboringCells` encodes this).

`BallsMap` holds the logical state (`StaticBall`s); `BallsConstraintsBuilder.BuildBallsStructure` mirrors it into a parallel `PhysicsBall[,,]` of dynamic Bepu bodies connected by `BallSocket` constraints to their neighbors, with the top level constrained to a kinematic ceiling body. The whole cluster hangs from the ceiling and jiggles physically.

The play field is larger than the initial ball layout: map JSON stores field dimensions (`sx`/`sz`/`l`) separately from the layout array, the layout is placed at the **top** of the field and the empty bottom levels are room for shot balls to attach into. Legacy map files without field dimensions get 6 extra bottom levels on load (an even number, to preserve level parity). The Testbed ceiling repositions/resizes itself to the loaded map (`FitCeilingToMap`).

### Constraint handle bookkeeping

Each constraint is shared by two balls, so `PhysicsBall` stores handles in three slot groups (`HandlesBottom`/`HandlesMiddle`/`HandlesTop` = balls below / same level / above + ceiling; four slots each, filled via `TryStore` in no particular order — a ball touches at most four neighbors per group, so the builder **throws** when a group is full rather than drop the handle, #585). `ClusterInvariants.Verify` checks the whole bookkeeping against the solver (every stored handle a live socket between lattice neighbours or to the ceiling, every neighbouring pair exactly once, no socket a ball does not store), and the logic tests run it after every operation of long random attach/release sequences. Every pair gets exactly one constraint by construction: the build pass connects same-level pairs only towards +X/+Z from each ball, and cross-level pairs only from the **even** (unshifted) level of each pair — adjacent levels always differ in parity, and neighbor index offsets depend on it (`diagonalShift`). The runtime attach path for a newly shot ball (`AttachBallToStructure`) instead connects all four same-level directions plus both adjacent levels, since the new ball has no constraints yet. Anchor offsets must be rotated into body-local space (`WorldToLocalOffset`) since bodies no longer have identity orientation once the simulation has run.

## Conventions

- **Triangle winding**: procedural meshes (`BoxMesh`, `SphereMesh`, `CannonMesh`, `LatheMesh`) wind their triangles **clockwise seen from outside**, which is what MonoGame's default `CullCounterClockwiseFace` treats as the front face — the viewport transform flips Y, so a triangle whose `(b - a) × (c - a)` points at the viewer comes out counter-clockwise in window space and is culled. Both classes had it backwards for a long time and it is a nasty bug to spot: nothing disappears, the far side of the object is drawn instead. A box reads as a hollow shell seen from inside; a sphere keeps its exact silhouette and only its shading is wrong, so the balls just looked washed out. Loaded models are wound the normal way — the opposite — so the two cannot be reconciled by picking a cull mode; flipping the mesh is the fix. `Tools/WindingCheck` checks every procedural mesh against this rule without a frame and names the deliberate exceptions (the dome, the editor's wire box, the drain's `CullNone` rims). (The sky domes carried that loaded winding until #113 made them procedural, and their captured triangle order keeps it deliberately: a dome shows front faces to a camera *inside* it, and the Testbed and the editor draw the sky under an inherited rasterizer state that is frequently `CullCounterClockwiseFace`. The last loaded model anywhere is the MapEditor's GUI `Selector.x`.) The Testbed **states** `RasterizerState` before the scene rather than inheriting it: the tonemap pass leaves `CullNone` and the overlay's `SpriteBatch` leaves its own, so what the scene culled used to depend on which of them ran last.
- Two vector types coexist: `Microsoft.Xna.Framework.Vector3` in game/render code and `System.Numerics.Vector3` in Bepu code, with **named** conversions at the boundary — the framework's own `ToNumerics()` outbound, `Prazsky.Core.Tools.NumericsExtensions`' `ToXna()` inbound. MonoGame 3.8.5 declares an implicit conversion for the inbound direction, so such a crossing compiles with nothing on the line to mark it; the named call is used anyway, deliberately, so the boundary is visible where it is crossed rather than inferred. Reading cannot find a crossing that has no call on it; `Tools/VectorBoundary` finds them with the compiler, and found five a reading pass had missed (#400).
- **Per-frame render hygiene** — the full discipline, each rule with the incident that taught it, is in `BestPractices.md`; hold all new code to it. The short form: cache `EffectParameter`/`EffectTechnique` references at load (the by-name indexers are linear scans; `InstancedModelRenderer` and `CloudField` are the patterns) and set never-changing parameters once; never `new` a GPU state object per frame (framework statics); no per-frame managed allocations (iterators included), no console I/O on load/gameplay paths, one `GetState()` per input device per frame; write a translation into `M41–M43` instead of multiplying `R × CreateTranslation` in per-ball loops; in shaders, scene-gated work goes behind a `[branch]` on a uniform (non-divergent, derivative-safe with no gradient ops inside). And comments are load-bearing: update them in the same change as the behaviour, reference constants instead of repeating values, never leave a wrong "why" standing.
- **The documents in `docs/` are held to the same standard as the comments**, and for the same reason: a measured figure that is quietly wrong is worse than no figure. When behaviour changes, change the document in the same commit; when a number is stated, it is because it was measured, so do not carry one over from a test rig into the record without re-measuring it on the real thing.
- **`git clean` and `git reset --hard` are refused in this repository**, by a `PreToolUse` hook (`.claude/hooks/guard-destructive-git.sh`, wired in `.claude/settings.json`) and by matching `permissions.deny` rules. Untracked files here are **data**: a level saved out of the MapEditor lands in `Game/Levels` as a `??`, and the editor's save dialog defaults to the working directory. A `git reset --hard origin/main && git clean -fd` once deleted three hand-built levels outright — no blob in the object database, nothing in the Recycle Bin, noticed four days later. `git add` a new level the moment it exists: a staged blob survives even a hard reset. The hook's own header carries the incident.
- **Line endings are LF, everywhere, and `.gitattributes` says so** (`* text=auto eol=lf`) — in the stored blob and in the working tree alike. **Do not hand-write CRLF back in**, and after any script has touched a tracked file run `git diff -w --numstat` before committing: if it disagrees with `git diff --numstat`, the file was re-ended and the commit is whole-file churn (a file whose every line differs conflicts *whole* at a merge, a lone CR makes git classify a file as binary, and `.claude/hooks/*.sh` must be LF or bash refuses the shebang). The history, the figures and `.git-blame-ignore-revs` are in `docs/repo-conventions.md`.
- **Branches are the unit of work, and there are no pull requests.** Commit a change to a feature branch off `origin/main` and push the branch; the branch is **merged into `main` with a merge commit** as soon as the work is done and verified (the standing instruction at the top of this file): `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`. **Never `--ff-only`** — two branches off the same `main` cannot both fast-forward, and refusing the second invites a rebase and a force-push of a branch already pushed, on the one repository several machines share. Never open a PR and never offer one. A direct push to `main` is the one action that can leave another machine's checkout diverged. Name a branch `<issue-number>-<slug>` when there is an issue, a plain slug otherwise. One change per branch: the working tree often carries several unrelated threads, so stage only the files belonging to the change at hand. (The full reasoning: `docs/repo-conventions.md`.)
- **A merged branch is deleted immediately, on the remote and locally, in the same breath as the merge**: `git push origin --delete <branch>` and `git branch -d <branch>` (the safe `-d`, never `-D`: it refuses anything not actually merged, which is the check). A branch ref says "this is in flight", and on a repository several machines share the branch list is how one machine asks what the other is in the middle of. Two temporary exceptions: a branch checked out in a worktree (`git worktree list`) until it moves off it, and a branch the other machine has not fetched since the merge. (Why it is a rule: `docs/repo-conventions.md`.)
- The user (sole author) communicates in Czech; code and comments are in English.

## How work is run

Four rules about the *process*, set on 2026-10-03 after the owner and an agent reviewed how this project is being run. The figures they rest on, and why each exists, are in `docs/repo-conventions.md`.

- **A player-facing feature is done when a player can understand it, not when it works.** An issue is not closed, and not labelled `shipped-awaiting-verdict`, until: (1) a player who has not read the Help page can tell what it does and when to use it — the chip, card or cue that says so ships **with** the mechanism, never in a later issue; (2) its look and its sound are its own, not another kind's; (3) the issue carries a **"Not verified"** line saying what no run could judge (not heard, not felt, not played on a pad, no level uses it yet). A mechanism that no level uses and no tutorial reaches is half built — #368 and #692 are what that cost.
- **The owner's verdict is the scarce resource, so its queue is capped.** The queue is `gh issue list --label shipped-awaiting-verdict`. With **more than 15** in it, start no further change whose verdict is a look, a sound or a feel; take work the queue does not grow with (a bug, a gate, a refactor, a measurement) or work that unblocks a decision the owner owes. Ask for verdicts in **batches** — one before/after page or one list — never one message per issue.
- **A claim lives on the issue.** Before starting: `gh issue list --label in-progress`, then the journal grep (`grep -rn "#N" docs/agent-notes.md docs/agent-notes-archive/`) and `git log --all --oneline | grep "(#N)"`. Then `gh issue edit N --add-label in-progress` and one comment saying who (machine and session name), what is intended and the date. Take the label off when the branch is merged or you stop. The journal entry (`docs/agent-notes.md`) records the findings and the merge.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

It is the overview: the project, how to build and run it, the one data structure everything turns on, the repo-wide conventions, and **which document covers what**. The detail lives in `docs/` — see "Where the rest is documented" below, and read the relevant document before working on that area.

## Project

BS3D is a 3D Puzzle-Bobble-style game (shoot balls at a hanging 3D cluster of balls) built with MonoGame and BepuPhysics 2. Repo: https://github.com/AntoninPrazsky/BS3D — tasks are tracked in GitHub issues.

**Finished work lands on main immediately** (the owner's standing instruction): once a task is done and verified, its branch is merged to main right away — work sitting on a side branch is work the owner cannot see. This said "its PR is merged" until 2026-08-14, which contradicted the branch rule below and had two agents working two different ways at once; the owner's ruling is that the branch rule below stands, so **the merge is a direct `--no-ff` merge into main and there is still no PR anywhere in this repo**. The point of the sentence is the *immediacy*, not the mechanism.

There are **three executables**: the **Testbed** (where every system was built and is still tuned), the **MapEditor**, and **Game** — the shipping product, founded deliberately small on top of the libraries the other two already share (see `docs/game-session.md`).

All three run on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0). MapEditor used to be on **DesktopGL**, where MojoShader capped shaders at Shader Model 3.0 and everything 5.0-only in the shared `InstancedModel.fx` had to sit behind `#if OPENGL` — it was moved to WindowsDX so it can render the balls exactly as the game does (full linear + tonemap parity, see "The map editor's render pipeline" in `docs/formats-and-tools.md`). There is no OPENGL build of any shader now, and the `#if OPENGL` branches are gone. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers, and each executable brings its own reference (all now the same WindowsDX package). MapEditor and Game build `Testbed/Content/Shaders/InstancedModel.fx` (and `Tonemap.fx`, `Glare.fx`, the scene shaders, the sky domes' `Sky.fx`, …) out of the Testbed content directory, so there is one copy of each shader and a change reaches every executable at once.

## Build and run

```powershell
# Build everything (libraries + Testbed game)
dotnet build C:\GitHub\Testbed.sln

# Run the game testbed / the map editor / the game
dotnet run --project C:\GitHub\Testbed\Testbed.csproj
dotnet run --project C:\GitHub\MapEditor\MapEditor.csproj
dotnet run --project C:\GitHub\Game\Game.csproj

# Testbed can load a map right at startup (useful for testing)
Testbed.exe C:\GitHub\Testbed\Maps\Full.json
```

There are four solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln`, `MapEditor.sln` and `Game.sln` (each executable plus the libraries it uses). There are no test projects and no lint configuration.

Besides the three executables there are two **tools**, both in `Game.sln` and both plain `net10.0` console apps with no graphics device. `Tools/LevelGen` is the generator that writes the game's pattern levels and the checks that say a generated level is playable before anyone plays it. `Tools/ScoreSim` plays every shipped level several ways through the real `ScoreKeeper`/`StarRating` and refuses a scoring rule that rates them wrongly — it exists because #173 found the star rating ordered backwards against skill on every level, a fault no individual number showed. Both exit non-zero on a failure so they can go in front of a commit; see "The level generator" and "The scoring simulator" in `docs/formats-and-tools.md`.

```powershell
# Regenerate the pattern levels and the level set
dotnet run --project C:\GitHub\Tools\LevelGen\LevelGen.csproj

# Check the scoring still rates the shipped levels the right way round
dotnet run --project C:\GitHub\Tools\ScoreSim\ScoreSim.csproj
```

MonoGame content (`Content/Content.mgcb` in each executable) is compiled automatically during build by `MonoGame.Content.Builder.Task`; editing the .mgcb itself is normally done with the MonoGame Pipeline Tool. **Each executable needs its own `.config/dotnet-tools.json`** pinning the `mgcb` tool — the content build shells out to `dotnet mgcb`, and the manifest search walks up from the *project* directory, so a new executable without one fails the content build with "Nenašel se soubor manifestu" even though its siblings build fine (`dotnet tool restore` once after adding it). All three executables target `net10.0-windows` and pull in WinForms (WindowsDX hosts its window on it), so they are Windows-only; the libraries target plain `net10.0`.

## Architecture

Three layered libraries under `BS3DLibs/`, consumed by the three executables:

- **Prazsky.Core** — game-agnostic 3D infrastructure: `BasicCamera3D`/`ICamera`, `CameraShake` (a camera's recoil-and-rattle response to a violent event, offsets only — see "Recoil and camera shake" in `docs/game-session.md`), `RecoilCamera` (the `ICamera` that composes a per-frame base pose with `CameraShake`'s offsets and can roll — `BasicCamera3D` structurally cannot), model/bitmap/info renderers, `InstancedModelRenderer` (GPU instancing), `PostProcessPipeline` (the shared HDR target + bloom pyramid + tonemap resolve all three executables run, and the end-of-level defocus only the Game asks for — see docs/rendering.md), `SkyDome` (the sky: one procedurally built dome mesh and a stored palette per sky — it was eighteen `.dae` models built by three content pipelines until #113), the shared setting no executable keeps a copy of any more (#75) — `ArenaIsland` (the drawn stone island, the glass drain, its gold beads, the dark pit shaft and every figure of them), `CeilingPlate` (the glass plate a cluster hangs from), `SkyLightRig` (the dome-derived light rig), `SceneLights` (a scene's own point lights) and `ForestScatterRenderer` (the forest's trees, boulders and stumps — every mesh, material and encoded tint of them), all under "The setting, in one copy" in `docs/scenes.md` — what a shot puts on the screen, one copy each since #76: `LaunchSmears` (the muzzle streak), `AimBeam` (the dashed line of light out of the muzzle — the overview's only word on where the gun points, and the one that carries a refusal there; it borrows `ShotTrail.fx` from `LaunchSmears`, which is why both push the trail widths per draw) and `Crosshair` (four procedural bars, no bitmap) — the procedural meshes (`SphereMesh`, `BoxMesh`, `FunnelMesh`, `LatheMesh` and the `IslandMesh` built on it, plus `CannonMesh`, the `CannonGlassMesh` that glazes its loading window with the firing round notched out of the pane, `GunCarriageMesh` and `GunWheelMesh` on the small `MeshBuilder` that carries the winding correction as a service), `SurfaceTexture` (procedural, exactly tiling stone and concrete), the screen stack (`Screens/`), and `Tools/Constants.cs` (named float constants like `HALF`, `SQRT_TWO` used throughout).
- **Prazsky.BS3D** — game logic without physics: the ball grid (`GameStructure/BallsMap.cs`), `StaticBall`, `BallType`, JSON map (de)serialization (System.Text.Json), the `Levels/Level` file format with the `LevelSet` order over it and the persisted `PlayerProgress` beside it (`Levels/PlayerProgress.cs` — best score and stars per level, the star total that unlocks entries), the scoring rules (`Scoring/ScoreKeeper.cs`) and the star rating over them (`Scoring/StarRating.cs`), input helpers, and the gameplay hardware no executable keeps a copy of any more (#76) — `Cannon` (the gun's pose, the barrel's and the carriage's draw matrices, its muzzle, the W/S advance walk with its rubber-ended range, and since #115 the recoil stroke — the tube's slide and the undercarriage's smaller, later shove, off one clock the executables only tick), `CannonRig` (the procedural barrel with its domed breech, its **glazed** loading window — a pane of dark blue glass with the round that fires next notched out of it — and carriage: every figure the tube is cut to, plus the cheeks, their trunnion pins, the axle, the split trail and the spoked wheels the walk rolls), `Magazine` (the loaded queue, its post-shot glide and its place in the bore), `GameCameraFit` (the camera's stand-off, its aim height, the gun's orbit radius and the walk's range, solved together), `PreciseAim` (the lens leaning in over the barrel) and `AimReachability` (whether every cell of a field can be shot at), all under "The gun's hardware, in one copy" in `docs/testbed.md` — plus `BallRenderSet` (the sphere LODs, every figure of the balls' look and the instance buckets, with the once-per-frame ball visit made structural) and `MouseAim` (the aim off a captured cursor), under "The rest of the hardware, in one copy" there. (See `docs/formats-and-tools.md`.)
- **Prazsky.BS3D.Physics** — BepuPhysics representation: `PhysicsBall` (body reference + constraint handle slots + array position), `BallsConstraintsBuilder` (builds the constrained ball structure, and implements the match rule that releases a group), `FunnelPhysics` (the drain's double-sided triangle mesh, which is the island's whole collision floor — one copy since #75), `PhysicsWorld` (the dispatcher, the buffer pool, the simulation, the contact stream and the mandatory order inside one step — the stepping *policy* deliberately stays with each executable, #76), `ClusterCollector` (the one walk that turns a simulated cluster into ball instances, #76), `ShotPlacement` (**where a shot lands** — the one answer, asked by the contact handler when a ball touches and by the aim preview every frame from the barrel's line, so the ghost and the attach cannot disagree; see "The landing preview" in `docs/game-session.md`), `BallContactEventHandler` with the `BallLanding` it reports through (**what happens when a shot touches something** — the snap into the lattice, the constraints and the match rule, in one copy since #68; it stood in the Game and again inside `Testbed.cs`, and merging them changed the Testbed's contact path rather than moving it, so read the handler's own class doc before touching it), and the Bepu callback/contact infrastructure.
- **Testbed** — the original playable game loop: simulation setup, shooting, contact handling, backdrops, HUD. Test maps live in `Testbed\Maps\*.json`.
- **Game** — the shipping product (`Game/`, assembly `BS3D.exe`). Founded small and deliberately **not** a copy of `Testbed.cs`: a hanging cluster over the island in any of the thirteen shared scenes, the gun with its visible magazine, the fast shot with its launch smear, a real Bepu simulation, and a camera that is hit every time the gun fires — behind a Myra front end (main menu, pause, settings, scene picker) over a slowly orbiting camera. It plays levels off disk, ordered by a level set. See `docs/game-session.md` and `docs/game-shell.md`.
- **MapEditor** — visual editor for those map JSON files (supports drag-and-drop of a map file onto the window). It draws the balls and the sky the same way the game does, so a map looks in the editor the way it will play: the same instanced procedural spheres, the same shader, the same sky-derived lighting and the same full render pipeline — linear radiance into an HDR target, glare, then the ACES tonemap. It builds the shaders straight out of the Testbed content directory, so there is one copy of each (the sky domes stopped being content in #113 — `SkyDome` builds the one dome and its eighteen palettes procedurally); B cycles the domes and **V cycles the seven scenes**, so a map can be previewed against every backdrop it might play in. It loads and saves whole **levels** (map + scene + sky) and carries a live scene-config editor. See `docs/formats-and-tools.md`.

### The ball grid

The central data structure is a 3D array `[x, z, level]` where **level is the vertical (Y) axis**. Odd levels are shifted by +0.5 in X and Z (hexagonal-like packing); vertical spacing between levels is `1/√2`. `BallsMap.GetRealPosition` maps array coordinates to world positions, and `Center()`/`ComputeCentered` translate between the raw grid frame and the centered world frame. A cell has 4 neighbors on its own level and up to 4 on each adjacent level; which diagonal offsets are the true neighbors depends on level parity (`GetNeighboringCells` encodes this).

`BallsMap` holds the logical state (`StaticBall`s); `BallsConstraintsBuilder.BuildBallsStructure` mirrors it into a parallel `PhysicsBall[,,]` of dynamic Bepu bodies connected by `BallSocket` constraints to their neighbors, with the top level constrained to a kinematic ceiling body. The whole cluster hangs from the ceiling and jiggles physically.

The play field is larger than the initial ball layout: map JSON stores field dimensions (`sx`/`sz`/`l`) separately from the layout array, the layout is placed at the **top** of the field and the empty bottom levels are room for shot balls to attach into. Legacy map files without field dimensions get 6 extra bottom levels on load (an even number, to preserve level parity). The Testbed ceiling repositions/resizes itself to the loaded map (`FitCeilingToMap`).

### Constraint handle bookkeeping

Each constraint is shared by two balls, so `PhysicsBall` stores handles in three slot groups (`HandlesBottom`/`HandlesMiddle`/`HandlesTop` = balls below / same level / above + ceiling; four slots each, filled via `TryStore` in no particular order — a ball touches at most four neighbors per group). Every pair gets exactly one constraint by construction: the build pass connects same-level pairs only towards +X/+Z from each ball, and cross-level pairs only from the **even** (unshifted) level of each pair — adjacent levels always differ in parity, and neighbor index offsets depend on it (`diagonalShift`). The runtime attach path for a newly shot ball (`AttachBallToStructure`) instead connects all four same-level directions plus both adjacent levels, since the new ball has no constraints yet. Anchor offsets must be rotated into body-local space (`WorldToLocalOffset`) since bodies no longer have identity orientation once the simulation has run.

## Conventions

- **Triangle winding**: procedural meshes (`BoxMesh`, `SphereMesh`, `CannonMesh`, `LatheMesh`) wind their triangles **clockwise seen from outside**, which is what MonoGame's default `CullCounterClockwiseFace` treats as the front face — the viewport transform flips Y, so a triangle whose `(b - a) × (c - a)` points at the viewer comes out counter-clockwise in window space and is culled. Both classes had it backwards for a long time and it is a nasty bug to spot: nothing disappears, the far side of the object is drawn instead. A box reads as a hollow shell seen from inside; a sphere keeps its exact silhouette and only its shading is wrong, so the balls just looked washed out. Loaded models are wound the normal way — the opposite — so the two cannot be reconciled by picking a cull mode; flipping the mesh is the fix. (The sky domes carried that loaded winding until #113 made them procedural, and their captured triangle order keeps it deliberately: a dome shows front faces to a camera *inside* it, and the Testbed and the editor draw the sky under an inherited rasterizer state that is frequently `CullCounterClockwiseFace`. The last loaded model anywhere is the MapEditor's GUI `Selector.x`.) The Testbed **states** `RasterizerState` before the scene rather than inheriting it: the tonemap pass leaves `CullNone` and the overlay's `SpriteBatch` leaves its own, so what the scene culled used to depend on which of them ran last.
- Two vector types coexist: `Microsoft.Xna.Framework.Vector3` in game/render code and `System.Numerics.Vector3` in Bepu code, with **named** conversions at the boundary — the framework's own `ToNumerics()` outbound, `Prazsky.Core.Tools.NumericsExtensions`' `ToXna()` inbound. MonoGame 3.8.5 declares an implicit conversion for the inbound direction, so such a crossing compiles with nothing on the line to mark it; the named call is used anyway, deliberately, so the boundary is visible where it is crossed rather than inferred.
- **Per-frame render hygiene** — the full discipline, each rule with the incident that taught it, is in `BestPractices.md`; hold all new code to it. The short form: cache `EffectParameter`/`EffectTechnique` references at load (the by-name indexers are linear scans; `InstancedModelRenderer` and `CloudField` are the patterns) and set never-changing parameters once; never `new` a GPU state object per frame (framework statics); no per-frame managed allocations (iterators included), no console I/O on load/gameplay paths, one `GetState()` per input device per frame; write a translation into `M41–M43` instead of multiplying `R × CreateTranslation` in per-ball loops; in shaders, scene-gated work goes behind a `[branch]` on a uniform (non-divergent, derivative-safe with no gradient ops inside). And comments are load-bearing: update them in the same change as the behaviour, reference constants instead of repeating values, never leave a wrong "why" standing.
- **The documents in `docs/` are held to the same standard as the comments**, and for the same reason: a measured figure that is quietly wrong is worse than no figure. When behaviour changes, change the document in the same commit; when a number is stated, it is because it was measured, so do not carry one over from a test rig into the record without re-measuring it on the real thing.
- **`git clean` and `git reset --hard` are refused in this repository**, by a `PreToolUse` hook (`.claude/hooks/guard-destructive-git.sh`, wired in `.claude/settings.json`) and by matching `permissions.deny` rules. Untracked files here are **data**: a level saved out of the MapEditor lands in `Game/Levels` as a `??`, and the editor's save dialog defaults to the working directory. A `git reset --hard origin/main && git clean -fd` once deleted three hand-built levels outright — no blob in the object database, nothing in the Recycle Bin, noticed four days later. `git add` a new level the moment it exists: a staged blob survives even a hard reset. The hook's own header carries the incident.
- **Branches are the unit of work, and there are no pull requests.** Commit a change to a feature branch off `origin/main` and push the branch; the branch is then **merged into `main` with a merge commit** when the author asks — `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`, which is what every merge in the log is. This said `--ff-only` until 2026-08-12 and the history had never done that: it matters because **two branches off the same `main` cannot both fast-forward**, so an `--ff-only` rule refuses the second one and invites a rebase and a force-push of a branch that is already pushed — on the one repository whose whole point is that several machines share `main`. The merge commit also keeps the branch's name and its one-line summary in the log, so the history reads as a list of named changes rather than a flat run of commits. Never open a PR and never offer one — a sole author reviewing their own work gains nothing from the round-trip. The branch is not a review artefact: it exists because several machines are active on this repo at once (a laptop and a desktop), so `main` is shared between them and a direct push to it from one machine is the one action that can leave another machine's checkout diverged. Name a branch `<issue-number>-<slug>` when there is a GitHub issue, a plain descriptive slug otherwise. One change per branch — the working tree here often carries several unrelated threads at once, so stage only the files belonging to the change at hand.

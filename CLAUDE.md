# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BS3D is a 3D Puzzle-Bobble-style game (shoot balls at a hanging 3D cluster of balls) built with MonoGame and BepuPhysics 2. Repo: https://github.com/AntoninPrazsky/BS3D — tasks are tracked in GitHub issues.

Testbed runs on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0); MapEditor is still on **DesktopGL**, where MojoShader caps shaders at Shader Model 3.0. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers: both platform packages ship an assembly called `MonoGame.Framework`, and keeping the reference compile-time-only is what lets each executable bring its own backend without the two colliding over the same output file. Since MapEditor builds `Testbed/Content/Shaders/InstancedModel.fx` out of the Testbed content directory, anything in that file that SM 5.0 allows and SM 3.0 does not has to sit behind `#if OPENGL`, or MapEditor stops compiling.

## Build and run

```powershell
# Build everything (libraries + Testbed game)
dotnet build C:\Projects\Testbed.sln

# Run the game testbed / the map editor
dotnet run --project C:\Projects\Testbed\Testbed.csproj
dotnet run --project C:\Projects\MapEditor\MapEditor.csproj

# Testbed can load a map right at startup (useful for testing)
Testbed.exe C:\Projects\Testbed\Maps\Full.json
```

There are three solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln` and `MapEditor.sln` (each executable plus the libraries). There are no test projects and no lint configuration.

MonoGame content (`Content/Content.mgcb` in Testbed and MapEditor) is compiled automatically during build by `MonoGame.Content.Builder.Task`; editing the .mgcb itself is normally done with the MonoGame Pipeline Tool. Testbed and MapEditor target `net10.0-windows` and use WinForms interop, so the executables are Windows-only; the libraries target plain `net10.0`.

## Architecture

Three layered libraries under `BS3DLibs/`, consumed by two executables:

- **Prazsky.Core** — game-agnostic 3D infrastructure: `BasicCamera3D`/`ICamera`, model/bitmap/info renderers, `InstancedModelRenderer` (GPU instancing), `SkyDome`, and `Tools/Constants.cs` (named float constants like `HALF`, `SQRT_TWO` used throughout).
- **Prazsky.BS3D** — game logic without physics: the ball grid (`GameStructure/BallsMap.cs`), `StaticBall`, `BallType`, JSON map (de)serialization via Newtonsoft, input helpers, `Cannon`.
- **Prazsky.BS3D.Physics** — BepuPhysics representation: `PhysicsBall` (body reference + constraint handle slots + array position) and `BallsConstraintsBuilder` (builds the constrained ball structure).
- **Testbed** — the actual playable game loop: simulation setup, shooting, contact handling, backdrops, HUD. Test maps live in `Testbed\Maps\*.json`.
- **MapEditor** — visual editor for those map JSON files (supports drag-and-drop of a map file onto the window). It draws the balls and the sky the same way the game does, so a map looks in the editor the way it will play: the same instanced procedural spheres, the same shader and the same sky-derived lighting (see "Ball rendering"). It builds `Shaders/InstancedModel.fx` and all eighteen `Skyes/SkyDome*.dae` straight out of the Testbed content directory (`/build:../../Testbed/Content/…;<asset name>` in its own .mgcb), so there is one copy of each; B cycles the domes (the game's NumPad1, which the editor uses for ball types). It has no ground, castle, cannon or shadows; the play field is marked by a translucent procedural outline (`GUI/AABB.cs` + `WireBoxMesh`) instead of the game's glass ceiling, and only the selector gizmo still draws through `ModelRenderer`/`BasicEffect`.

### The ball grid

The central data structure is a 3D array `[x, z, level]` where **level is the vertical (Y) axis**. Odd levels are shifted by +0.5 in X and Z (hexagonal-like packing); vertical spacing between levels is `1/√2`. `BallsMap.GetRealPosition` maps array coordinates to world positions, and `Center()`/`ComputeCentered` translate between the raw grid frame and the centered world frame. A cell has 4 neighbors on its own level and up to 4 on each adjacent level; which diagonal offsets are the true neighbors depends on level parity (`GetNeighboringCells` encodes this).

`BallsMap` holds the logical state (`StaticBall`s); `BallsConstraintsBuilder.BuildBallsStructure` mirrors it into a parallel `PhysicsBall[,,]` of dynamic Bepu bodies connected by `BallSocket` constraints to their neighbors, with the top level constrained to a kinematic ceiling body. The whole cluster hangs from the ceiling and jiggles physically.

The play field is larger than the initial ball layout: map JSON stores field dimensions (`sx`/`sz`/`l`) separately from the layout array, the layout is placed at the **top** of the field and the empty bottom levels are room for shot balls to attach into. Legacy map files without field dimensions get 5 extra bottom levels on load. The Testbed ceiling repositions/resizes itself to the loaded map (`FitCeilingToMap`).

### Constraint handle bookkeeping

Each constraint is shared by two balls, so `PhysicsBall` stores handles in three slot groups (`HandlesBottom`/`HandlesMiddle`/`HandlesTop` = balls below / same level / above + ceiling; four slots each, filled via `TryStore` in no particular order — a ball touches at most four neighbors per group). Every pair gets exactly one constraint by construction: the build pass connects same-level pairs only towards +X/+Z from each ball, and cross-level pairs only from the **even** (unshifted) level of each pair — adjacent levels always differ in parity, and neighbor index offsets depend on it (`diagonalShift`). The runtime attach path for a newly shot ball (`AttachBallToStructure`) instead connects all four same-level directions plus both adjacent levels, since the new ball has no constraints yet. Anchor offsets must be rotated into body-local space (`WorldToLocalOffset`) since bodies no longer have identity orientation once the simulation has run.

### Shooting flow (Testbed)

Contact detection uses `Testbed/Contacts/ContactEvents.cs` (adapted from the Bepu demo); Bepu callbacks fire on worker threads, so contact events are queued and processed on the main thread. When a shot ball hits the structure, it is snapped into the nearest free neighboring cell (`BallsMap.PutBallAtClosestEmptyPositionNextTo`) and then wired into the physics structure with `AttachBallToStructure`.

### The city and the glass arena

The default of the two settings (NumPad2 switches to the sea, below) — no flag: a play surface of marble and glass panels in a clearing between the towers of a procedural city (`Testbed/Backdrops/City.cs`). The castle backdrop is gone, and neither the marble ground blocks nor the shadow overlay are drawn any more; the ground blocks remain only as physics bodies holding the balls up, since the arena has no collision of its own yet.

The city stands **over** the arena and falls away **underneath** it at the same time, and both halves of that took a correction. The first version cleared the blocks under the glass, which left nothing to look through the glass at; the city now continues underneath, cut off far below so the drop reads as a drop. The second version put the roofline below the floor, so no tower was ever seen against the sky — only bright roofs with dark canyons beside them, which the eye reads as holes punched in a white plain rather than as buildings (it was reported as inverted normals, and it was not). `ROOFLINE_Y` therefore sits well above the play surface.

The drawn floor is laid off the **physics** ground blocks rather than at a height of its own: `ARENA_Y`/`ARENA_PIT_Y` are derived from `GROUND_PLATEAU_Y`/`GROUND_PIT_Y`, and the recessed centre block — the bath the cluster settles into — is reproduced as a recess in the panel grid. A flat sheet at one height leaves the balls resting on nothing visible. This is why `ARENA_HALF_EXTENT`/`ARENA_PANEL_SIZE` are whole multiples that divide `GROUND_BLOCK_SIZE` evenly, and why mullions are laid one panel at a time (a band spanning the whole width would cut through the air over the recess; a lip belongs to the higher of the two floors it separates, and crossing bands are shortened by one mullion width so their coplanar tops do not z-fight).

The floor is a mosaic of solid marble panels and glass ones (glass towards the middle, stone confined to the outer ring) because a single glass sheet gives depth with nothing to measure it against, and a single stone one gives no depth at all.

Windows are not lit once and for all: each keeps its own rhythm off `CityWindowTime` (wall clock, like the balls' pulse — a city's lamps do not stop when the simulation is paused), holding a state for an interval of its own length and then deciding again, with a short fade rather than a cut. `CITY_WINDOW_BRIGHTNESS` stays **under** `GLARE_THRESHOLD`: a window that glares veils the tower behind it, and a thousand of them turn the skyline into one white haze.

Everything about the buildings is procedural and there are no assets; the marble of the floor is the texture off the `GroundMarble` model, projected triplanar (a `DetailTexture` on the frame renderer — **without** one the renderer falls through to the plain technique and every `SlabSize`/`CavityStrength`/relief setting on it is silently dead). One 1×1×1 `BoxMesh` serves all of it — every building, the four marble bands and each mullion is that cube under a different instance matrix, so the whole city is a single instanced draw call. Non-uniform scale is safe here because the boxes are axis-aligned in object space: a diagonal scale maps each face normal onto itself, so `normalize` in the pixel shader recovers it without an inverse transpose. The `InstancedCity` technique evaluates the window grid from **world position** rather than object space — the buildings are one cube scaled per instance, so an object-space grid would give a hundred-storey tower the same number of floors as a low one. Windows band-limit to their own average coverage, so a distant tower is a dim glowing block rather than a moire of floors.

Two things learned tuning it, both worth keeping in mind elsewhere. The **specular ambient is not multiplied by albedo** (a reflection does not care how dark the surface under it is), which is physically right but washes a whole skyline in sky color at grazing angles. Almost every facade of a city seen from inside it, and almost every square metre of a floor beyond your own feet, is at a grazing angle where Fresnel is near 1 — so the city runs the term at 0.07 and the marble floor at 0.4, and both were bleached white before that. And a translucent sheet over a lit city reads as *no floor at all*; the mullions dividing the glass into panels are what make the eye accept there is glass there.

### The sea (Testbed)

The second setting, reached with NumPad2 the way NumPad1 cycles the sky domes (or `scene=sea` on the command line, since a synthetic NumPad press never reaches the SDL window). Only the environment swaps: the marble-and-glass arena stays exactly as it is, now a platform floating a little above open water instead of standing among towers, and the translucent floor shows the sea beneath it just as it showed the city. It is `Testbed/Content/Shaders/Sea.fx` with its switch and draw plumbing in `Testbed.cs` (`SceneKind`, `SwitchScene`, `DrawSea`), and it borrows the scene's whole toolkit rather than inventing its own.

The water is one flat quad — `SEA_HALF_EXTENT` across, recentred on the camera every frame like the dome, dropped to `SEA_LEVEL_Y` below the platform's glass so the panels read as looking down onto the sea rather than the water poking up through them. Nothing about it is displaced: a sum-of-sines **slope** field tilts the normal through the same normal-from-height idiom the balls' skin and the ground relief use, and each octave band-limits against the pixel footprint, so the ripples (vlnky, not swell) flatten into a mirror towards the horizon instead of aliasing into a shimmer — the trick the clouds and the relief already lean on. The phase runs off the wall clock, so the sea keeps moving while the simulation is paused, like the clouds and the balls' pulse.

What sells it as water is the reflection, not the body. Fresnel over water's ~2% head-on reflectance rises to a mirror at the grazing angles that cover most of a sea, and the reflected ray samples the dome's two-color gradient in closed form (`SkyRadiance`'s trick again), so the water takes the mood of each of the eighteen skies — turquoise at noon, lavender under a violet dome, clouds and all — without a cubemap. A small reflection floor keeps a little sky in the surface even looking straight down, which is what stops stylised water from reading as flat black paint; the deep body is a dark reflectance lit by the sky above it (so a night sea goes dark) plus a dim always-present skylight tint. A sharp sun glint sparks where the reflected ray points at the sun, and the cloud shadow is the same one line the rest of the scene gets — `CloudSunlight` off the shared `Clouds.fxh` field — so the water darkens under the very cloud the sky shows overhead, glint and all. A horizon haze fades the finite plane into the skyline color over `SEA_HORIZON_HAZE_DISTANCE`, so it has no visible edge and no seam against the dome. It is drawn opaque, first in the scene block where the city would be, so the arena glass composites over it unchanged; the wave, color and placement dials (`WAVE_*`, `WATER_COLOR_*`, `SEA_LEVEL_Y`) sit at the top of `Testbed.cs`. One quad, so it costs nothing next to the city's instanced skyline. `Sea.fx` is Testbed-only — the map editor draws no backdrop — so unlike `InstancedModel.fx` it needs no Shader Model 3.0 branch.

### The weather (Testbed)

Procedural clouds that drift, shade the sky, throw shadows across the scene and flatten the light when they cover the sun. They live on **a flat plane at a finite altitude**, not as a texture on the dome, and that is the decision everything else follows from: a dome texture sits at infinity and casts no shadow anyone can derive from it, so what you look at and what shadows you would have to be two fields, and two fields drift apart. With a plane there is one field and three ray-plane intersections into it — the sky shader crosses it with the view ray, the scene shader with the sun ray, the CPU with the sun ray from the arena.

The field is defined **once**, in `Testbed/Content/Shaders/Clouds.fxh` (`#include` works in the MonoGame content pipeline, and `.fxh` edits *do* trigger a rebuild of the `.fx` that includes them — both verified). It is split in two, and the split is what removes the usual CPU/GPU noise-synchronisation problem:

- the **weather** layer is coarse, and mirrored in `Prazsky.Core.Render.CloudField` — the only part that exists twice. Its hash is built from `frac`/`dot`/multiply and no `sin`, because a sine-based hash is exactly where a C# and an HLSL copy would part company.
- the **detail** layer is fine, lives only in the sky shader, and nothing the shadow or the light rig looks at ever touches it.

`CloudField.ApplyTo(effect)` hands the shared parameters to both shaders, so the drawn cloud and the shadow it throws cannot be tuned apart by accident.

Things that took a while to get right:

- **Shading needs unclamped thickness, opacity needs the clamped one.** With one `saturate` for both, everything inside a cloud is exactly 1 and the interior comes out as a flat wash with a nice edge. `CloudThickness` runs past 1 on purpose.
- **The ACES curve eats cloud contrast.** Two linear values close together up in the highlights tonemap to the same white, so the shadowed underside has to be *well* below the sunlit top (0.18 against 1.7), not a shade under it.
- **Detail strength must be read against `CoverageGain`**, which is what the weather is multiplied by. At 0.55 against a gain of 2.8 the detail modulated the thickness by six percent and the clouds came out airbrushed.
- **Cloud shadows plug into the existing `keyShadow`** in `ShadePixel` — one line, and balls, city, floor and cannon all get them, because they all come through there. They use the coarse layer alone: a shadow thrown from that height has a penumbra hundreds of units wide, so the fine octaves would not survive the trip anyway. `SunDirection` is a separate uniform, not `KeyLightPosition`, which is a point forty units out whose direction fans across the scene.
- **The key light is dimmed per pixel by the shader, the ambient on the CPU, and never both.** Dimming the key on both sides counts the same cloud twice and darkens everything uniformly, which is the look this exists to avoid. Sun goes, sky stays: overcast reads *flat*, not dark.
- **Ambient reads an area, not a point** (`CoverAround`, five taps). "How much sky is over me" is an average by definition, and a single tap lurches between 0 and solid every time a cloud edge crosses it — smoothing afterwards does not turn that back into the quantity that was wanted.
- **Coverage is also the dial for whether the weather is noticeable at all**, which is a different question from whether it looks right: a handsome sky with a fifth of it covered leaves the arena in unbroken sun for minutes, because a shadow only lands when cloud happens to sit on the one patch its sun ray crosses.
- **Cloud color follows the dome** (`ApplyCloudPalette`, re-run on every dome switch). A cloud has no color of its own — its lit side is the color of the sun and its underside the color of the sky — so the lit side takes the same tint the scene's key light takes (`SKY_TINT_STRENGTH`, shared with the rig, so the clouds are lit by literally the same light as everything under them) and the underside takes the zenith, harder (`CLOUD_SHADOW_TINT_STRENGTH`), since it sees no sun at all. One fixed white cloud over all eighteen domes read as a grey smear pasted onto turquoise day, blood-red dusk and near-black night alike; checking a change like this means a launch per dome (`sky=<n>`), because synthetic NumPad presses do not reach the window.

Costs nothing measurable — 265–338 FPS on `Dense20x10x15` uncapped, the same CPU-physics ceiling as before. `SkyDome` takes an optional `Effect`; leave it null and it draws the plain gradient through `BasicEffect`, which is what the MapEditor does (it does not build `Sky.fx`, and the cloud shadow in `InstancedModel.fx` is stubbed out under `#if OPENGL`).

### Color management (Testbed)

The Testbed renders in **linear radiance** and leaves it exactly once. The scene always draws into a half-float HDR `RenderTarget2D` (`_sceneTarget`, `SurfaceFormat.HdrBlendable`, sized backbuffer × `_supersampleFactor`), and `Tonemap.fx` resolves it in one full-screen pass: box filter over the supersampled block, exposure (`DEFAULT_EXPOSURE`, `exposure=<f>` to override), the ACES filmic curve, then sRGB encode. The text overlay and aimer draw after it, in display space.

Between the scene and the tonemap sits **glare** (`Glare.fx`), two passes at a quarter of the *back buffer* resolution (not of the supersampled target — glare is blurry anyway, so the extra samples buy nothing; it costs ~0.03 ms and is independent of `ssaa`). A bright pass keeps each pixel's excess over `GLARE_THRESHOLD`, tinted with the pixel's own color so a red ball glares red; a streak pass smears it into a six-armed star. Each arm is normalized against **its own** weights and the arms are combined with `max` — summing all taps and dividing by the total weight of every arm collapses the star into a round blob. `Tonemap.fx` adds the result back **before** the ACES curve, so a glaring ball bleaches through the same highlight roll-off as everything else instead of looking like a decal. It is deliberately exaggerated: the point is to make it unmistakable that the balls emit light, not to model a lens. `GLARE_INTENSITY` was retuned from 2.6 to 1.3 when the procedural meshes' winding was fixed — the balls had been showing their far hemisphere, so everything above the threshold got brighter at once and the old number bleached a hole in the skyline.

Where a color is decoded depends on what it is. **Textures and model material colors** are sRGB data and are linearized in the shader at the point of use (`SrgbToLinear`, a cubic fit). **The light rig and the sky palette** are decoded on the CPU by `Prazsky.Core.Tools.ColorSpace`, because everything applied to them there — the `1.3`/`0.75` scales, the tint lerps — are multiplications, and `SrgbToLinear(a*b) != SrgbToLinear(a)*SrgbToLinear(b)`. `InstancedModelRenderer.SkyColor`/`GroundColor` therefore hold **linear** values and are not clamped to 1; `LinearLightRig` selects whether `SetLightTint` decodes the rig (Testbed true, MapEditor false — the map editor draws in gamma space straight to the back buffer, and `SrgbToLinear` is a no-op there under `#if OPENGL`). Adding a color to the frame without linearizing it is the recurring bug in this area: it has happened twice (the balls' sheen, the ambient scales).

Lighting is Blinn-Phong plus a **specular ambient**: `SkyRadiance` evaluates the dome analytically (the domes are two-color vertical gradients, so a prefiltered cubemap would only reproduce this at lower resolution), sampled along the normal for diffuse and along the reflection for specular, with roughness — derived from the Blinn-Phong exponent, so no material was re-authored — lerping towards the sky average. Fresnel is Schlick over a **dielectric F0 of 0.04** modulated by the material's specular color; handing `SpecularColor` to Schlick directly makes F ≈ 1 at every angle and veils the whole scene.

### Ball rendering (Testbed)

Balls are procedurally generated spheres (`SphereMesh` in Prazsky.Core) drawn with GPU instancing at three LOD resolutions picked by camera distance: `CollectBallInstances` fills one bucket per `BallType` × LOD (no camera culling — measurements showed it saved nothing on this scene) and `InstancedModelRenderer` issues one `DrawInstancedPrimitives` call per bucket. Per-instance data (`ModelInstance`, TEXCOORD1–5) carries the world matrix plus the ambient-occlusion vector (direction towards occupied neighbor cells + base factor, recomputed every frame from the grid). The shader (`Testbed/Content/Shaders/InstancedModel.fx`) does per-pixel Blinn-Phong with a positional key light ("sun"), hemisphere ambient tinted by the sky dome palette (`SkyDome` extracts zenith/horizon colors from the dome's vertex colors; `ApplySkyLighting` distributes them, `DefaultLighting` holds the base rig), directional AO, and a per-type diffuse tint (`GetDiffuseTintByType`). Balls draw with the `InstancedModelPattern` technique: a procedural beach-ball pattern (gores alternating between the type tint and white, white discs at the poles) evaluated in object space so it turns with the ball and makes rotation readable; `PatternGoreCount` on the renderer enables it, the tint passed to `Draw` becomes the primary gore color, and `PatternGoreWidth` sets how much of each pair of segments the color takes. Balls are **emissive and alive**: they radiate the ball's own type tint — `primary`, not the blended pattern color, whose gores and polar discs are white and made half of every ball radiate white light (`EmissiveStrength`, `BALL_EMISSION`) on a `Heartbeat` curve — two gaussian bumps per cycle, lub-dub, not a sine — whose phase is offset by world position along `PulseDirection` so the beat travels up the cluster as a wave instead of every ball flashing together. `PulseTime` is driven from wall-clock time in `Update`, so the pulse survives a paused or slowed simulation. The emission is deliberately **not** occluded: a light source buried in the pile is the one that should still glow out. `TranslucencyStrength` adds light carried through the shell from a source behind. Note the ad-hoc Fresnel "vinyl sheen" that used to live here is gone — it was a sky reflection, which the specular ambient now does for every surface, and two Fresnel sky terms stacked on a sphere bleached the balls out.

The same technique gives the ball its inflatable-vinyl surface: a sine-sum height field (molded micro-relief plus a groove along every panel weld) tilts the normal through `PerturbNormalFromHeight`, breaking up the highlight, and a Fresnel term adds the grazing-angle sky sheen (`PatternReliefStrength`, `PatternSheenStrength`). Each relief octave band-limits itself against its own wavelength using the screen-space pixel footprint (not camera distance), because the perturbation is derivative-driven and turns into a checkerboard once a wave gets near pixel size. The scene therefore renders into a supersampled `RenderTarget2D` (`_supersampleFactor`, default 2, `ssaa=<n>` to override) that is box-filtered onto the back buffer: more samples shrink the footprint, which is what keeps the fine octaves alive and sharp. MSAA antialiases geometry edges but not shading, so it is switched off while supersampling is on. The text overlay and aimer draw after the resolve, at native resolution. The old ball shadows are gone with the drawn ground: the `InstancedDepth` shadow-map pass and the `ShadowOverlay.fx` ground overlay were dropped when the city became the scene (`DrawDepth` and the `InstancedDepth` technique still sit in `InstancedModelRenderer`, unused, and the `.fx` is now an orphaned content asset). The scene objects — the ceiling and cannon as single-instance draws, the city and arena floor as instanced arrays — render through the same shader (`InstancedModelRenderer.Draw(...)` with per-part material colors/specular read from the model), so the whole scene shares one lighting model; `SkyLitRenderers()` enumerates every sky-lit renderer for `ApplySkyLighting`. The ceiling is a procedurally generated translucent glass box (`BoxMesh` in Prazsky.Core), regenerated at the exact field size whenever a map is loaded (`RecreateCeilingRenderer`) and drawn after the opaque scene. Models whose materials carry a texture use the `InstancedModelTextured` technique. Models without one can set `DetailTexture` on their renderer — a texture that only modulates the material colors — mapped either world-space (`DetailMapping.Triplanar` + optional procedural masonry joints, used by the arena's marble floor, whose boxes carry no UVs worth the name) or through the model's own UVs (`DetailMapping.ModelUVs`, used by the cannon: moving objects must not use the world-space projection or the texture swims across them). The UV path can add a `DetailNormalMap` for actual relief; its tangent frame comes from screen-space derivatives (`CotangentFrame` in the shader), so no model needs tangent vertex data. On top of any of these, `SurfaceReliefStrength`/`SurfaceReliefFrequency` add a procedural micro-relief (seven summed sines in world space) that tilts the normal through the same `PerturbNormalFromHeight` — no texture, no tiling, and it holds its grain to whatever the pixels can still resolve. The scene path band-limits each octave through `ReliefOctaveDirectional`, which measures the footprint **along that octave's own wave direction** (`abs(dot(dpdx, waveDirection)) + abs(dot(dpdy, waveDirection))`) rather than as one scalar: a pixel only fails to resolve a wave when it is wide across its crests, and on a surface seen at a grazing angle — a pixel covering meters along the view but millimeters across it — a scalar footprint reports the long axis and fades out every octave at once, leaving the surface geometrically perfect exactly where it should look roughest. The ball path still uses the scalar `ReliefOctave`, spheres being small enough that it does not show. `TextureSampler` is anisotropic for the same reason: isotropic mip selection blurs a textured surface into a smear at grazing angles. The cannon and the arena's marble floor use it. A model is rarely one material throughout, so `SetMeshSurfaceStyle(meshName, SurfaceStyle)` declares per mesh what it is made of — `Masonry` (coursed blocks with mortar cut in as real recesses), `Wood` (upright boards, seams between them, grain stretched along their length) or `Plain`; meshes left undeclared default to `Masonry`. Nothing calls it now that the multi-material castle model is gone, so it — and `MasonryStrength` — sit unused as library features. Testing CLI args: `autoshoot` (logs FPS + LOD distribution once per second), `nocap` (no vsync), `sky=<n>`, `switchmap=<path>` — see `.claude/skills/verify/SKILL.md`. `Maps/Dense20x10x15.json` (3000 balls) is the perf stress map; the frame budget ceiling there is the CPU physics (~300 FPS uncapped), not rendering.

### Conventions

- **Triangle winding**: procedural meshes (`BoxMesh`, `SphereMesh`) wind their triangles **clockwise seen from outside**, which is what MonoGame's default `CullCounterClockwiseFace` treats as the front face — the viewport transform flips Y, so a triangle whose `(b - a) × (c - a)` points at the viewer comes out counter-clockwise in window space and is culled. Both classes had it backwards for a long time and it is a nasty bug to spot: nothing disappears, the far side of the object is drawn instead. A box reads as a hollow shell seen from inside; a sphere keeps its exact silhouette and only its shading is wrong, so the balls just looked washed out. Loaded models (cannon, sky domes) are wound the normal way, so the two cannot be reconciled by picking a cull mode — flipping the mesh is the fix. The Testbed **states** `RasterizerState` before the scene rather than inheriting it: the tonemap pass leaves `CullNone` and the overlay's `SpriteBatch` leaves its own, so what the scene culled used to depend on which of them ran last.
- Two vector types coexist: `Microsoft.Xna.Framework.Vector3` in game/render code and `System.Numerics.Vector3` in Bepu code, with `ToNumerics()` conversions at the boundary.
- The user (sole author) communicates in Czech; code and comments are in English.

# Building, CI, releasing and the tools

Part of the BS3D documentation. `CLAUDE.md` keeps the build commands and the rules; this document holds what it used to carry in full about the platform, the solutions and root files, the two workflows and the release, and what each tool is for. The paragraphs below are **word for word as they stood in `CLAUDE.md` when they were moved (2026-10-03)** — a long history and many measurements, which every agent had to read before every task and which are looked up here when the work touches them.

## The platform, and how the shaders came to be built once

All three run on **MonoGame.Framework.WindowsDX** (DirectX 11, Shader Model 5.0). MapEditor used to be on **DesktopGL**, where MojoShader capped shaders at Shader Model 3.0 and everything 5.0-only in the shared `InstancedModel.fx` had to sit behind `#if OPENGL` — it was moved to WindowsDX so it can render the balls exactly as the game does (full linear + tonemap parity, see "The map editor's render pipeline" in `docs/formats-and-tools.md`). There is no OPENGL build of any shader now, and the `#if OPENGL` branches are gone. The three libraries reference MonoGame with `PrivateAssets="all"` so the package does not flow to consumers, and each executable brings its own reference (all now the same WindowsDX package). **Every shader lives and compiles once in the `Prazsky.Shaders` library** (`BS3DLibs/Prazsky.Shaders/Content/Shaders`, #618 — `InstancedModel.fx` and its include tree, `Tonemap.fx`, `Glare.fx`, the scene shaders, …): its `Content/Shaders.mgcb` is built by the content task in that project, and the compiled `.xnb` files are Content items MSBuild copies into the output and the publish folder of every project that references it, at `Content/Shaders/<name>.xnb` where `Load<Effect>("Shaders/…")` has always looked. So there is one copy of each shader, one compilation, and a change reaches every executable at once; the executables' own `Content.mgcb` files carry no shaders, and nothing that ships builds anything out of the Testbed (until #618 all three compiled the shaders out of `Testbed/Content/Shaders` each). **`Sky.fx` is the one the MapEditor never loads**: it arrives beside the editor with the rest, but the editor draws the dome through its own `BasicEffect` and gets no cloud deck and no sun disc — which is what `Sky.fx`'s own header says, and is why a scene wanting a per-scene sky feature cannot put it there (see "The storm" in `docs/scenes.md`).

## GamePi: the Game on Linux ARM64

`GamePi/` builds the Game for Linux ARM64 — a Raspberry Pi 5 — on **MonoGame.Framework.DesktopGL** (an SDL2 window and input, OpenAL Soft for the sound, OpenGL for the picture; the package carries `linux-arm64` builds of SDL2 and OpenAL). It is not a second game and not a fork: `GamePi.csproj` compiles every source under `Game/` and replaces only what cannot be shared, so a change to `Game/` reaches both builds, and `Game.csproj` does not know GamePi exists. Started 2026-10-05 as a skeleton for the Pi port and its locked "Potato" tier.

- **What it replaces.** Five files of `Game/Platform` are left out of its compile and stand in `GamePi/Platform` under the same names and members — `QualityLock` (#788: none on Windows, `Potato` in GamePi, see "The quality tier" in `docs/game-shell.md`), `AudioBackend` (#790: OpenAL Soft places a voice only while it holds a source, which it takes at `Play`, so `ProceduralAudio.Speak` places after `Play` there; see "The sound" in `docs/game-feedback.md`) and three that are Win32 or WinForms: `DisplayRefresh` (the monitor's refresh from SDL instead of user32 — it read 60 Hz on the Pi's 60 Hz panel), `WindowIcon` (a no-op: MonoGame's SDL window takes its icon from the embedded `BS3D.Icon.bmp`, `GamePi/Icon.bmp` made from `Game/Icon.ico`'s 256-pixel frame at 128, #792 - the window's `_NET_WM_ICON` reads 128 × 128 under Xwayland) and `CrashDialog` (the crash notice through `SDL_ShowSimpleMessageBox`; on Windows it is the WinForms box `RunLog` used to call inline). `GamePi/Platform/Sdl.cs` declares the SDL calls they make. A new Win32 or WinForms file in `Game/Platform` belongs on `GamePi.csproj`'s exclusion list with a namesake beside it.
- **What the shared code does about it.** The Win32 calls that sit inside platform-neutral logic are guarded with `OperatingSystem.IsWindows()` rather than moved: `FrameLimiter`'s `timeBeginPeriod`/`timeEndPeriod` (Linux's `Thread.Sleep(1)` is already fine — 1.06 ms on average over 500 sleeps on the Pi) and its `DwmFlush` (no DWM: `WaitForCompositor` answers false and the schedule alone paces the frame), `LoadingIndicator`'s `PeekMessage`, and `InternetCheck`'s COM network list, so GamePi goes straight to the adapter test. GamePi makes CA1416 an **error** (#787), so the platform analyzer is the check that a Windows-only .NET API reached shared code: it is what found `InternetCheck`, and taking that guard out again fails GamePi's build with `error CA1416` on `Marshal.FinalReleaseComObject` (seen, 2026-10-05). A `DllImport` is not something it sees, so a new call into user32 compiles and fails only at run time.
- **Its content.** `GamePi/Content/Content.mgcb` builds the Game's two assets for DesktopGL: the logo, and the InfoRenderer's `Fonts/segoeui` from Inter (`Game/Content/Fonts/Inter-Regular.ttf`), because "Segoe UI" exists on no Linux machine. Its `.config/dotnet-tools.json` pins the official `dotnet-mgcb` 3.8.5 rather than the `bad-echo-mgcb` 3.8.2.1 the other projects pin: that one imports textures through FreeImage, which has no ARM64 build, and fails on the Pi with `libFreeImage.so: cannot open shared object file`.
- **Its own shaders, and how they get built (#789).** Every effect in `Prazsky.Shaders` is Shader Model 5.0, and DesktopGL compiles effects through MojoShader, which stops at 3.0; GamePi references no `Prazsky.Shaders` and draws through the **Potato render path** (`Game/BS3DGame.Potato.cs`, "The Potato path" in `docs/rendering.md`) with eight SM 3.0 effects of its own in `GamePi/Shaders`: `PotatoModel` (under every `InstancedModelRenderer`), `PotatoSky`, and ports of `ShotTrail`, `LaserGrid`, `Blast`, `Wormhole`, `Fireworks` and `Confetti` under their desktop names. **Compiling an effect for OpenGL needs the Windows D3D compiler** (mgfxc runs the HLSL through it to SM 3.0 bytecode, then MojoShader to GLSL; off Windows it needs Wine, `MGFXC0001`, and there is no Wine for ARM64), so the compiled `.xnb` are **committed** in `GamePi/Shaders/Compiled`, which `GamePi.csproj` only copies into `Content/Shaders` (and `EnableMGCBItems=false` keeps the content task from globbing `Shaders.mgcb` and failing on the Pi). `GamePi/Shaders/compile.ps1` compiles them on Windows (under `pwsh` or under the Windows PowerShell 5.1 a stock Windows has: 3.5 s on the owner's laptop, and its eight files were byte-identical to the ones CI had committed, 2026-10-05 — so a Windows machine at hand can stand in for the workflow); **`gamepi-shaders.yml`** runs it on every push that touches `GamePi/Shaders`, uploads the result as the run's artifact `gamepi-gl-shaders` and fails when it differs from what is committed (the compile is deterministic: byte-identical across two compiles). On the Pi a shader change is therefore edit, push, let the run fail, `GamePi/Shaders/fetch.sh` (the run's compile for HEAD, through `gh`), commit, push. ⚠ **One dynamically indexed uniform array per GL shader, at most**: mgfxc lays a shader's uniform block out in register order while MojoShader's GLSL reads each indexed array from a base of its own, and with two or more they were seen to disagree (reversed by name) - `Fireworks` and `Blast` read every array from another's slots and compiled without a word. Their ports take one packed array (`ShellData`, `BlastData`; `Fireworks.cs` and `Blasts.cs` pack it when the effect has that parameter), and `compile.ps1` refuses any compiled program with more than one `#define ARRAYBASE_` (its logic, run over the compile that had the fault, named exactly those two).
- **On the Pi, measured (#792, 2026-10-05).** From launch to the first frame (`nosplash`, `shot=0`, the PNG's time): **6.2 s**, three runs within 0.07 s - the desktop's 4.2, and no backdrop is built. labwc marks nothing unresponsive in that time. **Frame pacing stays the limiter's**: `FrameLimiter` targets the refresh + 3% and, with no DWM, its schedule alone paces the frame (`WaitForCompositor` is false). Vsync forced through Mesa (`vblank_mode=3`) was measured against it at 1080p on a 60 Hz panel: the frames take about 20-22 ms, so vsync halves them to 30 FPS and alternates 8 and 60 ms (per-second standard deviation 22 ms on Pennant), where the limiter holds about 45 FPS at 1.4 ms (Pennant) and 2-4 ms (Girandole).
- **Building it.** On the Pi: `dotnet tool restore` once in `GamePi/`, then `dotnet build GamePi.sln`, or `dotnet publish GamePi/GamePi.csproj -c Release -r linux-arm64 --self-contained` for a folder that runs with no .NET installed (475 MB, of which `Music/` is 351 MB). The logic tests (`dotnet test Tests/BS3D.Tests`) pass on the Pi unchanged (588). **`build.yml` builds it on every push** (#787), in a job of its own on an `ubuntu-24.04-arm` runner beside the Windows one: `GamePi.sln` in Debug and Release, the logic tests on ARM64 (Bepu's wide types are four lanes there, eight under AVX2), and a self-contained `linux-arm64` publish whose folder must hold the executable apphost, `libSDL2-2.0.so.0`, `libopenal.so`, the two content assets and `Levels/Levels.json`. Nothing builds GamePi itself on Windows; its GL shaders are compiled there by `gamepi-shaders.yml` (above).

## The solutions, the test project and the four root files

There are five solutions: `BS3DLibs.sln` (libraries only), `Testbed.sln`, `MapEditor.sln` and `Game.sln` (each executable plus the libraries it uses), and `GamePi.sln` (the Game's sources built for Linux ARM64, see "GamePi" above). There is one test project, `Tests/BS3D.Tests` (xUnit, plain `net10.0`, in `Game.sln` and `BS3DLibs.sln`, #586). It checks the invariants the libraries state "by construction": the neighbour rule, one constraint per pair (at the build and through 300 random landings and releases a level), the legacy padding's parity, the level round-trip, the save outcomes, the scoring mechanics and the top-level ceiling anchor. Run it with `dotnet test Tests\BS3D.Tests`; `build.yml` runs it on every push (see "The logic tests" in `docs/formats-and-tools.md`). There is no lint configuration. **Four root files configure every project at once** (#587, #594): `global.json` names the SDK band (`10.0.200`, `rollForward: latestFeature` — a floor, so a newer band still builds; both workflows install `10.0.2xx` so CI and the release compile with the band the owner does), `Directory.Packages.props` holds **every NuGet package version** (central package management — a `PackageReference` names the package and nothing else, so MonoGame, Bepu and NVorbis cannot drift apart between projects; bump a version there, never in a `.csproj`), `.editorconfig` the indentation and LF, and `Directory.Build.props` turns on `GenerateDocumentationFile`, so a `cref` that does not resolve, a stale `<param>` or malformed doc XML is a compiler warning (CS1591 and CS1573 suppressed; a project's own `<NoWarn>` must be `$(NoWarn);…` or it drops them — see "The doc comments are compiler-checked" in `docs/formats-and-tools.md`). `Prazsky.Core` references no Bepu: `Prazsky.BS3D.Physics` is the one library that does, so a `using BepuPhysics;` in Core or `Prazsky.BS3D` no longer compiles and the MapEditor no longer carries `BepuPhysics.dll`. Every executable's Debug build writes `bin\net10.0-windows\` and its Release build `bin\Release\net10.0-windows\` (the MapEditor's Release wrote over its Debug exe until #587).

## The workflows and the release

**Three GitHub Actions workflows run on `windows-latest`** (`.github/workflows/`) - the third is GamePi's `gamepi-shaders.yml` (#789, "GamePi" above) - and all are free because this repository is **public** — GitHub bills neither standard-runner minutes nor release storage on a public repo. `build.yml` (#387) fires on every push (except one touching only the agent journal or `Research/`), builds all four solutions and `Game.sln` once more in Release — the configuration players get — runs both gates (the level regeneration check refuses an untracked level file too) and, since #588, the "seen to fire" self-checks every push rather than by hand (`ScoreSim --ceiling-scale 0.25` must refuse, `WindingCheck --selftest`, the destructive-git guard's test and, since #657, `Tools/PathGuard.test.ps1` — the check every skill script's path arguments go through, because a Windows path typed unquoted into bash loses its backslashes and arrives as the drive-relative `C:foo`, which `New-Item` turns into a folder in the repository's root); since #787 a second job, on an `ubuntu-24.04-arm` runner, builds `GamePi.sln` and runs the logic tests on ARM64 (see "GamePi" above); it is what says `main` compiles on a machine that is not the author's. `release.yml` (#453) makes the download a player runs: a pushed tag `v*` publishes `Game` self-contained for `win-x64` (`dotnet publish -r win-x64 --self-contained`), asserts the published folder really carries the runtime, the compiled shaders, the levels and the music, zips it (one top-level folder holding **`BS3D.exe` and four folders, `Content`, `Levels`, `Music` and `Sfx`**, since #714 — 456 files, **397.9 MB** zipped from a 491 MB publish, measured on the release workflow's own rehearsal run on 2026-10-03; the old layout of 299 files and 17 folders zipped to 417.0 MB with the same content, and this sentence said **218.1 MB** on 2026-09-23 before the generated music grew: **`Music/` is 350 MB of the publish**, so most of the download is audio. It was 70.9 MB with the logo and 68.3 without before those tracks landed) and creates a **GitHub Release** with the zip attached (and, since #549, ScoreSim's score ceiling table beside it; since #588 a `SHA256SUMS` of both, and the level gate and ScoreSim run in the release job itself, so a tag on a commit whose gate fails publishes nothing) — nothing for the player to install, no .NET, no MonoGame, no DirectX redistributable. The "Run workflow" button does the same build and leaves the zip as a workflow artifact **without** publishing anything, which is how the pipeline is rehearsed. Only the Game ships; the Testbed is the instrument and the MapEditor an authoring tool. Deliberately **not** trimmed (Myra, FontStashSharp and the content pipeline all reflect) but a **single file** since #714: untrimmed, bundling removes no type, and what a player opens after extracting is one exe and its four content folders instead of a wall of 299 files with the right one somewhere in it (the check step fails the build on anything else at the top level). The `.pdb`s are embedded (`-p:DebugType=embedded`), so a crash report still names file and line — checked on the runner's exe by forcing a crash — and `Game.csproj` keeps the stale 2.1 runtime pack and apphost that `MonoGame.Framework.WindowsDX` still declares, and WinForms' 13 languages of translations, out of the publish. The exe is **unsigned** — a certificate is the one part of this that costs money, so SmartScreen warns on a player's first launch and the release notes say so. The notes open with a screenshot of the version when `Images/releases/<tag>.jpg` was committed before the tag was pushed — `Tools/release-screenshot.ps1 -Version v0.2.1` makes it (the Game built with the tag's stamp, one scripted run on a scratch profile, a JPEG; the default is the neon city's *Reel*, `-Level`/`-Menu` pick another) and the workflow links it at the tag's own ref, so the release keeps showing the build it describes; a tag without one still publishes. A build's name — `v0.2.1`, or `dev-<sha>` — is shown small in the front end's and About's bottom-right corner (`Game/BuildVersion.cs`, "The build's name" in `docs/game-shell.md`).

## The tools

Besides the three executables there are eight **tools**, all in `Game.sln` and all but two plain `net10.0` console apps with no graphics device. `Tools/LevelGen` is the generator that writes the game's pattern levels and the checks that say a generated level is playable before anyone plays it. `Tools/ScoreSim` plays every shipped level several ways through the real `ScoreKeeper`/`StarRating` and refuses a scoring rule that rates them wrongly — it exists because #173 found the star rating ordered backwards against skill on every level, a fault no individual number showed; since #549 it also refuses a score ceiling a simulated clear reaches and, with `--ceilings`, writes the table the online boards whitelist levels against, keyed by `LevelIdentity`. Those two exit non-zero on a failure so they can go in front of a commit; see "The level generator" and "The scoring simulator" in `docs/formats-and-tools.md`. `Tools/MusicBake` renders the game's six procedural pieces of music to .wav and prints what they measure (length, loudness, channel balance, where the energy sits, and a two-second envelope that says when a piece arrives) — it is not a gate but an ear (though since #464 it does refuse a limiter drive or a streamed render that drifted from the one-shot piece, exit 3 and 4, and since #467 a loudness meter off its standard, exit 5 — every table carries a K-weighted LUFS column beside the RMS, and `--shipped` prints it for every track in `Game/Music` without the masters): music is the one part of this game that cannot be judged from a screenshot, and hearing a piece in the game means playing a level of the right chapter for two minutes. It compiles `Game/Audio/ProceduralMusic.cs` straight into itself, so what it writes is the same arithmetic the About page's player plays. **Since #443 the music a level plays is generated recordings** (`Game/Music/*.ogg`, grouped into families by the name before the first dash and decoded to PCM when a family is first asked for, played by `GameMusic`), and `MusicBake --tracks` is what writes them — every master named `theme-<track>.wav` in `Research/AI-Music` (or in a `--masters` folder outside the repository, where the generated families' masters live since #486) brought to the themes' loudness, its peaks held under full scale, encoded as Ogg Vorbis (#444) and decoded straight back through the game's own decoder to check that every loop still has its exact length. `MusicBake --drums <wav> <recording>` writes a recording's separated drums beside it (`Game/Music/Drums`, #495), the layer the music turns up as the cluster nears the line. `MusicBake --sfx <wav> <name>` does the same for one generated **sound effect** (#482): `Game/Sfx/<name>.ogg`, mono, decoded back to prove its length — the shot, a landing, a release, the firework's burst, the victory fanfare, the ceiling's step (#500) and the line's cut (#434) are such renders since #482 (`--music` keeps a piece stereo and writes the key and tempo tags the star chime tunes to), and `ProceduralAudio` bakes any one whose file is missing ("The sound" in `docs/game-feedback.md`). `Tools/SemanticSearch` ranks the GitHub issues (and, with `--journal`, the agent journal; with `--docs`, the sections of the documents listed below, #490) by what they *mean* rather than by the words they share, through a local embedding model in LM Studio — run it before filing an issue, because #319 was filed an hour after #316 and #317 described the same levels in other words. It needs LM Studio running with `text-embedding-qwen3-embedding-0.6b` loaded — the default since #439, which measured it never worse than nomic on the English issues and far better on the Czech journal (see "The semantic search" in `docs/formats-and-tools.md`). Ask it before reading a whole document: on fifteen questions with a known section it put that section first twelve times and second twice. `--ask` then answers from those results through Gemma 4, citing them — a lead into the entry it names, never a source (#494). `Tools/DocDrift` lists the figures `docs/` and this file quote beside a name the code defines with another value — a hand-run triage sweep that always exits 0, never a gate: `dotnet run --project Tools\DocDrift` (`-- --all` adds the ones set aside as history; see "The number-drift sweep" in `docs/formats-and-tools.md`, #525). `Tools/LatticeProbe` (#674) answers the complaint that came back nine times — a procedural "random" field that a player's eye reads as a repeating grid and its author cannot see — by measurement: it scores tiles of a screenshot by their strongest spectral peak over the spectrum round it against the 99.9th percentile of pure 1/f² noise (`--selftest` holds it to synthetic fields of known answer, and CI runs that on every push), and `Tools/lattice-sweep.ps1` photographs the twenty-one scenes at pinned vantages through the Testbed and prints the table; an instrument, not a gate, and a column of zeros is not a clearance (see "The lattice probe" in `docs/formats-and-tools.md`). Two others check a convention below rather than a number (#400), and neither is a gate: `Tools/WindingCheck` (`net10.0-windows`, on DirectX's software rasteriser, no GPU and no window) builds every procedural mesh through its own constructor and judges every triangle's winding against its normals and by signed volume, and `Tools/VectorBoundary` is a Roslyn analyzer a build is pointed at to list every Xna/Numerics crossing through a conversion operator (see "The winding check" and "The vector boundary scan" in `docs/formats-and-tools.md`).

### The commands

```powershell
# Regenerate the pattern levels and the level set
dotnet run --project Tools\LevelGen\LevelGen.csproj

# Check the scoring still rates the shipped levels the right way round
dotnet run --project Tools\ScoreSim\ScoreSim.csproj

# Render every procedural piece of music to .wav and print the numbers (--no-write for the numbers alone)
dotnet run --project Tools\MusicBake\MusicBake.csproj -c Release -- --out C:\Temp\music

# Rebuild the game's music tracks (Game/Music) from the generated masters in Research/AI-Music
dotnet run --project Tools\MusicBake\MusicBake.csproj -c Release -- --tracks

# Write one generated sound effect into Game/Sfx (mono Ogg, decoded back to prove its length)
dotnet run --project Tools\MusicBake\MusicBake.csproj -c Release -- --sfx C:\Users\panrd\AI\sfx\out\482-picks\cannon-shot-c-11.wav shoot

# The issues most like #425, or like a drafted issue (--file draft.md), before filing one
dotnet run --project Tools\SemanticSearch -- --issue 425

# The sections of the documents most likely to answer a question, before reading a whole document
dotnet run --project Tools\SemanticSearch -- --docs "why are the shadow maps drawn before the scene target is bound"
```

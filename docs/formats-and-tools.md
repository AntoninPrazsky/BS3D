# Formats and tools

What is written to disk and what edits it: the map and level JSON, the map editor, the level generator, and the executables’ icon.

Part of the BS3D documentation. CLAUDE.md holds the project overview, the build commands, the ball grid and the repo-wide conventions, and says which of these documents covers what.

## Levels and serialization

The designer-meaningful tuning of every scene lives in **`SceneConfig`** POCOs (issue #44), one concrete subclass per `SceneKind` in `Prazsky.Core/Render/Config/`. **Since the format-2 refactor these are the scenes' FIXED parameters, in code and nowhere else** — a level names its scene and never carries a config, so a change to a scene's defaults reaches every level of that scene at once, with no file to regenerate. Only look/mood dials and particle/tree/building counts are exposed — mesh grid density and other hard limits stay as constants in `SceneRenderer`. `SceneRenderer` holds one config instance per scene and reads its values in `Apply*Parameters`/`Build*Buffers`, once, at load. There is no runtime re-apply any more: `SceneRenderer.Apply(SceneConfig)` re-pushed a scene's parameters and rebuilt the buffers it sizes for the map editor's live tuning panel, and #522 removed both (see "The scene-config panel (MapEditor)" below).

A **level** (issue #32, `Levels/Level.cs`) bundles a ball map with the **name of the scene** it plays in and the sky dome — everything needed to make a map play (and preview) as authored, and nothing that can be re-derived or that is fixed in code. It is a JSON object marked by `"format": "bs3d-level"`; `Level.IsLevelFile` is a cheap probe that tells it from a plain map file (both use `.json`), robust to a directory or unreadable path (returns false rather than throwing). The ceiling, physics statics and cannon/camera placement are **not** stored — they are all derived from the map size at load (`FitCeilingToMap` / `FitCannonAndGameCameraToMap`) — **and neither are the scene's parameters** (format version 2): version 1 serialized the active scene's whole `SceneConfig` into every file, and an audit before the change found every shipped level carrying pure defaults — tens of kilobytes per file restating what the code already said (`Colossus.json`, hand-authored, literally said `{"kind": "moon"}`). The one authored exception, the Testbed's `Level_SavannaDusk.json` test file, loads as a plain savanna now; its dusk lived mostly in its dome (13), which it keeps. Both executables **load** levels — the Testbed's `DeserializeMapFromFile` and the editor's `DeserializeMapFromJsonFile` probe and route a level through the scene/sky switch, a plain map through the layout-only path; the whole dispatch is wrapped so a broken or hand-edited file logs and leaves the running program untouched instead of crashing. The Testbed's startup `sky=` still pins the dome over a startup level's own dome. The **editor saves** levels (F4): the scene's name, the dome, the map — and the `music` and `author` a loaded level carried, which the old save silently dropped (the round-trip-unpins-the-theme trap this document used to record is fixed with the format).

A level may also name **which music it plays**, in a `"music"` field: a **family** of recordings in `Game/Music` — `"pulse"`, `"bohemia"`, `"nocturne"`, `"mural"`, `"ember"` and whatever families the folder gains (#486; #120 named the five procedural pieces, and `"dechovka"` still parses as an alias for `mural`, the piece that replaced it in #264) — or **one recording** by its file's stem (`"ember-punk-03"`), which pins it to that level. Leaving it out hands the choice to the set's own rotation, where a level's *position* picks the piece, so a set sounds varied without a single file having to say anything. That was the normal case until #194 and is now the exception: **every level in `Game/Levels` names its theme**, because the theme is a property of the campaign's five-level *block* rather than of the level, and because a rotation keyed to position means the order cannot be rearranged without silently rescoring the campaign — which is exactly what reordering into blocks does. It is a **string rather than an enum** on purpose, and for the same reason a scene is: the music lives in the game executable while this format is the shared library's, so the name is resolved against the folder (`GameMusic.SetTheme`), matched case- and whitespace-insensitively, and an unknown spelling falls back to the rotation instead of throwing a hand-edited file out. That fallback is silent and is the trap to know about here: **a misspelled theme does not fall back to Pulse, it falls back to whatever the level's position happens to give**, so it reads exactly as if the field were absent. `LevelGen` echoes each level's theme back off the *loaded* file for that reason, and groups its own printout by block so a block whose five levels disagree says so. One more edge worth knowing: **`MapEditor`'s F4 save used to drop `music`** (and `author`), so round-tripping a level through the editor silently unpinned its theme — fixed with the format-2 refactor: the editor captures both off a loaded level and writes them back (it still overwrites `name` with the chosen file name, deliberately). See "The rotation" in `docs/game-feedback.md`.

A level may also name **what its balls are made of**, in a `"balls"` field (#258): `"beach"` — the moulded vinyl beach ball the game has always drawn — or `"bubble"`, a hollow glass bubble with the type colour dyed into its film. Absent, which is what every level authored before the field says, is the beach ball, so no shipped file had to be rewritten and none was; unknown spellings read as absent rather than as a refused file, the leniency `"music"` and `"scene"` already take (`BallStyles.TryParse` also answers to `"bubbles"`, `"glass"` and `"vinyl"`, which is what a hand-editing author reaches for). It carries **no format bump**, deliberately: an older build ignores an unknown property and draws the level in vinyl, so the level still opens, still plays and still scores identically — a degraded *look*, which is what the version gate is for refusing when it would be a broken *file*, and the same argument admitted `"music"` at version 2. The map editor cycles it on **L** and writes it back on `F4` — and writes it **only when it is not the default**, so a round-trip does not start adding `"balls": "beach"` to every level in the set. What the style actually does to a ball is under "Ball rendering" in `docs/rendering.md`; nothing in the simulation, the lattice, the match rule or the score reads it.

The `"sky"` dome number a level carries is **inert for the four sky-replacing scenes** — space, the dream, the cavern and the Moon (`SceneRenderer.ReplacesSky`, issue #142): the dome mesh is not drawn there (each host guards `_sky.Draw` on the negation of `ReplacesSky`), the clear colour is black rather than the dome's horizon, clouds are suppressed, and each of those scenes' own `*LightingConfig` overrides the dome-derived light rig entirely (`SceneRenderer.TryGetLightRig`). The Moon keeps a ground under its replaced sky, but it sources its sun and fill from `MoonSceneConfig`, not the dome — so the number is just as inert there. A cavern, dream or space level plays identically with `"sky": 13` or `"sky": 1`; all the number still pins is `_skyDomeNumber` — what NumPad1 / B / the settings row cycle *from*, and what the editor's info line echoes — never a pixel. The field stays in every level file (it is uniformly shaped, harmless to carry, and means well as "the dome this level was authored against"), but a designer tuning one of these four scenes should not expect changing it to do anything visible.

A **`LevelSet`** (`Levels/LevelSet.cs`) is the tier above: a `"format": "bs3d-levels"` file listing level files **in play order**, so which level is first and which is second lives in one place rather than in a directory listing. Entries are objects (`file`, optional `name`, an optional `block` naming the chapter it belongs to, and the level's **rules** — `shots`, `minStars`, `ceilingStep`, and since #330 `wildcardEvery`) whose paths are relative to the set's own directory. The rules live on the entry rather than in the level file because this is the only place that can annotate a **plain map file**, which has nowhere to put metadata of its own. All four are **nullable, and null means "no rule" rather than zero** — a set authored before rules existed has to keep playing exactly as it did, and a sentinel cannot say the difference between "unlimited" and "none"; what each null falls back to is documented where it is *read*, not where it is declared. `Load` rejects a rule that is present but meaningless (a zero budget, a zero ceiling step, a negative star gate, a wildcard cadence of zero) rather than letting it surface as an unplayable level. `wildcardEvery` (#330) is the newest of them and the one that hands the player a **ball** rather than tightening a screw: one in every N balls dealt into the magazine is a wildcard, which is a free match, so how often one arrives is most of how hard the level is — which is precisely why it belongs beside `shots` and `ceilingStep` and not in the level file, where it would be a property of the picture. It carries no format bump on the ball style's argument (#258), with one honest difference: an older build ignoring it plays a **harder** level rather than a plainer-looking one, and no shipped entry authors it. `minStars` — the campaign star total the entry itself unlocks at — **replaced a per-entry `minScore`** that no shipped set ever authored (#111): a raw score is meaningless to a player as a target, and gating on the campaign's star total makes every level contribute. It sits on the entry it locks, so the picker reads each level's gate straight off it. (`Count` is `[JsonIgnore]`d — STJ serializes read-only properties, and every saved set used to carry a `"Count"` the loader then had to shrug off.) The game reads one set; the Testbed and the editor do not (they open whatever file they are handed). See "Levels in the game (Game)" in `docs/game-session.md`.

**`LevelIdentity`** (`Levels/LevelIdentity.cs`, #549) is **which online board a clear belongs to** (#542): an entry's `file` and a hash — SHA-256 over the level file's bytes followed by one line of the entry's rules (`\nshots=30;ceilingStep=5;wildcardEvery=-`, an absent rule spelled `-`), cut to its first 16 hex characters. A regenerated level or a retuned `shots`, `ceilingStep` or `wildcardEvery` changes the hash and starts a fresh board; a renamed `name`, a re-chaptered `block` or a moved `minStars` changes nothing. `wildcardEvery` is in it although #549 named only the other two, because a wildcard is a free match and its cadence is most of a level's difficulty. The **scoring rules** are not in the hash: they are `ScoreKeeper.RulesVersion`, sent beside it and bumped in the same commit as any change to a rate or a rule. The game computes the identity when it installs a level, from the bytes of the file it actually loaded, and prints it as the `[levels] Loaded` line's last word (`board One.json#113e5b5cdc39b7a9`). `Tools/ScoreSim`'s ceiling table is keyed by the same function, so the two cannot disagree — checked on levels 1 and 71, and a scratch program confirmed that `shots`, `ceilingStep`, `wildcardEvery` and one flipped byte of the file each change the hash while `name`, `block` and `minStars` do not. **Every carriage return is dropped before hashing, and nothing else is normalized.** The first cut hashed the bytes as they were, on the argument that the repository stores and checks out LF everywhere — and it does since 2026-09-21, but a checkout made before that keeps each file's old bytes until git next rewrites it: measured the same day, one such checkout held 280 tracked files CRLF in its working tree, **51 of them shipped level files** (and `Levels.json` beside them), and a local build copies those into its `Levels` folder as they are. Run on that checkout and on a clean `git archive` export of the same commit, the first cut's ScoreSim hashed **51 of the 120 levels differently — exactly those 51**; with the CRs dropped, **0**. Every submission from such a build for those levels would have been refused as an unknown level, silently. The release zip comes from a fresh runner checkout and is LF either way; the fix is for every build that is not.

**`PlayerProgress`** (`Levels/PlayerProgress.cs`, #92) is the save that measures a set: a `"format": "bs3d-progress"` file holding each entry's best score and best stars, keyed by the entry's `file` — the identifier that survives a renamed display name and a regenerated set (an entry a set no longer lists simply goes unread). The star total over the bests is what `minStars` gates against. Unlike every other loader here, `Load` is **lenient** — a missing, unreadable or malformed file comes back as a fresh empty progress, because an absent save is the normal case (a first run) and a corrupt one must cost the player their stars, never the game. `Save` still throws like `LevelSet.Save`; the game wraps it (`BS3DGame.SaveProgress`) and a failed write costs the write, not the session. Since #189 it also carries the tutorial's **`lessons`** — the keys of the lessons the player has completed (`"aim"`, `"fire"`, …, named by the game's `Tutorial` class), **null until the first**, on `skipped`'s own argument: a save with none round-trips as it did before the key existed, and an older build ignores it and simply teaches again, which is the safe direction. It is the save's and not the settings file's because it is a record of what the player has *done*, where the Tutorial row beside it is only whether they want to be shown the rest; `Reset` clears it with the stars. See "The tutorial" in `docs/game-feedback.md`.

**⚠ The save lives at `%LOCALAPPDATA%\BS3D\Progress.json`, and until #353 it lived inside the build output.** It was written beside `Levels.json`, which resolves to `Game\bin\net10.0-windows\Levels\` — gitignored, with no second copy anywhere — on the argument, stated in the class doc, that "progress through a set belongs with the set it measures". That argument loses to *a save must outlive the build output*: `dotnet clean`, a deleted `bin` to force a content rebuild and a fresh clone on the other machine are all routine here and all three took the campaign with them. It is now per **user** rather than per checkout, which also stops two machines' saves from pretending to be one file, and `LocalApplicationData` rather than roaming because a save describes *this machine*. `Game/UserData.cs` is the one place that answers where; `PlayerProgress` is handed a path and never asks. The **level set itself did not move** — `Levels.json` is content that ships with the build. **`userdata=<dir>`** (#546) moves every one of these files for one run, so a scripted run that clears a level or needs a particular setting never touches the player's own; see "Online scores" in `docs/game-session.md`.

**The write is atomic and keeps one generation back.** `Prazsky.Core.Tools.AtomicFile.WriteText` builds `Progress.json.tmp` in the same directory (`File.Replace` cannot cross a volume) and swaps it in with `File.Replace`, which demotes the previous save to `Progress.json.bak` in the same operation. It is in Core rather than in this class because `GameSettings` (#354) would otherwise have been a copy of it. The failure this guards is a torn `WriteAllText` — open, truncate, write — which on a machine lost mid-write leaves a short but *syntactically fine* file; this desktop hard-resets under GPU load (#250), so the window was not hypothetical. `Load` therefore tries the backup before it gives up, and comes back bound to the real save either way, so the next write never lands on the backup.

**And leniency made the loss silent, so `Load` now says what it did.** A wiped save and a first run produce the identical empty object and nothing could tell them apart. `PlayerProgress.Outcome` is one of `Fresh` (nothing was there), `Loaded`, `RecoveredFromBackup` (at most the last clear is lost) and **`Discarded`** — a file was there and none of it could be used, which is the one worth saying out loud; `BS3DGame.ReportProgressLoad` prints the last three. A save left in the old location is **adopted once** (`BS3DGame.AdoptProgressFromBuildOutput`, only when the new home holds neither the save nor its backup and the old file reads), byte for byte rather than re-serialized, and the old file is deliberately **left standing** — it was the only copy in existence, and losing it to the migration written to protect it would be a poor joke.

**But `Discarded` was still final within two saves, and that is #571.** The first write after it demoted the unreadable file to `.bak` and the second overwrote the `.bak`, so a save a *newer* build wrote — which reads as unreadable here, and this project runs older builds on purpose — was gone as soon as the player cleared two levels. Every player-file loader (`PlayerProgress`, `GameSettings`, `OnlineIdentity`, the online outbox) now calls **`AtomicFile.KeepUnreadable`** on a file that exists and does not read, before anything writes: a copy as `<name>.unreadable-<utc>`, which no write touches and nothing reads back — recovery is by hand — and one log line naming it (`[progress]`, `[settings]`, `[online]`; settings used to fall to the defaults without a word). The identity is the one where it matters most: its token is the only proof the boards' scores are the player's, and opting in again over a file that did not read minted a new one. The same change **flushes the temp file to the disk** before the replace (`File.Replace` is metadata, and a machine lost after it could leave the new file empty), **clamps the mix's rows** (`master`, `sfx`, `music`, `ambience`, `rumble`) to 0..1 on load, since they reach `SoundEffectInstance.Volume`, and routes **`Level.Save`, `LevelSet.Save` and `BallsMap.SerializeAsJson`** through the same atomic write with no backup (`backupSuffix: null`, so nothing extra lands in `Levels/`) — the editor saves hand-built levels through `Level.Save`. And a map whose ball has a colour or kind this build does not define is now **refused** with the cell named, where it used to hang an undrawn ball that could never match, so the level could never be cleared. Verified with a `userdata=` run over a version-99 `Settings.json`, a malformed `Progress.json` and a level with `"t": 14`: both files kept aside with their lines, the level refused, no crash; LevelGen still regenerates every level byte for byte and writes no `.bak`.

**`GameSettings`** (`Game/GameSettings.cs`, #354) is the save's neighbour: `%LOCALAPPDATA%\BS3D\Settings.json`, a `"format": "bs3d-settings"` file holding the player's answers — the four volumes, the exposure, the sky dome, fullscreen, the FPS counter, the FPS limit, aberration, film grain, the quality tier and whether the game may lower it on its own (#390) — and since #546 whether cleared levels go to the online score boards (`online`, off unless the player turned it on) and a `server` no settings row shows, which points a build at a local run of the score service and is the only way a local build submits at all. One directory, so there is one thing to back up. It shares `AtomicFile`'s write and the same read-the-backup-first leniency, for a weaker reason than the save's: an unreadable settings file costs nothing worth refusing to start over, so anything that is not one comes back as the defaults. The rule that governs it, and the two things it excludes (the adaptive probe's verdict, and **Unlock all**), are in "The settings page" in `docs/game-shell.md`.

**`Online.json` and `Outbox.json`** (#546) sit beside them. `Online.json` (`"format": "bs3d-online"`, `Game/Online/OnlineIdentity.cs`) is who this install is to the online score boards: a random `playerId`, a random 32-byte `token` in base64url and the `name` the player chose, written through `AtomicFile` with a backup. The settings page creates it at the first opt-in, renames it, and deletes it — with `Outbox.json` — once the service has forgotten the player (#548). It is **its own file and not a settings row**, because the settings file is rewritten by every settings click and restored by hand after scripted runs, and a token lost to either is a player who can no longer reach their own scores. `Outbox.json` (`"format": "bs3d-outbox"`) holds the clears not yet delivered, oldest first, each one the exact request that will be sent but for its `name`, which is restamped with the player's current nickname at every send (#572); it is written before anything is sent and emptied as the service answers. Both are lenient on read like the settings. What writes and reads them is under "Online scores" in `docs/game-session.md`.

Serialization is **System.Text.Json** throughout (issue #38; Newtonsoft is gone). STJ has no native multidimensional-array support, so `Balls3DArrayJsonConverter` reads and writes the exact nested `[x][z][level]` shape the legacy map files use (they were written by Newtonsoft, which does it natively) — a plain map file and a level's embedded map stay byte-shape-compatible, and legacy maps that omit the field dimensions still load (STJ defaults them to zero, and `BallsMap` then adds the extra bottom levels). A level's `"scene"` is a plain **name** since format 2 — the `scene=` command line's own parse keys (`SceneRenderer.TryParseScene`; `"neon"` for the neon city) — read and written by `SceneNameJsonConverter`, whose reading is deliberately lenient the way `music`'s is: an unknown name is a null scene (the consumer keeps its backdrop), and a **version-1 file**, where `"scene"` was a full `SceneConfig` object serialized polymorphically on a `"kind"` discriminator, still loads — the converter reads the object's `kind` (and its `Neon` flag, which is how version 1 told the neon city from the day one under one discriminator) and ignores every dial. The version bump to 2 exists for the other direction: a build older than the change refuses a new file with a plain versioned message instead of a polymorphism exception. `BallPositionType`/`BallPositionTypes` carry `[JsonPropertyName]` only.

**A cell may say what its ball *is*, beside what colour it is (#323).** `BallPositionType` grew one key, `"k"` — a `BallKind` — beside the `"t"` that has always carried the colour. It is written **only when it is not `Normal`** (`JsonIgnoreCondition.WhenWritingDefault`), so every map and level authored before kinds existed round-trips byte for byte and none had to be rewritten; absent means normal. There is no format bump, which is the same decision `"balls"` took in #258 and carries the same caveat, stated here rather than inherited: an older build opens a new file and plays it with ordinary balls, which has changed the *level* and not only its look. That caveat was written when the campaign's shipped files carried no kinds; **fifteen of the hundred and ten carry them today** — rock (Anvil, Cairn, Keystone, Obsidian, Seam), glass (Diadem, Facet, Harlequin, Solitaire, Trefoil), bomb (Vent, Sill, Paroxysm) and zap (Fume, Caldera, Paroxysm) — so the caveat above is a live case rather than a hypothetical: an older build opens one of those fifteen and plays a different level, with nothing on screen to say so. A kind is not a fourteenth colour and must never become one — see "Special ball kinds" in `docs/game-session.md` for the six things that would break.

## The music bakery (Tools/MusicBake)

`Tools/MusicBake` **renders the game's six procedural pieces of music to .wav and measures them, and builds the game's music tracks from the generated masters** (#443). `dotnet run --project Tools\MusicBake -c Release -- --out <dir>` writes `pulse.wav`, `bohemia.wav`, `nocturne.wav`, `mural.wav`, `ember.wav` and `menu.wav` and prints a table beside them; `--no-write` prints the table alone (it was `--no-wav` until #444), `--theme <name>` does one piece. Since #443 those pieces are the About page's rather than what a level plays (see "The music (Game)" in `docs/game-feedback.md`). **Two checks run with the table (#464)**: each piece's freshly measured limiter drive against the `LIMITER_DRIVE` figure a streamed render plays by (exit 3 on drift), and a second, streamed render of each composition against the one-shot one as 16-bit — within a step on every piece, exit 4 otherwise; see "The About page's player" in `docs/game-feedback.md`. **A third runs before every table (#467): the loudness meter held to its standard** — see the `lufs` column below — and a meter off it exits 5 without printing a row.

**`--tracks` is the other half.** Run from inside the repository, it reads every master in `Research/AI-Music/` — and in the folder `--masters <dir>` adds, where the generated families' masters live outside the repository (#486) — that is a track **by name**: `theme-<track>.wav` becomes `Game/Music/<track>.ogg`, `menu-loop-v2.wav` the front end's `menu.ogg`, and anything else is a reference and left alone (a table of eleven rows until #486). It brings a theme to the loudness the procedural pieces measured (−15.0 dBFS RMS, the menu loop to −19.5), bends any sample past −1 dBFS into the last decibel of headroom along a memoryless tanh knee, and encodes it as Ogg Vorbis at the master's rate to `Game/Music/<track>.ogg` (#444; 16-bit .wav until then) — printing the same table for every track, with a line under each saying the gain applied and the share of samples the knee touched. `--no-write` measures without writing, `--only <prefix>` bakes the tracks whose name starts so (one new family, not a hundred re-encodes), and `--quality <q>` overrides the encoder setting (0.59) for a trial, refusing 0.6 and up.

- **Every track it encodes it decodes again through the game's own `OggTrack`, and a second line says what came back:** the size and bitrate, the decode time, the decoded frame count against the master's, how many frames out the decode sits at the head and at the tail (a second of each matched against the master within ±2048 frames), samples the codec pushed onto the rails, the coding noise in the 2048 frames at each end of the loop against the rest, and how much the step from the last frame to the first grew. Under the table it gives the total size against the .wav it replaces, and the decode time one track after another and all at once on the thread pool as `GameMusic` loads them. **It exits 1 if any track's length or either end is out**, since that loop would jump or gap at every repeat.
- **Both halves of that check have caught something.** OggVorbisEncoder 1.2.2 dropped each track's first 1024 frames, because its buffer starts where libvorbis's pre-roll would be, so `EncodeOgg` writes half a block first. NVorbis 0.10.5 decoded Ember 80 frames long, so `OggTrack` stops at the stream's count.
  - **The alignment window is a second on purpose.** 8192 frames of Nocturne's opening, a sustained low note, matched best 726 frames out on a decode that was exact.
  - **The 0.6 limit is the encoder's too:** from there its coupled high residue is a copy of the low one, and at 0.8 the median SNR was 9 dB against libvorbis's 32. The measurements are under "The music (Game)" in `docs/game-feedback.md`.
- **The serial of each Ogg stream is fixed per track** rather than random, and a rebake of unchanged masters writes byte-identical files (checked on the desktop), so rerunning the tool leaves git nothing to commit. Another machine's JIT has not been checked for the same bytes. The masters are float and louder than the game's mix was tuned against, with peaks past full scale (−9.7 to −14.9 dBFS RMS, peaks up to +3.9); the knee is memoryless on purpose, so a loop cut sample-exact stays exactly as seamless. A generated track's row reads differently from a piece's in one place: its `head`/`tail` sit near its `rms` rather than at silence, because a loop runs straight on into itself — except the menu loop's, which predates the body-cut loops and dips there. **Adding a track is a master named `theme-<track>.wav`** (in `Research/AI-Music`, or in the `--masters` folder for the generated families); the game groups `Game/Music/*.ogg` into families by the name before the first dash, with no list of its own. The serial is derived from the track's name since #486 (it was the row's position, which moved when a master was added before it), so the eleven tracks of #443 re-encoded once to bytes that no longer move.

**`--sfx <wav> <name>` is the third half (#482): one generated sound effect into `Game/Sfx/<name>.ogg`.** The render — 32-bit float or 16-bit stereo, at the effects' 44.1 kHz or refused — is mixed to mono (the game's effects are placed by `Apply3D`, which takes a mono source), peak-normalised to 0.9, written through the tracks' encoder with both channels the one signal (the encoder and `OggTrack.Decode` are stereo-only, and a second channel of two seconds costs nothing; `ProceduralAudio.TryLoadSfx` reads one back) under a serial hashed from the name, so a rerun writes byte-identical files, and decoded straight back to prove the frame count; the exit code says whether it did. The loudness law is the game's own at load — a report through its bake's `Loudness` target, the rest peak-normalised (#498) — so the file holds the sound as it was chosen. `--music` (the victory fanfare) keeps the stereo image, estimates the key and the tempo — a Krumhansl-profile match on the piece's chroma, an autocorrelation of its onset flux over 70–180 BPM — prints the runners-up, and writes them as `ROOT` (a MIDI note) and `BPM` Vorbis comments, which `OggTrack.ReadTag` hands the fanfare player; `--root`/`--bpm` override them. Which four sounds are such files, and how a missing one falls back to its bake, is under "The sound" in `docs/game-feedback.md`.

It exists because **music is the one part of this game that cannot be judged from a screenshot**, and could barely be judged in the game either: hearing a piece there means playing a level of the right chapter for two minutes, and until #229 hearing the *same* piece twice was impossible by construction. Every number this document and `docs/game-feedback.md` record about the music was measured through a private baker reached by reflection from a throwaway harness, three times over (#119, #218, #264); this is that harness kept.

- **It compiles `Game/Audio/ProceduralMusic.cs` into itself** rather than referencing the Game project — with `MusicFade.cs` and `Spectrum.cs`, the fanfare's fade and the FFT, which the game shares and so keeps in files of their own — and calls `ProceduralMusic.Render`, the same door the About page's player goes through, so what is written to disk is the arithmetic that player plays and not a second copy of it. Its band table and that player's spectrum run on the one `Spectrum.Fft`. Since #444 it also compiles `OggTrack.cs`, the game's track decoder, and references the NVorbis version `Game.csproj` pins, plus OggVorbisEncoder (MIT, a managed port of libvorbis), so encoding needs nothing installed. A `ProjectReference` would drag WinForms, the MGCB content build and a Windows target framework behind a tool that writes audio files; instead it takes MonoGame the way `ScoreSim` does, compile-time only (the bakes name `MathHelper`, and nothing here touches an audio device).
- **What the table says**, a row a piece: length, render time, **where a level came in on the piece** while the pieces were the level music (`entry`, in seconds, #201 — `-` for the menu loop, which is a lobby and plays from the top, and for every generated track), peak and RMS in dBFS, **the integrated loudness in LUFS** (`lufs`, #467), channel balance, the mono fold's cost, then where the energy sits in six bands (under 100 Hz, 100–200, 200–500, 500–2k, 2k–6k, over 6k) as a percentage of the whole, then the RMS of the first and last half-second — which is what says a piece's repeat joins in silence rather than on a click. The bands are measured off the mono fold, since that is what a listener on one speaker hears.
- **The `lufs` column is ITU-R BS.1770-4's integrated loudness (#467)** — K-weighted, both channels weighing 1, mean squares over 400 ms blocks overlapping by three quarters, gated at −70 LUFS and again 10 LU under the loudness of what passed the first gate. It sits beside the RMS because the two disagree on exactly this game's material: the RMS weighs every hertz alike, and a piece whose energy sits mostly under 100 Hz, as most of these do, reads as loud as one whose energy is where the ear is most sensitive. The standard tabulates its two filters at 48 kHz only; `KWeighting` derives them from the analogue prototypes the table was designed from (libebur128's derivation), so one meter reads the procedural pieces at 44.1 kHz and the tracks at 48. **`CheckMeter` holds it to its standard before every table**: the 48 kHz coefficients against BS.1770-4's table (they agree to 1e-15), and five of EBU Tech 3341's minimum-requirement signals at both rates — a 1 kHz stereo sine at −23 and −33 dBFS, and three sequences whose right answer, −23 LUFS, only the gates give — within Tech 3341's 0.1 LU. Its failing branch was seen to fire: with the relative gate taken out, the third and fourth read −24.2 and the tool exited 5 (BestPractices §10).
- **`--shipped` prints the table for the tracks the game ships**, every `Game/Music/*.ogg` decoded through `OggTrack` at `GameMusic`'s 48 kHz (`--only <prefix>` narrows it), and under it the loudness range across the themes — the menu loop left out, being brought to its own lower level on purpose. It needs no masters, which since #486 mostly live outside the repository on the desktop, so it is the one way to put every track in one table on any machine; the "bake" column is the decode time. **Measured 2026-09-23:** the 118 themes read −15.7 to −11.9 LUFS, median −13.7, all at −15.0 RMS; the five procedural themes −12.8 to −13.6. What that settled is under "The music (Game)" in `docs/game-feedback.md`.
- **The envelope under each row is the arrangement as numbers**: the RMS of every two seconds of the piece in dB under its own loudest two seconds. A section 20 dB down is a hole; a piece whose first ten readings are all far down does not start for twenty seconds. That column is what #201's "it comes in long after the level starts" turned out to be, and it is the one measurement here that reads an arrangement rather than a mix. It is also what the `entry` column beside it is checked against: an entry is right when the reading it lands on is at the top of the piece's range rather than in its opening dip.
- **It is not a gate on the music** and exits 0 whatever the music measures, unlike the other two tools — it refuses only its own faults: a stale limiter drive or a streamed render off the one-shot one (3 and 4, #464), a meter off its standard (5, #467), a track that does not decode to its master's length (1). There is no number that says a piece of music is good; the point is to put the piece in front of an ear and the numbers beside it, and the numbers only catch the faults that are *not* about taste — a piece that would arrive louder than the one it replaces, a low end that has gone missing, an image that leans, a seam that would click.

## The semantic search (Tools/SemanticSearch)

`Tools/SemanticSearch` **finds the GitHub issues that mean the same as a piece of text**, through a local embedding model served by LM Studio, and the agent journal's entries too if asked. `dotnet run --project Tools\SemanticSearch -- "text"` ranks every issue, open and closed, against the text; `-- --issue 425` ranks them against an existing issue, which is the duplicate check; `-- --file draft.md` ranks them against a drafted one before it is filed. `--open` keeps to open issues, `--journal` adds `docs/agent-notes.md` and its archive, `--docs` adds the documents in `docs/` with `CLAUDE.md` and `BestPractices.md` section by section (#490), `--top N` sets the length of each list (8), and `--model`/`--endpoint` choose another model or server. It is in `Game.sln`, plain `net10.0` with no project references, since it knows nothing of the game's types.

It exists because a grep finds only the words you thought of. #319 was filed an hour after #316 and #317 had described the same three levels in other words, and the rule that came out of that — read the journal and the issue list again right before filing — only helps a search that happens to use the right words.

- **It needs LM Studio running on the machine**, with `text-embedding-qwen3-embedding-0.6b` loaded (`lms load text-embedding-qwen3-embedding-0.6b`, a 639 MB model; the default since #439, see below). Without it the tool says so and exits 3; a malformed command line exits 2. It is not a gate. **If `lms server start` answers `EACCES` on port 1234 after a reboot**, Windows has reserved the port (`netsh interface ipv4 show excludedportrange protocol=tcp` lists the ranges — 1136–1235 covered it on 2026-09-21); start the server on a free port and pass `--endpoint http://localhost:<port>/v1`.
- **Measured before it was kept (2026-09-16), and the two corpora came out very differently.** Over the 422 issues, seven issues with a known partner — a duplicate or a direct follow-up — ranked it 1st or 2nd four times (#319→#316/#317, #394→#395, #412→#342, #437→#330) and 9th, 11th and 53rd the other three, each time under issues on the same subject. Over the journal, six paraphrased questions whose answer carries an unambiguous marker put that answer 1st, 2nd (the one question asked in English), 9th, 62nd, 70th and 201st of 532 chunks, with the chunks scoring within a few hundredths of each other. That model, nomic-embed-text, is English-centric and the journal is Czech. That is why the journal sits behind a switch, and why `--model` exists.
- **The default became Qwen3-Embedding-0.6B on 2026-09-21 (#439), measured on the same questions, paired, with `--mark` reading the ranks off.** The issues, the known partner's rank, nomic against Qwen3 over 479 issues: #319→#316/#317 **1 / 1**, #394→#395 **1 / 1**, #412→#342 **1 / 1**, #398→#255 **9 / 3**, #425→#236 **4 / 3**, #437→#330 **2 / 1**, #422→#344 **1 / 1** — never worse, better wherever they differ. The Czech journal, the rank of the first of 707 chunks carrying the answer's marker: `ColourTransparentGroup` **83 / 49**, `StillEmission` **273 / 8**, `Kernel-Power` **1 / 2**, `CHEEK_INNER_X` **86 / 17**, `ResolveDisconnected` (the one question asked in English) **2 / 8**, `FunnelMesh` **10 / 2** — the answer in the top ten for 5 of 6 questions against 3 of 6, and nomic's two wins are the two it already had. The documents, #490's fifteen questions: nomic 11 first, 3 second, one 115th; Qwen3 **12 first, 2 second, that one 20th**. So one model serves all three corpora. Qwen3-Embedding takes an instruction on the *query* only (`Instruct: <task>\nQuery: <text>`, the documents bare), which the client sends for any model whose key contains `qwen3-embedding`. Cost: 639 MB against nomic's 84, and 112 s to embed the 1011 document pieces on the CPU alone (its GPU figure is unmeasured: the machine reset during that run). The nomic numbers above are today's, on today's corpora — they differ from the 2026-09-16 trial's because the journal grew from 532 to 707 pieces and #490 changed how a long paragraph is cut.
- **`--ask` hands the results shown to a local chat model and prints a short answer with the notes it came from (#494, measured 2026-09-21).** The model reads exactly the `--top` results printed above the answer — the corpora asked for, the issues only when no other was — so what it could not have known is on the screen; `--answer-model` picks the model (Gemma 4 12B by default), thinking off, temperature 0. Measured with the model on the CPU alone (`lms load google/gemma-4-12b --gpu off -c 16384`; the desktop had reset three times that morning), ten notes a question, 3.2k–8k prompt tokens, **53–134 s an answer**: on the six #439 journal questions the answer was right and cited the entry carrying the marker three times; twice it cited a *different part of the right entry* (the marker's piece ranked 17th and 8th, so `--mark` reports it as not cited); and **once — the marker at rank 49, outside the ten notes — it answered a neighbouring question confidently instead of saying the notes did not hold the answer**, which is the failure mode to expect: the instruction to say so was ignored. On four #490 document questions the answer was right and cited the right section every time. So the answer is a lead into the entry it cites and nothing more; the reader opens that entry, and an answer whose cited entries look off-topic is the sign that the ranking missed.
- **The issues are fetched live through `gh` on every run and never cached**, because a duplicate check that cannot see the issue somebody filed a minute ago is the #319 failure over again. The vectors are cached instead — one file per model and corpus under `%LOCALAPPDATA%\BS3D-Tools\SemanticSearch`, never in the repository, keyed by a hash of the exact text sent and written back with only what the corpus holds now, so an edited issue is embedded afresh and its old vector does not linger. The whole corpus goes through the cache even on a filtered run, so `--open` or `--issue` cannot drop a vector the next run needs. Measured: a first run with `--journal` embeds 422 issues and 533 chunks in 31 s; after that a run takes 4–7 s, nearly all of it `gh issue list`.
- **The texts are sent with the model family's own prefixes** — `search_document:` and `search_query:` for nomic, `passage:` and `query:` for e5, an instruction on the query alone for Qwen3-Embedding, none for a family the tool does not know — and clipped to 2500 characters, which keeps this project's English and Czech under nomic's 2048-token input. The journal is cut at its `## ` entry headings and then at paragraph breaks, and every piece carries its entry's heading, which is what dates a result; the documents are cut at `## ` and `### ` alike and labelled `section › subsection`, because a document's section runs to pages where a journal entry is one sitting. A paragraph longer than a piece is cut at its sentence ends rather than clipped (#490): these documents have paragraphs of several thousand characters, and a clipped one indexed only its opening.
- **The documents were measured the same way when they were added (#490, 2026-09-21).** Fifteen paraphrased questions whose answer sits in one known section put that section **1st eleven times and 2nd three times** — the sun shadows' draw order, the silent fallback of a misspelled `music` theme, the meshes' winding, `alt=`, the block name on a set entry, the About page's player, the recoil, the quality probe, cached effect parameters, the "38 FPS mountain", the drain funnel's mesh, ScoreSim's refusals, the wildcard clock, the editor's render pipeline. The one miss is instructive: *why the Testbed must never grow a menu* put CLAUDE.md's "Project" section 115th, because that piece packs the merge rule, the three executables and the Testbed's role into one text and the question matches a tenth of it — while the top hit was `docs/testbed.md`'s own opening, which answers it too. A question about what a section is *about* finds it; a question about one paragraph of a section that is about six things may not. 1010 pieces from 1.8 MB, 27 s to embed on the first run and 0.2 s over an issues-only run after that; a hit prints the first line of its piece under the label, since a section here can be thirty pieces long.

## The scoring simulator (Tools/ScoreSim)

`Tools/ScoreSim` plays **every shipped level several ways through the real `ScoreKeeper` and `StarRating`** and **refuses a scoring rule that rates them wrongly**. `dotnet run --project Tools\ScoreSim\ScoreSim.csproj [levels directory] [--ceilings out.json] [--ceiling-scale f]`; with no directory it walks up from its own bin directory to the first `Game\Levels` it finds, by landmark rather than by counting `..`, exactly as LevelGen does and for the same reason. It is in `Game.sln`, plain `net10.0` with MonoGame `PrivateAssets="all"` — it draws nothing.

It exists because of #173, and the shape of that defect is the argument for it. The rating was **ordered backwards**: the score rose with the number of shots taken, on every level in the pack, so the play style four of them are *designed* around was the one the stars punished. **Every individual number looked reasonable on its own** — the fault was only visible in the ordering *between* play styles, which is exactly what no amount of reading the code shows you. The levels had a validator and the scoring had nothing.

- **It models none of the scoring — it calls it.** So it cannot drift from the rules the way a written-down copy of them would, and a change to `ScoreKeeper` is felt here on the next run. It reads the **shipped set** for ball counts and budgets rather than carrying its own table, which caught three counts a hand-written table had wrong.
- **Three refusals, all with a non-zero exit** so this can go in front of a commit. **INVERTED**: an efficient clear rates no better than spending the whole budget — the #173 defect itself. **UNREACHABLE**: the best clean clear cannot earn four stars, which is what was reported from play. **UNEARNED**: a clear that misses one shot in three still earns four, i.e. the top of the scale means nothing.
- **Verified to actually guard**, which is the only thing that makes a guard worth having: put `MultiplierStep` back to 1 and `UnusedShotWorthInShots` to 1 — the pre-#173 rules — and it exits 1 reporting INVERTED and UNREACHABLE on level after level.
- A level with an **unlimited budget** is skipped rather than failed: it has no efficiency to rate and no completion bonus to earn, so the rating simply does not apply to it.
- **It states the online boards' ceilings (#549).** Every row ends with the level's `ScoreKeeper.ScoreCeiling`, the best simulated score as a fraction of it, and `minShots`. The header names the rules version (`Rules v1`). A fourth refusal, **OVER CEILING**, fires when a simulated clear reaches the ceiling. The service refuses a score over it, so the simulator reaching it means the bound is missing a term and real players would be refused. It was seen to fire, as §10 requires: with the ceiling cut to a quarter it refused all 120 levels and exited 1 — and `--ceiling-scale <f>` is that cut as a repeatable lever, multiplying every ceiling before the check and touching nothing written, so the gate can be seen to fire on any machine without editing the tool (`--ceiling-scale 0.25`: all 120 refused, exit 1).
  - **The ceiling is a bound above every reachable score, not the best clean clear.** Every term of the rules is taken at its maximum: the level's balls *and* every ball the budget can fire, each at the richest rate (the orphan's 20) and at ×5 throughout, plus the completion bonus for the whole budget unused but one. Counting the budget twice is what makes it loose. The simulator's best clears land at **0.44 to 0.53** of it on the 120 shipped levels, which also says no term is overcounted by orders of magnitude. The derivation is on `ScoreCeiling` itself, beside the rules it bounds, so the next rule change re-derives it in the same place.
  - **`minShots` is `ClearProbe`'s anchor-course floor (#458), stricter.** A ball on the top course can only leave in a match, and one shot matches one colour, so a level cannot be cleared in fewer shots than the colours standing up there. LevelGen drops that floor only for a special on the top course itself. Here any special anywhere drops it to 1: a blast can take anchor balls by geometry, a zap empties a colour off the whole field, and an infection repaints. Checked against the 21 clears LevelGen's probe actually played: the floor is **never above one of them and equal to 18**. Across the set it is 1 on 17 levels, 2–3 on 47 and 4–8 on 56, so a forged "cleared in one shot" is refused on 103 of the 120.
  - **There is no time floor**, though #549 asked for a `minSeconds`. Nothing in the game spaces shots out: `Shoot` has no interval between shots, and several can fly at once. The only duration floor that holds for every player is one flight, a tenth of a second, and no forged duration worth sending falls under it. A real floor needs a rule the game does not have (a fire interval), and that is the owner's call.
  - **`--ceilings <out.json>` writes the table** the score service loads (#543): a `"format": "bs3d-ceilings"` file carrying the rules version, the hash length and one row per level with a budget — `file`, `name`, `hash`, `rulesVersion`, `shots`, `ceiling`, `minShots`. A level with an unlimited budget has no ceiling and is left out, so the service holds no board for it. `release.yml` runs it and attaches `BS3D-<version>-ceilings.json` to every GitHub Release beside the zip, so the service can load the table of each game version players are actually running. Written even when a gate failed, so the table can be looked at; the exit code is what refuses it.

## The logic tests (Tests/BS3D.Tests)

`Tests/BS3D.Tests` checks **the rules the libraries state as holding "by construction"** (#586). ScoreSim and LevelGen's regeneration check gate the shipped *data*. Nothing gated the *rules*: the neighbour relation, one constraint per pair, the legacy padding's parity. Several bugs filed in #400's fourth pass were invariants of exactly that kind, and a playtest almost never shows them. Run it with `dotnet test Tests\BS3D.Tests`: **293 cases in about 5 s** (about 7 s with the build up to date). `build.yml` runs it after ScoreSim on every push. It is in `Game.sln` and `BS3DLibs.sln`.

**Why xUnit and not a `Tools/LogicCheck` console gate.** The house pattern is a console tool that exits non-zero, but here a test framework earns its keep. Most of these checks are one assertion repeated over every shipped level or every lattice cell, and `[Theory]` with `MemberData` gives each level its own named pass or fail. The console alternative is a hand-written loop that stops at the first failure or hand-rolls the report. `dotnet test` exits non-zero exactly as a gate should, so CI needs nothing extra. The packages come from NuGet like every other dependency, and nothing in the repository made them awkward. The project is plain `net10.0`, with MonoGame DesktopGL referenced compile-only (`PrivateAssets="all"`) exactly as `Tools/LevelGen` takes it. It references the three libraries and Bepu directly. It draws nothing and opens no window. It finds `Game\Levels` by walking up from its bin directory by landmark, like the other tools. **Tests run one at a time** (`DisableTestParallelization` in `Shipped.cs`): `BallsConstraintsBuilder.GetSphereShapeIndex` caches the sphere's shape index in two statics keyed on the last `Simulation` it saw. That is correct for a game with one simulation and a race for a runner that builds several at once. Serial, the whole gate still takes seconds.

What it checks:

- **Neighbours** (`NeighbourTests`, 5×5×6 and 6×7×7 fields, every cell of both parities as a centre). b ∈ N(a) ⇔ a ∈ N(b). No group holds more than four cells, and no cell is listed twice. Every neighbour lies exactly 1.0 from its cell in `GetRealPosition`, and every other cell of the 3×3×3 window lies further. The allocation-free enumerator and `CountOccupiedNeighbors` (over a seeded random occupancy) agree with `FillNeighboringCells`.
- **One constraint per pair** (`ConstraintTests`, **every shipped level** plus the Testbed's `Full.json`). Each level is hung as the Game hangs it, with `FitWorldOffset`, the kinematic glass and `BuildBallsStructure`. The solver's constraint count must equal the neighbour graph's edges plus the top level's balls. Every ball's stored handles must equal its occupied neighbours (plus one on the top level), which is how a failed `TryStore` shows, and every stored handle must exist in the solver.
- **Formats** (`LevelFormatTests`). Every shipped level survives `Save` → `Load` with its metadata and every ball's type, kind and position unchanged, and still builds a `BallsMap` of the same size and count. A ball of colour 14 or 0, or of an undefined kind, is refused with `InvalidDataException` when the map is built (#571; `Level.Load` itself does not look at colours). A legacy map with no `sx`/`sz`/`l` is padded by an even number of levels, and every layout level keeps its parity. A sized map whose gap below the layout is odd is grown by one.
- **Save files** (`SaveFileTests`). `AtomicFile.WriteText` keeps one generation as `.bak`, keeps none with a null suffix, and leaves no `.tmp` behind. `KeepUnreadable` copies the file. `PlayerProgress.Load` reports **Fresh**, **Loaded**, **RecoveredFromBackup** (bound back to the real path) and **Discarded**. The copy in `KeptUnreadable` holds the unreadable bytes, including a save a newer build wrote, and it survives the two saves after it (the #353/#571 incident).
- **Scoring** (`ScoringTests`). Every figure is derived from `ScoreKeeper`'s own constants, so nothing is a copy of the rules. The award is paid first and the multiplier raised after, capped at `MaxMultiplier`. A landing that matches nothing resets the multiplier and scores nothing. `Score` is `BaseScore` plus the streak bonus. The completion bonus pays `UnusedShotValue` for every unused shot. `ScoreCeiling` stays above a hand-built best run (the whole level down on the first shot, the rest of the budget unused). The floor clear rates one star, and the rating never falls as the score rises.
- **The top-level ceiling anchor of #561** (`TopLevelAttachTests`). `Anchor.json` is hung as above and left to settle for a second. One ball is then landed in its first free top-level cell beside an occupied one, the way SagProbe lands a shot: a body at the cell's world position, `PutBallAt`, then `AttachBallToStructure` with the world offset. After 6 s it must still sit within 0.1 of its lattice offset from that neighbour. It settles **0.009** off. The level's world offset is 7.57 long in X/Z, and the test asserts it is over 1, so a level whose offset happened to be near zero cannot pass for the wrong reason.

**Every test was seen to fail, as `BestPractices.md` §10 asks** (2026-09-26, each break made by hand, run, and reverted before the commit):

| Deliberate break | What failed |
|---|---|
| `FillNeighboringCells` drops its −X neighbour | symmetry, one-diameter, walks-agree, and the constraint count on all 130 levels and `Full.json` |
| `FillNeighboringCells` with the parity of `diagonalShift` swapped | one-diameter, walks-agree, constraint count. **Not symmetry**: a swap applied to both parities is still a symmetric relation, which is why the distance check exists |
| The per-group cap tightened to `<= 3` in the test | at-most-four |
| `BuildBallsStructure` connecting cross-level pairs from both parities | constraint count, all 131 cases |
| `ConnectOnSameLevel` not storing the handle on its second ball (the dropped-`TryStore` bug) | constraint count, all 131 cases |

Two of those runs are §10 lessons in their own right. A first try at the constraint break connected cross-level pairs twice only from level 1, and **nothing failed**, because no shipped level and not `Full.json` has a ball on level 1: the padded empty levels sit at the bottom. A break only proves a check if it reaches data the check actually reads. And a first try at the round-trip break ignored `"k"` and `"weather"` with `[JsonIgnore]`, and **nothing failed**, because an attribute that drops a field on write drops it on read too, so both loads agree. **The round-trip test proves that writing and reading are symmetric. It cannot prove that a field is persisted at all.** A field the reader never reads is invisible to it.

What it does not cover yet, from #586's own list: the 500 seeded attach/release/zap/bomb operations with `ClusterInvariants.Verify` (#585), `LevelSet.Load`'s refusals, the Testbed switch spellings, `BallKind` completeness (#584), and `Center()`'s midpoint. It adds no `Lattice` static either: that is a refactor of the parity arithmetic's copies, and these tests are what should stand guard over it when it is done.

## The number-drift sweep (Tools/DocDrift)

`Tools/DocDrift` finds **a figure the documents quote beside a name that the code defines with a different value** (#525). `dotnet run --project Tools\DocDrift [-- --all] [-- --root <repository>]`; with no `--root` it walks up from its own bin directory to the first directory holding `Game.sln` and `docs/`, as the other tools do. It is in `Game.sln`, plain `net10.0` with no project references, since it reads the tree as text.

It exists because the rule that a document changes in the same commit as the behaviour had nothing checking it, and a thirty-line scan found two figures that had quietly gone wrong on its first run (the space volume's `VOLUME_HAZE` was documented as 0.22 against 0.12, the storm's `PuffOpacity` as 0.40 against 0.30, both fixed in `98b553b`) and a third a day later (`MarbleMottle` 0.30 against 0.38, `90056a6`). The one claim in these documents a machine can check is a number beside a name.

- **What it reads.** Every named numeric in the tree: a C# `const`, a config property with an initialiser (`{ get; set; } = n;`), a `static readonly` scalar, a shader `static const` — a plain literal only, in `.cs`, `.fx` and `.fxh`, outside `bin`/`obj`. It keeps the names defined **exactly once** (about 2,870 of 3,340), since a name defined twice cannot say which value a document means. Then it reads `docs/*.md` and `CLAUDE.md` for a name in backticks with a figure **within 50 characters after it**, in the same sentence, with at most one word between them that is not a connector (`is`, `at`, `set to`, `of about` …) — "at `SHOOT_SPEED` the shot crosses 1.667 units" is a consequence of the constant, not its value.
- **`docs/agent-notes.md` and its archive are left out outright.** The journal is history by construction, and it is Czech with a decimal comma.
- **What it forgives**, because each one was a false alarm on a real document: a figure rounded to the digits the document gives; `~`/`about`/`≈` within 10 %; a range the value lies inside (`140–380`); `0.22 → 0.12`, where the figure the arrow ends on is the current one; a percentage, degrees against radians and milliseconds against seconds when the unit is written; a half-extent written `±600` for a 1200; a multiplier (`×5`) and a compound word (`8-ball`), which are not figures at all; and **a name list paired in order**, `YoungFraction`/`DeadFraction`/`BrokenFraction` (0.2 / 0.12 / 0.1) giving the n-th name the n-th figure — a list with fewer figures than names is skipped and counted.
- **History is filtered per sentence, never per line.** A paragraph in these documents is one line of several thousand characters, so a line-wide filter would silence almost everything. A disagreement in a sentence carrying *was, were, until, instead of, would have, before, no longer, used to, it read as, reads as, had been, formerly, previously, originally, dropped/raised/lowered from* or an issue number is set aside, not printed; `--all` prints those too, with the word that set each aside. **A bare "read as" and "rather than" are deliberately not on the list**: both are as often present tense here ("what makes the scene read as cloud rather than as a ceiling"), and with them the storm's `PuffOpacity` — one of the three drifts the tool exists for — was filtered away.
- **It always exits 0.** It reports; it is not a gate and does not go in front of a commit. At its first run on the tree (2026-09-25) it put **fifteen candidates** in front of a reader, two of them real, and set **23** aside as history, two of which were real too — so `--all` is worth the extra minute on a sweep. The rest are the shapes no filter here catches: history told without any of the words (the first figure of a paragraph that later states the second, "the numbers said the opposite"), a figure that is a measurement *of* the constant's effect (a rank in a table, a clearance computed from it), and a property's default quoted against the one instance that overrides it (`SpecularAmbientStrength` 1 by default, 0.03 on the drain). ## The winding check (Tools/WindingCheck)

`Tools/WindingCheck` proves CLAUDE.md's winding rule — procedural meshes wind **clockwise seen from outside** — mesh by mesh, without a frame to look at (#400). `dotnet run --project Tools\WindingCheck [-- --verbose] [-- --detail <text>] [-- --selftest]`. It is in `Game.sln`, and it is the one tool that is `net10.0-windows` with a real MonoGame backend: it runs the meshes' **own constructors**, and those upload straight into GPU buffers. It asks DirectX for **WARP**, the software rasteriser every Windows install carries (`GraphicsAdapter.UseDriverType = FastSoftware`), on a form that is never shown — so no GPU is touched and no window takes focus — and reads every buffer back. It loads `InstancedModel` from the Testbed's compiled content, so **build `Testbed.sln` first**.

- **What it builds.** Through their owners where an owner can stand alone, so the figures are the real ones: `CannonRig`, `ArenaIsland` (all eight island shapes, the drain, its rims, the pit, the drift), `CeilingPlate` (after a `Fit`), `BallRenderSet`, `ForestScatterRenderer`, `ForestFireflies`, `SavannaScatter`; every sky dome; and directly, at their call sites' figures, the meshes whose owners need a whole scene — the tropical palms, scrub, tufts, driftwood, rocks and moss caps and the bird of `SceneRenderer`, `CityRooftops`' five props, the unit box, the editor's wire box, both trophies and every letter `LetterShapes` supports. The owners' fields are walked by reflection for anything that is an `IProceduralMesh` (or holds one index buffer beside a positioned vertex buffer, as the dome does). **168 parts, 374,598 triangles** on its first run.
- **Two independent judgements per part.** *Against its own normals*: clockwise from outside means `(b − a) × (c − a)` points inward, so its cosine against the outward vertex normals must be negative; past **+0.25** a triangle is reported. That threshold is measured, not chosen: the parts wound backwards all sit near +1, and the only triangles between 0.05 and 0.18 are half of each quad in the baobab's foot flare, where the smoothed normals lean across the crease (`--detail Wood` lists them) — soft shading, not a flipped face. *By signed volume*, per welded piece that is closed (every edge shared by exactly two triangles, once each way): a correct shell encloses a negative volume. The second does not trust the normals at all, so it also catches a piece wound backwards whose normals were flipped to match.
- **The deliberate exceptions it names and still prints.** The sky dome (its captured order, seen from inside — CLAUDE.md), the editor's `WireBoxMesh` (wound inward on purpose, its `AddBox` doc says why) and the drain's `FunnelRimsMesh` — **wound wholly backwards**, all 2,560 triangles, and harmless only because its ribbons are drawn `CullNone` and nothing reads their facing: `TwoSidedNormals` is not set on that renderer. ⚠ Enrol the rims in `TwoSidedNormals`, or in any culled pass, and they shade from the wrong side; rewind the mesh first. The other `CullNone` sheets — palm fronds, bird wings, the drain's cone and pit — pass it anyway, and the cone and pit must, since `TwoSidedNormals` reads `SV_IsFrontFace`, as does the refraction technique the ceiling plate and the gun's glass go through.
- **Not covered:** the grids and heightfields `SceneRenderer` fills into buffers itself (all drawn `CullNone`: "the winding is moot on a heightfield") and the Game's particle quads (`Blasts`, `Fireworks`, `Confetti`, `LaserGrid`, `LineSparks`, all `CullNone`).
- **Its first run found nothing wound backwards** outside those three: 0 findings, 22 expected exceptions (20 domes, the wire box, the rims). It always exits 0; it is a sweep, not a gate.
- **Seen to fire, as `BestPractices.md` §10 asks.** `--selftest` judges a unit `BoxMesh` as built, then with every triangle's winding reversed, then with the winding *and* the normals reversed: both judgements pass the first, both fire on the second (12 of 12 triangles outward, the volume positive), and only the volume fires on the third — exit 1 unless all of that holds. On real data the twenty sky domes fire both judgements every run.
- **One trap:** every mesh here is uploaded `BufferUsage.WriteOnly`, and MonoGame refuses `GetData` on such a buffer with a managed check of its own (`NotSupportedException`) although the DirectX staging read underneath works. The tool flips the managed flag by reflection on the buffers it reads; nothing in the game does.

## The vector boundary scan (Tools/VectorBoundary)

`Tools/VectorBoundary` is a **Roslyn analyzer**, not a program: it reports **VEC001** at every crossing between `System.Numerics` and `Microsoft.Xna.Framework` that goes through a conversion *operator* rather than the named `ToXna()`/`ToNumerics()` of CLAUDE.md's convention (#400). MonoGame 3.8.5 declares an implicit operator for the inbound direction, and a crossing through it has nothing on the line to find — no regex can, the compiler's bound tree can. It is wired into no project; a build is pointed at it:

```powershell
dotnet build Tools\VectorBoundary -c Release
dotnet build Game.sln -t:Rebuild "-p:CustomAfterMicrosoftCommonTargets=C:\GitHub\Tools\VectorBoundary\VectorBoundary.targets"
```

`-t:Rebuild` because an up-to-date project is not recompiled and so not analysed. `IMPLICIT` marks a conversion the source never spelled, `CAST` one written as a cast. It is in `Game.sln` (a `netstandard2.0` project, as analyzers must be) and excludes itself from the scan.

- **Its first run (2026-09-25) found five, all in `Prazsky.BS3D.Physics`**: the contact offset and normal passed from Bepu's manifold into `IContactEventHandler.OnContactAdded` at both of `ContactEvents`' dispatch sites (four), and the deepest contact's offset queued by `BallContactEventHandler.OnContactAdded` (one). All five are `ToXna()` now — behaviour-neutral, the operator and `ToXna()` both copy X, Y and Z — and all four solutions scan clean. #400's first pass had called this boundary clean from reading the three files; the conversions it missed sit inside argument lists, which is exactly where reading does not see them.
- **Seen to fire:** the five above on the tree before the fix, and again with one of them put back by hand.

## The level generator (Tools/LevelGen)

**It refuses an option it does not know (#574), exit 2, before anything is written** — every flag used to be read by looking for itself, so `--sagg` or `--clearfiles=x` ran a full regeneration instead of the probe asked for and `-sag` became the output directory. The Testbed and the Game do the same for the command line they read, without refusing (a diagnostic must never stop a run starting): an argument nothing recognised, or whose value did not parse, prints `[args] Ignored '…'`, and the Testbed takes a leftover only for its map when it looks like a file, and says so when there is no such file.

**Every level of the campaign but one is generated, not drawn**: `Tools/LevelGen` (a plain `net10.0` console tool, in `Game.sln`, referencing `Prazsky.BS3D` and `Prazsky.Core` with MonoGame `PrivateAssets="all"` exactly as the libraries do) writes them and rewrites `Levels.json`. `dotnet run --project Tools\LevelGen\LevelGen.csproj [output directory]`; with no argument it walks up from its own bin directory to the first `Game\Levels` it finds. It always writes the **whole** set. The one exception is **Colossus**, which is hand-drawn: its entry's rules are stated in the tool verbatim and its own file — scene, sky and `music` — is authored, so the generator has no opinion about it beyond where it sits. (This said "Three to Seven … One and Two included" until #194, from when the pack was five generated levels between two hand-authored ones; One has been a design since it was regenerated, and "Two" is Colossus, renamed when it moved from second in the order to last.) The set's **unlock ramp** is the tool's too (`MinStarsAt`), and deliberately a function of the entry's *position* rather than of any design — which level a gate guards is a property of the play order, so a design moved in the order carries its new place's gate: the opener is free, the second entry asks 1 star, and from the third the ramp climbs 2 per level, so par (two-star) clears keep the road open with no replays while the most a player can hold at entry *i* is 4 × *i*. That survived the campaign growing from 14 entries to 25, to 30, to 35 and now to 40 without retuning, and it was checked rather than assumed each time: a player who two-stars everything ahead of entry *i* holds 2*i* against a gate of 2(*i* − 1), which clears by two at every position however long the set is, and the last entry's gate of 76 is still under half the 156 that four-star clears would have banked.

**The designs are one partial class split by block (#386).** Until #597 `Program.cs` was the generator itself — `Main`, the block tables (`BLOCKS`, `MUSIC_*`, `BALLS_*`), the set and its unlock ramp, `Emit` with every gate, and the `Design` type (see the next paragraph for where each went) — and each block's designs live beside it in `Designs/Block01_Meadow.cs` … `Designs/Block11_Mirage.cs`, each file with every helper that only its own block's designs use. A helper the designs of more than one block use is in `Designs/Shared.cs`, and moves there the day a second block starts using it. So a new design goes into its block's file, and a new block is a new file plus a row in the tables. It was one file of 17,511 lines until then, and the most-edited source file in the repository, so every parallel level change collided on it. Where each member went was decided by the reference graph off Roslyn's semantic model rather than by name — which is how `Picture` turned out to be the Gallery's alone while `PixelAt`, the part the Arcade and the Reveal also read, is shared — and the split was proven null rather than trusted: the moved lines are the old file's, line for line and in their original order, the class's 1,540 members kept their signatures, and the generator's whole stdout and all 111 files it writes came out byte-identical. Two things follow from it being a partial class. **A static field's initialiser must not read a static field declared in another of its files**, because the order in which a partial class's parts are initialised is unspecified; at the split four initialisers read another field at all (`BOLT_TIER_ODD`, `BOLT_TIER_EVEN`, `PLEAT_TIER_SHIFT`, `CUBE_GLYPHS`), each one declared earlier in its own block's file. And **`git blame` stops at the split unless it is told to look across files with a better diff**: `git blame -C -C --diff-algorithm=histogram <file>` (or `diff.algorithm=histogram` set once) reaches the commits before it and leaves little more than each file's new header and footer on the split — 12 of the Eruption file's 1,553 lines — where the default Myers diff leaves 1,550 of them there.

**The rest of the generator is split by what it does (#597), and only the designs stay in `Program`.** `Program.cs` (128 lines) holds the figures every design is drawn against — `FIELD_LEVELS`, `PICTURE_FIELD_LEVELS`, the ceiling-budget arithmetic, `HALF` — and `Cli.cs` (815) is the rest of `partial class Program`: `Main` with the unknown-flag refusal and the campaign's play order (the design arrays, which stay here because they are lists of `Program`'s own design factories), the `--sagfile=`/`--clearfile=`/`--arrival` runners, and `RunSagGate`. Everything else is its own type: `Design.cs` (170) is the `Design` a factory returns; `LevelEmitter.cs` (331) is `Emit`, `HollowOut`, `RepairLonelyBalls`, `ROCK_TINT` and `OutDir`, the directory everything is written to; `LevelGates.cs` (1,154) is `Validate` and every gate it calls, `MIN_GROUP` and `ONE_SHOT_PERCENT` with them; and `CampaignSet.cs` (499) is the `BLOCKS`, `MUSIC_*` and `BALLS_*` tables, `WriteLevelSet`, `DescribeBlock` and the unlock ramp. The block files reach the music and material constants through `using static BS3D.Tools.LevelGen.CampaignSet`, so no design body changed. The split was proven the way #386's was: the generator's stdout and every file it writes under `Game/Levels` came out identical, and so did `--clearfile=` and `--arrival`. Moving the gates into a library ScoreSim and the tests can reference is the step after this one, not part of it.

**A block exists in the data as a name on the entry** (`LevelSetEntry.Block`, #184): a run of **consecutive** entries carrying the same one is one block, and null on every entry — which is what every set authored before it says — means the set has no blocks and nothing celebrates one. Three candidates were weighed. A `blockSize` on the set would have been cheapest, but it can only make blocks all of one length and it gives the player's milestone nothing to be *called* — "BLOCK 3 COMPLETE" is a number where "THE TOWER COMPLETE" is a place. Grouping by the levels' own `scene` would need no new field at all, but a scene is a property of the level *file* while the grouping is a property of the *order*, so two sets sharing a level could not chapter it differently — and it would name a block after its backdrop, which is a coincidence of this campaign rather than a rule. The name says what the grouping is **for**, sits with the other per-entry rules for the reason those do, and needs no arithmetic to read. `LevelSet.Load` **refuses a name that opens a second run later in the set**: a block is a stretch of the campaign, so a name in two places is either a typo or a milestone that fires twice. `LevelSet` answers the five questions over it — `HasBlocks`, `BlockName`, `BlockRange`, `BlockNumber`, `BlockCount` — by walking the run on every call rather than caching a table at load, because a set is built in memory as often as it is loaded (LevelGen writes one it never reads back) and anything computed in `Load` would be absent exactly where a tool needs it. LevelGen sets it from the entry's **position** where it sets the music on each design, and the asymmetry is not an oversight: a theme is written into the level *file* so it must belong to the design, while a block is written into the *set*, which is built from positions — and deriving it from the position makes the blocks contiguous and equal by construction, which is the one thing `Load` refuses a file for getting wrong. What the game does with it is "Finishing a block of levels is its own moment" in `docs/game-feedback.md`.

Five things about this are worth knowing before touching it.

- **The scene pairings that moved, moved with an argument, and the arguments are in the code.** Six designs changed scene: One (savanna → meadow, because the savanna is the one campaign scene with point lights of its own and the level that teaches colour matching is the last whose colours should be tinted by the backdrop — and it misses 75 FPS at High on a 6900XT, #165, where the meadow's terrain is the cheapest in the game), Pinwheel and Gem into the meadow, Heart and Star into the savanna, Onion into the cavern, and Mosaic, Prism and Static onto the Moon. Two of those give something up and say so: **Star loses the wittiest pairing in the pack** (a star picture against the one scene whose own sky is already a star field), and **Mosaic keeps "dark" but gives up "enclosed"** — the Moon replaces its sky with black and drives its own light rig, so the CMY blocks are still the only saturated thing in frame, and vacating the cavern is what let the Reveal block have the one scene documented as chosen for being dark and enclosed.
- **A recorded decision is reversed.** The three pictures were deliberately *interleaved* with the geometric levels, "because they are all gentle by design, and three easy levels back to back is a lull rather than a ramp". They are a block now. What changed is the thing that reasoning rested on: in a flat ramp of fourteen a run of easy levels is simply a flat stretch of it, where a block is a chapter with its own scene, sky and music and a chapter of pictures is a change of register. The lull was real, though, and five gentle levels would still be one — so the block's two new pictures are the answer to it: **Elephant**'s symbol is drawn in three inks and **Zebra**'s in two, so neither has the single big payoff that makes the shipped three gentle, and the block's best single shot falls **40 % → 21 % → 9 %** across its last three levels.
- **Every chapter hangs a different material, and since #325 one material hangs two** (#258, #272). `Design.Balls` is a property of the *block* exactly as `Music` is — the material changes when the chapter does, not when the level does — and one `BALLS_*` constant states it for each chapter's ten designs. In play order: the Meadow **bubble**, the Gallery **wool**, the Coil **marble**, the Tower **ice**, the Reveal **vinyl**, the Quarry **metal**, the Nebula **plasma**, the Eruption **lava**, the Spectrum **porcelain**, the Arcade **gem**, the Mirage **porcelain** again. Each constant carries its own reasoning; the placements are not interchangeable, because two of the styles are scene-bound (the metal goes flat on a dome with nothing to mirror, the plasma washes out on a bright one) and the bubble is the only style dearer than vinyl, which is why it sits on the block with the smallest clusters (385 balls, against the Quarry's 959). **Ten materials against eleven chapters ends the one-each era by arithmetic**, and the reprise was chosen against the two ball *kinds* rather than against the scene: neither special takes the level's material, so a Mirage level is its style standing next to a ball with no colour and a ball that was never worked, and the glaze is the deepest colour and the most worked surface in the set — the widest gap from both at once. The traps the other nine would have walked into are on `BALLS_MIRAGE` (the bubble is transparency beside a transparent kind; the marble is stone beside a stone kind, and the granite's own separation from a marble is its roughness). A style is written into the file as `"balls": "<name>"`; a level that says nothing gets vinyl, so absent and `"beach"` mean the same thing to a reader and the writer omits the field rather than stating the default.
- **Nothing refuses a broken block.** The four validation gates below are per level; that a block's five levels agree on scene, dome, theme and ball material is not a property any of them can see. `WriteLevelSet` therefore groups its printout by block and reads the scene, dome and theme back off the **level files the game will load** rather than off the designs that wrote them, reporting `MIXED SCENES` / `MIXED` / `MIXED THEMES` where they disagree. Colossus is the level that makes this necessary: the tool does not write its file, so its `"music"` has to be authored in `Colossus.json` itself — it agreed by luck before this was noticed, because position 25 gave `24 % 4 = 0`, which is Pulse, which is the Quarry's theme. That luck is now gone **twice over, and independently**: #163 made it five pieces, which alone turns the same position into `24 % 5 = 4`, and #207 made it thirty entries, which moves Colossus to position 30 and gives `29 % 5 = 4`. Both land on Ember — so an unnamed Colossus would put the Quarry's finale on the rock ballad, which is the Coil's piece eleven levels earlier. The authored field is what holds it, which is the point of authoring it.
- **The Coil's dome was picked by looking, and the palette table would have picked the wrong one.** Five warm-sunset candidates were shot in the running game against the desert and three of them — 2, 10 and 18 — came out a **pink** within a hair of the mountains' violet, because a dome's fiery lower rings sit below the horizon where the scene's own terrain covers them and only its upper rings are ever seen. Dome 6 is the one of the eighteen that is cool where the ground is warm, which is the desert postcard and belongs to no other block. Dome 16 (a near-black zenith over pale sand) is the most striking frame of the six and makes the cluster pop hardest; it was passed over because it is darker than the violet dusk that follows it, which would make the next block a step back into the light.

### What a design is, and what the tool refuses

A design is one `Design` object: a silhouette (a predicate on the centred polar or taxicab radius, or since #130 on the **raw lattice indices**), a colouring, a scene, a dome, since #194 a music theme, since #325 a **kinding**, and the set entry's rules. The point of the tool is not the writing — it is that **the things that make a pattern level wrong are all invisible in a screenshot**, and each was got wrong here at least once:

- **Nothing may float free of the glass.** Read back through `Level.Load` and `BallsMap`, then `GetCellsDisconnectedFromCeiling` must be empty, or the layout drops the moment the level is built.
- **No colour's best shot may take the whole cluster.** Balls hang off the field's *top* level, so a same-colour group spanning it is the last anchor for everything below: one matching ball ends the level. The drop test releases a group on a throwaway map and counts what is orphaned with it; over `ONE_SHOT_PERCENT` (90) fails. Horizontal colour bands are the obvious way to stripe a cluster and are exactly this trap — Mosaic and Gem were both banded first and took 100%.
  - **⚠ It tries EVERY group of a colour, not merely the largest, and it did not until #98 — which is how a one-shot level shipped.** How much comes down is not monotonic in group size: a small group can be the cluster's last anchor while a much larger one merely hangs off it. Worse, testing only the largest had to break ties, and it kept whichever group of the winning size the scan reached first. `Column` is a 24-course column of horizontal bands whose anchor course is 21 balls of one colour and whose top two courses are one 45-ball group — **one shot took all 540 balls** — and the test measured one of the two *other* 45-ball groups of that colour and reported a comfortable 33 %. It had passed every run since the level was authored. The corrected test refuses it outright, and it refuses exactly one level in the pack: run over all forty, nothing else moved by more than a point. **A gate that is sound in principle and samples one case of several is worth no more than no gate at all on the case it misses.**
- **No ball may stand alone.** Cells on one level touch only their four **orthogonal** neighbours, never their diagonals, so a colour band one cell wide running diagonally is a string of balls that do not touch each other. A lone ball needs *two* landed balls to reach `MINIMUM_CLUSTER_SIZE`, which is a chore rather than a puzzle. The first Gem coloured its octahedron by `floor(m/2.2)` on the taxicab radius, which made its top layer's rim the single shell `m = 7` — twenty-eight isolated balls against the glass, with no level above to connect through either. Rings are two units wide now and every layer's rim stops on an odd `m`. `FindLonelyBalls` refuses the general case, and `RepairLonelyBalls` recolours the handful a rounded-off rim leaves behind (2 in Mosaic) to whichever neighbouring colour puts them in the largest group — a rim artefact belongs in the repair pass, a whole rim of them belongs in the design.

- **No colourless special may be unreachable, no glass ball may be a ceiling anchor, and no rock may hang from one** (#325, widened by #326 and #343; `FindStrandedSpecials`). A transparent ball is coloured, and a bomb detonated, by a shot landing in a cell *beside* it, and both count against the level being cleared — so either with no empty neighbour at all is a level that **cannot be finished while every other gate here passes it**: it does not float, it has no colour group to stand alone in, the margin is whatever the body's is, and no colour one-shots it. And glass on the field's top level is a ceiling anchor that *dissolves* — one shot beside it and the cluster's hanging width drops, which is #301/#302's failure mode with the one ingredient those issues did not have, namely that the ball gave no warning because it had no colour to warn with. Both are refused, and the walled-in half is stated as a PROPERTY — removable but not matchable, i.e. "a ball a landing beside it has to reach" — so the next special that answers it is gated the day it exists rather than the day somebody remembers this file. **The dissolving-anchor half stays glass-only**: a bomb up there costs the ceiling far more, but the whole of what made the glass case a refusal was that it gives *no warning*, and a bomb is a dark ribbed casing with a charge burning in it that only ever goes off because the player aimed at it. That is a trap the player can see and choose. **#343 added the third refusal and it is the one made for the player rather than for the ceiling**: a rock on that same course hangs off a socket nothing the player does can cut, so it is a ball that is on the field for the whole level whatever they do — and the walk skipped it twice over, once because it only ran on levels holding glass or a bomb and once because the rock is the one kind that answers *no* to `Removable`, which is the guard every later line of that walk sits behind. ⚠ A bomb within blast radius **would** take such a rock down (`DetonateBombs` makes a victim of any cell in reach whatever its kind), so it is not literally permanent in that one pairing; it is refused anyway, on this gate's own standing rule that it reads the level *as it hangs*. ⚠ **#396 widened that footnote without changing the refusal**: a bomb also goes off now when it loses its last path to the glass, so the ways a walled-in bomb might still be reached are no longer only the ones a player can aim at. The gate reads the level as it hangs and refuses all of them for the same reason it always did — a removal path that depends on the rest of the level collapsing in a particular order is not the guarantee #343 asked for. The gate is a design law and not a solvability proof: it reads the level as it hangs, and a buried glass ball could in principle become reachable once the body around it is cleared — that argument is true and is refused anyway, because a ball the player cannot see, reach or plan around is not a puzzle element on the shot it is buried. **#329 added a fourth refusal, and it is the first that could not be a property** — a frozen ball is opened by a **group being cleared** next to it, not by a shot landing beside it, so the walled-in test above passes it in silence on a level that can never be finished. It leaves that walk before the test and is asked its own question instead: has it a **matchable neighbour** (glass counts — one landing makes it ordinary). That is deliberately the *certain* half of the question, since a block with no matchable neighbour can never thaw in any order of play; the dynamic half — whether such a group is actually completed within the shots the player has — is not estimated here, because the sag probe plays the level for real and thaws through the same `ReleaseSameTypeCluster` the game does. Reported as `ice a group can ever reach`. ⚠ **The same change fixed a live gap of #328's**: the counts that decide whether this walk runs at all listed rocks, glass, bombs and zaps and had never been given the acid, so a level built of acid and colour alone skipped the whole gate — #343's own bug arriving through the next kind. Anything not matchable belongs in that list. **#331 added a fifth refusal and it is the first about a MATCHABLE kind**, so it too is asked ahead of the guard that would swallow it — the rock's own arrangement, arriving from the other side. A sick ball on the **anchor course** hardens into stone up there on the very first tick, and #343 already settled what a rock on that course is: a ball hanging off a socket nothing the player can cut, on the field for the whole level whatever they play. What makes the authored case a refusal is that it arrives with **no player agency at all** — a fait accompli handed over on shot one. Lower down it is fair, because the infection climbs and how many shots the player has before it gets there *is* the game being played. Reported as `infection off the anchor course`. ⚠ It is also the one exception to the census rule stated above: `BallKind.Infectious` is deliberately **not** counted as one of the specials that trigger this walk in the "anything not matchable" sense — it *is* matchable, so it needs none of what the walk asks — but it is counted towards running the walk at all, because that anchor-course question lives inside it. It caught two real faults while the Mirage was being written, and the second is the one worth knowing: **a hollow body stops being hollow when it gets small enough**, so Solitaire's shell — two taxicab units thick, clear on the outer one — became a *solid* ball five cells across at the tip, and cleared the whole tip left one cell with glass on all six sides. **#333 added a sixth refusal and it is the buried well's turned upside down**: a **heavy ball with an empty lattice under it**. A well needs open space around it or no shot ever flies near enough to be bent; a heavy ball needs balls *under* it or its twelvefold mass has nothing to pull on — and either way it is a special that does nothing, which is #344's verdict arriving through the tenth kind. It is asked ahead of the matchable guard for the third time running (a heavy ball is matchable, like the sick ball and the well), and the test is deliberately **one course down** rather than the whole load path below it: a single ball hanging off a heavy one already droops visibly, so anything stricter would be this gate deciding how much droop is enough — a design question that belongs to the sag probe, where it is measured rather than asserted. Reported as `heavy balls with a load`.

A design's field is `FIELD_LEVELS` (16) deep unless it says otherwise: `Design.FieldLevels` is what makes a **tall** level possible (Column is 34), and the emitter still refuses an odd layout offset, which would make the loader extend the field a level and move the design off where it was drawn.

**Since #325 a design also states a KINDING**, `Design.Kind` (polar frame) or `Design.BlockKind` (raw lattice), mirroring `Colour`/`BlockColour` and resolved in `Emit` alongside the colour rather than instead of it — the colour is still written for a rock or a glass ball, because the cell is not nullable and has to carry something, and neither kind reads it. Left null every cell is `BallKind.Normal`, which is every design written before the eleventh block. Six things in the tool had to learn about kinds, and one of them was a silent data loss:

- **`RepairLonelyBalls` skips them, and that is not tidiness.** A rock and a glass ball have no colour group by definition, so `GetConnectedSameTypeCells` returns an empty list for either — a group of *nought*, which reads to that pass as the worst lonely ball in the level. And the repair is `PutBallAt`, whose `kind` parameter **defaults to Normal**: without the skip, every special in the Mirage would have been "repaired" into an ordinary coloured ball, silently, with the level file written from the result.
- **`Validate`'s colour census is over the matchable balls only** — and a rock counted there would have entered `counts` under the colour its cell happens to carry and *never* entered `largestGroup`, since its own group is empty. The report loop indexes one by the other's keys, so a specials-only colour was a `KeyNotFoundException` rather than a wrong number.
- **`CountGroups` skips them too**, or each one counts as its own group and is never struck off (the walk that marks a group's members finds nothing to mark): Cairn's 253 rocks would have been 253 phantom groups and the budget ratio would have read a third of what it is.
- **`FindLonelyBalls` skips them**, glass having no colour to be lonely in and a rock never being matched at all.
- **Two denominators split.** Everything about what a *shot* is worth — balls a shot at par, and the one-shot percentage — is priced off `GetRemovableBallsCount`, because a rock never comes down to one; the anchor load stays priced off the whole cluster, because everything the glass carries weighs on it, rocks included. On a level with no specials the two are equal and every historical figure reads exactly as it did.
- **The sag probe had to learn all of it as well**, and it is the one that was measuring a different game. See its section below.

**The block that uses them states two laws, and they are mirrors** (`Designs/Block11_Mirage.cs`). **Glass goes on the skin** — never buried, never on the anchor course — which is what the gate above enforces; and **stone stops one course short of the glass, and what is left standing at the end is the stone**. The three facts a rock design is built out of: it stops the flood fill exactly like an empty cell (so a wall of stone divides one colour into two groups the player can *see*); **it may not sit on the anchor course** (#343) — that used to read "a rock on the anchor course is an anchor nothing can take, the one thing in this game that can only *improve* what `WorstAnchorLoad` measures", which was true and was answering the wrong question, since an anchor nothing can take is a good deal for the cluster and a ball the player can never be rid of; and it is not a ball the level is waiting for, so a field of nothing but rock is a **cleared** field, cut loose and dropped by `CheckLevelCleared` for no score. What the retraction cost is worth stating, because it is the argument the original rule rested on: `Obsidian` gave up a stone rim that made its anchor load unloseable, its measured load went 5.6 → 6.2, and the sag probe — the instrument that rim was implicitly insuring against — read **3, 1, 2 of 5 with the rim and 1, 2, 1 of 5 without it**, which is to say the insurance was never paying out. A wall's thickness is decided by the lattice and not by looks: a cross-level step changes `dx + dz` by −1, 0 or +1, so a **diagonal** plane one cell thick has a door in every course and needs three (Seam), where an **axis-aligned** one does not, an on-level step changing `x` by exactly one (Keystone's piers and Cairn's cross are one cell). And an axis-aligned wall is written `|dx| ≤ ½` rather than `dx == 0`, because the lattice shifts every other course by half a cell and an equality finds no column at all on the shifted ones.

**What the glass buys a designer is a shape no colour may take.** A colour band one cell wide running diagonally is a string of balls that do not touch each other — the lonely-ball defect above — and glass has no colour and therefore no group, so the rule does not reach it. Three of the Mirage's five glass levels are built on exactly that: a terraced gem outlined along its taxicab rims (Facet), three pyramids drawn in outline along their corner arrises (Trefoil), an argyle stitched along one diagonal family (Harlequin). The payoff figure is printed by the validator as **the best glass landing** — the most glass one shot can colour. A landing pays the shot plus what it colours: one is two and drops nothing, two is three and clears on the spot.

**⚠ That figure changed by an order of magnitude in #344, and the mechanic under it did.** The colouring used to stop at the panes touching the landing; it now runs through the whole connected **body** of glass (`BallsMap.ColourTransparentGroup`), so what one shot turns into one colour is no longer a pocket but a pane. The Mirage's five went from 4, 4, 4, 3 and 12 to **5, 34, 45, 50 and 116** — Solitaire's whole clear surface is one body. Two *different* bodies round one landing are both reached and so are summed; two panes of one body are one payment. The five designs were drawn when glass was worth a pocket, and Diadem needed its ceiling anchors widened a second time to stay under the sag threshold after it (see the note on its own design).

**#362 settled that question and it came out as one gate fix and one design change.** The owner's ruling: the spectacle is what #344 asked for and four of the five keep it; only the outlier was touched. **Solitaire, where one landing coloured 116 of 444 balls and brought 186 of them down, now has its four edges coloured** so each step's ring is four stacked facets instead of one ring, and a riser landing takes two facets rather than two whole steps — **21 coloured, 86 down (19 % of what can be removed)**, which is where Harlequin and Diadem already sat. The block's payouts now read **5, 34, 45, 50, 21** and its one-shot figures **26, 29, 19, 19, 19 %**. Its sag probe reads **3 of 5** on the level after the change, the figure it read before it. See `SolitaireKind` for why a taxicab ring is not connected within its own course, which is the fact the whole thing turns on.

**A picture is a different kind of design (#130), and four facts about the lattice decide how one is drawn.** Every other shape in the pack is a solid of revolution or a taxicab shape, solved from a centred distance; the three pictures — **Heart, Smiley and Star** — are flat walls with a symbol drawn across them, read off a bitmap written as text in the source, top line first, so a mistake in one is visible in the diff. They need `Design.OccupiedBlock`, the raw-index sibling of the `BlockColour` the colourings already had. `Picture()` builds the pair of lambdas from the bitmap, whose own dimensions are the wall's, so a new symbol is added by drawing it and nothing else; `#` is the symbol, `o` an accent for a symbol with detail *inside* it (the smiley's eyes and mouth — a hole would be background, and background enclosed by the symbol is a pocket the wall's own background cannot reach), anything else the background.

- **The picture plane is (x, level), and the wall is thin in Z.** The gun starts at +Z looking at the origin, so X runs across the screen and the level axis up it; a wall spanning X and *Z* instead would be drawn on the floor and seen edge-on.
- **It is two cells thick, not one.** Which diagonal offsets are a cell's cross-level neighbours depends on the level's parity, so a wall one cell thick in Z has half its vertical neighbours reaching to a Z that is not there. Two is the thinnest slab that holds whatever the parity, and it doubles every group, which is most of what keeps the strokes clear of the lonely-ball floor.
- **Rows are shorter than columns are wide.** Levels sit 1/√2 apart against a cell pitch of 1, so a bitmap drawn square comes out squashed to 71 % of its height. A picture is drawn about 1.4× taller in rows than it is meant to look — the heart is 14 rows for 13 columns and comes out very nearly square.
- **The symbol must not reach the wall's edge, and the top rows must be background.** This is the drop test's trap arriving from the *other* side, and it is what the first draft got wrong: a symbol filling the full width and touching the top row is one connected group holding everything under it up, and dropping it took **93 % of the level in one shot**. Background down both sides and across the top is what keeps the wall hanging when the symbol goes. The background is a 2×2 check of two colours for the same reason Mosaic's blocks are — one flat colour behind the symbol is the identical trap from the first side.

**How many inks the symbol is drawn in is the difficulty dial — and the background's palette is not.** That asymmetry is the whole finding of the Gallery block, and it cost two rounds of screenshots. A symbol drawn in *one* ink is one connected group by construction, so its own colour drops more of the wall at once than almost anything else in the pack: Star 40 %, Heart 42 %, Smiley 52 % — comfortably inside `ONE_SHOT_PERCENT`, and deliberate, because on a level whose point is being recognised the symbol coming away in one piece is the reward. The same drawing split across more inks has no single payoff at all: **Elephant**'s face took **21 %** of its wall and **Zebra**'s stripes **9 %**, where either outline in one ink would have taken half of it. That dial is free. (The elephant's face takes 38 % since #556, below: with no ground under the head, the trunk hangs off the face alone and leaves with it.)

The background looked like the same dial from the other side and **is not**. More ground colours does quarter every background group and does thin the magazine's draw — and it also *destroys the picture*. Measured by looking: the zebra over a three-colour warm check and the elephant over a four-colour one were both **unreadable**, because a symbol is drawn in the palette's least saturated colours (a zebra is black and white) and three or four saturated hues behind it mean the eye reads the check and not the shape. Both were fixed the same way — a **quiet two-colour ground**, cool behind the zebra so it is close in hue and luminance, warm behind the cool elephant so the contrast is hue rather than noise — and the difficulty moved onto the symbol's inks. So: two background colours, always, and never one; a picture level's difficulty is drawn in the symbol. A four-ink *scene* was tried too and dropped — a flat-crowned acacia with a low sun behind it and a band of ground under both, which passed every gate comfortably (420 balls, a 14 % best shot, the flattest colour spread of any picture) and did not read at all, because a wide flat crown, a sun and a ground band are three horizontal bands and horizontal bands at this scale read as bands. **A wall of 15 × 14 cells carries a symbol, not a composition.**

Mechanically, `Picture()` takes a *palette* of symbol colours indexed by `SYMBOL_INK` (`#o+=`) rather than the `symbol`/`accent` pair it had while there were three pictures. An ink past the end of a picture's own palette is refused rather than drawn as background, since a hole in a symbol is the one mistake in a hand-drawn bitmap that looks deliberate. (The three shipped bitmaps come out **byte-identical** through the palette form — verified on the emitted `map` of each.)

**No ground under a drawing (#556).** A full rectangle of check has a band of ground *under* the symbol, and once the symbol is shot away that band hangs by the margins alone and swings through the line — found on the Silhouettes (#491, which leaves such cells empty by rule) and then re-measured on the Gallery with the sag probe at each level's own budget and ceiling step: **Moon 3 of 5, Balloon 3, Paw 2, Elephant 2, Meerkat 1**, all but one of the eleven losses with the glass still at rest, and in every one the ball that went under was on the wall's bottom row, under the drawing (on Moon, Paw, Elephant and Meerkat on the symbol's own shot or the one after it). The Gallery's walls are shaped by hand, so the cut is drawn in the bitmaps with the space character (`PICTURE_EMPTY`), which `Picture()` honours for every picture since #556 — it was Balloon's own occupancy lambda until then. After: **Moon 1, Balloon 0, Paw 0, Elephant 0, Meerkat 0** (three sweeps each). Moon's one is a different loss, a ground group off the top-right corner leaving the right margin hanging off the crescent; Giraffe's 1 of 5, untouched, is another again (cutting all the ground under its head and neck still read 1). ### The sag gate: hanging a level instead of reading it (#301, #302)

**Every gate above reads the layout as authored, and all of them are true of a level that cannot be finished** — because none of them knows what the remainder *weighs*. That gap has now been found by hand four times (the Ziggurat's ring thickness, Garland's strand in #182, the Trellis's pitch and the Bolt's elbow plates in #253/#255), each time by hanging a level in the running game and watching it, and each time the note written down was the same sentence: *the gate that says the links exist cannot say there are enough of them to carry the weight*. #301 and #302 are that sentence one step later still — after a few shots have removed part of the mass — reported on nine shipped levels at once.

`Tools/LevelGen`'s **`SagProbe`** answers it by not reading the layout at all. It stands up the very simulation the game does — `PhysicsWorld`, the kinematic glass at `CeilingPlate.CentreYAbove`, the island's funnel floor, `BallsConstraintsBuilder.BuildBallsStructure` — hangs the level where `ClusterHang.FitWorldOffset` hangs it, and then **plays it**. The physics is entirely the game's: the same Bepu at the same `SolveDescription(8, 1)`, the same `BallSocket` lattice, the same 1/120 s step, the glass dragging the cluster down as it descends. After every shot the world is stepped while the matched group falls and **the remainder rotates into a new rest pose**, and the death line is read off the *live body poses* through the game's own `ClusterLineWatch`. It needs no graphics device; the simulation was never the part that drew anything. It is **opt-in** (`--sag`, or `--sag=Pylon,Orrery` to narrow it, which also turns on a shot-by-shot trace) because it plays whole levels five ways through a nine-hundred-body simulation, where every other gate here costs milliseconds.

**What is not simulated is the shot's flight.** Nothing is launched and no contact is waited for: the gun is a real `Cannon` (pose arithmetic with no renderer in it, seating its own trunnions off the island through the static `CannonRig.TrunnionHeightAt`), its line is swept against the live structure by `ShotPlacement.TryFindFirstHit` — the same sweep the game's landing preview runs — and the cell is `ShotPlacement`'s answer, so the ghost, the game and the probe cannot disagree about where a ball ends up. The landing then mirrors `BallContactEventHandler` step for step, including the order it had to learn the hard way (#265): the body is **put** in its cell before its constraints are made.

**The hang arithmetic and the loss rule had to come out of `GameplayScreen` for it** (`Prazsky.BS3D.Levels.ClusterHang`, with `ClusterLineWatch` beside it): a gate that hangs a cluster somewhere else, or forgives a dip differently, answers a question about a different game. That is exactly the fault #288 was closed on — an arithmetic that was correct about the wrong moment — and the point of sharing the figures is that the two cannot drift.

- **⚠ The probe's own first verdicts were all about a bug in the probe, and the shape of it is worth knowing.** `ReleaseSameTypeCluster` cuts constraints and only *then* wakes the balls it cut them from. In the game that order is safe by construction — a group is only ever released from inside the contact handler, on the frame a shot has just touched the structure, and the contact woke it. With nothing being fired, Bepu sleeps a settling cluster **in pieces** (the solver's active constraint count on a 502-ball level falls from 3836 to 2740 over four seconds of hanging still), so waking one ball wakes one island of several — and cutting constraints out of a sleeping island left the survivors holding a graph the solver never re-examined. The remainder came apart and fell at three quarters of gravity. The game's own note that *"one ball is enough for the cluster — the structure is a single connected constraint graph"* is true of the game and false of a probe that fires nothing, and `WakeCluster` therefore wakes every ball.
- **What it found, and it is 9 for 9**: every one of the nine levels reported in #301 and #302 sags, seven of them **with the glass still at rest** — which is the owner's own reading confirmed against the machine, and it rules `CeilingStep` out for good. Pylon and Bolt and Ghost go under on their **first shot**.
- **⚠ Its first model condemned three levels that play perfectly well, which is how the player half came to be rebuilt.** Asked "does any order lose this level" while it picked groups to delete, it lost **38 of the 90** shipped levels — Amphora, Giza and Saturn among them, all three then confirmed finishable from play. That refutation is what the rest of this section is about.

**⚠ The physics was never the hard part. The player was, and every wrong verdict this probe printed came from that half** — three faults in a row, each found only by being refuted:

- **It picked a group and deleted it.** That let it cut a vase's waist and leave the foot dangling: on Amphora it took a 57-ball group out of the middle on the first shot, with all twenty ceiling anchors intact and nothing orphaned, and the foot — cells with two lattice neighbours apiece — stretched five levels down. **No gun can make that cut.** The gun stands underneath and shoots up, which is what `TALL_AIM_HEADROOM_LEVELS` already says out loud (*"the column has to be eaten from the bottom"*); `SagProbe.AIM_BAND_LEVELS` is that constant and the aim is held to it.
- **It aimed at balls it could not see.** Pointing the gun at a ball deep in the body meant `ShotPlacement` dutifully landed the shot beside whatever the *line* met first, usually another colour entirely — so almost nothing matched and the cluster **grew** while being cleared, 502 balls to 513 over eighteen shots. A candidate is only taken now if the sweep comes back holding that very ball.
- **It was handed a zero orbit centre.** `Cannon.RecalculateRotation` builds its aim target as `Position + Transform(OrbitCenter, rotation)`, so that vector is doing double duty — a direction *and* the distance the aim point is thrown out to. Zero aims the gun at its own trunnions, `AimDirection` normalises `(0,0,0)` to NaN, and the probe fired nothing at all while scoring every level as survived. Both executables construct their cannon with `(0, 5, 0)`; so does this.

Two more followed once it was firing, and both were found the same way — by reading a trace rather than by thinking about it:

- **A bounce ended the run.** A shot that finds no free cell in either ring is the game's own bounce and costs a shot; the probe read it as *"this level cannot be played on"* and stopped, once with 946 balls still hanging, and scored the level as survived. The same shape of silent false pass as the NaN aim: a probe that stops playing reports no sag.
- **It aimed at a ball rather than at a gap.** Pointing at a ball's centre lets `ShotPlacement` land the shot in whichever cell of the ring the contact falls nearest, which is very nearly arbitrary — **29 % of shots matched**, the other 71 % stuck to the underside, and on Pylon the probe walked a column of its own misses six levels below the layout's floor and into the death line at shot 41. Then reported the *level* as sagging. Candidates are **empty cells** now, the matching ones first: **86 %**.

The model loads a colour the way `RandomBallType` does (uniform over the colours still standing, count-blind), aims at the gap, prefers the one that completes a group, and lets the shots that complete nothing **stick** — which is what puts balls back onto the underside, and is the difference between a probe and a wrecking ball.

**⚠ A sixth fault, of the same family and found the same way: the probe was playing a different game from the one the Mirage ships (#325).** It does not run `BallContactEventHandler` — it lands a ball straight into the lattice — so every *step of a landing* that lives in the handler has to be repeated in it or it silently diverges, and the transparent ball's colouring is exactly such a step. Without it the glass could only ever leave a cluster by being **orphaned**: two of the five glass levels came back as layout faults (5 of 5, glass at rest) and the block's opener came back as a level that clears in ten shots. Three lines had to move, and each one is the handler's or the game's rule arriving late:

- **`ColourTransparentGroup` between the attach and the group check**, which is the handler's own order and the whole of where it may go, plus the same call inside `WouldMatch` with an exact undo — otherwise the probe cannot *see* the shot the kind exists to make worth taking, and ranks every glass pocket as "sticks but does not match".
- **`LoadedColour` over the matchable balls only** (`RecountBallTypes`'s rule). A rock carries a colour in the file that nothing reads, so counting it loaded the barrel with slate on all five stone levels — a colour no matchable ball in any of them wears, so about one shot in five was unmatchable by construction and every one added a ball to the underside.
- **The run ends on `GetRemovableBallsCount`, not `GetBallsCount`** (`CheckLevelCleared`'s rule). A rock is not a ball the level is waiting for, so a probe asking for an *empty* field plays every rock level to the end of its budget and reports `OutOfShots` on a level the player had finished.

**#326 is the same lesson arriving on purpose rather than by discovery**, and it is now the rule to apply to every special that follows: *a step of a landing that lives in the contact handler has to be repeated in the probe, or the probe is measuring a different game.* The bomb's detonation is such a step, so `FireOneShot` collects the armed bombs before the release and detonates after it, in the handler's own order; and `WouldMatch` answers **true for any cell that arms a bomb**, before the lattice is touched, because a blast is not a colour question at all — without that the probe ranks every bomb-adjacent gap as "sticks but does not match" and only lands there by fallback, which underrates the one shot a bomb level is played on. **That day came with #369, so the parity is load-bearing now rather than waiting.** It said "nothing in the shipped set has bombs in it, so the pack's figures are unchanged" until 2026-09-13, and the Eruption's five new levels had made it false six days after it was written (2026-09-01, against the #368/#369 merge of 2026-09-07): the campaign ships **three levels with live bombs** — Vent (8), Sill (5) and Paroxysm (6, beside its eight zaps) — so the sag answers those three were tuned against are answers from a probe that arms and detonates in the handler's own order, and the same probe without this parity would have been reading a different level on exactly the shots the block is built around. ⚠ **The scoring side of the bomb is still unmeasured and this is not the place that measures it**: `ScoreSim` plays all three through the real `ScoreKeeper` and reports the whole set rating the right way round (re-run 2026-09-15), but its model lands every shot as `Landed(balls, 0)` and so never destroys a ball — see "a destroyed ball is a third scoring category" in `docs/game-session.md`. #396 made that gap **wider rather than deeper**: the orphaned-bomb trigger adds landings that are part orphan and part destroyed, which this model cannot produce even in principle, so it still says nothing about the rate either way.

**⚠ #329 is the first special that did NOT need that rule applied, and the reason is worth taking to every kind after it.** The frozen ball's ice breaks when a group is cleared beside it — so the trigger is *the release itself* rather than the landing — and the rule was therefore written inside `BallsConstraintsBuilder.ReleaseSameTypeCluster`, the one place in the whole game where a group is cleared. The probe calls that method, so it thaws correctly with **not one line added to it**, and so do the Testbed and the Game. Four kinds in a row had to be taught to this file one at a time (the glass, the bombs, the zaps, the acids), each an opportunity to measure a different game, and the fifth cost nothing because its rule was keyed to a *call* rather than to a call site. Where a new kind's trigger allows it, that is the shape to reach for.

**#396 is the second time that shape paid, and the first time it paid on a rule that REVERSED one.** An orphaned bomb now detonates instead of falling — the opposite of what this file's own comment said in so many words ("a bomb the release orphans has already fallen and must not go off in mid-air", which was the handler's sentence repeated here, as the rule above requires). Because the new trigger is keyed to *the disconnection walk* rather than to the landing, it went into the one pass all four removals end in (`BallsConstraintsBuilder.ResolveDisconnected`) and the probe needed **no line** — only the comment, which was a fifth copy of a "why" that had stopped being true. ⚠ **What did move is the probe's own figures for the three levels with live bombs**, and they were re-measured rather than assumed: on the same `--sag=Vent,Sill,Paroxysm` run, before and after, all three still report **sagged 0 of 5 and a cleared worst run** — the verdict is unchanged — while the individual numbers wander (Vent cleared in 23 shots against 26 and stood 2.68 off the line against 0.90; Sill 41 against 33 and −0.43 against −0.12; Paroxysm 10 either way, −0.97 against −0.75). They wander because these are **different playthroughs and not an A/B**: the first orphaned bomb changes the field, and every shot the model picks after it is picked against a level the other run never saw.

**⚠ #332 is the first time the probe's own AIM had to change rather than its landing.** A gravity well bends a shot, so a probe sweeping a straight line on a field with wells lands its shots where the player's would not — and it would do so silently, reporting a layout fault that is really its own aim. It sweeps with `ShotPlacement.TryFindFirstHitCurved` off the level's own wells now, refreshed once per shot. That also makes it **the dynamic gate for how many wells a level may carry**, since `AimReachability`'s straight-line answer is necessary but no longer sufficient on such a field (see that class's own remarks). The static half is the generator's refusal of a **buried** well — one with no open space inside `GravityWells.RANGE` of itself, which no shot can ever fly near and which therefore bends nothing.

**⚠ And #331 is the first step of a shot's resolution that is not a step of a LANDING at all**, so it lands back on the original rule with a twist. The infection ticks once per **resolved shot**, hit or miss, which means it sits in this probe's shot *loop* rather than inside `FireOneShot` — a bounce is a miss and ticks it too. What it does to a measurement is the largest thing after a zap: a sick ball hardens into stone, so the cluster **keeps its mass and loses the ability to shed it**, and a level that rots faster than it can be cleared shows up here as `OutOfShots` rather than as a layout fault. That is deliberate — the sag probe is now the dynamic gate for how many sick balls a level may seed, because no static check can answer it.

**⚠ #333 is the first kind that needed NOTHING repeated here at all, and the first whose sag is DELIBERATE.** A heavy ball is a mass and not a rule — the kind reaches one line in `BallsConstraintsBuilder` and nothing else in the game knows it exists — so the probe hangs it correctly by standing up the same simulation, with not one line added. What it *did* need is the opposite question, and it is the one #333 put to this file: **a probe that reports sag, reporting a sag somebody asked for.** Neither the threshold nor the death line moves for that — a branch under the line has lost the level whether the weight on it was designed or was an accident, and forgiving an authored sag would be forgiving a level nobody can play. So what was added is **attribution**, not tolerance: a level carrying heavy balls is hung a **second time with every one of them weighing what an ordinary ball does** (`SagProbe.HeavyBaseline`, which rewrites the kind through `BallsMap.PutBallAt` — the mass being the whole of the kind, that *is* the same level with the mechanic switched off), and the gate prints both readings plus the difference between them. Then the two say it outright: **if the baseline sags too, the layout is the fault and the mass is a passenger; if only the loaded pass sags, the design has hung too much off its heavy ball.** ⚠ It is deliberately **not** a figure authored beside the level, which was #333's other suggestion: a number written down by hand goes stale the first time a design moves — this file records that failure twice already — and a second run of the same simulation cannot. ⚠ And the difference is read against this probe's own noise: measured on a real level with its four lowest balls made heavy, the mass was worth **−0.04 of clearance** with the loaded pass sagging 1 of 5 and the baseline 2 of 5, which is inside the run-to-run wobble the calibration section below documents and therefore says *layout*, not *mass*.

**`--sagfile=<path>[,<path>]` hangs level FILES instead of set entries** (#333), generating nothing at all: it probes what it is given and exits. The set *is* the campaign, so a level built to try a mechanic on is never in it, and until this existed the only way to put one in front of the probe was to edit the campaign — which the next run of this tool overwrites. Its two pressures are stated rather than read, since a file outside the set carries neither: no budget (the run ends when nothing removable is left standing) and a glass that holds still, which is the gentler pair on purpose — what such a level is being asked is whether its own shape hangs. Same shape as the Game's `levelfile=`, and for the same reason.

**And what it then found is a lesson about rings.** Over the whole 105-level pack the corrected probe reported exactly one level, and it was one of the new ones: `Diadem`, 5 of 5. The obvious diagnosis was wrong twice — four pendulums six courses long hanging off a coronet, so the stems were shortened (still 4 of 5) and the ceiling step widened (no change). The trace says why: the untouched cluster starts **7.7 above the line** and goes under on the shot that releases sixty balls at once, so it is a **swing** and not a sag — and what a ring is short of, against a solid body of the same width, is **ceiling sockets**. Its inner radius went 3.6 → 2.6, i.e. **80 anchors to 100**, and it reads 0–1 of 5 from the first probe after. The `anchor load` column below is the figure that would have said so in advance.

**⚠ And the probe answers a different question from the one a budget is priced against, which #414 is (2026-09-19).** The sag probe asks whether the cluster **survives** — whether any order walks it into the death line. A level can survive every order and still be one the player runs out of balls on, and Causeway was exactly that: **0 of 5 losing orders**, its own design doc calling the budget measured and safe, and the owner's report from play was *"players often run out of balls"*. Both were true. What nobody had named was the **clear margin**: how many shots the dearest order that actually *cleared* the level left unspent. Causeway's was **one**, which is inside what a single ricochet or colour misread costs.

The number was readable all along — `SagProbe.Run.Shots` has always carried it and the table has always printed it — but it was never subtracted from the budget, so a level one shot from the wire looked exactly like one with twenty. The table now prints `clear margin` per level and marks anything under `CLEAR_MARGIN_TO_REPORT` (6) as **THIN**. Like everything else in that table it is a **ranking and not a verdict**: this probe shoots at random, a random player is worse than the one a budget is priced for, and a thin margin is a thing to go and look at rather than a refusal.

⚠ **It is taken over the clearing runs only.** A run that ended `OutOfShots` spent the whole budget by definition, so folding those in would price every level at a margin of nought and say nothing. A level no order cleared reports no margin rather than a margin of zero; the sag lines speak for those.

⚠ **And the fix for a thin level raises the budget and the ceiling step TOGETHER.** The glass descends once every `CeilingStep` shots, so buying eight more shots at an unchanged step buys the *cluster* another descent — 0.60 nearer the line — and the headroom the report asked for would have been paid for with pressure the report never mentioned. Causeway went 52 shots at a step of 8 to **60 at a step of 10**: six descents either way, the #288 clearance sum unchanged, and the clear margin **1 → 9** with the sag count still 0 of 5.

**Four losing orders in five separates them completely: all nine reported named, none of the three finishable.** That is `SAG_RUNS_TO_REPORT`, and it is the one threshold here fitted to play rather than chosen. ⚠ It was three while the player was a poor shot, and the way it moved is the point: aiming at the gap instead of at a ball took the match rate from 29 % to 86 % and moved every level the right way at once — Ghost and Cabinet up from 1 to 4, Amphora down the ranking to 3. **The separation is a property of a competent player, not of a threshold.** ⚠ One caveat the instrument itself measured (#301): the seeds fix the shot *sequences*, not the count — Bepu's threaded solve is not bit-deterministic, so an order whose deepest dip sits within a few hundredths of the allowance flips run to run, and a borderline level read 2, 3, 3, 3, 2 across five identical sweeps. A reading at the threshold's edge is repeated before anything is concluded from it; a 0 or a 5 is not.

**#301 then fixed its five against this instrument** — Pylon, Orrery, Ghost, Cabinet and Globe, which read 5, 5, 4, 4 and 5 of 5 as reported (Pylon on its first shot, glass at rest) and read **2, 3, 2, 3 and 3** fixed, none with the glass at rest — inside the band the finishable controls occupy, Saturn at 2 and Amphora at 3. What moved them is recorded on each design's own constants; the two findings that recurred across three of the five are the **diagonal fuse** (a cross-level neighbour IS a diagonal in (x, z), so a two-entry dither's same-colour blocks weld across levels — Ghost's body, Cabinet's woodgrain and Globe's ocean were one mechanism three times over, and a third entry in the band is the cure) and **the one-cell wall as a chain** (fourteen levels of it yield past the line under sustained load however braced the box looks — Cabinet's depth and Globe's shell both paid it).

**#302 then gave the four Spectrum spirals their banded tiers** — Pinecone, Pleat, Bolt and Totem had read 5 of 5 apiece (Bolt losing on its first shot with the glass at rest), and read **0, 0, 1 and 0** fixed, Bolt's one a hairline −1.00 exactly at the allowance, surviving orders clearing the levels outright. A tier is never a floor of one colour — the resolution against the block's own no-floors premise, and the rule every tier obeys, is written in the Spectrum block's header in `LevelGen`.

A threshold of 2 at rest names thirteen levels, a threshold of 3 names four (Amphora, Moon, Orrery, Harlequin), and **Amphora — the calibration's known-finishable level — reads 4 of 5, all four at rest**, so every at-rest threshold low enough to catch Moon also names the level play has already cleared. The column stays, as the per-level fact a trace would otherwise be needed for; the verdict stays `SAG_RUNS_TO_REPORT`'s.

### The anchor load: what the glass actually carries (#301, #302)

Measured on every run, printed beside the group count, and **new**: only the field's topmost level is bonded to the glass, so a level's entire mass hangs from however many cells its own top course happens to occupy. The drop test asks what a shot *orphans*, which is a question about the lattice — a cell still joined to the top level by any path passes it. This asks the other half, which is a question about **weight**.

It came out of the probe rather than from reasoning. Hanging **Amphora** in the real simulation and shooting one group off it dropped the ceiling links from **20 to 14 with nothing orphaned**, and the vase then descended five and a half units in a second — through a death line it had started four and a half above. Every gate in this tool passed that level, and passes it still: nothing floats, nothing stands alone, its best single shot takes 12 %.

The pack's spread of *balls per surviving anchor at the worst single shot* runs from **Gantry at 3.4** to **Giza at 139.2**, and the shipped set sits across the whole of it: Trilithon 4.4, Cube 7.1, Cabinet 12.0, Ziggurat 12.7, Chest 13.8, Spring 15.1, Belfry 17.1, Vortex 25.9, Analemma 29.8, Pylon 34.0, Globe 35.1, Orrery 37.0, Bolt 64.7, Ghost 66.8, Ten 100.8. (#301's fixes moved the five it touched — Globe most, 92.4 → 35.1, the polar plateau's whole point — but only as a side effect; the loads above are the re-measured set.) **⚠ It does not separate the reported levels from the rest either** — Giza at 139 and Ten at 101 are worse than most of the reported nine ever were and are not complained about, while Cabinet was reported at 13.1 — so it is a figure to design against and *not* a gate, and no threshold is enforced on it. What it is good for is the same thing the group-count ratio is good for: knowing, while a design is being written, that a shape hanging 900 balls off five cells is asking something of the glass that a shape hanging 300 off ninety is not. **#325 is the first time it would have answered a question in advance**: `Diadem` was the one level of 105 the probe reported, its cause was that a ring band has fewer ceiling sockets than a solid body of the same width, and widening the band from 80 anchors to 100 is the whole fix. The Mirage's ten sit at **3.7 (Trefoil) to 14.7 (Keystone)**, which is the low end of this table — a chapter built out of wide flat plates and stone tops.

### The shortest clear: how few shots empty the field (#458)

**Every gate above reads ONE cut.** The drop test asks what one shot is worth and refuses a level where one shot
is worth everything; the anchor load asks what the glass carries afterwards. The fault none of them can see is a
level that is not taken by one shot and *is* taken by two — and the owner found it by playing: **"Saturn can be
finished in two shots."** The planet was two 180-degree meridian halves, blue and green, so its anchor course
carried exactly two colours and two matches took all 377 balls off a budget of 36, the ring and the spokes falling
as orphans behind them. Every number the tool printed about it was true: nothing floats, nothing stands alone, the
best single shot took 33 %, the anchor load was the block's boldest and inside the pack's spread.

`Tools/LevelGen/ClearProbe.cs` asks the missing question on every run. It **plays** the level on the lattice — a
move is a landing (an empty pocket a shot can reach, a colour, the glass body that landing would colour, and the
group it completes), then everything that group was holding up falls with it — and the field is *clear* when no
removable ball is left standing, which is `CheckLevelCleared`'s own condition. The answer is the fewest moves that
get there. It is not the simulation: `SagProbe` is that, and costs minutes where this costs milliseconds.

**The cheap half is a sound lower bound and it answers most of the pack before a move is played.** The
disconnection walk seeds from every cell of the field's **top** level, so a ball up there can never be orphaned —
nothing the player does to the rest of the level can drop it, and it has to be *matched*. One shot matches one
group and a group is one colour, so **a level cannot be emptied in fewer shots than there are colours standing on
its anchor course**. Saturn's fault is that sentence as a number, and so is its cure:

| Saturn's anchor course (9 cells) | colours | shortest clear |
|---|---|---|
| before #458 | green x5, blue x4 | **2 shots**, matching 233 of 377 (61 %) |
| after | green x4, blue x3, yellow x1, red x1 | **no fewer than 4** — the block's own standard |

**⚠ THE REFUSAL IS NOT THE SHOT COUNT, AND THAT IS WHAT THE PACK TAUGHT THE GATE.** Measured over all 110 shipped
levels the day it was written: **sixteen levels besides Saturn empty in two matched shots and nine more in three**
(Pendant, Mobile, Column, Helix, Sail, Analemma, Binary, Kepler, Orrery, Garland, Ghost, Giza, Globe, Bridge,
Crane and Minaret at two; Horn, Trophy, Onion, Lean, Wishbone, Cairn, Cube, Knot and Carousel at three). They are
not faults. A field hangs off its top course alone, so the cheapest clear is always *cut what holds it* — and half
the Coil block is **designed** to be cut that way: Pendant is a weight on four ropes, and taking two rope tops of
eight balls apiece drops all 147. A gate refusing every clear under three shots would have sent seventeen shipped
levels back, which is a campaign rewrite and not a gate.

What separates Saturn from those sixteen is **how much of the field the cheap clear takes by matching rather than
by orphaning** — #458's own sentence, *"the two easiest shots on the field end the level"*, turned into a number,
because a group you cannot miss is a group that is a large part of what is hanging there. Saturn matched **61 %**
away in its two shots; every other two-shot level is at **39 % or below** (Crane 39, Minaret 29, Ghost 21, median
12). The refusal is therefore both halves at once — **a clear in under 4 shots that matches over 50 % of the
removable field**.

**⚠ It was under 3 until #474, and the extra shot is the owner's ruling rather than a measurement.** #458 drew the
line where the only reported fault was and said so; the table it printed then showed nine more levels emptying in
three, four of them matching most of themselves away — **Horn 90 %, Trophy 68, Onion 64, Lean 50.1** — and whether
that is the same fault one shot further out is a question about what those chapters are for, which the tool cannot
answer. Asked, the owner took the widest of three options offered. The four levels the wider rule then refused were
redrawn the way Saturn was, and the cure was a **colouring** in every case — not one cell moved:

| level | what it was | what it is | groups | shortest clear |
|---|---|---|---|---|
| Horn | three concentric shells, one colour each | the gold skin staved in four, gold and silver alternating | 4 → 10 | 3 → 6 |
| Onion | the white bulk one group of 300 | the same wedges the swing already drew, alternating white and silver | 6 → 15 | 3 → 5 |
| Lean | 3×3×3 masonry summed over three colours | four colours and strides 1, 2, 3 | 16 → 28 | 3 → 4 |
| Trophy | the bowl's gold a two-entry dither | three golds and two strides | 19 → 29 | 3 → 10 |

**Three of those four are the same fault wearing different clothes, and it is one this file already names:** a
*plain sum* over a palette gives two blocks a step apart in opposite axes the same index, and **a cross-level
neighbour is a diagonal in (x, z)** — so those blocks weld through the half-shift into sheets. Strides that are
coprime with the palette length are the cure (Trilithon's "+1 per x tile, +2 per z tile and +3 per level pair" was
the first statement of it), and a two-entry dither cannot have them at all, which is why Trophy needed a third gold
before its strides could work.

**⚠ The refusal multiplies out rather than reading the printed percentage**, which #474 is also the reason for:
Lean matches 258 of 515, 50.09 %, and the integer percentage in the log truncates that to 50 — a level genuinely
over the line would have passed on a rounding.

**The search is exhaustive as deep as it reports (3), so a refusal is proved rather than sampled** — and then the
line it found is **played back through `BallsMap` itself** (put the ball, colour the glass, count the group, take
it, drop the orphans: `BallContactEventHandler`'s own order) and the refusal is only made if the library agrees
the field really is empty. A model is a second copy of a rule, and the one thing worth doing with a second copy is
checking it against the first; a disagreement prints as a fault in the tool rather than as a refused level.

**What it does not play, and why it is still sound.** Only the ordinary landing: the match, the glass a landing
colours (whole bodies, #344) and the orphans. A blast, a zap, an acid shaft, a thaw and an infection are not —
they live in `BallsConstraintsBuilder` over a `PhysicsBall` array, and a second copy of them here is the one thing
this repository refuses. A **setup shot** is not modelled either: a landing that completes no group parks a ball
and is still a shot spent, so no sequence left out can be *shorter* than one played. Both omissions point the same
way — **the probe can only over-state how many shots a level needs** — so a level it refuses is really that cheap,
and the levels holding a bomb or a zap are the ones it can miss. The same conservatism decides where a shot may
land: the empty cells are flooded from the field's walls and floor (never from its lid, which is the glass), and a
pocket that flood cannot reach is not offered, since an unreachable landing would make a clear look cheaper than
it is.

`--clear` adds a **beam** line to every level's report — one greedy line of play, an upper bound and labelled one —
which is where the pack's deeper figures come from: seventeen levels clear in 4, and the tail runs out to
**Ziggurat at 24**. `--clearfile=<path,...>` asks the same of level files the set has never heard of, which is how
Colossus (the one hand-drawn level, which `Validate` never sees) and a design being redrawn get measured.

### Shot arrival: which landings can be got to, and from how far round (#514)

`--arrival` (the whole shipped pack, 120 levels in under four seconds) or `--arrivalfile=<paths>` for a level the set has never heard of, over `Tools/LevelGen/ArrivalProbe.cs`. Split out of #457, where two instruments were built to ask whether a level needs a control its tutorial has not taught and **both turned out to be checks that cannot fail**: `AimReachability` asks whether the barrel can be *pointed* at a cell, and a field subtending ~20° against a 45° traverse cone means nothing can ever fall outside it; the open-space flood asks whether a cell is connected to the outside through empty neighbours, and a flood has no direction in it, so the ring of empty cells round the cluster joins every wall to every other. Both pass everything, on every level in the pack and on the hardest shapes in the game.

- **What neither models is the only thing that stops a shot: it travels in a straight line and comes to rest against the first ball it touches.** So a pocket on the far side of the cluster can be aimed at, is connected to open space, and still cannot be arrived at. The probe asks that directly: a ray from the gun's trunnions to the landing cell's centre, blocked by any standing ball whose centre comes within `BLOCK_CLEARANCE` of the line.
- **The gun walks the whole orbit, so the honest question is not "reachable" but "from how far round".** `Cannon.EnsureOrbitAngleInBounds` wraps the orbit angle into 0..2π and clamps nothing, so A/D carries the carriage all the way round. The probe tries **16 stations** (22.5° apart, comfortably inside the barrel's own ±45° traverse cone) outwards from the stance a level opens in, and reports the first that works — so the answer is the *shortest walk*, and "reachable from no station at all" is a separate and much stronger statement.
- **⚠ A gap one cell wide is CLOSED, and that is correct rather than conservative.** Neighbouring cells sit exactly 1 apart and the ball flying between them is 1 across, so the clearance is a hair under 1 (0.98, the hair being the landing contact itself, which is at exactly 1 by definition). The old flood counted such a gap as open, which is half of why it passed everything.
- **The line is walked, not tested against the field.** At 4 500 cells and 16 stations, testing every cell against every ray is ~300 million distance tests a level; walking the segment in 0.7-unit steps and testing the 3×3×3 block around each touches the couple of dozen cells that actually lie near it. The occluder list of one (cell, station) is pure geometry, so it is computed once and cached — **what changes after a cut is only which of those cells are still standing**, which is a scan over a handful of indices. That is what makes it affordable to re-ask after every cut, which the issue rightly insists on: computing reachability once on the intact cluster understates it, and understating is the wrong direction to err in for a check whose job is to refuse a design.
- **Measured over the shipped pack** (120 levels, **2.2 s**, on the intact field): **68 139** candidate landings, of which **24 %** can be reached from the stance the level opens in, **48 %** need a walk round the orbit, and **28 %** are reachable from no station at all. The last figure is the enclosed pockets of an intact cluster and is *expected* — they open as the cluster is cut — which is why the report says "on the intact field" in its own header and why this is **a report and not a gate**: a check that refuses level designs has to be shown first not to refuse the designs that already play.
- **⚠ And the issue's own premise — that a cut opens lines and so an up-front answer understates reachability — is NOT borne out.** `ClearProbe.Measure` takes an optional per-cut observer now (it replays the line that cleared the level through `BallsMap` itself, so this is the game's own map code and not a second copy of the rules), and the report asks the same question again at each state. Over the **21** shipped levels the exhaustive search cracks within `PROVEN_SHOTS`: **25.8 %** of landings reachable from no station on the intact field against **27.4 %** averaged over every state of the played line. It does not improve; it very slightly worsens. Cutting a group opens some lines and *closes* others, because the hole it leaves is walled by whatever is still standing. Two caveats, both real: the levels with a proven line are the **shallowest** ones, so the sample is biased, and the after-cuts figure averages over near-empty states as well as full ones.
- **So #457's question has a number now, and the answer is yes.** Three quarters of the landings on an intact field are not reachable from the opening stance, and the furthest walk a level demands is 180° on most of the pack (112.5° on the most open shapes — Colossus, Facet, One, which also have **zero** landings reachable from no station).
- **⚠ The probe's landing count was checked against an independent implementation, and the one result that looked like a bug was not.** Heart, Smiley and Star report *identical* numbers — 476 landings, 201 from the opening stance, 19 from no station. They are the same 364-ball wall with different **colour** drawings on it, so their geometry is identical by construction and identical answers are the correct ones. A separate count written from the level JSON agreed exactly on all five levels tried (Heart/Smiley/Star 476, Cube 933, Colossus 209), which is what says the probe's idea of a landing is the same as everything else's.

### The coiled levels (#207)

The Coil block is five layouts that hang on **slender links**, because that — and not the silhouette — is what makes a cluster spring. The cluster is one Bepu body per ball tied to its neighbours and to the glass along the field's top level, so a wide solid slab is stiff by construction and a long thin member is not. That is also the block's one structural danger, since slender links are exactly what the drop test refuses, and every design carries a **second load path**: Rope's four strands pinch together periodically so each hangs off the others; Minaret's ledge and core are tied at every level and coloured out of disjoint palettes so no group can span both; Basket's two rib families wind opposite ways, so the shell is a mesh rather than a set of lines; Pendulum's four ropes take two inks in diagonal pairs, so a colour taken cuts two and leaves two; Knot is a **closed loop** touching the glass three times, the one topology on which a single cut drops nothing.

Four things are worth knowing before touching it.

- **A palette here has to have a SUBJECT, and until #285 none of them did.** All five shipped with a colour rule that was nothing but the group topology — one free ink per member — so the crane came out with a green mast, a magenta stay, a silver-and-blue jib and a brown-and-white counterweight, and the owner read the block as "like a child randomly tried colours". The bar named in that report is **Horn** (#33), whose rule is nothing but *reading what is coming*: white core, red flesh, gold skin, three shells ordered by radius. A rig cannot be ringed by radius, so the equivalent is a subject — an orange-and-yellow crane on a grey steel jib with a red load; a Calder mobile, primaries hung on black-and-grey wire; a suspension bridge in International Orange over a grey roadway; a jewel on a gold chain and a steel one; a web whose one warm thing is the spider. **The topology did not move**: which member gets its own ink, which pairs are banded so a released colour thins a beam instead of severing it, and which are diagonal so no ink lists a rope both ways all stand exactly as they were, so every group and best-single-shot figure in the designs' own doc comments is untouched by construction. Where two inks touch, they are checked against measured CIEDE2000 (`.claude/skills/screenshot/palette.ps1 -Focus`) — which is what keeps red off orange (14.1 dE, the palette's tightest pair) and yellow off white (14.5, the second).

- **The whole block is hung deeper than it needs to be, on purpose.** `DUNES_FIELD_LEVELS` is 18 against layouts of 12 or 14 — the same arithmetic `REVEAL_FIELD_LEVELS` reaches and a different reason for it. The six or four empty levels under a layout are its clearance, so its lowest ball starts **5.38** above the line instead of the 3.38 a 16-level field would give it. (While the death line stood at −5.5 an 18-level field was also *raised* off it, hanging 1.36 higher for a clearance of 4.74; the line has since been lowered onto the island, so the field is pinned again and the air comes from the line being 2 lower instead — more of it either way.) On a block whose point is that the cluster swings, that clearance is the whole margin: #203 is the same fact arriving as a bug report on the picture levels, where gravity pulls part of a layout down into a stalk and the stalk crosses the line. Eighteen and not twenty, because `FRAMED_LEVELS` is 18 and a block the camera framed from the floor up would be a second Tower — **none of these is tall, and that is the Tower's boundary being respected rather than an oversight.** (#182 has since crossed that boundary deliberately — the Nebula is a second tall block at the owner's ask, its statement being the new colours rather than the Tower's premise; the Coil's own reasoning here stands as it was made.)
- **Two of the five passed every gate and were refused by a photograph.** `Rope` shipped first as three strands of 1.6 at a radius of 2.5: 285 balls, margin 2, nothing alone, nothing recoloured — and in the running game a shapeless column with no twist visible in it, because at 120° apart those centres leave barely a cell between neighbours and the lattice rounds it away. `Minaret` ran its ramp at a wedge of 82°, a quarter of the ring at every level, which over the 1.3 turns a twelve-level layout allows photographs as scattered lumps rather than as one thing winding. Both were fixed the same way — **thinner and further apart** (four strands of 1.3 at 3.0; a 63° wedge reaching out to 5.3 instead of 4.6) — and both cost balls to buy the shape. Nothing in `Validate` can see either failure.
- **A closed loop cannot be coloured by a formula on its parameter.** `Knot` is a (2, 3) torus knot, so it **touches itself**: arcs half a loop apart are neighbours in the field, and every such touch has to fall on a colour boundary or the two arcs are one group. Coloured as six arcs by `arc % 3` it measured **33 %** best shots against an expected 12 %, every ink reading as a single group — the loop had welded itself into three pieces. The fix is `KNOT_INKS`, a twelve-entry table solved against the contact graph **measured on the emitted cells**, which mattered: there are ten touching arc pairs, nine of them between arcs that are not loop neighbours at all, half again as many as reasoning about the curve predicts. The figure that says the table still holds is the tool's own *largest standing group*, 36 — about a twelfth of the level, i.e. one arc.

`Validate` cannot tell whether the thing looks like the intended picture, which is exactly what the `screenshot` skill is for; all three pictures were checked in the running game before they were called done, and so was all of #207.

It also prints, per level, **how many standing colour groups it is made of and how many shots the budget allows per group** — the number a budget is actually priced against, since one landed ball takes exactly one group with it (plus whatever that group was the last anchor for, which is what makes a design with cascades cheaper than the count says). It is not a gate, because the right ratio is a design decision and the pack spans two orders of it: **Colossus 0.98** (364 balls in 46 groups against 45 shots, the hardest level in the game), Static 1.43, the Arcade's five from 1.65 down to 1.37, the Nebula's around 3, and **Horn 20**, where four shells mean the budget is not the thing being fought at all. A design under 1 with no cascade in it cannot be finished, which is how the Arcade's first drafts were caught: every one of the five was over-tight before it was measured.

It exits non-zero when any level fails, so it can be put in front of a commit. What it cannot check is whether the result *looks* good: that is `.claude/skills/screenshot`, and it is not a formality — **two of the Gallery's own designs were refused by it after passing every gate**, and the third of them was dropped outright (see the picture bullets above); **two of the Coil's five were refused by it as well** (see above). `AimReachability` (whether the gun can reach every cell) is the Testbed's `aimcheck`, not this tool's — it needs the solved gun orbit, which needs a graphics device. Both were run over the whole of #194's new content: every new design was looked at in the running Testbed in its own scene and dome, and all eleven **PASS** `aimcheck`, the steepest being Chest's corner cell at 69.9° of a 80.2° clamp. All five of #207's do too, the steepest being Minaret's corner cell at 69.7°, all five of #182's — the steepest being Wishbone's corner cell at 54.1° of the same clamp — and all five of the Arcade's, the steepest being the Donut's field corner at 72.0°, its 17-wide field being the widest in the pack. **All five of the Spectrum's do as well, and they were checked through the Game rather than the Testbed** — every one of them is a tall level, and the Testbed's `aimcheck` stopped answering for those the day levels could be taller than the frame (it measures the Testbed's own fit, which stands the gun back far enough to see the whole field; see "Tall levels" in `docs/game-session.md`), so the figures are the Game's own `[aimcheck]` line over its working band: steepest 47.5° of a 50.4° limit, on Trellis and Turbine. `Tools/ScoreSim` still reports every level rating the right way round — all 105 of them since #325, whose ten are the block table's eleventh row. **The Mirage's ten were not put through `aimcheck`**: it needs the solved gun orbit and therefore a graphics device, and every one of them is a framed-whole level in a field of 16 or 17, which is the shape the check has never once refused — so the figure to reach for is the Donut's 72.0° on the same 17-wide field, and running it on this block is a matter of an hour at a machine rather than of a doubt.

### The arcade levels (the eighth block)

The Arcade is **the Gallery given a third dimension**: five hollow solids with pixel art wrapped onto them, over the neon city. A Gallery wall shows its symbol from where the gun starts and the level is read in one glance; a cube shows one face, and the other three and the underside are read by walking the gun round it. Four things about the block are worth knowing before touching it, and three of them were paid for.

- **A hollow body's anchor is whatever its own top happens to be**, and only the field's topmost level is bonded to the glass. That is a 100-cell plate on the cube, 49 on the temple, a disc on the reel's head, an annulus on the donut — and about **twenty cells** at the globe's pole, where a true shell narrows to a point. One colour across any of them is a level that ends on the first lucky ball of it, so every cap here carries at least two colours interleaved; the globe's ice caps are broken into floes for that reason and not for geography's. The drop test is the check, and the whole block's best single shot is 11 %.
- **A one-cell-thick hollow ring does not survive its own weight.** The temple was drawn first as one-cell courses twelve levels deep and **lost itself in eight seconds with no shot fired** — the whole thing sagged past the death line while the camera was still settling. A ring that thin is a curtain of `BallSocket` links with nothing bracing it across; Garland found the same wall at 1.15 cells of strand (#182), and the Chest's two-cell box and the Vortex's two-cell wall are the ones that hold. It is two cells thick and eight levels tall now. The cube's one-cell walls are fine because a closed box is braced by its own corners — the shape matters as much as the thickness, and 35 seconds hanging unshot in the running game is how each of the five was checked.
- **The group count is the budget, and the ground's block size is what sets it.** These are dithered surfaces, so the number of standing colour groups is large and it is a design output rather than an input: the same cube measured **75, 44 and 34 groups** at three ground-block sizes, which is a budget of a hundred shots, seventy, or the fifty-six it ships with. All five are priced off the ratio the validator prints and ramp 1.65 → 1.58 → 1.50 → 1.44 → 1.37 shots a group, the finale tighter than anything in the game but Colossus and Static.
- **Black on navy is not a drawing.** The cube's cool faces were cyan-and-navy first, and in the running game the black glyph on them was invisible — half of every face was as dark as the symbol drawn on it. Both wall pairs are bright now (red/orange and cyan/magenta), which is the same finding the Gallery records from the other side: a picture's difficulty is drawn in the *symbol*, and its legibility in the **ground**.


### The spectrum levels (the ninth block, #253)

The Spectrum is **one hue family a level, swept through the whole body as a gradient** — the owner's brief was a chapter whose levels read as *one colour* rather than as a set of arbitrary matching ones, seeded by a level sweeping white → light blue → blue → dark blue and back to white as it climbs. Five families, all of them tall, all of them in the city at morning: `FROST` (white/cyan/blue/navy, the seed), `TWILIGHT` (white/magenta/navy/black), `MOSS` (white/green/olive/black), `HEAT` (white/yellow/orange/red/brown) and `SPECTRUM` — the wheel itself, seven of the thirteen in hue order, on the finale. Five things about the block are worth knowing, and the first two are the block.

- **No new ball colour is involved, and that is a constraint the owner stated rather than an accident of what was to hand.** A family is a **subset and an ordering** of the fixed thirteen `BallType` already has; the seed example needs nothing added, White(4)/Cyan(5)/Blue(3)/NavyBlue(12) sitting in exactly that order. The reason is #152's and #246's: each of the five colours added there was placed at a *measured* distance from an existing one — silver a cool slate so it does not vanish into the white gores, navy re-spaced against black once "darker than blue" had made it the same as black — and a hue picked to fill a gap in a ramp is precisely the way back into the trap those spacings exist to avoid. What this chapter adds to the palette is order, not paint.
- **The sweep is a helicoid, and that is not a look — it is what makes the levels playable at all.** The rule the block obeys is that **every stop of the family has to stand on the top level**: a stop that exists only further down hangs off the stop above it and nothing else, so one matching ball takes it and everything under it. The first cut of the opener swept a *tilted plane* — 3D, not a stack of floors, and it still measured **80 %** in the drop test; the Kiln's first cut measured **92 %**, over the gate. Wound instead, at a pitch of one whole folded family a turn, the top level carries every colour in wedges and what a cut leaves behind is a **screw thread** that still spirals from the tip to the glass. The same three levels then measured 34 %, 25 % and (the Hourglass, whose conical shells were closed *sleeves* round a waist before) **89 % → 17 %**. The tilt is what makes the gradient three-dimensional; the pitch is what makes it a level.
- **The fold is the brief and it costs an even colour count.** A sweep runs out through the family and *back* rather than wrapping (`Sweep`), because the seed says "and back to white": wrapped, every period would put navy against white along one hard seam, the single boundary in the family that does not read as a gradient. The price is that a fold of `n` stops has period `2n − 2` and hits the two **ends** once against the middles' twice, so white and navy come out at roughly half the count of cyan and blue. It shows in every one of these levels' reports and is left alone — a family's ends are its extremes, and being rarer is what makes them read as ends.
- **The block's order is a measured difficulty ramp, and the families are not what ramps.** A green level is no harder than a blue one; what varies is how finely each design's sweep cuts its body up. Standing groups run **6, 9, 15, 22, 31** across Icicle, Hourglass, Trellis, Kiln and Turbine — 6.67, 5.33, 3.47, 2.55 and 1.68 shots a group, from a level of four huge spirals to one of 31 pieces in seven colours, the finale landing inside the Arcade's own 1.37–1.65 band. One term was measured and *rejected* on the way: shearing the Icicle's sweep outward as well (0.9 levels a cell) carries each stop's ribbon across the gap to the turn of itself outside it and **merges** the level — six standing groups become four, one per colour, the whole thing in four shots. Every other design in the block wants that term; a bare cone under a bare helicoid is the one place it does the opposite of what it looks like.
- **The city was chosen for this block by looking, and the sea was refused.** The obvious pairing was the sea — the one scene of the original seven the campaign has never used, and "first light over open water" as the step after the Arcade's artificial neon. It is the worst backdrop in the game for *this* chapter for exactly the reason it looked right: the water **mirrors the dome**, so the sky's hue fills the top of the frame and the bottom of it too, and a chapter about telling neighbouring hues apart is then played inside one of them. Shot under four domes it came out monochrome every time; under dome 4 it was a magenta sky over a magenta sea, which is the trap already on record against the dream scene and magenta balls. The city's facades are the largest low-chroma surface in the game and its ground is grey, so only the top third of the frame carries the dome's colour — and it is deliberately the **same city the Arcade plays in**, at morning with its neon off, which says "light received again" harder than a new place could. Dome 11 was picked over 1, 3 and 9 on shots of the Icicle and the Hourglass (the block's coolest family and its most fragile): 1 and 3 put a cyan and a lavender sky behind a blue cluster and a magenta one, each swallowing the family it should set off, and 9 is a dusk, which reads as a step back into the dark rather than as light returning.

- **One of the five is bounded by the physics rather than by the drop test, and it says so out loud.** The Trellis's two ribbons close once over its 22 levels; winding them faster (0.032 → 0.055 turns a level) buys a *second* pass and improves every number the tool prints — green's best single shot 34 % → 19 %, standing groups 15 → 14 — and the level then **failed in the running game at ten seconds with no shot fired**, on "the cluster reached the line". At that pitch a ribbon steps its cells more than a cell sideways per level at the outer orbit, so consecutive levels barely overlap: the links exist, which is exactly why the disconnection gate passes, but there are too few of them to carry the weight and the whole thing stretches. **The gate that says the links exist cannot say there are enough of them** — Garland found the same wall by strand thickness (#182) and the Ziggurat by ring thickness, and the only thing that finds any of them is hanging the level unshot in the game.

All five **PASS** the Game's own `aimcheck` (steepest 47.5° of a 50.4° limit, Trellis and Turbine) and all five hung **35 s unshot** in the running game without sagging near the death line. `Tools/ScoreSim` reports every level rating the right way round.

## The map editor at a glance

Visual editor for the map JSON files (it supports drag-and-drop of a map file onto the window). It draws the balls and the sky the same way the game does, so a map looks in the editor the way it will play: the same instanced procedural spheres, the same shader, the same sky-derived lighting and the same full render pipeline (below).

It builds `Shaders/InstancedModel.fx`, `Shaders/Tonemap.fx`, `Shaders/Glare.fx` and the scene shaders (`Sea`/`Savanna`/`Desert`/`Acacia`/`Flame`/`Birds`/`Mountain`/`Snow`/`Spray`/`Meadow`/`Forest`/`Space`) straight out of the Testbed content directory (`/build:../../Testbed/Content/…;<asset name>` in its own .mgcb), so there is one copy of each. The sky domes need no content at all since #113: `SkyDome` builds the one dome geometry the eighteen `.dae` files turned out to share, and a sky is one of eighteen stored palettes.

**Keys.** B cycles the domes (the game's NumPad1, which the editor uses for ball types instead — NumPad1–9 pick the first nine directly, and NumPad +/− cycle all thirteen, the four past nine having outgrown the numpad's digits with #152) and **V cycles all twenty scenes** (the Testbed's NumPad2), so a map can be previewed against every backdrop it might play in. ⚠ **It walked a seven-long prefix until #380, and that sentence was false for ten of them for as long as it stood.** The prefix was "the scenes a map is authored against", which was true when it was written and stopped being true as the campaign was built: **fifty of the hundred and ten shipped levels are authored in space, the dream, the cavern, the Moon and the volcano**, every one past the prefix. The cost was worse than ten unreachable backdrops. Loading such a level left the scene index past the cycle's end, so the first V restarted at the city and there was **no way back to the level's own scene except reloading the file** — in the one program whose job is previewing a map against every backdrop. (#73 had already fixed the *arithmetic* of that restart, here and in the Testbed's copy of the same one-liner: `(index + 1) % 7` landed wherever it fell rather than at a boundary, so from a forest level the first V came out at the *sea*, three scenes deep. What it could not fix was the prefix.) Both keys now walk the enum through `SceneRenderer.NextScene`, and nothing counts the scenes any more, so a twentieth kind is reachable the moment it is declared. **V deliberately does not adopt the scene's default dome** the way the Testbed's switch and the game's `SetScene` do: here the dome is *data* — F4 writes it into the level and in play the level's own sky is applied after the scene's default and wins — so setting it on a cycle would overwrite the author's choice for the sake of a preview. The same shared `SceneRenderer` and city the game uses (see "The shared scene backdrops" in `docs/scenes.md`). It loads and saves not just plain map files but whole **levels** (map + scene + sky): F2 and drag-drop load, F1 and F4 save. **L cycles what the balls are made of** (#258) — the vinyl beach ball or the glass bubble — and applies it to the render set at once, so the preview *is* the answer rather than a description of one; it is a property of the map, so F4 writes it into the level and F2 brings it back, and a fresh map or a plain map file resets it to vinyl. L for "look" because it was what was free: S, W, A, D, Q and E drive the camera, B is the dome, V the scene, N fills the map and M clears it. The cycle is `BallStyles.Next`'s, off the enum itself, so a third material cannot be added and left unreachable in the one program that exists to choose between them. **K cycles what the next placed ball *is*** (#323) — normal, or a rock (#324) — and it is a key of its own rather than more entries on the colour cycle, because the two are orthogonal: a rock is not a fourteenth colour and a picker that mixed them would say it was. The colour keys go on working while a rock is armed, since a rock carries a type like every other cell and nothing reads it — and the moment a kind exists that *does* read it (a frozen ball is a coloured ball inside ice), the two pickers already compose. **That moment arrived with #329 and the two pickers did compose, with nothing added**: a frozen ball is placed by arming the kind with K and the colour with the numpad exactly as an ordinary ball is, and the colour is the one that appears when the ice breaks. Also `BallKinds.Next`, for the same reason L's is. ⚠ **#331 is where that composition stops being merely tidy and becomes load-bearing**: an infectious ball's colour is not decoration but the shot that kills it, so the two pickers together are the whole authoring interface for the kind. ⚠ The hint line under the key names each kind in a `switch`, and **the acid's case was missing from #328 until #329 added it** — the drift that switch's own comment was written against, arriving one kind later.

**What it deliberately does not draw.** It has no ground, castle, cannon or shadows, and no arena platform (the AABB replaces it); the play field is marked by a translucent procedural outline (`GUI/AABB.cs` + `WireBoxMesh`) instead of the game's glass ceiling, and only the selector gizmo still draws through `ModelRenderer`/`BasicEffect`.

## The map editor's render pipeline

The map editor renders through the **same linear-radiance pipeline as the game**, so a map looks in the editor the way it will play — that is the whole point of moving it off DesktopGL. `MapEditor.Draw` binds the shared pipeline's supersampled HDR scene target (`SUPERSAMPLE_FACTOR`, a fixed 2 — there is no `ssaa=` CLI here), clears it to the **current dome's horizon colour** (`_rig.HorizonLinear`), draws the sky, the chosen scene backdrop and the balls into it, then `PostProcessPipeline.Resolve` runs `Glare.fx` and `Tonemap.fx` — since #74 literally the same code every executable runs, in `Prazsky.Core.Render`, with the editor passing the game's own look figures so the two agree by construction. (Under the old ported-verbatim copy the editor's glare threshold had silently stayed at the pre-pyramid 0.38 against the shipped 0.55 — exactly the drift the shared copy exists to prevent; fixed in the hoist, so the editor previews a touch less bloom than it used to and exactly as much as the game.) The clear colour is the horizon rather than a fixed blue because the hemisphere dome covers only above the horizon and the finite scene only reaches its own edge, so at a wide aspect (21:9) the bottom corners look below the horizon past both — and a fixed clear colour showed through there as a blue band; clearing to the horizon makes that gap blend with the hazed skyline the dome and terrain both fade to. Both executables do this. The pipeline's `EnsureTarget` is called from `LoadContent`, `Window_ClientSizeChanged` and `SetGraphics`, so the target tracks the back buffer through a resize or an F11 fullscreen switch; back-buffer MSAA is off because only the resolved full-screen quad ever touches the back buffer.

**The balls go through the shared `BallRenderSet` since #76, and that closed a second drift of exactly the same kind.** This document claimed the editor drew them "exactly as the game draws them"; it did not. It set only the pattern's gore count and a **full albedo**, so its balls were twice as bright as the game's (`BallRenderSet`'s albedo is 0.5 — a flat 1 is a surface that reflects every photon reaching it, which nothing real does) and were neither emissive, translucent nor pulsing at all. There is one set of look figures now and the editor reads it, so the claim is finally true: the same albedo, the same emission and translucency, and the same slow heartbeat travelling up the cluster. The one thing it deliberately does not take is the landing **ripple**, which is a rule about a cluster being played (`ripples: false`, which also selects the deeper resting pulse depth, the breath both non-playing executables keep). None of it needs physics — the editor hands its `BallsMap` to `BallDrawFrame.AddMap` and its own scene clock to `Draw`, which is what makes a caller with no simulation a first-class one (see "The rest of the hardware, in one copy" in `docs/testbed.md`).

**And it draws the forest's wood** since #75. The trees, boulders and stumps standing on the forest floor were the Game's alone while the floor itself was always the shared `SceneRenderer`'s, so the editor — and the Testbed — previewed a bare clearing; `ForestScatterRenderer` is that piece shared (see "The forest" in `docs/scenes.md`). V reaches it like every other scene since #380 (until then only loading a forest level did), and until #522 it was the one place the editor needed something the Game never did — a `Replant` for the live scene-config panel's edits; the panel and the method went together (see "The scene-config panel (MapEditor)" below).

Two things do **not** go through the shared shader and needed handling for the linear target:

- **The sky dome** is drawn through `BasicEffect` (the editor builds no `Sky.fx`), so its stored vertex-colour gradient is sRGB. `SkyDome` is therefore built with `linearVertexColors: true`, which converts the gradient to linear whenever a palette is written into the buffer — otherwise the tonemapper reads a gradient of display values as radiance. `ApplySkyLighting` likewise decodes the palette to linear (`ColorSpace.SrgbToLinear`) before scaling and tinting it, and sets `LinearLightRig = true` on the ball renderers — and since #75 it does not *mirror* the game's derivation, it **is** it: all three executables run the one `Prazsky.Core.Render.SkyLightRig`, so a palette, a scale or a tint cannot mean one thing here and another in play. What stays the editor's own is only the enrolment — the balls and the city, there being no island, drain or ceiling here to light. **The drawn sun disc is the one thing this costs, and not having it was decided rather than overlooked** (#220): the disc lives in `Sky.fx`, so the editor could only have one by building that shader, which drags the whole cloud field's evaluation into its sky pass for a deck it does not want. It buys less than it looks — this sky has no weather at all, so a sun in it is no more faithful than a sun-less one, while everything an author actually judges here (the terrain, the water, the trees, the balls' own lighting) **does** follow the dome's sun already, through the very light rig and `SceneFrame` above. See "The weather" in `docs/rendering.md`.
- **The AABB field outline and the selector gizmo** are drawn through `BasicEffect`. The AABB is opaque-coloured and depth-tested against the balls, so it stays in the HDR pass and its one flat colour is linearised on the CPU (`ColorSpace.SrgbToLinear(COLOR)` in `AABB.cs`) — handed over raw it would tonemap too bright. The selector is additive and drawn with depth off (always on top), so it is drawn **after** the resolve, in display space, where `BasicEffect`'s gamma output is already correct — the same split the game makes for its crosshair and text overlay, which also draw post-resolve (`base.Draw` runs last). The **axis gizmo** (`GUI/AxisGizmo.cs`) — a small X/Y/Z cross in the bottom-left corner showing how the world axes sit relative to the camera, to keep the user oriented while building a map — draws post-resolve too: it binds a small square viewport, draws the three coloured axes (X red, Y green, Z blue) through a rotation-only view of the camera under an orthographic projection, then labels the tips with `SpriteBatch`. It reflects only the camera's orientation, not the scene, so it needs no depth and no scene state.

Because both executables now build the shared shaders for DirectX/SM 5.0, `InstancedModel.fx` has no `#if OPENGL` branches left at all: `SrgbToLinear` always decodes, `Clouds.fxh` is always included (the editor just never sets the cloud uniforms), and the relief self-shadow / parallax marches are always compiled (guarded at runtime by their strength uniforms, which the editor leaves at zero).

## The scene-config panel (MapEditor) — removed in #522

The editor carried an in-engine GUI built on **Myra** from #45 to #522: a right-docked `PropertyGrid` reflecting over the active scene's `SceneConfig` (issue #33's Level Editor skeleton, realized inside the MapEditor rather than as a separate tool), **G** toggling it, an edit firing `PropertyChanged` and re-applying the config through `SceneRenderer.Apply` (or rebuilding the city) so the backdrop updated live. It was a run-time tuning tool from before the format-2 refactor, when a level still carried its scene's config; after that refactor its edits persisted nowhere (the panel's own header said so) and it survived as a way of developing a scene's fixed look against the real pipeline.

**It was removed because a scene's look is programmed, not configured** — the owner's ruling in #522. Since the format-2 refactor a level names its scene by string and the scene's parameters are fixed in code (`SceneConfig` class docs), and a per-run editor of shader and material parameters is not something this project wants at all. The scene passes of 2026-09 (#503–#512, #445) were all made by drawing references locally, editing the config classes and photographing the Testbed under `campos`/`camtarget` — the panel took no part in any of them.

**What went with it**, because it existed only for the panel: Myra and its name-clash aliases from the map editor (the Game is the only executable on Myra now, see "The front end (Game)" in `docs/game-shell.md`); the editor's input arbitration that stood its own keys and camera down while a Myra widget had focus; `SceneRenderer.Apply(SceneConfig)`, the runtime re-apply of a scene's parameters (the per-scene `Apply*Parameters`/`Build*Buffers` it called all still run once at load); `ForestScatterRenderer.Replant` and `ForestFireflies.Replant`, which rebuilt the wood for a config edited under them (see "The forest" in `docs/scenes.md`); and the one reason `Rgb`/`Vec2`/`Vec3` were **classes** — Myra's `PropertyGrid` edits a nested value type's sub-properties on a boxed copy it never writes back, so a struct colour could not be tuned live. They are `readonly struct`s since #522: nothing edits a config at runtime, nothing serializes one (the format-1 reader takes only the scene's name off an old file's config object), and a heap object behind every colour field of every scene config bought nothing.

**What outlived it:** the configs' *shape*. Several scenes' configs use named nested groups rather than arrays (`NebulaOne`/`Two`/`Three`, the storm's `Clouds`/`Surface`/`Flash`/`Air`, …) because the grid was built `IgnoreCollections = true` and a list was invisible in it. The shape stays — a named group reads as a config where an index does not — but no document should justify it by a constraint that no longer exists (`docs/scenes.md` says so where it comes up).

The old **Level Editor** direction (#33) is not coming back through this door: a level is a map plus a scene name, a sky and a ball style, all of which the editor already authors.

## What a run says it is: the `[build]` lines (#372)

All three executables open with three lines on stdout, from `Prazsky.Core.Tools.BuildStamp`, before anything else they print:

```
[build] Testbed.dll 2026-09-07 21:37:16 50145c15
[build] libraries 3 set 08f67881, newest Prazsky.BS3D.Physics 2026-09-23 04:10:46
[build] shaders 28 set 54512ed6, newest Glare 2026-09-07 21:38:53, oldest Sky 2026-09-02 16:17:17
```

**They exist because a run could not be asked the question every capture and every measurement rests on: *which shader are you running?*** Three consecutive rounds of measurement once ran on a Testbed that did not have the edited shader in it and produced a conclusion, a change made to satisfy it, and then a retraction written into five files and committed (`e71fdff`). One of the two causes is permanent: **MGCB skips an `.fx` whose `.xnb` is newer and then copies nothing** — the content task copies only what it built in that invocation, `dotnet build` prints `Skipping …\InstancedModel.fx` and reports success, and deleting `bin` is not enough (only `Content\bin`, MGCB's own intermediate, forces the rebuild and the copy). The other is an exe built into a configuration nobody launches, which the first line answers.

- **The first line is the managed assembly, not the apphost `.exe`** — the code is in the `.dll`, so its write time is what says whether a C# change reached what is running. Its hash is of that file. Neither is the PE header's timestamp, which deterministic builds (the SDK default) fill with a content hash rather than a date.
- **⚠ The first line cannot see most of this repository's code, which is why the second exists.** All three executables are thin shells over `Prazsky.Core`, `Prazsky.BS3D` and `Prazsky.BS3D.Physics` — `ArenaIsland`, `InstancedModelRenderer`, `SceneRenderer`, the gun and the physics all live there — so a library-only change leaves the exe's line **and** the shader `set` hash identical, and an A/B of two such builds has nothing on its own output saying which is running. It has been hit twice: a run that drew a new mesh under the previous run's exact hash, and a #404 pair whose halves were distinguishable only because they came from two different worktrees. **Demonstrated:** one constant changed in one library method and nothing in the Testbed's own sources, then a rebuild — `[build] Testbed.dll 04:10:47 67ecbe20` came back byte-identical *and with the same write time* (MSBuild did not re-emit it), while `libraries 3 set` moved `08f67881` → `fe6b0676` and `newest` changed to name `Prazsky.Core`. The libraries line carries `newest` but no `oldest`: there are three and they rebuild together, so the oldest answers nothing the set hash does not. Third-party assemblies are deliberately excluded — they move only with a package version, and hashing forty megabytes of MonoGame at every startup would be noise on the line and time on the clock.
- **`set` is one SHA-256 over every `.xnb` beside the exe — each file's name as well as its bytes**, ordinal-sorted so it does not depend on locale. It is **the authority on content, and the timestamps are not**: verified by editing one constant in `Glare.fx` (`54512ed6` → `8b72d45a`) and reverting it (`54512ed6` again, from a freshly written `.xnb` with a new timestamp). Two runs with the same `set` are running the same shaders.
- **`newest` is the shader most recently compiled**, which after a shader rebuild that landed is the file you just edited. When it names something else, MGCB skipped yours.
- **It reports and never judges.** A shader older than the exe is entirely normal — an `.xnb` changes only when its source does — so there is no verdict here that could be wrong; the lines carry evidence into the same log as the capture, and the reading is the reader's. Every failure inside it is swallowed: a run must never fail to start because a diagnostic could not read a directory.

The counts differ by executable and that is the content projects talking, not a fault: the Game builds 32, the Testbed 28 and the MapEditor 26 (which has no `Sky.fx` entry at all — see "The map editor's render pipeline").

## The application icon (Game)

The icon the shell draws on `BS3D.exe` and the window publishes at runtime. The artwork is `Images/Icons/ico6.svg`, exported to the `ico6-<N>.png` ladder, and `Images/Icons/Build-Icon.ps1` assembles that ladder into `Game/Icon.ico` — run it with no arguments after the artwork changes. `<ApplicationIcon>Icon.ico</ApplicationIcon>` was already in all three `.csproj`, and MSBuild embeds **every** frame (verified: `RT_ICON images=14` in both the apphost `.exe` and the managed `.dll`, each frame pixel-exact against its source PNG through `PrivateExtractIconsW`), so nothing in the projects needed changing — only the file, which until then held a **single 256×256 image** that Windows downscaled for every size it drew.

- **The fourteen sizes are not padding and not an MSIX artefact.** `{16, 20, 24, 30, 32, 36, 40, 48, 60, 64, 72, 80, 96, 256}` is exactly the union of the sizes the Windows 11 shell asks a Win32 executable for across its 100–400 % scale factors — 16–64 for the title bar, context menu and tray, 24–96 for the taskbar, search results and the all-apps list, 32–256 for a Start pin (MS `app-icon-construction`). They coincide with the MSIX `AppList.targetsize-*` list, which is why the middle steps get mistaken for packaging leftovers. Windows matches a request exactly if it can and otherwise takes the next size **above** and scales down, which is what makes the 256 entry matter even at 100 %.
- **The payload split is DIB through 96, PNG for the 256 only, and the reason is not the shell.** PNG sub-images at every size would take the file from 185 KB to 79 KB (measured, `-BmpMaxSize 0`: 78 627 B against 184 590 B, i.e. 43 %) and the Win11 shell reads them perfectly — `PrivateExtractIconsW` and `LoadImageW` return all fourteen pixel-exact from an all-PNG icon — so the usual folklore about small PNG entries breaking Explorer is false on current Windows. What is true is that **an old enough `System.Drawing` consumer cannot read a PNG sub-image at all**, and that it fails **silently**: it takes the entry's bytes for a DIB and decodes the compressed stream as raw pixels, so the frame comes back as **noise** — measured on the real ladder, 0 % of pixels matching the source at every size from 16 to 96, with as many distinct colours as there are pixels (1024 of 1024 at the 32) — and with **no exception and no blank frame anywhere**. Two things about that are easy to get wrong and both were, here, before they were measured:
  - **It is gated on the consumer's own target framework, not on ".NET Framework".** The switch is `Switch.System.Drawing.DontSupportPngFramesInIcons`. Measured with two byte-identical builds of one probe differing *only* in their `[TargetFramework]` attribute: targeting **v4.5** every size of the all-PNG ladder reads as noise, targeting **v4.8** every size reads 100 % pixel-exact. A host that declares no target framework — PowerShell 5.1, i.e. this repo's own harness scripts — takes the broken path. So the consumers at risk are old installers and script hosts, not everything pre-.NET-10.
  - **Do not test it by looking for a throw or a blank frame — there is neither.** An earlier version of this note claimed a blank at 16–24 and an `ArgumentOutOfRangeException` from 30 up. Both were artefacts of measuring against a synthetic icon whose payloads were a couple of hundred bytes: `Icon.BmpFrame` copies `40 + w·h·4` bytes from the entry's offset, so it throws only when that read runs off the end of the file, which a real ladder's later entries prevent. Compare pixels against the source PNG instead.

  The failure does track the payload encoding rather than the size: in a `-BmpMaxSize 48` file the DIB range reads pixel-exact and the PNG range reads noise. And the shipping split is what makes the question moot — **`Game/Icon.ico` reads 100 % pixel-exact at every size even for a consumer targeting v4.5**, which is the whole point of it. That consumer is old installers, PowerShell 5.1 tooling, shell extensions and Mono, and it is the whole reason the small entries are stored as classic DIB. The 256 stays PNG because uncompressed it alone is 262 KB — as PNG it is 30 984 B against 270 376 B, i.e. the one place a tenth really is the ratio. `-BmpMaxSize 48` gives up 87 KB of that compatibility and is still right for every size a legacy consumer realistically asks for; the default follows Microsoft's literal rule ("only the 256×256 image should be compressed") and has no failure mode below 256 at all.
- **A DIB entry's `biHeight` is twice the icon height and its 1 bpp AND mask has to actually be there** (bottom-up, rows padded to 4 bytes, a set bit meaning transparent) — it is the colour image stacked over that mask. The builder derives it from the alpha channel rather than leaving it blank, so the silhouette survives the paths that ignore alpha. A PNG entry takes the opposite contract: 32 bpp ARGB, **no** `BITMAPINFOHEADER`, **no** mask (alpha *is* the mask), and its directory entry writes the 256 dimension as **0**. Pillow is no help here — its `sizes=` route silently *resamples* from one base image, and its BMP mode writes the doubled `biHeight` with no mask at all.
- **One trap in the builder itself, worth knowing before editing it:** PowerShell's `-shl` keeps the **left operand's type**, so decoding a PNG's big-endian IHDR dimensions straight out of a `byte[]` truncates every shift back into a byte and reports every image as 0×0 (`[byte]1 -shl 8` is 0). The `[int]` casts around those shifts are load-bearing. The builder also refuses to trust a filename — it checks each PNG's declared dimensions against the size it is being filed under, since a ladder exported at the wrong DPI would otherwise be assembled into a directory that lies about its own payloads.
- **MonoGame does set a window icon, and it is not enough.** `WinFormsGameWindow.SetIcon` calls shell32's `ExtractIcon`, which returns a **single** handle at the system large-icon size (measured 32×32 at 96 DPI), through `Icon.FromHandle` — which keeps no icon-file bytes, so WinForms' small-icon path has no frames to choose from and can only copy the large one. Measured on the live game: the window published **ICON_SMALL as a 32×32**, i.e. the title bar was squeezing the 32 px artwork into 16 px while the authored `ico6-16.png` sat unused in the exe. `BS3DGame.ApplyWindowIcon` fixes it with `PrivateExtractIcons` — the API that picks a *named size* out of a group — straight from the running executable's own resources, so there is no second copy of the icon to keep in step. It reads `Environment.ProcessPath` and **not** `Assembly.Location`, which is what MonoGame uses and what comes back empty under a single-file publish (where MonoGame's own `SetIcon` silently does nothing and this becomes the only thing setting the icon). The **order is mandatory**: assigning `Form.Icon` makes WinForms send *both* messages, deriving the small one by stretching, so the authored small frame has to be `WM_SETICON`'d after it. It runs after `base.Initialize()`, so the window handle exists and MonoGame's own assignment has already been published — this has to win that race, not lose it. Measured after the fix: ICON_BIG 32×32 and ICON_SMALL 16×16, both 100 % pixel-exact against their authored PNGs, and both held across two F11 fullscreen round-trips (window 1616×939 → 1920×1080 → back), so nothing has to re-publish them on a resize.
- **`System.Drawing.Icon` can never select the 256 frame out of a group,** because `ICONDIRENTRY` stores 256 as `bWidth = 0` and its best-fit metric is `|bWidth − requested|` — asking for 256 returns the 96 instead. It happens with an all-DIB file too, so it is a GDI+ limitation and not a defect in the file, it degrades to a correct smaller icon rather than a blank one, and nothing here asks GDI+ for 256. Use `LoadImage(..., IMAGE_ICON, cx, cy, LR_LOADFROMFILE)` if a frame above 128 is ever needed in managed code.
- The **Testbed and the MapEditor deliberately keep the old single-frame `Icon.ico`** — the tools are not the shipping game, and telling their windows apart from it at a glance is worth more than a crisp icon on a developer executable. (All three were byte-identical before this, so `Game/Icon.ico` is the only one regenerated; copying it over one of theirs is all it would take to change that. `Build-Icon.ps1`'s `-Output` resolves a *relative* path against the **caller's** directory, not the script's — only its default is script-relative — so pass an absolute path unless the shell is sitting in `Images\Icons`.) All three used to declare a `<PackageIcon>Icon.ico</PackageIcon>` beside the `<ApplicationIcon>`; it has been removed. It was inert — nothing packs these projects — and would have been invalid if anything did, since NuGet takes a PNG or JPEG there and never an `.ico`. The empty `<PackageIconUrl />` beside it was a dead NuGet vestige of the same kind and has gone with it, in all three and in `Prazsky.Core`.


## `width=` / `height=` reach the Game too

⚠ **They were the Testbed's alone until now, and the Game ignored them in silence.** A run asking for the owner's 3840×1600 came back at the windowed default of 1600×900 and the frame looked entirely plausible at the wrong size — which is the worst shape a capture fault can take, and the same shape as the `-c Release` and MGCB-skip traps in the `screenshot` skill. Several issues ask for a page or a HUD to be judged at the owner's own panel (a type size, a menu's layout, an aspect-dependent band) and could not have it.

They pin the **windowed** back buffer only. Fullscreen stays the display's, which is this project's standing rule — the game always renders at the panel's native resolution — and a capture argument does not get to break it.

**And `shot=` does not cap out**, whatever a run that seems to stop after three or four suggests. Measured: seven timestamps in one process, seven files. Its clock is the game's own and starts at the **first Update**, so every entry is that many seconds after content load, the device init and the splash — several seconds of wall time before the first one is even due. A schedule that looks truncated has been killed early, not throttled.

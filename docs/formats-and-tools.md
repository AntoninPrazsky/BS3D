# Formats and tools

What is written to disk and what edits it: the map and level JSON, the map editor, the level generator, and the executables’ icon.

Part of the BS3D documentation. CLAUDE.md holds the project overview, the build commands, the ball grid and the repo-wide conventions, and says which of these documents covers what.

## Levels and serialization

The designer-meaningful tuning of every scene lives in **`SceneConfig`** POCOs (issue #44), one concrete subclass per `SceneKind` in `Prazsky.Core/Render/Config/`. **Since the format-2 refactor these are the scenes' FIXED parameters, in code and nowhere else** — a level names its scene and never carries a config, so a change to a scene's defaults reaches every level of that scene at once, with no file to regenerate. Only look/mood dials and particle/tree/building counts are exposed — mesh grid density and other hard limits stay as constants in `SceneRenderer`. `SceneRenderer` holds one config instance per scene and reads its values in `Apply*Parameters`/`Build*Buffers`; `SceneRenderer.Apply(SceneConfig)` re-pushes a scene's effect parameters and rebuilds the scatter/particle buffers it sizes (acacias, birds, snow, spray) at runtime — since format 2 that is the **live tuning panel's** path alone (below), never a level load's. A `CitySceneConfig` is a no-op in `Apply` (the city lives outside `SceneRenderer`, in `City` + the instanced city technique), so its caller rebuilds the `City`. The shared savanna/desert/outback bird flock is sized to the **largest** of the three configs' counts, or a desert scene's flock would be silently capped to the savanna's. Its geometry is not sized from anything — since #235 a bird is one shared rest-pose mesh, and only the per-bird orbit and flap state is rebuilt. Colours are `Rgb`, 2D/3D vectors `Vec2`/`Vec3` — all **reference types** (see "The scene-config panel" for why), holding linear values that may exceed 1.

A **level** (issue #32, `Levels/Level.cs`) bundles a ball map with the **name of the scene** it plays in and the sky dome — everything needed to make a map play (and preview) as authored, and nothing that can be re-derived or that is fixed in code. It is a JSON object marked by `"format": "bs3d-level"`; `Level.IsLevelFile` is a cheap probe that tells it from a plain map file (both use `.json`), robust to a directory or unreadable path (returns false rather than throwing). The ceiling, physics statics and cannon/camera placement are **not** stored — they are all derived from the map size at load (`FitCeilingToMap` / `FitCannonAndGameCameraToMap`) — **and neither are the scene's parameters** (format version 2): version 1 serialized the active scene's whole `SceneConfig` into every file, and an audit before the change found every shipped level carrying pure defaults — tens of kilobytes per file restating what the code already said (`Colossus.json`, hand-authored, literally said `{"kind": "moon"}`). The one authored exception, the Testbed's `Level_SavannaDusk.json` test file, loads as a plain savanna now; its dusk lived mostly in its dome (13), which it keeps. Both executables **load** levels — the Testbed's `DeserializeMapFromFile` and the editor's `DeserializeMapFromJsonFile` probe and route a level through the scene/sky switch, a plain map through the layout-only path; the whole dispatch is wrapped so a broken or hand-edited file logs and leaves the running program untouched instead of crashing. The Testbed's startup `sky=` still pins the dome over a startup level's own dome. The **editor saves** levels (F4): the scene's name, the dome, the map — and the `music` and `author` a loaded level carried, which the old save silently dropped (the round-trip-unpins-the-theme trap this document used to record is fixed with the format).

A level may also name **which composition it plays**, in a `"music"` field: `"pulse"`, `"bohemia"`, `"nocturne"`, `"mural"` or `"ember"` (#120; `"dechovka"` still parses as an alias for `mural`, the piece that replaced it in #264). Leaving it out hands the choice to the set's own rotation, where a level's *position* picks the piece, so a set sounds varied without a single file having to say anything. That was the normal case until #194 and is now the exception: **every level in `Game/Levels` names its theme**, because the theme is a property of the campaign's five-level *block* rather than of the level, and because a rotation keyed to position means the order cannot be rearranged without silently rescoring the campaign — which is exactly what reordering into blocks does. It is a **string rather than an enum** on purpose, and for the same reason a scene is: the music lives in the game executable while this format is the shared library's, so the name is a parse key (`ProceduralMusic.ThemeFor`), matched case- and whitespace-insensitively, and an unknown spelling falls back to the rotation instead of throwing a hand-edited file out. That fallback is silent and is the trap to know about here: **a misspelled theme does not fall back to Pulse, it falls back to whatever the level's position happens to give**, so it reads exactly as if the field were absent. `LevelGen` echoes each level's theme back off the *loaded* file for that reason, and groups its own printout by block so a block whose five levels disagree says so. One more edge worth knowing: **`MapEditor`'s F4 save used to drop `music`** (and `author`), so round-tripping a level through the editor silently unpinned its theme — fixed with the format-2 refactor: the editor captures both off a loaded level and writes them back (it still overwrites `name` with the chosen file name, deliberately). See "The rotation" in `docs/game-feedback.md`.

A level may also name **what its balls are made of**, in a `"balls"` field (#258): `"beach"` — the moulded vinyl beach ball the game has always drawn — or `"bubble"`, a hollow glass bubble with the type colour dyed into its film. Absent, which is what every level authored before the field says, is the beach ball, so no shipped file had to be rewritten and none was; unknown spellings read as absent rather than as a refused file, the leniency `"music"` and `"scene"` already take (`BallStyles.TryParse` also answers to `"bubbles"`, `"glass"` and `"vinyl"`, which is what a hand-editing author reaches for). It carries **no format bump**, deliberately: an older build ignores an unknown property and draws the level in vinyl, so the level still opens, still plays and still scores identically — a degraded *look*, which is what the version gate is for refusing when it would be a broken *file*, and the same argument admitted `"music"` at version 2. The map editor cycles it on **L** and writes it back on `F4` — and writes it **only when it is not the default**, so a round-trip does not start adding `"balls": "beach"` to every level in the set. What the style actually does to a ball is under "Ball rendering" in `docs/rendering.md`; nothing in the simulation, the lattice, the match rule or the score reads it.

The `"sky"` dome number a level carries is **inert for the four sky-replacing scenes** — space, the dream, the cavern and the Moon (`SceneRenderer.ReplacesSky`, issue #142): the dome mesh is not drawn there (each host guards `_sky.Draw` on the negation of `ReplacesSky`), the clear colour is black rather than the dome's horizon, clouds are suppressed, and each of those scenes' own `*LightingConfig` overrides the dome-derived light rig entirely (`SceneRenderer.TryGetLightRig`). The Moon keeps a ground under its replaced sky, but it sources its sun and fill from `MoonSceneConfig`, not the dome — so the number is just as inert there. A cavern, dream or space level plays identically with `"sky": 13` or `"sky": 1`; all the number still pins is `_skyDomeNumber` — what NumPad1 / B / the settings row cycle *from*, and what the editor's info line echoes — never a pixel. The field stays in every level file (it is uniformly shaped, harmless to carry, and means well as "the dome this level was authored against"), but a designer tuning one of these four scenes should not expect changing it to do anything visible.

A **`LevelSet`** (`Levels/LevelSet.cs`) is the tier above: a `"format": "bs3d-levels"` file listing level files **in play order**, so which level is first and which is second lives in one place rather than in a directory listing. Entries are objects (`file`, optional `name`, an optional `block` naming the chapter it belongs to, and the level's **rules** — `shots`, `minStars`, `ceilingStep`) whose paths are relative to the set's own directory. The rules live on the entry rather than in the level file because this is the only place that can annotate a **plain map file**, which has nowhere to put metadata of its own. All three are **nullable, and null means "no rule" rather than zero** — a set authored before rules existed has to keep playing exactly as it did, and a sentinel cannot say the difference between "unlimited" and "none"; what each null falls back to is documented where it is *read*, not where it is declared. `Load` rejects a rule that is present but meaningless (a zero budget, a zero ceiling step, a negative star gate) rather than letting it surface as an unplayable level. `minStars` — the campaign star total the entry itself unlocks at — **replaced a per-entry `minScore`** that no shipped set ever authored (#111): a raw score is meaningless to a player as a target, and gating on the campaign's star total makes every level contribute. It sits on the entry it locks, so the picker reads each level's gate straight off it. (`Count` is `[JsonIgnore]`d — STJ serializes read-only properties, and every saved set used to carry a `"Count"` the loader then had to shrug off.) The game reads one set; the Testbed and the editor do not (they open whatever file they are handed). See "Levels in the game (Game)" in `docs/game-session.md`.

**`PlayerProgress`** (`Levels/PlayerProgress.cs`, #92) is the save that measures a set: a `"format": "bs3d-progress"` file holding each entry's best score and best stars, keyed by the entry's `file` — the identifier that survives a renamed display name and a regenerated set (an entry a set no longer lists simply goes unread). The game reads and writes `Progress.json` beside `Levels.json`; the star total over the bests is what `minStars` gates against. Unlike every other loader here, `Load` is **lenient** — a missing, unreadable or malformed file comes back as a fresh empty progress, because an absent save is the normal case (a first run) and a corrupt one must cost the player their stars, never the game. `Save` still throws like `LevelSet.Save`; the game wraps it (`BS3DGame.SaveProgress`) and a failed write costs the write, not the session.

Serialization is **System.Text.Json** throughout (issue #38; Newtonsoft is gone). STJ has no native multidimensional-array support, so `Balls3DArrayJsonConverter` reads and writes the exact nested `[x][z][level]` shape the legacy map files use (they were written by Newtonsoft, which does it natively) — a plain map file and a level's embedded map stay byte-shape-compatible, and legacy maps that omit the field dimensions still load (STJ defaults them to zero, and `BallsMap` then adds the extra bottom levels). A level's `"scene"` is a plain **name** since format 2 — the `scene=` command line's own parse keys (`SceneRenderer.TryParseScene`; `"neon"` for the neon city) — read and written by `SceneNameJsonConverter`, whose reading is deliberately lenient the way `music`'s is: an unknown name is a null scene (the consumer keeps its backdrop), and a **version-1 file**, where `"scene"` was a full `SceneConfig` object serialized polymorphically on a `"kind"` discriminator, still loads — the converter reads the object's `kind` (and its `Neon` flag, which is how version 1 told the neon city from the day one under one discriminator) and ignores every dial. The version bump to 2 exists for the other direction: a build older than the change refuses a new file with a plain versioned message instead of a polymorphism exception. `BallPositionType`/`BallPositionTypes` carry `[JsonPropertyName]` only.

## The music bakery (Tools/MusicBake)

`Tools/MusicBake` **renders the game's six pieces of music to .wav and measures them**. `dotnet run --project Tools\MusicBake -c Release -- --out <dir>` writes `pulse.wav`, `bohemia.wav`, `nocturne.wav`, `mural.wav`, `ember.wav` and `menu.wav` and prints a table beside them; `--no-wav` prints the table alone, `--theme <name>` does one piece.

It exists because **music is the one part of this game that cannot be judged from a screenshot**, and could barely be judged in the game either: hearing a piece there means playing a level of the right chapter for two minutes, and until #229 hearing the *same* piece twice was impossible by construction. Every number this document and `docs/game-feedback.md` record about the music was measured through a private baker reached by reflection from a throwaway harness, three times over (#119, #218, #264); this is that harness kept.

- **It compiles `Game/Audio/ProceduralMusic.cs` into itself** rather than referencing the Game project, and calls `ProceduralMusic.Render` — the same door the game's own playback goes through, so what is written to disk is the arithmetic the game plays and not a second copy of it. A `ProjectReference` would drag WinForms, the MGCB content build and a Windows target framework behind a tool that writes .wav files; instead it takes MonoGame the way `ScoreSim` does, compile-time only (the bakes name `MathHelper`, and nothing here touches an audio device).
- **What the table says**, a row a piece: length, render time, **where a level comes in on the piece** (`entry`, in seconds — `-` for the menu loop, which is a lobby and plays from the top), peak and RMS in dBFS, channel balance, the mono fold's cost, then where the energy sits in six bands (under 100 Hz, 100–200, 200–500, 500–2k, 2k–6k, over 6k) as a percentage of the whole, then the RMS of the first and last half-second — which is what says a piece's repeat joins in silence rather than on a click. The bands are measured off the mono fold, since that is what a listener on one speaker hears.
- **The envelope under each row is the arrangement as numbers**: the RMS of every two seconds of the piece in dB under its own loudest two seconds. A section 20 dB down is a hole; a piece whose first ten readings are all far down does not start for twenty seconds. That column is what #201's "it comes in long after the level starts" turned out to be, and it is the one measurement here that reads an arrangement rather than a mix. It is also what the `entry` column beside it is checked against: an entry is right when the reading it lands on is at the top of the piece's range rather than in its opening dip.
- **It is not a gate** and exits 0 whatever it finds, unlike the other two tools. There is no number that says a piece of music is good; the point is to put the piece in front of an ear and the numbers beside it, and the numbers only catch the faults that are *not* about taste — a piece that would arrive louder than the one it replaces, a low end that has gone missing, an image that leans, a seam that would click.

## The scoring simulator (Tools/ScoreSim)

`Tools/ScoreSim` plays **every shipped level several ways through the real `ScoreKeeper` and `StarRating`** and **refuses a scoring rule that rates them wrongly**. `dotnet run --project Tools\ScoreSim\ScoreSim.csproj [levels directory]`; with no argument it walks up from its own bin directory to the first `Game\Levels` it finds, by landmark rather than by counting `..`, exactly as LevelGen does and for the same reason. It is in `Game.sln`, plain `net10.0` with MonoGame `PrivateAssets="all"` — it draws nothing.

It exists because of #173, and the shape of that defect is the argument for it. The rating was **ordered backwards**: the score rose with the number of shots taken, on every level in the pack, so the play style four of them are *designed* around was the one the stars punished. **Every individual number looked reasonable on its own** — the fault was only visible in the ordering *between* play styles, which is exactly what no amount of reading the code shows you. The levels had a validator and the scoring had nothing.

- **It models none of the scoring — it calls it.** So it cannot drift from the rules the way a written-down copy of them would, and a change to `ScoreKeeper` is felt here on the next run. It reads the **shipped set** for ball counts and budgets rather than carrying its own table, which caught three counts a hand-written table had wrong.
- **Three refusals, all with a non-zero exit** so this can go in front of a commit. **INVERTED**: an efficient clear rates no better than spending the whole budget — the #173 defect itself. **UNREACHABLE**: the best clean clear cannot earn four stars, which is what was reported from play. **UNEARNED**: a clear that misses one shot in three still earns four, i.e. the top of the scale means nothing.
- **Verified to actually guard**, which is the only thing that makes a guard worth having: put `MultiplierStep` back to 1 and `UnusedShotWorthInShots` to 1 — the pre-#173 rules — and it exits 1 reporting INVERTED and UNREACHABLE on level after level.
- A level with an **unlimited budget** is skipped rather than failed: it has no efficiency to rate and no completion bonus to earn, so the rating simply does not apply to it.

## The level generator (Tools/LevelGen)

**Every level of the campaign but one is generated, not drawn**: `Tools/LevelGen` (a plain `net10.0` console tool, in `Game.sln`, referencing `Prazsky.BS3D` and `Prazsky.Core` with MonoGame `PrivateAssets="all"` exactly as the libraries do) writes them and rewrites `Levels.json`. `dotnet run --project Tools\LevelGen\LevelGen.csproj [output directory]`; with no argument it walks up from its own bin directory to the first `Game\Levels` it finds. It always writes the **whole** set. The one exception is **Colossus**, which is hand-drawn: its entry's rules are stated in the tool verbatim and its own file — scene, sky and `music` — is authored, so the generator has no opinion about it beyond where it sits. (This said "Three to Seven … One and Two included" until #194, from when the pack was five generated levels between two hand-authored ones; One has been a design since it was regenerated, and "Two" is Colossus, renamed when it moved from second in the order to last.) The set's **unlock ramp** is the tool's too (`MinStarsAt`), and deliberately a function of the entry's *position* rather than of any design — which level a gate guards is a property of the play order, so a design moved in the order carries its new place's gate: the opener is free, the second entry asks 1 star, and from the third the ramp climbs 2 per level, so par (two-star) clears keep the road open with no replays while the most a player can hold at entry *i* is 4 × *i*. That survived the campaign growing from 14 entries to 25, to 30, to 35 and now to 40 without retuning, and it was checked rather than assumed each time: a player who two-stars everything ahead of entry *i* holds 2*i* against a gate of 2(*i* − 1), which clears by two at every position however long the set is, and the last entry's gate of 76 is still under half the 156 that four-star clears would have banked.

### The campaign is nine blocks of ten (#194, #207, #182, the Arcade, #253, #255)

The order the tool emits is not a ramp of single levels but **blocks of `BLOCK_SIZE` (10)**, each block **one scene, one dome, one music theme, one ball material and one statable style**, contiguous — so a fixed chunk of ten *by position* **is** a block, which is what #184's block-completion celebration needs and what a flat list could not have given it. There were five of them at #194, six since #207 added the desert, seven since #182 appended the Nebula, eight since the Arcade and nine since #253 appended the Spectrum. The campaign's light drains out of it as it goes — past the airless black into deep space since #182 — and then the Arcade turns it back on, artificial, because past the void there is no darker place to go; the Spectrum turns it back to **received** light, on the Arcade's own skyline at morning with the neon off, which is the one direction left after that and the one pairing in the campaign that repeats a place on purpose. **Every chapter is ten levels since #255, and the five that were added to each keep the chapter's own style rather than extending it.** The owner's ask was for the campaign to be twice as long and for the new levels to be *surprising*, to make the lattice's cannonball packing visible, and to stage the physics -- the thing he singled out about `Helix`, that a cluster left hanging on slender links springs and swings after every shot. So the additions are read as five more answers to a question each block already asked: the Meadow's are lathe bodies with suspension in them (a waist the lower cone pendulums through, feathers whose loss tips the cork they carry), the Coil's are five new slender topologies (a pendant on a V of chains, an orb web, a tower crane, a Calder mobile, a suspension bridge), the Reveal's are payoffs that *do* something where the first five were objects at rest (a balance that springs when a pan is cut, a weight on a double coil), and so on. **The block finales did not move**: `Gem`, `Zebra`, `Knot`, `Lean`, `Lantern`, `Colossus`, `Garland`, `Globe` and `Turbine` keep their tenth seats, so the milestones fire where they did and the campaign's last word is still Turbine's.

- **The unlock ramp needed no retuning at ninety entries, and that was re-derived rather than assumed.** `MinStarsAt` is a function of position, so doubling the set doubles the gates: a player who two-stars everything ahead of entry *i* holds 2*i* against a gate of 2(*i* - 1), which still clears by two at every position, and the last gate is **176 stars against the 356 that four-starring the eighty-nine before it would bank** -- 49.4 %, still the under-half the ramp has always kept. `PlayerProgress` is keyed by the entry's **file name** and never by position, so a saved campaign survives the whole change untouched.
- **Two of the new designs measured as accidental plates and one was left alone deliberately.** `Pagoda` took **88 %** of its own cluster on a single ball and `Amphora` **81 %**, against a pack whose worst had been Smiley's 52. A pagoda is a vertical chain -- core storey, roof, core storey -- so every roof is the sole link to everything below it and one colour a course made it a plate; cut into quadrants the way its cores already were, a colour is two opposite sheets that meet nowhere and half the roof always holds (**88 % -> 10 %**). The Amphora fused **across its own axis**: four gores put the two orange ones opposite each other, six on two inks makes neighbours and opposites both differ (81 % -> 68 %), and the rest was the solid foot and neck, where every gore is within a cell of every other whatever the count -- those ends are painted out of a palette of their own now, in two colours rather than one because the neck is what the vase hangs from (**-> 12 %**). `Kepler` keeps its **85 %** because it is a string of beads and *pop a waist and everything below it goes* is the level: the band across the ninety now runs **5-85 %**, and the top of it is cascades that were designed.
- **A sweep folded over the ANGLE is not a helicoid, and two Spectrum levels had to be measured to find it.** Written as a fold over the bearing with a slow drift down, every stop comes out a near-vertical stave -- and on a solid body the two staves a fold gives a colour meet through the core. `Totem` and `Pinecone` each measured **four standing groups on ~919 balls**, i.e. levels a perfect player takes in four shots, which is the Icicle's own recorded failure arriving from the other side. The block's canonical form is the one the Icicle states; `Totem` needed **a spine half a fold out of step** on top of it, because the axis is where every radial wedge meets its opposite and a drum 4.2 wide has a real core where the Icicle's cone has a tip (4 -> 19 groups). `Pinecone` kept its idea -- the gradient *is* the phyllotaxis -- by running the ramp **along** each arm and offsetting neighbours a stop, rather than holding one stop constant down each (4 -> 8).
- **One of the twenty-five lost itself in 1.1 seconds with no shot fired, and every gate had passed it.** `Bolt` is a column that jogs sideways at gusseted elbows, and a jog puts the whole of the column below an elbow onto that elbow's plate. Two of its four jogs were **five columns** against a section reaching two either side of its centre, so those segments overlapped **nowhere** and a two-level plate was carrying the join alone: the links existed, which is exactly why the disconnection gate was happy, and there were too few of them to hold nine hundred balls. A ball crossed the death line at **-7.84 against -7.50** while the camera was still settling. Held to three columns the footprints share two whole columns, the plate went to three levels and braces a joint that is already made, and the level hangs. That is the Trellis's own finding on a different shape -- *the gate that says the links exist cannot say there are enough of them* -- and the only thing that finds it is hanging the level unshot in the running game, which is what the twenty-five runtime checks are for.
- **The level picker holds ninety, and it was looked at rather than reasoned about.** #245 sized it for a campaign of thirty-five to forty; it is a scrolling grid four tiles wide (`LevelSelectPage`), so the growth is vertical and the page's own furniture is what had to be checked. Shot at ninety entries: the heading, the star total and **Back stay put while the grid scrolls under them** -- which is the property that page was built for, *a campaign is as long as it is, and the way out of the page must not be the thing that scrolled off the bottom* -- and the block boundaries read as they did.
- **Only the Spectrum's order is a difficulty ramp, so only it was re-sorted.** Its ten interleave rather than following the first five: standing groups **6, 8, 9, 10, 15, 14, 19, 22, 26, 31**, with the Icicle still opening (the plainest body states the premise) and the Turbine still closing. Every other block orders by its own recorded criteria and never was monotone -- reading a ramp into them and "fixing" it would be undoing decisions, not making one.
- **Shots-per-group is not comparable across a cascade design and a flat one.** `Gantry` priced at exactly **1.00**, the tool's own stated floor, and it is built of nothing but cascades -- a nine-ball sling group takes twenty-seven stones with it. It was never the unfinishable case that floor describes, but a level sitting *on* the line has no room for the shot that misses, so it went to 64 shots and 1.14. Nothing else was re-priced by ratio.
**A block's style is stated by its first level, and until #206 the Tower's was not.** That block's style is *the layout is deeper than the camera frames*, and Crown — its opener until then — is the one member of it that is framed whole: the only 16-level field in the block, and chosen to open precisely for that (a hollow ring teaching the axis, with the drain visible straight up the middle of it). So the chapter spent its first level on the one level in it that does not demonstrate what the chapter is. **Column** opens it now, being the plainest tall level in the game — a column reaching out of shot with no second idea in it — and Crown sits second, where its teaching reads exactly as well. The gates moved with the **order** and not with the designs, which is `MinStarsAt`'s whole point: Column 22 → 18, Crown 18 → 20, Horn 20 → 22, with Helix (24) and Lean (26) untouched, and no level file changed at all — a reorder rewrites `Levels.json` and nothing else. What the move costs is that the chapter now opens on the **longest level in the game** (90 shots, a ceiling step of 5), which is the thing to weigh if this block is ever paced again (#98).

**Five pieces against nine blocks, so four are reprised.** The first is **Pulse**, #207's bookend: the campaign opens on the piece Level One has always played and the Quarry brings it back — *forced* while there were four pieces and five blocks, a kept choice now, because a reprise at the end of the original ramp is a real musical idea where "every block gets its own" is only tidy. The second is the **Nebula taking `nocturne`** (#182): a seventh block against five pieces makes a second reprise unavoidable short of composing a sixth piece (#229's line of work, not #182's), and night jazz over the void is the register that fits — a desk decision, one constant (`MUSIC_NEBULA`) if the ear disagrees. The third is the **Arcade taking `pulse` back**: it is the only one of the five that sounds like the place it plays in, an electronic piece over a neon city, and it puts the campaign's last block on the piece its first one opened with — a frame round the whole thing or one reprise too many, depending on the ear (`MUSIC_ARCADE`). **The Coil takes `ember`, and that is #163 and #207 answering each other.** #163 wrote the rock ballad and left it with no block using it; #207 wrote, while it still had to reprise Nocturne on the desert, that this was the block with the weaker claim on a reprise and the one to hand the ballad to when it landed. Both came true at once, so the desert gets the amplifier and Nocturne is left to the Reveal alone. **The fourth reprise is the Spectrum taking `bohemia`** (#253), and it is chosen rather than left over: Bohemia is the one of the five whose form is a statement, a second subject and *a coda that brings the statement back*, which is what a final chapter is — and it evens the tally at two apiece for Pulse, Nocturne and Bohemia against one each for Mural (the Gallery's own piece since #264 replaced the polka in its slot) and Ember. The block themes are named once each, as constants, rather than five times per block — if a block's music changes it changes in one place.

**The Coil went in at 3 rather than on the end, and both halves of that are decisions.** Appended, a bright hot chapter would have followed the airless black one and taken the last word off Colossus, which is the level the whole ramp is built to arrive at; slotted third, the desert is the step the light was missing between the savanna's gold and the mountains' violet. Nothing had to be retuned to move eleven levels down the order, because the unlock ramp is a function of position — which is what `MinStarsAt` was written for. **The Nebula IS appended, and that reverses the second half of that reasoning deliberately** (#182, the owner's ask): the campaign's last word — the campaign-complete heading and confetti, which ride the set's last entry — moves off Colossus onto Garland. The first half survives, because space is not a bright chapter after the airless black one but the step *past* it, the ramp continuing outward. Colossus keeps every rule it had and still closes the Quarry. **The Arcade is appended behind the Nebula on the same terms**, and the last word moves once more, onto Globe: a neon city is not a step back into daylight either — its light is *made* rather than received, which is the one direction left after the void, and the city's facades stay dark under any dome. Nothing was retuned to append it, the ramp being a function of position; the entries simply run to forty and the last gate to 76 stars. **The Spectrum is appended behind the Arcade on the same terms again** (#253), and the last word moves a third time, onto `Turbine`: the one direction left after light that is *made* is light that is received again, so the campaign ends on the Arcade's own skyline at morning. Nothing was retuned once more — entries ran to forty-five and the last gate to 86 stars, against the 176 that four-starring the forty-four before them would bank. (#255 has since doubled every chapter, so the figures are ninety and 176 against 356; the arithmetic is unchanged and is re-derived in the bullets above.)

**A block exists in the data as a name on the entry** (`LevelSetEntry.Block`, #184): a run of **consecutive** entries carrying the same one is one block, and null on every entry — which is what every set authored before it says — means the set has no blocks and nothing celebrates one. Three candidates were weighed. A `blockSize` on the set would have been cheapest, but it can only make blocks all of one length and it gives the player's milestone nothing to be *called* — "BLOCK 3 COMPLETE" is a number where "THE TOWER COMPLETE" is a place. Grouping by the levels' own `scene` would need no new field at all, but a scene is a property of the level *file* while the grouping is a property of the *order*, so two sets sharing a level could not chapter it differently — and it would name a block after its backdrop, which is a coincidence of this campaign rather than a rule. The name says what the grouping is **for**, sits with the other per-entry rules for the reason those do, and needs no arithmetic to read. `LevelSet.Load` **refuses a name that opens a second run later in the set**: a block is a stretch of the campaign, so a name in two places is either a typo or a milestone that fires twice. `LevelSet` answers the five questions over it — `HasBlocks`, `BlockName`, `BlockRange`, `BlockNumber`, `BlockCount` — by walking the run on every call rather than caching a table at load, because a set is built in memory as often as it is loaded (LevelGen writes one it never reads back) and anything computed in `Load` would be absent exactly where a tool needs it. LevelGen sets it from the entry's **position** where it sets the music on each design, and the asymmetry is not an oversight: a theme is written into the level *file* so it must belong to the design, while a block is written into the *set*, which is built from positions — and deriving it from the position makes the blocks contiguous and equal by construction, which is the one thing `Load` refuses a file for getting wrong. What the game does with it is "Finishing a block of levels is its own moment" in `docs/game-feedback.md`.

Five things about this are worth knowing before touching it.

- **The scene pairings that moved, moved with an argument, and the arguments are in the code.** Six designs changed scene: One (savanna → meadow, because the savanna is the one campaign scene with point lights of its own and the level that teaches colour matching is the last whose colours should be tinted by the backdrop — and it misses 75 FPS at High on a 6900XT, #165, where the meadow's terrain is the cheapest in the game), Pinwheel and Gem into the meadow, Heart and Star into the savanna, Onion into the cavern, and Mosaic, Prism and Static onto the Moon. Two of those give something up and say so: **Star loses the wittiest pairing in the pack** (a star picture against the one scene whose own sky is already a star field), and **Mosaic keeps "dark" but gives up "enclosed"** — the Moon replaces its sky with black and drives its own light rig, so the CMY blocks are still the only saturated thing in frame, and vacating the cavern is what let the Reveal block have the one scene documented as chosen for being dark and enclosed.
- **A recorded decision is reversed.** The three pictures were deliberately *interleaved* with the geometric levels, "because they are all gentle by design, and three easy levels back to back is a lull rather than a ramp". They are a block now. What changed is the thing that reasoning rested on: in a flat ramp of fourteen a run of easy levels is simply a flat stretch of it, where a block is a chapter with its own scene, sky and music and a chapter of pictures is a change of register. The lull was real, though, and five gentle levels would still be one — so the block's two new pictures are the answer to it: **Elephant**'s symbol is drawn in three inks and **Zebra**'s in two, so neither has the single big payoff that makes the shipped three gentle, and the block's best single shot falls **40 % → 21 % → 9 %** across its last three levels.
- **Every chapter hangs a different material** (#258, #272). `Design.Balls` is a property of the *block* exactly as `Music` is — the material changes when the chapter does, not when the level does — and one `BALLS_*` constant states it for each chapter's ten designs. In play order: the Meadow **bubble**, the Gallery **wool**, the Coil **marble**, the Tower **ice**, the Reveal **lava**, the Quarry **metal**, the Nebula **plasma**, the Arcade **gem**, the Spectrum **porcelain**. Each constant carries its own reasoning; the placements are not interchangeable, because two of the styles are scene-bound (the metal goes flat on a dome with nothing to mirror, the plasma washes out on a bright one) and the bubble is the only style dearer than vinyl, which is why it sits on the block with the smallest clusters (385 balls, against the Quarry's 959). **The moulded vinyl beach ball is the one style the campaign no longer hangs** — nine chapters, ten materials — and it remains what the map editor, the Testbed and any unauthored map draw. Putting it back is one constant, at the cost of that chapter's own style losing its only home. A style is written into the file as `"balls": "<name>"`; a level that says nothing gets vinyl, so absent and `"beach"` mean the same thing to a reader and the writer omits the field rather than stating the default.
- **Nothing refuses a broken block.** The four validation gates below are per level; that a block's five levels agree on scene, dome, theme and ball material is not a property any of them can see. `WriteLevelSet` therefore groups its printout by block and reads the scene, dome and theme back off the **level files the game will load** rather than off the designs that wrote them, reporting `MIXED SCENES` / `MIXED` / `MIXED THEMES` where they disagree. Colossus is the level that makes this necessary: the tool does not write its file, so its `"music"` has to be authored in `Colossus.json` itself — it agreed by luck before this was noticed, because position 25 gave `24 % 4 = 0`, which is Pulse, which is the Quarry's theme. That luck is now gone **twice over, and independently**: #163 made it five pieces, which alone turns the same position into `24 % 5 = 4`, and #207 made it thirty entries, which moves Colossus to position 30 and gives `29 % 5 = 4`. Both land on Ember — so an unnamed Colossus would put the Quarry's finale on the rock ballad, which is the Coil's piece eleven levels earlier. The authored field is what holds it, which is the point of authoring it.
- **The Coil's dome was picked by looking, and the palette table would have picked the wrong one.** Five warm-sunset candidates were shot in the running game against the desert and three of them — 2, 10 and 18 — came out a **pink** within a hair of the mountains' violet, because a dome's fiery lower rings sit below the horizon where the scene's own terrain covers them and only its upper rings are ever seen. Dome 6 is the one of the eighteen that is cool where the ground is warm, which is the desert postcard and belongs to no other block. Dome 16 (a near-black zenith over pale sand) is the most striking frame of the six and makes the cluster pop hardest; it was passed over because it is darker than the violet dusk that follows it, which would make the next block a step back into the light.

### What a design is, and what the tool refuses

A design is one `Design` object: a silhouette (a predicate on the centred polar or taxicab radius, or since #130 on the **raw lattice indices**), a colouring, a scene, a dome, since #194 a music theme, and the set entry's rules. The point of the tool is not the writing — it is that **the three things that make a pattern level wrong are all invisible in a screenshot**, and each was got wrong here at least once:

- **Nothing may float free of the glass.** Read back through `Level.Load` and `BallsMap`, then `GetCellsDisconnectedFromCeiling` must be empty, or the layout drops the moment the level is built.
- **No colour's best shot may take the whole cluster.** Balls hang off the field's *top* level, so a same-colour group spanning it is the last anchor for everything below: one matching ball ends the level. The drop test releases a group on a throwaway map and counts what is orphaned with it; over `ONE_SHOT_PERCENT` (90) fails. Horizontal colour bands are the obvious way to stripe a cluster and are exactly this trap — Mosaic and Gem were both banded first and took 100%.
  - **⚠ It tries EVERY group of a colour, not merely the largest, and it did not until #98 — which is how a one-shot level shipped.** How much comes down is not monotonic in group size: a small group can be the cluster's last anchor while a much larger one merely hangs off it. Worse, testing only the largest had to break ties, and it kept whichever group of the winning size the scan reached first. `Column` is a 24-course column of horizontal bands whose anchor course is 21 balls of one colour and whose top two courses are one 45-ball group — **one shot took all 540 balls** — and the test measured one of the two *other* 45-ball groups of that colour and reported a comfortable 33 %. It had passed every run since the level was authored. The corrected test refuses it outright, and it refuses exactly one level in the pack: run over all forty, nothing else moved by more than a point. **A gate that is sound in principle and samples one case of several is worth no more than no gate at all on the case it misses.**
- **No ball may stand alone.** Cells on one level touch only their four **orthogonal** neighbours, never their diagonals, so a colour band one cell wide running diagonally is a string of balls that do not touch each other. A lone ball needs *two* landed balls to reach `MINIMUM_CLUSTER_SIZE`, which is a chore rather than a puzzle. The first Gem coloured its octahedron by `floor(m/2.2)` on the taxicab radius, which made its top layer's rim the single shell `m = 7` — twenty-eight isolated balls against the glass, with no level above to connect through either. Rings are two units wide now and every layer's rim stops on an odd `m`. `FindLonelyBalls` refuses the general case, and `RepairLonelyBalls` recolours the handful a rounded-off rim leaves behind (2 in Mosaic) to whichever neighbouring colour puts them in the largest group — a rim artefact belongs in the repair pass, a whole rim of them belongs in the design.

A design's field is `FIELD_LEVELS` (16) deep unless it says otherwise: `Design.FieldLevels` is what makes a **tall** level possible (Column is 34), and the emitter still refuses an odd layout offset, which would make the loader extend the field a level and move the design off where it was drawn.

- **Past 16 levels, field depth is a lever on HANGING HEIGHT and not on growth room, and that is the whole of #203.** `GameplayScreen.FitFieldToMap` hangs every field at `FIELD_TOP_Y` unless the field is deep enough that its bottom level would start past the death line, in which case it raises the **whole** field until the floor clears the line by `FIELD_FLOOR_MARGIN`. So depth added past that point pushes the layout *up*, and since a layout always hangs at the top of its field, this is the only lever a design has on how much air its lowest row starts with. The five **pictures** are what needed it: 14 rows in a field of 16 put their lowest ball 1.96 above the line by centre and 1.46 by surface, where every other level in the pack has at least 2.88 and most 7 to 8.5. They now take `PICTURE_FIELD_LEVELS` (18). **Every figure in this bullet and the one under it is against the death line at −5.5, where it stood until it was lowered onto the island** (`ArenaIsland.TOP_Y + 1`, after a report that a cluster which merely *swung* dipped under it a few shots into a level). Re-measured after that move: an 18-level field is no longer raised at all — it is pinned at `FIELD_TOP_Y` again, hanging 1.36 lower — and a picture's lowest ball starts **3.96** above the line rather than 3.33, which is 6.6 descents against a budget that buys six. The depth still does the work it was chosen for; two of the three units of air now come from the line rather than from the raise.
  - **What made it a fault rather than a tight margin is that the level's two clocks disagreed.** An untouched wall crossed the line on its **fourth** descent (1.96 / 0.6), against a budget that buys **six** on every one of the five — 60 shots stepping every 10, 55 every 9, 48 every 8 — so the ceiling could end these levels before their own budget ran out. Two smaller symptoms sat on top of it: the floor alarm arms at `CEILING_DEATH_Y` + 3 steps of 0.6 = −3.70 and the walls *started* at −3.54, 0.16 from lighting the net on a cluster whose own trigger budgets "a few tenths of a unit" of bob for a shove; and a stalk left dangling two lattice levels below the wall began at −4.95.
  - **Measured before and after on all five, off the game's own `[field]` line**: top Y 5.66 → 7.02 (and it now says *raised off the line*, the raise being what does the work), floor −4.95 → −5.00, lowest ball −3.54 → −2.17 — 1.96 → 3.33 above the line by centre, 1.46 → 2.83 by surface. An untouched wall survives five descents now and crosses on the sixth, which is where the budget ends anyway. The raise costs about 2.3° of the gun's elevation budget (`[aimcheck]`'s steepest cell moves from (0,0,14) at 67.3°/69.9° to (0,0,16) at 69.6°/72.0° of the same 80.2° limit, so all five still PASS with ~8° spare) and re-solves the camera a hair closer, 30.8 → 30.7 out on the 15-wide pictures and 31.5 → 31.4 on the 17-wide.
  - **18 is also the ceiling on this lever.** `GameplayScreen.FRAMED_LEVELS` is 18 and its test is `Levels > FRAMED_LEVELS`, so a 20-level picture would quietly become a **tall** level — fed by `FeedTallColumn`, aim-clamped by `TALL_AIM_HEADROOM` — which is a different kind of level, not a higher-hanging one. And 18 − 14 = 4 is even, which is what keeps every row's level parity and therefore the drawing itself exactly where it was. If this air is ever not enough the next lever is fewer bitmap rows, i.e. redrawing the pictures.

**A picture is a different kind of design (#130), and four facts about the lattice decide how one is drawn.** Every other shape in the pack is a solid of revolution or a taxicab shape, solved from a centred distance; the three pictures — **Heart, Smiley and Star** — are flat walls with a symbol drawn across them, read off a bitmap written as text in the source, top line first, so a mistake in one is visible in the diff. They need `Design.OccupiedBlock`, the raw-index sibling of the `BlockColour` the colourings already had. `Picture()` builds the pair of lambdas from the bitmap, whose own dimensions are the wall's, so a new symbol is added by drawing it and nothing else; `#` is the symbol, `o` an accent for a symbol with detail *inside* it (the smiley's eyes and mouth — a hole would be background, and background enclosed by the symbol is a pocket the wall's own background cannot reach), anything else the background.

- **The picture plane is (x, level), and the wall is thin in Z.** The gun starts at +Z looking at the origin, so X runs across the screen and the level axis up it; a wall spanning X and *Z* instead would be drawn on the floor and seen edge-on.
- **It is two cells thick, not one.** Which diagonal offsets are a cell's cross-level neighbours depends on the level's parity, so a wall one cell thick in Z has half its vertical neighbours reaching to a Z that is not there. Two is the thinnest slab that holds whatever the parity, and it doubles every group, which is most of what keeps the strokes clear of the lonely-ball floor.
- **Rows are shorter than columns are wide.** Levels sit 1/√2 apart against a cell pitch of 1, so a bitmap drawn square comes out squashed to 71 % of its height. A picture is drawn about 1.4× taller in rows than it is meant to look — the heart is 14 rows for 13 columns and comes out very nearly square.
- **The symbol must not reach the wall's edge, and the top rows must be background.** This is the drop test's trap arriving from the *other* side, and it is what the first draft got wrong: a symbol filling the full width and touching the top row is one connected group holding everything under it up, and dropping it took **93 % of the level in one shot**. Background down both sides and across the top is what keeps the wall hanging when the symbol goes. The background is a 2×2 check of two colours for the same reason Mosaic's blocks are — one flat colour behind the symbol is the identical trap from the first side.

**How many inks the symbol is drawn in is the difficulty dial — and the background's palette is not.** That asymmetry is the whole finding of the Gallery block, and it cost two rounds of screenshots. A symbol drawn in *one* ink is one connected group by construction, so its own colour drops more of the wall at once than almost anything else in the pack: Star 40 %, Heart 42 %, Smiley 52 % — comfortably inside `ONE_SHOT_PERCENT`, and deliberate, because on a level whose point is being recognised the symbol coming away in one piece is the reward. The same drawing split across more inks has no single payoff at all: **Elephant**'s face takes **21 %** of its wall and **Zebra**'s stripes **9 %**, where either outline in one ink would have taken half of it. That dial is free.

The background looked like the same dial from the other side and **is not**. More ground colours does quarter every background group and does thin the magazine's draw — and it also *destroys the picture*. Measured by looking: the zebra over a three-colour warm check and the elephant over a four-colour one were both **unreadable**, because a symbol is drawn in the palette's least saturated colours (a zebra is black and white) and three or four saturated hues behind it mean the eye reads the check and not the shape. Both were fixed the same way — a **quiet two-colour ground**, cool behind the zebra so it is close in hue and luminance, warm behind the cool elephant so the contrast is hue rather than noise — and the difficulty moved onto the symbol's inks. So: two background colours, always, and never one; a picture level's difficulty is drawn in the symbol. A four-ink *scene* was tried too and dropped — a flat-crowned acacia with a low sun behind it and a band of ground under both, which passed every gate comfortably (420 balls, a 14 % best shot, the flattest colour spread of any picture) and did not read at all, because a wide flat crown, a sun and a ground band are three horizontal bands and horizontal bands at this scale read as bands. **A wall of 15 × 14 cells carries a symbol, not a composition.**

Mechanically, `Picture()` takes a *palette* of symbol colours indexed by `SYMBOL_INK` (`#o+=`) rather than the `symbol`/`accent` pair it had while there were three pictures. An ink past the end of a picture's own palette is refused rather than drawn as background, since a hole in a symbol is the one mistake in a hand-drawn bitmap that looks deliberate. (The three shipped bitmaps come out **byte-identical** through the palette form — verified on the emitted `map` of each.)

The pack's one-shot band now runs **6–52 %** across the 44 generated levels — and every figure in this paragraph is a re-measurement, because until #98 the drop test sampled one of a colour's tied-largest groups rather than trying them all (see its bullet above); the band it reported was 5–52 % with `Column` silently sitting outside it at 100 %, and it is worth knowing what is at each end, because an earlier version of this paragraph put "the three pictures" at the top against "4–16 % for the geometric levels" and that was never true of One or Bullseye. The top is Smiley at **52 %** — a symbol drawn in one ink is one connected group by construction — and behind it the other two pictures, Heart at 42 % and Star at 40 %, for that same reason. **The gentle block that teaches what a colour group *is* used to sit up there with them** (Bullseye 45 %, Toadstool 42 %) and does not any more: #234's second pass cut its rings into sectors, and the four now measure **33 / 21 / 24 / 25 %** — Bullseye, Toadstool, Pinwheel, Gem. Their shells are as wide as they ever were; what changed is that a shell is no longer one group from the glass to the point, which is the same distinction One's own two figures below turn on. **One is the level that has sat at both ends of this band without its shape changing at all**: banded a course a colour it topped the pack at 74 %, because a course of a pyramid is load-bearing and the band that goes takes the tip with it; with the same three colours turned onto the pyramid's *walls* (#234's third pass) it measures **30 %**, because a shell hangs off the glass plate it reaches and not off the shell inside it. Same 385 balls, same courses, 44 points of difference — the figure is about where the colour boundaries run, not about how much is hanging. The bottom of the band is the hard end of the campaign, where nothing is a plate: Cube, Mosaic, Ziggurat, Lantern and Vortex all at 6 %, Globe with them since #301's rebuild (6 %, from 8). **`Column` is the level this band was hiding**: banded a course a colour it was a one-shot level at 100 % — the identical fault One records against banding a pyramid, in a shape where it is worse, since a pyramid at least widens towards the glass and a column is the same 21 cells all the way up. Its bands are unchanged and are now cut into a shell and a core one palette step apart, so the anchor course is a ring and a plug of different colours and whichever a shot takes the other still holds the column: **100 % → 8 %**, a perfect player 1 shot → 12, largest group 45 either way. The Coil's five sit low and flat across it (7–20 %), which follows from what they are: a shape made of slender members has no plate anywhere on it. **The Spectrum's five sit across the middle of it, 14–34 %**, and where each one falls is a reading of how finely its sweep cuts the body up rather than of its family: the Icicle's bare helicoid gives four spirals and 34 %, the comb-cut Kiln 25 %, the finale's 31 pieces 14 %. Those figures are the *second* set — the first, on sweeps tilted but not wound, ran 80 % and 92 % and are the whole reason the block's rule is a pitch (see below).

**Depth is not what makes a level last, and the Meadow block is where that was measured (#234's second pass).** The complaint was that One plays and the other four do not — the remains of One swing on their constraints after every shot, and the rest of the block just sits there. The cause looked like depth and partly was: Bullseye and Pinwheel were **four** courses and Gem six, so every ball of them was within a few levels of the glass and nothing could hang. But taking all three to ten courses moved only Pinwheel. Bullseye and Toadstool still finished in **three shots**, and the reason is worth stating because it is invisible in the shape: *a ring coloured on the radius alone is one connected shell from the glass to the point*, so three rings are three colours touching the glass and three shots take the cluster however deep it hangs. Every terrace size, taper step, palette size and per-terrace palette roll was swept against the game's own neighbour rule and **none of them clears four shots**, because none of them changes that. What does is an angular term: cut the rings into sectors and every group reaches the ceiling on its own, so taking one leaves the rest hanging instead of dropping it. That is the same fix the owner prescribed for One one pass earlier — colours on the walls, not on the courses — arrived at from the other direction. Measured, the block went 6 / 3 / 4 / 4 shots to a perfect player before and **6 / 9 / 8 / 7** after, with the body still hanging nine levels under the glass for most of them (Bullseye holds a waist of a single ball through four consecutive shots). Two designs are deliberate exceptions to the sector cut: **Gem** buys its groups with a fourth colour instead, because a cut facet is unbroken in life and a radial seam is the one thing that would stop the shape reading as a crystal; and **One** already had the fix.

### The sag gate: hanging a level instead of reading it (#301, #302)

**Every gate above reads the layout as authored, and all of them are true of a level that cannot be finished** — because none of them knows what the remainder *weighs*. That gap has now been found by hand four times (the Ziggurat's ring thickness, Garland's strand in #182, the Trellis's pitch and the Bolt's elbow plates in #253/#255), each time by hanging a level in the running game and watching it, and each time the note written down was the same sentence: *the gate that says the links exist cannot say there are enough of them to carry the weight*. #301 and #302 are that sentence one step later still — after a few shots have removed part of the mass — reported on nine shipped levels at once.

`Tools/LevelGen`'s **`SagProbe`** answers it by not reading the layout at all. It stands up the very simulation the game does — `PhysicsWorld`, the kinematic glass at `CeilingPlate.CentreYAbove`, the island's funnel floor, `BallsConstraintsBuilder.BuildBallsStructure` — hangs the level where `ClusterHang.FitWorldOffset` hangs it, and then **plays it**. The physics is entirely the game's: the same Bepu at the same `SolveDescription(8, 1)`, the same `BallSocket` lattice, the same 1/120 s step, the glass dragging the cluster down as it descends. After every shot the world is stepped while the matched group falls and **the remainder rotates into a new rest pose**, and the death line is read off the *live body poses* through the game's own `ClusterLineWatch`. It needs no graphics device; the simulation was never the part that drew anything. It is **opt-in** (`--sag`, or `--sag=Pylon,Orrery` to narrow it, which also turns on a shot-by-shot trace) because it plays whole levels five ways through a nine-hundred-body simulation, where every other gate here costs milliseconds.

**What is not simulated is the shot's flight.** Nothing is launched and no contact is waited for: the gun is a real `Cannon` (pose arithmetic with no renderer in it, seating its own trunnions off the island through the static `CannonRig.TrunnionHeightAt`), its line is swept against the live structure by `ShotPlacement.TryFindFirstHit` — the same sweep the game's landing preview runs — and the cell is `ShotPlacement`'s answer, so the ghost, the game and the probe cannot disagree about where a ball ends up. The landing then mirrors `BallContactEventHandler` step for step, including the order it had to learn the hard way (#265): the body is **put** in its cell before its constraints are made.

**The hang arithmetic and the loss rule had to come out of `GameplayScreen` for it** (`Prazsky.BS3D.Levels.ClusterHang`, with `ClusterLineWatch` beside it): a gate that hangs a cluster somewhere else, or forgives a dip differently, answers a question about a different game. That is exactly the fault #288 was closed on — an arithmetic that was correct about the wrong moment — and the point of sharing the figures is that the two cannot drift.

- **⚠ The probe's own first verdicts were all about a bug in the probe, and the shape of it is worth knowing.** `ReleaseSameTypeCluster` cuts constraints and only *then* wakes the balls it cut them from. In the game that order is safe by construction — a group is only ever released from inside the contact handler, on the frame a shot has just touched the structure, and the contact woke it. With nothing being fired, Bepu sleeps a settling cluster **in pieces** (the solver's active constraint count on a 502-ball level falls from 3836 to 2740 over four seconds of hanging still), so waking one ball wakes one island of several — and cutting constraints out of a sleeping island left the survivors holding a graph the solver never re-examined. The remainder came apart and fell at three quarters of gravity. The game's own note that *"one ball is enough for the cluster — the structure is a single connected constraint graph"* is true of the game and false of a probe that fires nothing, and `WakeCluster` therefore wakes every ball.
- **What it found, and it is 9 for 9**: every one of the nine levels reported in #301 and #302 sags, seven of them **with the glass still at rest** — which is the owner's own reading confirmed against the machine, and it rules `CeilingStep` out for good. Pylon and Bolt and Ghost go under on their **first shot**.
- **⚠ Its first model condemned three levels that play perfectly well, which is how the player half came to be rebuilt.** Asked "does any order lose this level" while it picked groups to delete, it lost **38 of the 90** shipped levels — Amphora, Giza and Saturn among them, all three then confirmed finishable from play. That refutation is what the rest of this section is about.

**⚠ The physics was never the hard part. The player was, and every wrong verdict this probe printed came from that half** — three faults in a row, each found only by being refuted:

- **It picked a group and deleted it.** That let it cut a vase's waist and leave the foot dangling: on Amphora it took a 57-ball group out of the middle on the first shot, with all twenty ceiling anchors intact and nothing orphaned, and the foot — cells with two lattice neighbours apiece — stretched five levels down. **No gun can make that cut.** The gun stands underneath and shoots up, which is what `TALL_AIM_HEADROOM_LEVELS` already says out loud (*"the column has to be eaten from the bottom"*); `SagProbe.AIM_BAND_LEVELS` is that constant and the aim is held to it.
- **It aimed at balls it could not see.** Pointing the gun at a ball deep in the body meant `ShotPlacement` dutifully landed the shot beside whatever the *line* met first, usually another colour entirely — so almost nothing matched and the cluster **grew** while being cleared, 502 balls to 513 over eighteen shots. A candidate is only taken now if the sweep comes back holding that very ball.
- **It was handed a zero orbit centre.** `Cannon.RecalculateRotation` builds its aim target as `Position + Transform(OrbitCenter, rotation)`, so that vector is doing double duty — a direction *and* the distance the aim point is thrown out to. Zero aims the gun at its own trunnions, `AimDirection` normalises `(0,0,0)` to NaN, and the probe fired nothing at all while scoring every level as survived. Both executables construct their cannon with `(0, 5, 0)`; so does this.

Two more followed once it was firing, and both were found the same way — by reading a trace rather than by thinking about it:

- **A bounce ended the run.** A shot that finds no free cell in either ring is the game's own bounce and costs a shot; the probe read it as *"this level cannot be played on"* and stopped, once with 946 balls still hanging, and scored the level as survived. The same shape of silent false pass as the NaN aim: a probe that stops playing reports no sag.
- **It aimed at a ball rather than at a gap.** Pointing at a ball's centre lets `ShotPlacement` land the shot in whichever cell of the ring the contact falls nearest, which is very nearly arbitrary — **29 % of shots matched**, the other 71 % stuck to the underside, and on Pylon the probe walked a column of its own misses six levels below the layout's floor and into the death line at shot 41. Then reported the *level* as sagging. Candidates are **empty cells** now, the matching ones first: **86 %**.

The model loads a colour the way `RandomBallType` does (uniform over the colours still standing, count-blind), aims at the gap, prefers the one that completes a group, and lets the shots that complete nothing **stick** — which is what puts balls back onto the underside, and is the difference between a probe and a wrecking ball.

**Calibrated, and here is the calibration.** Three levels are known finishable from play and nine are known not to be. Against that set the probe reads:

| known finishable | | reported unfinishable | |
|---|---|---|---|
| Giza | 0 of 5 | Pylon, Orrery, Globe, Pinecone, Pleat, Bolt, Totem | **5 of 5** |
| Saturn | 2 of 5 | Ghost, Cabinet | **4 of 5** |
| Amphora | 3 of 5 | | |

**Four losing orders in five separates them completely: all nine reported named, none of the three finishable.** That is `SAG_RUNS_TO_REPORT`, and it is the one threshold here fitted to play rather than chosen. ⚠ It was three while the player was a poor shot, and the way it moved is the point: aiming at the gap instead of at a ball took the match rate from 29 % to 86 % and moved every level the right way at once — Ghost and Cabinet up from 1 to 4, Amphora down the ranking to 3. **The separation is a property of a competent player, not of a threshold.** ⚠ One caveat the instrument itself measured (#301): the seeds fix the shot *sequences*, not the count — Bepu's threaded solve is not bit-deterministic, so an order whose deepest dip sits within a few hundredths of the allowance flips run to run, and a borderline level read 2, 3, 3, 3, 2 across five identical sweeps. A reading at the threshold's edge is repeated before anything is concluded from it; a 0 or a 5 is not.

**#301 then fixed its five against this instrument** — Pylon, Orrery, Ghost, Cabinet and Globe, which read 5, 5, 4, 4 and 5 of 5 as reported (Pylon on its first shot, glass at rest) and read **2, 3, 2, 3 and 3** fixed, none with the glass at rest — inside the band the finishable controls occupy, Saturn at 2 and Amphora at 3. What moved them is recorded on each design's own constants; the two findings that recurred across three of the five are the **diagonal fuse** (a cross-level neighbour IS a diagonal in (x, z), so a two-entry dither's same-colour blocks weld across levels — Ghost's body, Cabinet's woodgrain and Globe's ocean were one mechanism three times over, and a third entry in the band is the cure) and **the one-cell wall as a chain** (fourteen levels of it yield past the line under sustained load however braced the box looks — Cabinet's depth and Globe's shell both paid it).

**#302 then gave the four Spectrum spirals their banded tiers** — Pinecone, Pleat, Bolt and Totem had read 5 of 5 apiece (Bolt losing on its first shot with the glass at rest), and read **0, 0, 1 and 0** fixed, Bolt's one a hairline −1.00 exactly at the allowance, surviving orders clearing the levels outright. A tier is never a floor of one colour — the resolution against the block's own no-floors premise, and the rule every tier obeys, is written in the Spectrum block's header in `LevelGen`.

**The pack-wide sweep after both rounds of fixes** (solo, nothing else on the machine): **57 of 90 never sag, 11 lose one order, 14 two, 3 three, 5 four and none five** — the first sweep on which nothing reads 5 of 5. Above the report threshold stand five names: **Giraffe (4 of 5, glass at rest — a layout reading)** and **Cube and Donut (4 of 5, mostly with the glass stepped, which smells of the ceiling sum rather than the lattice)** — three levels nobody has reported — plus **Amphora and Cabinet at 4**, both threshold-edge wobblers whose counts flip between 3 and 4 run to run (Amphora is the calibration's known false positive; Cabinet read 3, 3, 4 across its post-fix sweeps), which is the ±1 caveat above doing exactly what it says. The poorer player's six extra names (Belfry, Organ, Vortex, Sail, Garland, Trellis) all fell to 2 or under once the probe could shoot — the slender-member note those designs carry stands, but the competent player is not troubled by them. ⚠ The probe still **refuses nothing** — it prints a ranking, and the levels it names are where to look first.

### The anchor load: what the glass actually carries (#301, #302)

Measured on every run, printed beside the group count, and **new**: only the field's topmost level is bonded to the glass, so a level's entire mass hangs from however many cells its own top course happens to occupy. The drop test asks what a shot *orphans*, which is a question about the lattice — a cell still joined to the top level by any path passes it. This asks the other half, which is a question about **weight**.

It came out of the probe rather than from reasoning. Hanging **Amphora** in the real simulation and shooting one group off it dropped the ceiling links from **20 to 14 with nothing orphaned**, and the vase then descended five and a half units in a second — through a death line it had started four and a half above. Every gate in this tool passed that level, and passes it still: nothing floats, nothing stands alone, its best single shot takes 12 %.

The pack's spread of *balls per surviving anchor at the worst single shot* runs from **Gantry at 3.4** to **Giza at 139.2**, and the shipped set sits across the whole of it: Trilithon 4.4, Cube 7.1, Cabinet 12.0, Ziggurat 12.7, Chest 13.8, Spring 15.1, Belfry 17.1, Vortex 25.9, Analemma 29.8, Pylon 34.0, Globe 35.1, Orrery 37.0, Bolt 64.7, Ghost 66.8, Ten 100.8. (#301's fixes moved the five it touched — Globe most, 92.4 → 35.1, the polar plateau's whole point — but only as a side effect; the loads above are the re-measured set.) **⚠ It does not separate the reported levels from the rest either** — Giza at 139 and Ten at 101 are worse than most of the reported nine ever were and are not complained about, while Cabinet was reported at 13.1 — so it is a figure to design against and *not* a gate, and no threshold is enforced on it. What it is good for is the same thing the group-count ratio is good for: knowing, while a design is being written, that a shape hanging 900 balls off five cells is asking something of the glass that a shape hanging 300 off ninety is not.

### The coiled levels (#207)

The Coil block is five layouts that hang on **slender links**, because that — and not the silhouette — is what makes a cluster spring. The cluster is one Bepu body per ball tied to its neighbours and to the glass along the field's top level, so a wide solid slab is stiff by construction and a long thin member is not. That is also the block's one structural danger, since slender links are exactly what the drop test refuses, and every design carries a **second load path**: Rope's four strands pinch together periodically so each hangs off the others; Minaret's ledge and core are tied at every level and coloured out of disjoint palettes so no group can span both; Basket's two rib families wind opposite ways, so the shell is a mesh rather than a set of lines; Pendulum's four ropes take two inks in diagonal pairs, so a colour taken cuts two and leaves two; Knot is a **closed loop** touching the glass three times, the one topology on which a single cut drops nothing.

Four things are worth knowing before touching it.

- **A palette here has to have a SUBJECT, and until #285 none of them did.** All five shipped with a colour rule that was nothing but the group topology — one free ink per member — so the crane came out with a green mast, a magenta stay, a silver-and-blue jib and a brown-and-white counterweight, and the owner read the block as "like a child randomly tried colours". The bar named in that report is **Horn** (#33), whose rule is nothing but *reading what is coming*: white core, red flesh, gold skin, three shells ordered by radius. A rig cannot be ringed by radius, so the equivalent is a subject — an orange-and-yellow crane on a grey steel jib with a red load; a Calder mobile, primaries hung on black-and-grey wire; a suspension bridge in International Orange over a grey roadway; a jewel on a gold chain and a steel one; a web whose one warm thing is the spider. **The topology did not move**: which member gets its own ink, which pairs are banded so a released colour thins a beam instead of severing it, and which are diagonal so no ink lists a rope both ways all stand exactly as they were, so every group and best-single-shot figure in the designs' own doc comments is untouched by construction. Where two inks touch, they are checked against measured CIEDE2000 (`.claude/skills/screenshot/palette.ps1 -Focus`) — which is what keeps red off orange (14.1 dE, the palette's tightest pair) and yellow off white (14.5, the second).

- **The whole block is hung deeper than it needs to be, on purpose.** `DUNES_FIELD_LEVELS` is 18 against layouts of 12 or 14 — the same arithmetic `REVEAL_FIELD_LEVELS` reaches and a different reason for it. The six or four empty levels under a layout are its clearance, so its lowest ball starts **5.38** above the line instead of the 3.38 a 16-level field would give it. (While the death line stood at −5.5 an 18-level field was also *raised* off it, hanging 1.36 higher for a clearance of 4.74; the line has since been lowered onto the island, so the field is pinned again and the air comes from the line being 2 lower instead — more of it either way.) On a block whose point is that the cluster swings, that clearance is the whole margin: #203 is the same fact arriving as a bug report on the picture levels, where gravity pulls part of a layout down into a stalk and the stalk crosses the line. Eighteen and not twenty, because `FRAMED_LEVELS` is 18 and a block the camera framed from the floor up would be a second Tower — **none of these is tall, and that is the Tower's boundary being respected rather than an oversight.** (#182 has since crossed that boundary deliberately — the Nebula is a second tall block at the owner's ask, its statement being the new colours rather than the Tower's premise; the Coil's own reasoning here stands as it was made.)
- **Two of the five passed every gate and were refused by a photograph.** `Rope` shipped first as three strands of 1.6 at a radius of 2.5: 285 balls, margin 2, nothing alone, nothing recoloured — and in the running game a shapeless column with no twist visible in it, because at 120° apart those centres leave barely a cell between neighbours and the lattice rounds it away. `Minaret` ran its ramp at a wedge of 82°, a quarter of the ring at every level, which over the 1.3 turns a twelve-level layout allows photographs as scattered lumps rather than as one thing winding. Both were fixed the same way — **thinner and further apart** (four strands of 1.3 at 3.0; a 63° wedge reaching out to 5.3 instead of 4.6) — and both cost balls to buy the shape. Nothing in `Validate` can see either failure.
- **A closed loop cannot be coloured by a formula on its parameter.** `Knot` is a (2, 3) torus knot, so it **touches itself**: arcs half a loop apart are neighbours in the field, and every such touch has to fall on a colour boundary or the two arcs are one group. Coloured as six arcs by `arc % 3` it measured **33 %** best shots against an expected 12 %, every ink reading as a single group — the loop had welded itself into three pieces. The fix is `KNOT_INKS`, a twelve-entry table solved against the contact graph **measured on the emitted cells**, which mattered: there are ten touching arc pairs, nine of them between arcs that are not loop neighbours at all, half again as many as reasoning about the curve predicts. The figure that says the table still holds is the tool's own *largest standing group*, 36 — about a twelfth of the level, i.e. one arc.

`Validate` cannot tell whether the thing looks like the intended picture, which is exactly what the `screenshot` skill is for; all three pictures were checked in the running game before they were called done, and so was all of #207.

It also prints, per level, **how many standing colour groups it is made of and how many shots the budget allows per group** — the number a budget is actually priced against, since one landed ball takes exactly one group with it (plus whatever that group was the last anchor for, which is what makes a design with cascades cheaper than the count says). It is not a gate, because the right ratio is a design decision and the pack spans two orders of it: **Colossus 0.98** (364 balls in 46 groups against 45 shots, the hardest level in the game), Static 1.43, the Arcade's five from 1.65 down to 1.37, the Nebula's around 3, and **Horn 20**, where four shells mean the budget is not the thing being fought at all. A design under 1 with no cascade in it cannot be finished, which is how the Arcade's first drafts were caught: every one of the five was over-tight before it was measured.

It exits non-zero when any level fails, so it can be put in front of a commit. What it cannot check is whether the result *looks* good: that is `.claude/skills/screenshot`, and it is not a formality — **two of the Gallery's own designs were refused by it after passing every gate**, and the third of them was dropped outright (see the picture bullets above); **two of the Coil's five were refused by it as well** (see above). `AimReachability` (whether the gun can reach every cell) is the Testbed's `aimcheck`, not this tool's — it needs the solved gun orbit, which needs a graphics device. Both were run over the whole of #194's new content: every new design was looked at in the running Testbed in its own scene and dome, and all eleven **PASS** `aimcheck`, the steepest being Chest's corner cell at 69.9° of a 80.2° clamp. All five of #207's do too, the steepest being Minaret's corner cell at 69.7°, all five of #182's — the steepest being Wishbone's corner cell at 54.1° of the same clamp — and all five of the Arcade's, the steepest being the Donut's field corner at 72.0°, its 17-wide field being the widest in the pack. **All five of the Spectrum's do as well, and they were checked through the Game rather than the Testbed** — every one of them is a tall level, and the Testbed's `aimcheck` stopped answering for those the day levels could be taller than the frame (it measures the Testbed's own fit, which stands the gun back far enough to see the whole field; see "Tall levels" in `docs/game-session.md`), so the figures are the Game's own `[aimcheck]` line over its working band: steepest 47.5° of a 50.4° limit, on Trellis and Turbine. `Tools/ScoreSim` still reports every level rating the right way round — all ninety of them since #255, whose own twenty-five runtime checks are in the bullets under the block table.

### The arcade levels (the eighth block)

The Arcade is **the Gallery given a third dimension**: five hollow solids with pixel art wrapped onto them, over the neon city. A Gallery wall shows its symbol from where the gun starts and the level is read in one glance; a cube shows one face, and the other three and the underside are read by walking the gun round it. Four things about the block are worth knowing before touching it, and three of them were paid for.

- **A hollow body's anchor is whatever its own top happens to be**, and only the field's topmost level is bonded to the glass. That is a 100-cell plate on the cube, 49 on the temple, a disc on the reel's head, an annulus on the donut — and about **twenty cells** at the globe's pole, where a true shell narrows to a point. One colour across any of them is a level that ends on the first lucky ball of it, so every cap here carries at least two colours interleaved; the globe's ice caps are broken into floes for that reason and not for geography's. The drop test is the check, and the whole block's best single shot is 11 %.
- **A one-cell-thick hollow ring does not survive its own weight.** The temple was drawn first as one-cell courses twelve levels deep and **lost itself in eight seconds with no shot fired** — the whole thing sagged past the death line while the camera was still settling. A ring that thin is a curtain of `BallSocket` links with nothing bracing it across; Garland found the same wall at 1.15 cells of strand (#182), and the Chest's two-cell box and the Vortex's two-cell wall are the ones that hold. It is two cells thick and eight levels tall now. The cube's one-cell walls are fine because a closed box is braced by its own corners — the shape matters as much as the thickness, and 35 seconds hanging unshot in the running game is how each of the five was checked.
- **The group count is the budget, and the ground's block size is what sets it.** These are dithered surfaces, so the number of standing colour groups is large and it is a design output rather than an input: the same cube measured **75, 44 and 34 groups** at three ground-block sizes, which is a budget of a hundred shots, seventy, or the fifty-six it ships with. All five are priced off the ratio the validator prints and ramp 1.65 → 1.58 → 1.50 → 1.44 → 1.37 shots a group, the finale tighter than anything in the game but Colossus and Static.
- **Black on navy is not a drawing.** The cube's cool faces were cyan-and-navy first, and in the running game the black glyph on them was invisible — half of every face was as dark as the symbol drawn on it. Both wall pairs are bright now (red/orange and cyan/magenta), which is the same finding the Gallery records from the other side: a picture's difficulty is drawn in the *symbol*, and its legibility in the **ground**.


### The spectrum levels (the ninth block, #253)

The Spectrum is **one hue family a level, swept through the whole body as a gradient** — the owner's brief was a chapter whose levels read as *one colour* rather than as a set of arbitrary matching ones, seeded by a level sweeping white → light blue → blue → dark blue and back to white as it climbs. Five families, all of them tall, all of them in the city at morning: `FROST` (white/cyan/blue/navy, the seed), `TWILIGHT` (white/magenta/navy/black), `MOSS` (white/green/olive/black), `HEAT` (white/yellow/orange/red/brown) and `SPECTRUM` — the wheel itself, seven of the thirteen in hue order, on the finale. Five things about the block are worth knowing, and the first two are the block.

- **No new ball colour is involved, and that is a constraint the owner stated rather than an accident of what was to hand.** A family is a **subset and an ordering** of the fixed thirteen `BallType` already has; the seed example needs nothing added, White(4)/Cyan(5)/Blue(3)/NavyBlue(12) sitting in exactly that order. The reason is #152's and #246's: each of the five colours added there was placed at a *measured* distance from an existing one — silver a cool slate so it does not vanish into the white gores, navy re-spaced against black once "darker than blue" had made it the same as black — and a hue picked to fill a gap in a ramp is precisely the way back into the trap those spacings exist to avoid. What this chapter adds to the palette is order, not paint.
- **The sweep is a helicoid, and that is not a look — it is what makes the levels playable at all.** The rule the block obeys is that **every stop of the family has to stand on the top level**: a stop that exists only further down hangs off the stop above it and nothing else, so one matching ball takes it and everything under it. The first cut of the opener swept a *tilted plane* — 3D, not a stack of floors, and it still measured **80 %** in the drop test; the Kiln's first cut measured **92 %**, over the gate. Wound instead, at a pitch of one whole folded family a turn, the top level carries every colour in wedges and what a cut leaves behind is a **screw thread** that still spirals from the tip to the glass. The same three levels then measured 34 %, 25 % and (the Hourglass, whose conical shells were closed *sleeves* round a waist before) **89 % → 17 %**. The tilt is what makes the gradient three-dimensional; the pitch is what makes it a level.
- **The fold is the brief and it costs an even colour count.** A sweep runs out through the family and *back* rather than wrapping (`Sweep`), because the seed says "and back to white": wrapped, every period would put navy against white along one hard seam, the single boundary in the family that does not read as a gradient. The price is that a fold of `n` stops has period `2n − 2` and hits the two **ends** once against the middles' twice, so white and navy come out at roughly half the count of cyan and blue. It shows in every one of these levels' reports and is left alone — a family's ends are its extremes, and being rarer is what makes them read as ends.
- **The block's order is a measured difficulty ramp, and the families are not what ramps.** A green level is no harder than a blue one; what varies is how finely each design's sweep cuts its body up. Standing groups run **6, 9, 15, 22, 31** across Icicle, Hourglass, Trellis, Kiln and Turbine — 6.67, 5.33, 3.47, 2.55 and 1.68 shots a group, from a level of four huge spirals to one of 31 pieces in seven colours, the finale landing inside the Arcade's own 1.37–1.65 band. One term was measured and *rejected* on the way: shearing the Icicle's sweep outward as well (0.9 levels a cell) carries each stop's ribbon across the gap to the turn of itself outside it and **merges** the level — six standing groups become four, one per colour, the whole thing in four shots. Every other design in the block wants that term; a bare cone under a bare helicoid is the one place it does the opposite of what it looks like.
- **The city was chosen for this block by looking, and the sea was refused.** The obvious pairing was the sea — the one scene of the original seven the campaign has never used, and "first light over open water" as the step after the Arcade's artificial neon. It is the worst backdrop in the game for *this* chapter for exactly the reason it looked right: the water **mirrors the dome**, so the sky's hue fills the top of the frame and the bottom of it too, and a chapter about telling neighbouring hues apart is then played inside one of them. Shot under four domes it came out monochrome every time; under dome 4 it was a magenta sky over a magenta sea, which is the trap already on record against the dream scene and magenta balls. The city's facades are the largest low-chroma surface in the game and its ground is grey, so only the top third of the frame carries the dome's colour — and it is deliberately the **same city the Arcade plays in**, at morning with its neon off, which says "light received again" harder than a new place could. Dome 11 was picked over 1, 3 and 9 on shots of the Icicle and the Hourglass (the block's coolest family and its most fragile): 1 and 3 put a cyan and a lavender sky behind a blue cluster and a magenta one, each swallowing the family it should set off, and 9 is a dusk, which reads as a step back into the dark rather than as light returning.

- **One of the five is bounded by the physics rather than by the drop test, and it says so out loud.** The Trellis's two ribbons close once over its 22 levels; winding them faster (0.032 → 0.055 turns a level) buys a *second* pass and improves every number the tool prints — green's best single shot 34 % → 19 %, standing groups 15 → 14 — and the level then **failed in the running game at ten seconds with no shot fired**, on "the cluster reached the line". At that pitch a ribbon steps its cells more than a cell sideways per level at the outer orbit, so consecutive levels barely overlap: the links exist, which is exactly why the disconnection gate passes, but there are too few of them to carry the weight and the whole thing stretches. **The gate that says the links exist cannot say there are enough of them** — Garland found the same wall by strand thickness (#182) and the Ziggurat by ring thickness, and the only thing that finds any of them is hanging the level unshot in the game.

All five **PASS** the Game's own `aimcheck` (steepest 47.5° of a 50.4° limit, Trellis and Turbine) and all five hung **35 s unshot** in the running game without sagging near the death line. `Tools/ScoreSim` reports every level rating the right way round.

## The map editor at a glance

Visual editor for the map JSON files (it supports drag-and-drop of a map file onto the window). It draws the balls and the sky the same way the game does, so a map looks in the editor the way it will play: the same instanced procedural spheres, the same shader, the same sky-derived lighting and the same full render pipeline (below).

It builds `Shaders/InstancedModel.fx`, `Shaders/Tonemap.fx`, `Shaders/Glare.fx` and the scene shaders (`Sea`/`Savanna`/`Desert`/`Acacia`/`Flame`/`Birds`/`Mountain`/`Snow`/`Spray`/`Meadow`/`Forest`/`Space`) straight out of the Testbed content directory (`/build:../../Testbed/Content/…;<asset name>` in its own .mgcb), so there is one copy of each. The sky domes need no content at all since #113: `SkyDome` builds the one dome geometry the eighteen `.dae` files turned out to share, and a sky is one of eighteen stored palettes.

**Keys.** B cycles the domes (the game's NumPad1, which the editor uses for ball types instead — NumPad1–9 pick the first nine directly, and NumPad +/− cycle all thirteen, the four past nine having outgrown the numpad's digits with #152) and **V cycles the seven scenes** (the game's NumPad2), so a map can be previewed against every backdrop it might play in — and it can be **entered** from outside the cycle, which took a fix: a level whose scene names one of the six past the cycle's end (the forest, space, the dream, the cavern, the Moon, the outback) leaves the scene index past it too, and `(index + 1) % 7` then landed wherever the arithmetic fell rather than at a boundary. From a forest level the first V came out at the *sea*, three scenes deep, leaving the four entries before it unreachable without four more presses — in the one program whose job is previewing a map against every backdrop. Anything off the end restarts the cycle at the city. The Testbed's copy of the same one-liner was fixed with #73 — the same shared `SceneRenderer` and city the game uses (see "The shared scene backdrops" in `docs/scenes.md`). It loads and saves not just plain map files but whole **levels** (map + scene + sky): F2 and drag-drop load, F1 and F4 save. G toggles the scene-config panel. **L cycles what the balls are made of** (#258) — the vinyl beach ball or the glass bubble — and applies it to the render set at once, so the preview *is* the answer rather than a description of one; it is a property of the map, so F4 writes it into the level and F2 brings it back, and a fresh map or a plain map file resets it to vinyl. L for "look" because it was what was free: S, W, A, D, Q and E drive the camera, B is the dome, V the scene, G the panel, N fills the map and M clears it. The cycle is `BallStyles.Next`'s, off the enum itself, so a third material cannot be added and left unreachable in the one program that exists to choose between them.

**What it deliberately does not draw.** It has no ground, castle, cannon or shadows, and no arena platform (the AABB replaces it); the play field is marked by a translucent procedural outline (`GUI/AABB.cs` + `WireBoxMesh`) instead of the game's glass ceiling, and only the selector gizmo still draws through `ModelRenderer`/`BasicEffect`.

## The map editor's render pipeline

The map editor renders through the **same linear-radiance pipeline as the game**, so a map looks in the editor the way it will play — that is the whole point of moving it off DesktopGL. `MapEditor.Draw` binds the shared pipeline's supersampled HDR scene target (`SUPERSAMPLE_FACTOR`, a fixed 2 — there is no `ssaa=` CLI here), clears it to the **current dome's horizon colour** (`_rig.HorizonLinear`), draws the sky, the chosen scene backdrop and the balls into it, then `PostProcessPipeline.Resolve` runs `Glare.fx` and `Tonemap.fx` — since #74 literally the same code every executable runs, in `Prazsky.Core.Render`, with the editor passing the game's own look figures so the two agree by construction. (Under the old ported-verbatim copy the editor's glare threshold had silently stayed at the pre-pyramid 0.38 against the shipped 0.55 — exactly the drift the shared copy exists to prevent; fixed in the hoist, so the editor previews a touch less bloom than it used to and exactly as much as the game.) The clear colour is the horizon rather than a fixed blue because the hemisphere dome covers only above the horizon and the finite scene only reaches its own edge, so at a wide aspect (21:9) the bottom corners look below the horizon past both — and a fixed clear colour showed through there as a blue band; clearing to the horizon makes that gap blend with the hazed skyline the dome and terrain both fade to. Both executables do this. The pipeline's `EnsureTarget` is called from `LoadContent`, `Window_ClientSizeChanged` and `SetGraphics`, so the target tracks the back buffer through a resize or an F11 fullscreen switch; back-buffer MSAA is off because only the resolved full-screen quad ever touches the back buffer.

**The balls go through the shared `BallRenderSet` since #76, and that closed a second drift of exactly the same kind.** This document claimed the editor drew them "exactly as the game draws them"; it did not. It set only the pattern's gore count and a **full albedo**, so its balls were twice as bright as the game's (`BallRenderSet`'s albedo is 0.5 — a flat 1 is a surface that reflects every photon reaching it, which nothing real does) and were neither emissive, translucent nor pulsing at all. There is one set of look figures now and the editor reads it, so the claim is finally true: the same albedo, the same emission and translucency, and the same slow heartbeat travelling up the cluster. The one thing it deliberately does not take is the landing **ripple**, which is a rule about a cluster being played (`ripples: false`, which also selects the deeper resting pulse depth, the breath both non-playing executables keep). None of it needs physics — the editor hands its `BallsMap` to `BallDrawFrame.AddMap` and its own scene clock to `Draw`, which is what makes a caller with no simulation a first-class one (see "The rest of the hardware, in one copy" in `docs/testbed.md`).

**And it draws the forest's wood** since #75. The trees, boulders and stumps standing on the forest floor were the Game's alone while the floor itself was always the shared `SceneRenderer`'s, so the editor — and the Testbed — previewed a bare clearing; `ForestScatterRenderer` is that piece shared (see "The forest" in `docs/scenes.md`). It is reached here only by **loading a forest level**, V still stopping at the seventh scene, and it is the one place the editor needed something the Game never did: see "The scene-config panel" below.

Two things do **not** go through the shared shader and needed handling for the linear target:

- **The sky dome** is drawn through `BasicEffect` (the editor builds no `Sky.fx`), so its stored vertex-colour gradient is sRGB. `SkyDome` is therefore built with `linearVertexColors: true`, which converts the gradient to linear whenever a palette is written into the buffer — otherwise the tonemapper reads a gradient of display values as radiance. `ApplySkyLighting` likewise decodes the palette to linear (`ColorSpace.SrgbToLinear`) before scaling and tinting it, and sets `LinearLightRig = true` on the ball renderers — and since #75 it does not *mirror* the game's derivation, it **is** it: all three executables run the one `Prazsky.Core.Render.SkyLightRig`, so a palette, a scale or a tint cannot mean one thing here and another in play. What stays the editor's own is only the enrolment — the balls and the city, there being no island, drain or ceiling here to light. **The drawn sun disc is the one thing this costs, and not having it was decided rather than overlooked** (#220): the disc lives in `Sky.fx`, so the editor could only have one by building that shader, which drags the whole cloud field's evaluation into its sky pass for a deck it does not want. It buys less than it looks — this sky has no weather at all, so a sun in it is no more faithful than a sun-less one, while everything an author actually judges here (the terrain, the water, the trees, the balls' own lighting) **does** follow the dome's sun already, through the very light rig and `SceneFrame` above. See "The weather" in `docs/rendering.md`.
- **The AABB field outline and the selector gizmo** are drawn through `BasicEffect`. The AABB is opaque-coloured and depth-tested against the balls, so it stays in the HDR pass and its one flat colour is linearised on the CPU (`ColorSpace.SrgbToLinear(COLOR)` in `AABB.cs`) — handed over raw it would tonemap too bright. The selector is additive and drawn with depth off (always on top), so it is drawn **after** the resolve, in display space, where `BasicEffect`'s gamma output is already correct — the same split the game makes for its crosshair and text overlay, which also draw post-resolve (`base.Draw` runs last). The **axis gizmo** (`GUI/AxisGizmo.cs`) — a small X/Y/Z cross in the bottom-left corner showing how the world axes sit relative to the camera, to keep the user oriented while building a map — draws post-resolve too: it binds a small square viewport, draws the three coloured axes (X red, Y green, Z blue) through a rotation-only view of the camera under an orthographic projection, then labels the tips with `SpriteBatch`. It reflects only the camera's orientation, not the scene, so it needs no depth and no scene state.

Because both executables now build the shared shaders for DirectX/SM 5.0, `InstancedModel.fx` has no `#if OPENGL` branches left at all: `SrgbToLinear` always decodes, `Clouds.fxh` is always included (the editor just never sets the cloud uniforms), and the relief self-shadow / parallax marches are always compiled (guarded at runtime by their strength uniforms, which the editor leaves at zero).

## The scene-config panel (MapEditor)

The editor carries an in-engine GUI built on **Myra** (issue #45; the project's single GUI library, chosen over ImGui so the same stack could serve the game's menus — which it now does, see "The front end (Game)" in `docs/game-shell.md`). Myra's `Desktop` is rendered last in `MapEditor.Draw`, straight to the back buffer after the resolve and `base.Draw`; its default stylesheet is embedded, so no content pipeline change was needed. The panel is a right-docked `PropertyGrid` reflecting over the **active scene's `SceneConfig`** (issue #33's Level Editor skeleton, realized by extending the MapEditor rather than a separate tool): editing a value fires `PropertyChanged`, which re-applies the config through `SceneRenderer.Apply` (or rebuilds the city) so the backdrop **updates live**. The grid rebinds when the scene is switched (V) or a level is loaded; **G** toggles the panel. **Since the format-2 refactor its edits persist NOWHERE** — a level names its scene and the scene's parameters are fixed in code — and the panel's header says so ("edit to preview live; not saved"). It is the tool for **developing** those fixed looks: tune live against the real pipeline, then transcribe what earned its keep into the `SceneConfig` class defaults, which is now the one place a scene's look lives. Edits also mutate the renderer's shared per-scene instance, so a tuned value stands for the rest of the session (every level of that scene previews with it) until restart.

The forest is the one scene where re-applying a config is not enough, and it is the only thing `ForestScatterRenderer` grew for the editor. Tree proportions, the rocks' and stumps' shapes and the three colours are **baked** — into the meshes and into the tints encoded once at build time — so a changed config has to **re-plant** rather than re-scatter (`Replant`, which rebuilds the fifteen meshes, the twenty-five renderers, the tints and the scatter). Re-planting alone would answer a changed count while quietly ignoring a changed shape, which reads as a bug in the editor rather than in the component. And a re-planted wood is twenty-five brand-new renderers that have never been told the dome's palette, so the **re-light follows the re-plant** — the same dance `CeilingPlate.Fit` already requires of the game. Both calls sit in the same switch as the level-load path.

Two integration points matter. First, **input arbitration**: the editor's own keys and camera stand down while a Myra widget has keyboard focus (`_desktop.FocusedKeyboardWidget`) or the mouse is over the panel (`_desktop.IsMouseOverGUI`), or typing "42" into a field would fire hotkeys and dragging would spin the camera; Myra processes its input in `Draw`, so those flags lag one frame (negligible). Second, **name clashes**: `PropertyGrid`, `Label` and `HorizontalAlignment` also exist in `System.Windows.Forms` (used for the file dialogs), so Myra's are aliased (`MyraPropertyGrid`, `MyraLabel`, `MyraHAlign`).

`Rgb`/`Vec2`/`Vec3` are **reference types** specifically for this editor: Myra's `PropertyGrid` edits a nested *value* type's sub-properties on a boxed copy it never writes back, so as structs a colour's channels could not be tuned live; as classes the grid holds the same instance the config exposes, so an R/G/B change reaches the config `SceneRenderer` reads. The channels are individual float fields rather than a 0–255 colour picker because the values are linear radiance and may exceed 1 (a proper HDR colour-swatch widget would need a custom Myra editor — Myra 1.6.3 exposes no public per-type editor hook).

## The application icon (Game)

The icon the shell draws on `BS3D.exe` and the window publishes at runtime. The artwork is `Images/Icons/ico6.svg`, exported to the `ico6-<N>.png` ladder, and `Images/Icons/Build-Icon.ps1` assembles that ladder into `Game/Icon.ico` — run it with no arguments after the artwork changes. `<ApplicationIcon>Icon.ico</ApplicationIcon>` was already in all three `.csproj`, and MSBuild embeds **every** frame (verified: `RT_ICON images=14` in both the apphost `.exe` and the managed `.dll`, each frame pixel-exact against its source PNG through `PrivateExtractIconsW`), so nothing in the projects needed changing — only the file, which until then held a **single 256×256 image** that Windows downscaled for every size it drew.

- **The fourteen sizes are not padding and not an MSIX artefact.** `{16, 20, 24, 30, 32, 36, 40, 48, 60, 64, 72, 80, 96, 256}` is exactly the union of the sizes the Windows 11 shell asks a Win32 executable for across its 100–400 % scale factors — 16–64 for the title bar, context menu and tray, 24–96 for the taskbar, search results and the all-apps list, 32–256 for a Start pin (MS `app-icon-construction`). They coincide with the MSIX `AppList.targetsize-*` list, which is why the middle steps get mistaken for packaging leftovers. Windows matches a request exactly if it can and otherwise takes the next size **above** and scales down, which is what makes the 256 entry matter even at 100 %.
- **The payload split is DIB through 96, PNG for the 256 only, and the reason is not the shell.** PNG sub-images at every size would take the file from 185 KB to 79 KB (measured, `-BmpMaxSize 0`: 78 627 B against 184 590 B, i.e. 43 %) and the Win11 shell reads them perfectly — `PrivateExtractIconsW` and `LoadImageW` return all fourteen pixel-exact from an all-PNG icon — so the usual folklore about small PNG entries breaking Explorer is false on current Windows. What is true is that **an old enough `System.Drawing` consumer cannot read a PNG sub-image at all**, and that it fails **silently**: it takes the entry's bytes for a DIB and decodes the compressed stream as raw pixels, so the frame comes back as **noise** — measured on the real ladder, 0 % of pixels matching the source at every size from 16 to 96, with as many distinct colours as there are pixels (1024 of 1024 at the 32) — and with **no exception and no blank frame anywhere**. Two things about that are easy to get wrong and both were, here, before they were measured:
  - **It is gated on the consumer's own target framework, not on ".NET Framework".** The switch is `Switch.System.Drawing.DontSupportPngFramesInIcons`. Measured with two byte-identical builds of one probe differing *only* in their `[TargetFramework]` attribute: targeting **v4.5** every size of the all-PNG ladder reads as noise, targeting **v4.8** every size reads 100 % pixel-exact. A host that declares no target framework — PowerShell 5.1, i.e. this repo's own harness scripts — takes the broken path. So the consumers at risk are old installers and script hosts, not everything pre-.NET-10.
  - **Do not test it by looking for a throw or a blank frame — there is neither.** An earlier version of this note claimed a blank at 16–24 and an `ArgumentOutOfRangeException` from 30 up. Both were artefacts of measuring against a synthetic icon whose payloads were a couple of hundred bytes: `Icon.BmpFrame` copies `40 + w·h·4` bytes from the entry's offset, so it throws only when that read runs off the end of the file, which a real ladder's later entries prevent. Compare pixels against the source PNG instead.

  The failure does track the payload encoding rather than the size: in a `-BmpMaxSize 48` file the DIB range reads pixel-exact and the PNG range reads noise. And the shipping split is what makes the question moot — **`Game/Icon.ico` reads 100 % pixel-exact at every size even for a consumer targeting v4.5**, which is the whole point of it. That consumer is old installers, PowerShell 5.1 tooling, shell extensions and Mono, and it is the whole reason the small entries are stored as classic DIB. The 256 stays PNG because uncompressed it alone is 262 KB — as PNG it is 30 984 B against 270 376 B, i.e. the one place a tenth really is the ratio. `-BmpMaxSize 48` gives up 87 KB of that compatibility and is still right for every size a legacy consumer realistically asks for; the default follows Microsoft's literal rule ("only the 256×256 image should be compressed") and has no failure mode below 256 at all.
- **A DIB entry's `biHeight` is twice the icon height and its 1 bpp AND mask has to actually be there** (bottom-up, rows padded to 4 bytes, a set bit meaning transparent) — it is the colour image stacked over that mask. The builder derives it from the alpha channel rather than leaving it blank, so the silhouette survives the paths that ignore alpha. A PNG entry takes the opposite contract: 32 bpp ARGB, **no** `BITMAPINFOHEADER`, **no** mask (alpha *is* the mask), and its directory entry writes the 256 dimension as **0**. Pillow is no help here — its `sizes=` route silently *resamples* from one base image, and its BMP mode writes the doubled `biHeight` with no mask at all.
- **One trap in the builder itself, worth knowing before editing it:** PowerShell's `-shl` keeps the **left operand's type**, so decoding a PNG's big-endian IHDR dimensions straight out of a `byte[]` truncates every shift back into a byte and reports every image as 0×0 (`[byte]1 -shl 8` is 0). The `[int]` casts around those shifts are load-bearing. The builder also refuses to trust a filename — it checks each PNG's declared dimensions against the size it is being filed under, since a ladder exported at the wrong DPI would otherwise be assembled into a directory that lies about its own payloads.
- **MonoGame does set a window icon, and it is not enough.** `WinFormsGameWindow.SetIcon` calls shell32's `ExtractIcon`, which returns a **single** handle at the system large-icon size (measured 32×32 at 96 DPI), through `Icon.FromHandle` — which keeps no icon-file bytes, so WinForms' small-icon path has no frames to choose from and can only copy the large one. Measured on the live game: the window published **ICON_SMALL as a 32×32**, i.e. the title bar was squeezing the 32 px artwork into 16 px while the authored `ico6-16.png` sat unused in the exe. `BS3DGame.ApplyWindowIcon` fixes it with `PrivateExtractIcons` — the API that picks a *named size* out of a group — straight from the running executable's own resources, so there is no second copy of the icon to keep in step. It reads `Environment.ProcessPath` and **not** `Assembly.Location`, which is what MonoGame uses and what comes back empty under a single-file publish (where MonoGame's own `SetIcon` silently does nothing and this becomes the only thing setting the icon). The **order is mandatory**: assigning `Form.Icon` makes WinForms send *both* messages, deriving the small one by stretching, so the authored small frame has to be `WM_SETICON`'d after it. It runs after `base.Initialize()`, so the window handle exists and MonoGame's own assignment has already been published — this has to win that race, not lose it. Measured after the fix: ICON_BIG 32×32 and ICON_SMALL 16×16, both 100 % pixel-exact against their authored PNGs, and both held across two F11 fullscreen round-trips (window 1616×939 → 1920×1080 → back), so nothing has to re-publish them on a resize.
- **`System.Drawing.Icon` can never select the 256 frame out of a group,** because `ICONDIRENTRY` stores 256 as `bWidth = 0` and its best-fit metric is `|bWidth − requested|` — asking for 256 returns the 96 instead. It happens with an all-DIB file too, so it is a GDI+ limitation and not a defect in the file, it degrades to a correct smaller icon rather than a blank one, and nothing here asks GDI+ for 256. Use `LoadImage(..., IMAGE_ICON, cx, cy, LR_LOADFROMFILE)` if a frame above 128 is ever needed in managed code.
- The **Testbed and the MapEditor deliberately keep the old single-frame `Icon.ico`** — the tools are not the shipping game, and telling their windows apart from it at a glance is worth more than a crisp icon on a developer executable. (All three were byte-identical before this, so `Game/Icon.ico` is the only one regenerated; copying it over one of theirs is all it would take to change that. `Build-Icon.ps1`'s `-Output` resolves a *relative* path against the **caller's** directory, not the script's — only its default is script-relative — so pass an absolute path unless the shell is sitting in `Images\Icons`.) All three used to declare a `<PackageIcon>Icon.ico</PackageIcon>` beside the `<ApplicationIcon>`; it has been removed. It was inert — nothing packs these projects — and would have been invalid if anything did, since NuGet takes a PNG or JPEG there and never an `.ico`. The empty `<PackageIconUrl />` beside it was a dead NuGet vestige of the same kind and has gone with it, in all three and in `Prazsky.Core`.

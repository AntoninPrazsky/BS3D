# The application icon (Game)

Part of [Formats and tools](../formats-and-tools.md).

The artwork is `Images/Icons/ico6.svg`, exported to the `ico6-<N>.png` ladder; `Images/Icons/Build-Icon.ps1` assembles it into `Game/Icon.ico` (run it with no arguments after the artwork changes). MSBuild embeds **every** frame (`<ApplicationIcon>` is in all three `.csproj`). The **Testbed and MapEditor keep the old single-frame `Icon.ico`** on purpose (their windows differ from the game's).

- **Fourteen sizes**: `{16, 20, 24, 30, 32, 36, 40, 48, 60, 64, 72, 80, 96, 256}`, the union of what the Windows 11 shell asks a Win32 exe for across 100–400 % scale. Windows takes the exact size, else the next size **above** and scales down, so the 256 matters even at 100 %.
- **DIB through 96, PNG for the 256 only** (`-BmpMaxSize`, default 96). The reason is that **an old `System.Drawing` consumer cannot read a PNG sub-image and fails silently**, decoding it as **noise** with no exception and no blank frame, so compare pixels against the source PNG and never look for a throw. It is gated on the consumer's own **target framework** (`Switch.System.Drawing.DontSupportPngFramesInIcons`: v4.5 reads noise, v4.8 exact; a host declaring none, such as PowerShell 5.1, is broken).
- **A DIB entry's `biHeight` is twice the icon height and its 1 bpp AND mask must be there** (bottom-up, rows padded to 4 bytes, a set bit meaning transparent; derived from alpha). A PNG entry is 32 bpp ARGB with **no** `BITMAPINFOHEADER` and no mask, and its directory entry writes 256 as **0**.
- **Builder traps**: PowerShell's `-shl` keeps the left operand's type, so decoding a PNG's big-endian IHDR from a `byte[]` truncates every shift (the `[int]` casts are load-bearing); the builder checks each PNG's size against the one it is filed under; `-Output` resolves a *relative* path against the **caller's** directory.
- **MonoGame's own window icon is not enough**: `WinFormsGameWindow.SetIcon` uses shell32 `ExtractIcon` (one handle at the large size), so the title bar squeezed the 32 px artwork into 16. `BS3D.Platform.WindowIcon.Apply` (called from `BS3DGame` after `base.Initialize()`) picks the named sizes from the running executable's resources with `PrivateExtractIcons`. It reads `Environment.ProcessPath`, **not** `Assembly.Location` (empty under a single-file publish, where MonoGame's `SetIcon` does nothing). **The order is mandatory**: assigning `Form.Icon` makes WinForms send *both* messages (the small one stretched), so the authored small frame is `WM_SETICON`'d after it.
- **The sizes are the window's scale's** (#825): `GetSystemMetricsForDpi` at `GetDpiForWindow`, 16 and 32 at 96 DPI, 20 and 40 at 120, one pair extracted per DPI and kept. `GetSystemMetrics` alone answers for the process's system DPI (the primary monitor's scale when it started), which a window on another monitor, or one whose monitor changed scale, is not at.
- ⚠ **Every `WM_DPICHANGED` undoes it**: `Form.OnDpiChanged` calls WinForms' `UpdateWindowIcon`, which rebuilds the small icon from `Form.Icon`, a handle-only icon with one frame, so the small slot gets that **large** frame (40 px on a window at 120 DPI, 32 px at 96) and the large slot keeps the old scale's size. `BS3DGame.OnWindowScaleChanged` (through `DisplayRefresh.WatchScale`, posted behind the message) calls `Apply` again. To check it, `WM_GETICON` the window from outside and compare the pixels with the `ico6-<N>.png` ladder: a size alone does not tell an authored frame from a resampled one.

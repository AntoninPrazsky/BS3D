# Play statistics: what players do with each level

Part of [The game: a session](../game-session.md).

The game counts, per level, how often it is **started, retried, cleared, lost (out of balls, or at the line), quit and skipped**, the **shots and seconds** spent on it, and **how many starts a first clear took** (#709). The point is the question the level work keeps guessing at: *where does the game get stuck?* ScoreSim says how a simulated player rates; these say what real ones do. Counters only: no event log, no device, no time of day, no quality tier.

## What is counted, and where

- **The rules are the library's** (`Prazsky.BS3D/Levels/PlayStats.cs`): `PlayStatsRecorder` takes four events and returns the change each makes; `PlayStats` is the file. **One row per board** (`LevelIdentity` and `ScoreKeeper.RulesVersion`), so a regenerated or retuned level counts afresh, as it starts a fresh board. The built-in fallback (no identity) is counted nowhere.
- **The game's seam** is `Game/PlayStatsSession.cs` (`Game.Stats`), called from the gameplay screen:
  - **start**: `BuildLevel`, right after `InstallLevel` has said which board it is;
  - **ending**: `ShowResultScreen`, the funnel the save's record and the boards' submission share, with the same frozen `EndShots`/`EndSeconds`; a **first clear** is a clear of a level the save had no clear of, asked before the record writes it;
  - **quit** (abandoned): `TearDown`, so every way an attempt can be torn down before its page counts once: the pause's Restart, another level or New Game over a session kept for Continue, and the game closing (`UnloadContent` counts it **before** the online client stops, so the change still reaches its outbox). A level decided but left before its page (a Restart during the line's flight) counts as a quit;
  - **skip**: `SkipLevel`, on the board of the attempt the skip was offered over.
- **A run that used the dev build's debug row stays on this machine** (#876, `LevelRun.DebugKindLoaded`): its ending (`ShowResultScreen`) and its leaving (`AbandonAttempt`) are counted in `Stats.json` like any other, as the save keeps its record, but are passed with `online: false` and never handed to the online client, so they cannot reach a batch. Its start was handed over when the level began, before the row could have been used, and is not taken back: online it reads as an attempt that never ended, which the service accepts (only more endings than starts is refused). A skip spent over it is counted as usual.
- **A retry** is a start of the board the last attempt was on, while that attempt did not clear it (a loss, a Restart, the level left and picked again). A replay after a clear is a start, not a retry. Held in memory only: the first start after a launch is never one.
- **One attempt is open at a time**; a second close counts nothing, which is what lets `TearDown` say "quit" without asking whether the attempt ended first.
- ⚠ **The counts observe and never decide.** Nothing reads them back. The skip stays a per-chapter budget exactly as #347 ruled, not something earned by losing.

## The file: `Stats.json`

Beside `Progress.json` in the user data folder, **its own file and never part of the save**, so a bug in the counts cannot cost a player their progress. Through `AtomicFile` with a backup, and an unreadable one is kept aside (`KeepUnreadable`) before it is answered with an empty one, like every player file. **Off the frame but for the increments**: an event adds its change under a lock and hands one line of text over, and a task of its own (`PlayStatsSession.BackgroundWrite`) prints the line, serializes the totals under the same lock and writes the latest state, so a level's start or end costs the frame no serialization and no disk flush; the exit waits for the last write at most `PlayStatsSession.DisposeWait`. Each event prints one `[stats]` line with the board's totals. The file keeps `startsToFirstClear`, the starts each first clear took; it never leaves the machine (below).

**The report without a server**: `dotnet run --project Tools\ScoreSim\ScoreSim.csproj -- --stats [path]` prints a file's counts per level in play order (the player's own `%LOCALAPPDATA%\BS3D\Stats.json` without a path), every rate beside its counts, and the boards the set does not name as shipped after them ([The score simulator](../formats-and-tools/score-sim.md)).

## Sent only with online scores on, naming nobody

- **The owner's ruling (2026-10-15): sent only for a player who has online scores on**, with no opt-in of its own; the nickname is the consent (#763). With them off (or never decided) nothing of the counts leaves the machine: `OnlineSession.SubmitStats` and `OnlineScores.SubmitStats` hand a change on only while the client is `Enabled`. **Turning them off drops what is queued**: a client started off removes both batches from `Outbox.json` and its backup (`OnlineScores.DropQueuedStats`), keeping the clears, so consent withdrawn means nothing queued goes out later; Remove scores deletes the whole outbox anyway.
- **What a batch carries**: `POST /v1/stats` with a random `batchId` (the service counts a batch once by it) and rows of counts per board (`LevelPlayCounts`), and nothing else: **no player id, no token, no nickname, no version, no clock**. The request goes without its `Authorization` header, from a client of its own whose User-Agent is `BS3D` with no version. **`startsToFirstClear` is not sent**: the starts it counts include those made before the player turned online scores on, so the client zeroes it and a zero is not written. The service keeps running totals per board and the batch ids, with no player, address, time or version, and a refusal of a batch names no address either ([BS3D-API](https://github.com/AntoninPrazsky/BS3D-API), `play_stats`). The privacy sentence on Settings and About says only that: the counts are sent and stored without the player's id or name, so Remove scores cannot find them (`OnlineScores.PrivacySentence`).
- **Never beside a request that names the player.** Each change is merged into one **open batch** in `Outbox.json` (`statsOpen`) and a wake for the counts alone makes no request: it puts them on disk, and neither sends them nor retries a clear stuck behind a server that is away. The worker sends a batch **on its own timer**, in a step that sends nothing else: at least `StatsSchedule.Interval` (10 minutes) after the last batch, and a random `QuietMin` to `QuietMax` (2 to 8 minutes) after the worker's start and after every clear, rename, removal or board request (`OnlineScores.QuietStats`). It goes on its own connection (its own `HttpClient`, `Connection: close`), never the one a clear went over. So a session's counts go some minutes into the next session at the latest, and a session shorter than the quiet leaves them for the next.
- **One frozen batch at a time**: at the timer the open batch is frozen under a fresh id into `statsSending` (at most `StatsMaxLevels` rows), written to disk before the first byte goes, and sent unchanged until the service answers for it while new counts gather in the open one; so the outbox holds at most two.
- **Answers are read as a clear's are**: 2xx with the service's JSON delivered; a 4xx with its reason refused for good (dropped, logged); anything else kept. ⚠ **A service without the endpoint answers a bare 404, which is no answer (#691)**: the batch stays and costs one request an interval, never a clear. An older build reads past the two fields of the outbox and drops them at its next write (the outbox stays version 1 so it never keeps a whole file of clears aside for them).
- **What the service takes** (BS3D-API's `POST /v1/stats`): a row no more than one batch of real play can hold (half an hour of seconds, a hundred starts and one a second past the first five, a hundred shots an attempt) and on a board a ceiling table names; another row is left out, not refused. Counts that cannot add up (more retries than starts, more endings than starts and the one attempt a batch can carry over) refuse the batch.
- `Tests/BS3D.Tests/OnlineStatsTests.cs` runs the real `OnlineScores` against a loopback stand-in that records every request: nothing sent or queued without consent, a batch alone (no token, no version, its own connection, a quiet after a clear), the same id again after no answer, kept on a bare 404, dropped on a refusal, dropped from the outbox when scores are turned off. ⚠ A test that counts requests across a `Stop` pins the batch's retry timer out (`OneTry`, an hour) and waits for the stopped worker before it counts: a request in flight when the worker is cancelled is its own and may reach the stand-in after the count. A test reads the outbox with `FileShare.Delete`: a plain `File.ReadAllText` holds the file against the worker's `File.Replace`, the write fails (logged, the file keeps its old counts) and the test waits for counts that never reach the disk (the flakes of #931).

## Testing it

- `actions=<seconds>:<verb>,...` ([Controls](controls-and-testing.md)) presses a level's buttons on the clock: `retry`, `restart`, `skip`, `next`, `menu`, `level<n>`; `lineloss=` stages a loss at the line and `quitconfirm=<s>:quit` closes the game mid-level. Always with `userdata=<dir>`.
- A batch goes a random 2 to 8 minutes after the run starts: a scripted run that wants to see one sent lasts longer than that, or starts again on the same `userdata=` folder.
- Against a **local** BS3D-API (`dotnet run --project src/BS3D.Api --urls http://127.0.0.1:<port>` and `"server": "http://127.0.0.1:<port>"` in the run's `Settings.json`); never against the public service. `admin stats` on its database prints what arrived.

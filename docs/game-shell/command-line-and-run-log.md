# The command line, the run log and the narrow window

Part of [The game: shell](../game-shell.md).

## The command line (`Game/LaunchOptions.cs`, #583)

**Every launch argument is one property and one table row of `LaunchOptions`, parsed once and handed to `BS3DGame` as one object.** A row carries the spelling, its kind (a bare **flag**, or `name=` with an **int**, an invariant-culture **float**, **text**, a lenient **list** of seconds through `ScreenshotWriter.ParseSeconds`, or a **value** whose spellings belong to the type that owns them: `SceneRenderer.TryParseScene`, `BallStyles.TryParse`, a dome in range, a defined `QualityLevel`), the setter, an optional accept test (`fpscap=` above zero, `nextlocked=` a known lock) and why it exists.

- **Rows are walked in order and the first that takes the argument wins; a row whose name matches but whose value does not parse does not take it**, so `fpscap=abc`, `quality=ultr` and a typo alike reach `ScriptedPlay.TryParse` (`sweep=`, `rmb=`, `aim=`, `fire=`) and then the **`[args] Ignored '…'`** line (#574). A later argument overwrites an earlier one of the same name.
- **`Program.Main`'s order**: `RunLog.Install`, the `[build]` lines, the parse (its `[args]` lines), the scripted-play line, **`userdata=<dir>`** applied through `UserData.UseForTesting`, then `RunLog.Open` and the game. `userdata=` must speak before anything resolves `UserData.Directory`; it keeps a scripted run's save, settings and identity out of the player's profile, so **pass it to every scripted run**.
- **One-shot actions are `Game/StartupScript.cs`**, stepped by `_startupScript.Step(this)` after `_screens.Update` and the rumble; its constructor decides the implications (`level=`/`levelfile=` mean `play`, `lost` and `nextlocked=` mean `result`, `settings=` means `settings`). **`Step`'s order is load-bearing**: the startup level, then the celebrations (**after** it: `BuildLevel` stops both displays, #299), `tomenu=` (#650), the picker, About, the tour, Settings (its rows a frame later, once the page is up), the boards, Help and the staged result page last, **every page but the level held back while `SplashPage` is on the stack** (#576).
- **Levers that open or drive a page** are in [Launch arguments that open or drive the front end](front-end-launch-arguments.md); also **`nickprompt[=<steps>]`**, **`nointernet`** ([Online rows](online-and-nickname.md)), **`note=<seconds>:<steps>`** ([Write to the Author](send-a-note.md)) and **`quitconfirm[=<seconds>[:<steps>]]`** (#826): the Quit confirm over the main menu once the title card has gone, or at that second over whatever is up (a level is paused first); steps `back`, `cancel`, `quit` run through Escape's and the entries' handlers, each logging `[quit] Testing: the page up is PausePage`.

## The run log and the crash report (#570)

**The shipped build has no console, so everything the game says also goes to a file.** Release is `WinExe` (`Game.csproj`, by configuration) and Debug a console exe: a console build opened a window beside the game, closing it killed the game without an unload, and a click in it (QuickEdit) froze the frame.

- **`RunLog.Install`** is the first line of `Main` (so `[build]` lines are kept): it tees `Console.Out` and `Console.Error` into the log and hooks `AppDomain.UnhandledException` (a crash report) and `TaskScheduler.UnobservedTaskException` (logged `[error]`, marked observed, not fatal: the online worker and music decoder run on the pool).
- **`RunLog.Open`** runs after the command line, because the file lives in `UserData.Directory` (**`Logs\last-run.log`**) and resolving that before `userdata=` is read would refuse it; earlier output waits in memory. **The previous run's log is kept as `previous-run.log`** (the launch after a crash would otherwise overwrite the evidence). Every line is flushed as written, since a buffered writer loses the lines that led to a crash.
- **`Program.Main` wraps the game in a `try`**: anything thrown becomes **`Logs\crash-<utc>.txt`** (exception and stack, OS and runtime, anything printed before the log had a file) and a `[crash]` line, and a player sees a message box naming the file. **A run with `userdata=` gets no dialog** (a scripted run nobody sits at would wait for it until the harness killed it): it exits with code 1 and the harness reads the `[crash]` line.

## The menu in a narrow window (#593)

**The menu scales by height, and by width once the window is too narrow for its widest page.** `BS3DGame.MenuLayoutHeight` is `min(height, width × 2160 / MENU_MIN_DESIGN_WIDTH)` (`_menuScale` was `height / 2160` alone: a portrait window ran the picker off the edge); the menu, HUD fonts and rebuild quantum all read it, so a narrow window rebuilds on a width change alone. `MENU_MIN_DESIGN_WIDTH` is the widest page's width in design units: **High Scores**, rows plus plate padding about 2590 (#685's review found 2560 clipped them), so 2600; Settings no longer sets it (#686). Wider than about 1.2 aspect nothing changes; a portrait window gets small type, the lesser fault than controls off the screen.

# The window: size, borderless fullscreen, DPI

Part of [The game: shell](../game-shell.md).

## The windowed size is the player's (#137)

`_fullscreen` is F11's own switch; the OS maximize and an edge drag (`AllowUserResizing` is on) leave it `false`. A `SetGraphics` that set `PreferredBackBuffer` to `WINDOW_WIDTH`×`WINDOW_HEIGHT` whenever `!_fullscreen` shrank the swap chain under a window the OS did not shrink (maximized, it went 3840×1529 to 1600×900 and the picture was upscaled).

It restores `_windowedSize` instead, recorded in `OnClientSizeChanged` **only while windowed**, with a zero guard for the minimize. ⚠ The pass that goes fullscreen raises that event at the display's size; recording it would bring the game out of fullscreen into a window the size of the screen.

## Fullscreen is borderless (#157)

`SetGraphics` sets `HardwareModeSwitch = false`: minimizing exclusive fullscreen tears down the DXGI fullscreen state and, with no `Activated`/`Deactivated` handling, the window never restored. The back buffer is sized to the display either way. The Testbed and MapEditor have the same line (#400): a scripted `at=…:F11` on a window without focus crashed their hardware mode switch in `SwapChain.SetFullscreenState`.

## DPI awareness (#825)

The Game is **per-monitor DPI aware** (`Game/app.manifest`, `PerMonitorV2`). Unaware, Windows divides every size a process reads by the display scale: a 1920×1200 laptop at 125 % read `CurrentDisplayMode` as 1536×960, so the back buffer and the 3D were that size and blurred up, and mouse aim (which counts pixels) turned 1/1.25 as far.

- A manifest and not `Application.SetHighDpiMode`, because `Program.Main` is GamePi's too and has no WinForms there (`WFO0003` is suppressed in `Game.csproj`).
- **The run log says which it is**: `[display] 3840x1600 at 75 Hz, scale 125 % (120 DPI), DPI-aware per monitor` after the first `SetGraphics`, or `DPI-UNAWARE: …` (then the mode is the divided one, `3072x1280` on that display at 125 %, and so is the Resolution row). A note's context carries `"scale"` and `"dpiAware"` (`DisplayRefresh.TryGetScale`; GamePi answers nothing). A scale change while the game runs adds `[display] the window's scale changed: now 100 % (96 DPI)`.
- On a scaled display the frame is the panel's own pixels (3840×1600 back buffer in a 3840×1600 client at 125 %, so nothing is stretched) and costs more (1.56× at 125 %), and mouse aim is faster by the scale (Aim sensitivity carries a feel across).
- **Sizes are pixels, not the scale.** The 1600×900 default window stays 1600×900 pixels at 125 % (smaller beside the desktop's other windows), and the menus and the pointer are sized off the window's and the panel's height, so the scale does not move them either. Kept: a window scaled by 1.25 (2000×1125) would not fit the 1920×1200 laptop the issue came from.
- **`WM_DPICHANGED`** (the scale of the window's monitor changed under it, or the window was dragged onto a monitor of another scale) **keeps the window's size in pixels**: windowed, only the frame's thickness changes, so the client and the back buffer move by a few pixels through the ordinary resize (1600×900 becomes 1602×908 going from 125 % to 100 %); borderless fullscreen stays the panel's size. ⚠ **WinForms re-publishes the window icon on every one** (`Form.OnDpiChanged` calls its `UpdateWindowIcon`), putting the single large frame into the title bar's small slot. `DisplayRefresh.WatchScale` calls back once WinForms is done, and the callback republishes the authored frames of the new scale (see [the window icon](../formats-and-tools/application-icon.md)).
- **To check it without a scaled panel**, run the exe with `__COMPAT_LAYER=DPIUNAWARE` in its environment: the line says `DPI-UNAWARE`. A scale can be changed for a check without signing out through `DisplayConfigSetDeviceInfo` (the undocumented DPI-scale packet the open-source SetDPI tool uses); restore it and read it back.

## 10-bit colour (#859)

Inside, the frame is wide (the HDR targets, RGBA16F) and `Tonemap.fx` resolves it once into [0, 1]; the last step quantises to the back buffer's depth, 8 bits a channel until this. **Where the window's monitor reports 10 bits per colour, the back buffer is `R10G10B10A2`** (`SurfaceFormat.Rgba1010102`), and nothing else about the picture changes: the tonemap's output is the same, only the target it writes to is wider. The HUD's overlay targets and the Potato scene target stay 8-bit.

- **The panel is asked, not assumed**: `DisplayRefresh.TryGetBitsPerColor` matches the window's monitor (`MonitorFromWindow` → its `\\.\DISPLAYn` name, the refresh's own lookup) to the DXGI output of that name and reads `IDXGIOutput6`'s `BitsPerColor` — 8 on an ordinary panel, 10 on one set to deep colour in Windows. Asked at startup, on every `SetGraphics`, on a resize and on a scale change (the cheap hooks for a monitor change, as the refresh's are), never per frame; GamePi answers nothing.
- **The DISPLAY row "10-bit colour"** (`GameSettings.TenBitColour`, on by default, the way back to 8) is ticked only where the back buffer really is 10-bit; held off, the box is empty with the reason beside it: `(8-bit panel)`, `(panel)` when DXGI has no answer, `(Potato)` (that path draws 8-bit sources straight into the back buffer), `(driver)` after a refused swap chain. It took the FPS counter's slot, which moved to GAME: DISPLAY's twelve rows are its whole vertical budget (Back 24 px clear at 1600×900).
- **The first device is always made 8-bit and reset to 10 a moment later** (`RefreshBackBufferFormat` from `Initialize`, then every `SetGraphics`): a swap chain the driver refuses is an exception out of device creation, where nothing can answer it, and `ApplyChanges` *creates* the device when there is none, so the constructor's `SetGraphics` decides nothing. On a reset the refusal is `ApplyChanges`'s to throw, the run goes on at 8 bits and the log says `[display] 10-bit back buffer refused by the driver: …`. The owner's GTX 1060 answered `E_INVALIDARG` from `CreateSwapChain` to a 10-bit request through MonoGame (the issue's first finding); an AMD laptop takes the format in every mode (windowed, borderless, One and Immediate, set before or after the device, measured with a 3.8.5 repro). Which it is on that card, and whether DWM then presents 10 bits at all, is not known from here.
- **The run log**: `[display] panel 8 bpc, 8-bit back buffer, 10-bit colour on but held by the 8-bit panel`, or `[display] panel 10 bpc, 10-bit back buffer (R10G10B10A2)`.
- ⚠ **`GetBackBufferData` converts nothing**: a 10-bit back buffer read into `Color`s is its packed words misread as bytes — cornflower blue (100, 149, 237) came back as (145, 89, 121), measured. The screenshot writer and the note's picture read through `Prazsky.Core.Render.BackBufferPixels`, which reads the words and decodes them (`BackBufferPixelsTests` pins the decode and that misread). ⚠ The readback copies the swap chain into an 8-bit staging texture whatever the format; it worked on the AMD laptop and is not verified on NVIDIA.
- **`tenbit` / `tenbit=off`** force the format for a run whatever the panel and the settings (a run's instruction like `windowed`, never written back): `tenbit` on an 8-bit laptop is how the decode was checked (`level=1 tenbit shot=9`, the shot's colours right).
- **`ramp`** draws a grey ramp, 0 to 1 across the width, over the lower third of every frame straight into the back buffer from a 16-bit texture through `SpriteBatch` (`BS3DGame.DrawRamp`, after the foreground composite): 256 steps on an 8-bit buffer, 1024 on a 10-bit one **that the panel and DWM show as such** — the question only an eye on a 10-bit panel answers, comparing the row on and off (or `tenbit` against `tenbit=off`); DWM may re-quantise a windowed or borderless swap chain, and a screenshot cannot tell, a PNG being 8-bit.

# Repository conventions — the reasons

Part of the BS3D documentation. `CLAUDE.md` states each repo-wide convention as a rule; this document holds the **reasons, the incidents and the figures** behind four of them, **word for word as they stood in `CLAUDE.md` when they were moved (2026-10-03)**.

## Finished work lands on main immediately

**Finished work lands on main immediately** (the owner's standing instruction): once a task is done and verified, its branch is merged to main right away — work sitting on a side branch is work the owner cannot see. This said "its PR is merged" until 2026-08-14, which contradicted the branch rule below and had two agents working two different ways at once; the owner's ruling is that the branch rule below stands, so **the merge is a direct `--no-ff` merge into main and there is still no PR anywhere in this repo**. The point of the sentence is the *immediacy*, not the mechanism.

## Line endings

**Line endings are LF, everywhere, and `.gitattributes` says so** — in the stored blob and in the working tree alike (`* text=auto eol=lf`). Until 2026-09-21 there was no `.gitattributes` at all, so the ending was decided by each machine's `core.autocrlf` and by whichever tool last wrote the file; the repository carried **470 blobs stored LF against 28 stored CRLF** (the 2023-era library sources, the `.sln`/`.csproj` set, the agent journal). The cost never landed at the edit, it landed at the **merge**: a file whose every line differs from `main`'s conflicts *whole*, so the two or three real changes had to be dug back out of a conflict spanning the entire file — which is what had been happening on nearly every merge. It had also produced a defect nothing reported: `GameplayScreen.Session.cs` carried two `\r\r\n` sequences from a script that wrote one ending into a file using the other, and **a lone CR makes git classify a file as binary** — it was the only `.cs` in the repository git would neither diff nor merge by line. LF was the choice because it was already the de facto standard, because every tool writes it unless told otherwise, and because `.claude/hooks/*.sh` must be LF or bash refuses the shebang — and one of those hooks is what refuses `git reset --hard` here. **Do not hand-write CRLF back in**, and after any script has touched a tracked file run `git diff -w --numstat` before committing: if it disagrees with `git diff --numstat`, the file was re-ended and the commit is whole-file churn. The one renormalization commit is listed in `.git-blame-ignore-revs` (GitHub honours the name; locally `git config blame.ignoreRevsFile .git-blame-ignore-revs`, once per clone) — though **measured afterwards, blame had barely suffered**: `git blame` re-attributes a re-ended line to the commit that wrote its content, so of the lines the renormalization still owns, **every one is blank** (91 of 91 in `SkyDome.cs`). Those are also the lines `--ignore-revs-file` cannot rescue, since one blank line is indistinguishable from another. The file is therefore insurance for the *next* reformatting commit rather than a repair of this one.

## Branches are the unit of work, and there are no pull requests

Commit a change to a feature branch off `origin/main` and push the branch; the branch is then **merged into `main` with a merge commit** as soon as the work is done and verified (the standing instruction at the top of this file; this said "when the author asks" until #594, which contradicted it) — `git merge --no-ff <branch> -m "Merge branch '<branch>': <what it does> (#issue)"`, which is what every merge in the log is. This said `--ff-only` until 2026-08-12 and the history had never done that: it matters because **two branches off the same `main` cannot both fast-forward**, so an `--ff-only` rule refuses the second one and invites a rebase and a force-push of a branch that is already pushed — on the one repository whose whole point is that several machines share `main`. The merge commit also keeps the branch's name and its one-line summary in the log, so the history reads as a list of named changes rather than a flat run of commits. Never open a PR and never offer one — a sole author reviewing their own work gains nothing from the round-trip. The branch is not a review artefact: it exists because several machines are active on this repo at once (a laptop and a desktop), so `main` is shared between them and a direct push to it from one machine is the one action that can leave another machine's checkout diverged. Name a branch `<issue-number>-<slug>` when there is a GitHub issue, a plain descriptive slug otherwise. One change per branch — the working tree here often carries several unrelated threads at once, so stage only the files belonging to the change at hand.

## A merged branch is deleted immediately

`git push origin --delete <branch>` and `git branch -d <branch>` (the safe `-d`, never `-D`: it refuses anything not actually merged, which is the check, not a formality). The merge commit already carries the branch's name and its one-line summary, so once it has landed **the branch ref holds nothing the history does not** — what it still does is *say something*, and what it says is "this is in flight". That is the whole cost of leaving it: on a repository whose point is that several machines share `main`, the list of branches is how one machine asks what the other is in the middle of, and a list of finished work reads as a list of unfinished work. Left unenforced until 2026-09-10, when it had grown to **eighteen merged branches on GitHub and about a hundred and thirty locally** — every one of them merged, so the answer to "what is actually being worked on?" had to be computed rather than read. Two exceptions, and both are temporary rather than permitted: a branch checked out in a worktree cannot be deleted until that worktree moves off it (`git worktree list` says which), and a branch the **other machine** has not fetched since the merge simply loses its upstream there, which is harmless — the work is in `main`.

## How work is run — the reasons (2026-10-03)

`CLAUDE.md`'s "How work is run" has four rules. They come from a review of how the project is being run, done on 2026-10-03 by the owner and an agent, and the owner agreed with all four recommendations. This is what they rest on.

**What was measured that day.** Since 2026-09-19 (the day after the first release, v0.1.0 on 2026-09-18): **308 issues created, 287 closed, 1,564 commits on `main`**. 76 issues open, only 6 of them older than 30 days — the tracker flows, it is not rotting. CI green on the last runs; the level and scoring gates and the "seen to fire" self-checks hold; a critical review agent found real bugs in 3 of 9 merges it read (2026-10-01). **21 open issues carried `shipped-awaiting-verdict`.** `docs/*.md` were 3.9 MB, the journal 7,760 lines and `CLAUDE.md` 48,111 bytes before it was cut to 27,930 (the removed paragraphs are word for word in `docs/build-and-release.md`, `docs/libraries.md` and the sections above).

**Why "done" means a player can understand it.** Throughput measured in issues closed is not value to a player, and the owner's playtests show where the value was missing: the Cut "seems to do nothing" and the Brake was "not understood" (#692, 2026-10-01), the Swap's chip sat in the corner while the second chapter taught the score (#705), and the Bomb and the Zap were built and verified with no level in the campaign containing either (#368). Each shipped with a "Not verified" line that named exactly what the playtest then found, and the line was honest — but a mechanism whose use is not taught, not placed in a level and not visible when it fires is half built, and the owner's playtest became its first real test. The rule moves that test to the front: the thing that tells a player what it is ships with it.

**Why the verdict queue is capped.** Agents are cheap and the owner's attention is not. A session can produce requests for a verdict faster than one person can read them, and the things most in need of a verdict are the ones no agent can judge — sound (every run is muted) and feel. On the day of the review 21 issues were waiting, beside open questions only the owner can answer (#764's date, the power-ups' charge economy in #765 §5, the price of the Swap and the Brake). Past 15, more look-and-feel changes only lengthen the queue; the work that does not need the owner's eye (a bug, a gate, a refactor, a measurement) or that unblocks a decision he owes is what to take instead. Batches, because one page of before/after pairs is one sitting and thirty messages are thirty.

**Why a claim goes on the issue.** The journal is the place for findings, but it is 7,760 lines and a claim in it is the last thing a new session reads. Measured 2026-09-23 over all 58 open issues: **not one was untouched** — 39 had a merge commit carrying their own number, the other 19 were named in the journal — so the issue list alone cannot tell "shipped, awaiting a verdict" from "nobody has started", and #536 and #549 were each built twice by two machines in the same hours. `gh issue list --label in-progress` is the one look every session already makes. It does **not** fix the timing — a claim made after the other session started protects nobody (#549's was minutes late) — which is why the rule also asks for a `git fetch` and a look for the number during long work.

**Why CI is looked at after every merge.** A flaky physics test kept `main` red for seven hours on 2026-10-02 and nobody noticed; the workflow was doing its job and nobody was reading it.

**The fourth recommendation is an issue, not a rule:** put three to five outside players on the release before more breadth is added (#768). Every verdict so far is the owner's, the one person who knows what every chip means.

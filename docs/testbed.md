# The Testbed

Where every system was built and is still tuned: the shot, the gun, and the two cameras that aim it.

Part of the BS3D documentation. CLAUDE.md holds the project overview, the build commands, the ball grid and the repo-wide conventions, and says which of these documents covers what.

## How the executable is laid out (#73)

`Testbed.cs` was 3 548 lines with a second public top-level type inside it and region markers that actively lied — `#region Graphics` held the city, the island, the funnel and the glare; `#region Ground` held two constants and no ground. The shared hoists (#74, #75, #76) took the libraries' half of it, and #73 took the rest. It is **nine files** now, and which of them a change belongs in is the point of the split:

| File | Holds |
|---|---|
| `Testbed.cs` | The state and the lifecycle: every field, the constructor, `Initialize`/`LoadContent`/`UnloadContent`, the scene and sky (`SwitchScene`, `SetSkyDome`, `ApplySkyLighting`, `UpdateOvercast`), the setting it builds (`BuildCity`, `BuildCeiling`), map and level loading (`DeserializeMapFromFile`, `LoadLevel`, `InstallMap`, `FitCeilingToMap`) and the camera fit |
| `Testbed.Update.cs` | The frame's clock: one simulation step, the wall-clock ageing outside that gate, the input poll, the game-mode transition animation, and the one-line ticks of the three harnesses |
| `Testbed.Draw.cs` | The frame on the screen: the scene into the HDR target, the resolve, the overlay, `CollectMagazineBalls`, and the back buffer (`SetGraphics`, the two window/device handlers) |
| `Testbed.Input.cs` | The two modes and what drives the gun in them: `SwitchGameMode`, `UpdateCannon`, `UpdateMouseAim` |
| `Testbed.Shooting.cs` | A ball's whole life: `InitializeShooting`, `ShootBall`, the cull (`RemoveFallenBalls`, `KILL_PLANE_Y`) and a structure's teardown (`RemoveCurrentBallsStructure`, `RemoveAllConstraints`, `ReleaseAllBalls`) |
| ~~`Physics/BallContactEventHandler.cs`~~ | What happens when a shot touches something. #73 took it out of `Testbed.cs`, where it was a second public top-level type, and **#68 then took it out of this executable entirely** — it is `Prazsky.BS3D.Physics.BallContactEventHandler` now, one copy shared with the Game. That is what #73 was setting up: two comparable files rather than one of them being a nested class nobody reads. See the section below |
| `Diagnostics/TestOptions.cs` | Every command-line switch, parsed once. `Program.cs` is eighteen lines now and does nothing but `Testbed(TestOptions.Parse(args))` |
| `Diagnostics/AutoShootDriver.cs`, `AimShootDriver.cs`, `SwitchMapDriver.cs` | The test harness — the whole justification for this executable, and it used to be nine fields and four inline blocks scattered through `Update`. Each is **null unless its switch was given**, so a harness that exists is a harness that runs, and each is ticked from one line |

**Fields stayed in `Testbed.cs` rather than moving to the partial that uses them**, deliberately: several are initialised from each other, and a split that separates a field from the field it derives from is how a partial class starts fighting its own initialisation order. So the core file is the state and each partial is a phase of the frame.

Two things about the harness are worth stating because they are contracts rather than conveniences. **The argument spellings and every logged line are a CLI surface** — `.claude/skills/verify`, `.claude/skills/screenshot` and its `screenshot.ps1` drive this executable by those exact strings — so `TestOptions` may gain switches but must not rename them, and the `[autoshoot]`, `[aimcheck]`, `[aimshoot]`, `[switchmap]` and `[camera]` lines are unchanged to the character across the split. And **`[autoshoot]`'s line stays in `Testbed.cs`** (`AutoShootOnce`) while its cadence and random target box are the driver's: every figure on that line — the frame rate, the drawn count, the LOD split — belongs to this executable's own renderers.

Three defects the split fixed, each of them latent rather than visible:

- **The contact handler held a stale ceiling.** `FitCeilingToMap` replaces the whole `KinematicBody` wrapper on every map load so its world matrix matches the new pose, and the handler went on holding the one it was constructed with. It survived only because the body and its handle — the two things it reads — outlive the wrapper, so nothing pose-derived was ever asked of the stale one; a single later read of `Ceiling.World` would have made it a real bug with nothing on the line to hint at it. `InstallMap` pushes the wrapper on now, beside the map and the structure array it already pushed.
- **The overlay's ball/constraint count was computed on every change.** All five things that can move the population — an attach, a cull, a shot, a map load, a release — walked `Solver.CountConstraints()` over every constraint batch and composed two strings, whether or not the overlay was even visible; a cascade that releases a cluster does all five in one frame. It is a dirty flag now (`InvalidateBallCounts`), spent once a frame in `Update` (`RefreshBallCounts`) and only while F12 has the overlay up — and the visibility test comes *before* the flag is cleared, so the first frame after F12 brings it back states the truth rather than whatever the line last said.
- **NumPad2 could not enter the scene cycle from outside it.** The cycle is deliberately only `SceneRenderer.CycleLength` long (the seven scenes a map is authored against), but `(index + 1) % 7` cannot be entered from a scene reached with `scene=`: from the forest (index 7) it landed on the **sea**, three scenes deep, leaving the four cycle entries before it unreachable without four more presses. Anything off the end restarts the cycle at the city now. Measured after the fix: `scene=forest` then NumPad2 three times logs `[scene] City`, `Sea`, `Savanna`.

`TryFindMapBall`'s full walk of the structure array per structure-ball contact was left as it stood here, on the grounds that indexing one of a knowingly duplicated pair is what #68 existed to prevent — and #68 has since merged the pair, so there is now exactly one copy of that walk (`TryFindStructureBall` in the shared handler) and it is a normal optimisation rather than a divergence. It is still unoptimised: a hit returns as soon as it is found, but a shot that struck another loose ball examines all 8 000 cells of a 20×20×20 field.

## The gun's hardware, in one copy

The Testbed built the gun and the Game rebuilt it, and #76 ended that the way #75 ended two copies of the setting (see "The setting, in one copy" in `docs/scenes.md`). Five pieces stood in both executables with every dial value-identical — the camera fit for about 120 lines of it line for line — and are one copy each in `Prazsky.BS3D` now, so everything the rest of this document says about the barrel, the magazine, the game camera and precise aim is also what the Game does, and the differences are named here rather than left to be discovered:

- **`GameObjects.CannonRig`** — the gun's *hardware*: the procedural barrel and the instanced renderer that draws it, with every figure the tube is cut to (`BORE_RADIUS`, `WALL_THICKNESS`, `SLOT_HALF_ANGLE`, `CHAMBER_DEPTH` — the breech dome's cavity, the hood over it and the parked round's set-back, one figure on purpose — the wall's segment count, `STEEL_COLOR` and its specular ambient), and since the advance walk arrived the **carriage** under it too — the cheek plates with the trunnion pins they visibly hold the tube by (the pins are the carriage's and not the tube's, deliberately: they are coaxial with the elevation axis, so a fixed pin looks identical as the tube elevates, while the Game's recoil slides the tube and pins riding it would tear along the plates), the axle, the **split trail** (two beams diverging down and back, because the breech sweeps down exactly where one central beam would stand — at high elevation and under recoil it dips *between* the legs, which is what a split trail is for on a real gun) and the pair of spoked wheels (`GunCarriageMesh`/`GunWheelMesh` on the `MeshBuilder` that carries `CannonMesh`'s wind-against-the-face-normal trick as a service). The wheels' ground line is the one figure that reaches outside the rig, and it is derived rather than agreed: `CannonRig.TrunnionHeightAt(radius)` = `ArenaIsland.FloorHeightAt(radius) + AXLE_DROP + WHEEL_RADIUS`, and `Cannon` re-seats its own Y through it on every move — the walkable top is a **dish**, so the wheels sit on the stone actually under them (down the whole `DISH_DEPTH` near the drain, which is where the shipped maps stand the gun) instead of grazing the outer arris plane at every radius, which read as standing only at the arris itself and as levitating everywhere else. Past the arris there is nothing to stand on at all (a big map's orbit leaves the island entirely) and the stance holds the arris plane there, the one plane the eye takes for ground. `CannonRig.StanceGradeAt` is the stance's pitch: the ground's rise across the carriage's own footprint (wheel contact to trail feet, a secant rather than a point derivative), so the carriage leans ~6.4° nose-down on the dish and eases level across the arris over its own length; `Cannon.CarriageWorld` turns it into the stance basis, and the wheels and trail compose off that matrix, so they follow. The ground-darkening anchor rides the same stone: `Draw`/`DrawCarriage` re-anchor `GroundHeight` per frame off the pose's own translation, because a gun standing a `DISH_DEPTH` below a fixed anchor saturates the darkening over the whole undercarriage. Resizing the wheels still moves the gun, exactly as it would a real carriage — the gun has no collider, so where it stands is a drawing fact. `DrawCarriage` spins the wheel bodies by `Cannon.WheelTravel / WHEEL_RADIUS` — the ground actually covered, so they slow into the walk's rubber ends with it, and deliberately do **not** turn during an orbit (a carriage slewed sideways is dragged, not rolled). It is handed the queue's size and spacing and derives `PivotToFrontBall` from them — and `BarrelReach`, the trunnions-to-cascabel-pole distance off the mesh actually built, which is the gun box both executables hand the camera fit — so the tube that was built, the muzzle that is fired from, the balls drawn in the bore and the box that frames all of it cannot disagree. It owns no content: the shared `InstancedModel.fx` goes in and is emphatically **not** disposed there, being the balls', the city's, the island's and the ceiling's too. Since it also carries the window's **glazing** (`Prazsky.Core.Render.CannonGlassMesh`, a second mesh and a second renderer beside the tube's), it is how the gun says which round fires next without a mark on the HUD: a thin curved pane fills the slot, in a **dark blue glass of its own** (`GLASS_COLOR`, `GLASS_ALPHA`), with the **front of the queue notched out of its front edge** — so the round about to fire is never read through glass. The notch is **half** an ellipse (the pane's full width across it, `GLASS_NOTCH_REACH` back along the bore), and a half rather than a whole because the muzzle face sits exactly one ball radius ahead of the front ball's centre: glass in front of it would have to fit in a gap of zero. **How far back it reaches was a ball radius and is three of them since #204** — see the ADS bullet under "Precise aim" for the geometry, which is the point at which this stopped being a figure about the prop and became one about the *lens*. That necessarily leaves the **second** round open as well, which the issue licenses explicitly, so the pane no longer identifies the first on its own: #175's breathing mark on slot 0 (the Game's `MUZZLE_MARK_*`, not the rig's) is now the only thing that does, and must not be removed as redundant. Three of the pane's figures are not looks. It is seated on the **bore** and its thickness stays under the slimmest steel the window crosses (the chase dip), so it can never prove proud of the tube. It is held off the window's two cheeks and its end lip by a small **reveal**, because a glass face flush with a steel one is two coplanar surfaces fighting over the depth buffer; the reveal reads as the shadow line of a pane seated in a frame, which is what it is. And its **sky reflection is well under the full strength** every other surface here takes — measured rather than tasted: the game camera stands behind and only slightly above the barrel, which is a *grazing* angle across this pane, and grazing is exactly where the shader's Fresnel term takes the sky reflection to its maximum, so at the full strength every other surface takes the pane came out an opaque blue sheet from the one vantage the game actually plays from. The queue's colours were gone, and a window that hides the queue is a window with no reason to exist. The ceiling's plate has no such duty — nothing is read *through* it — which is why it keeps the full reflection and this cannot. `DrawGlass` is deliberately **not** part of `Draw`: the pane is translucent, so both executables draw it **last of their translucent surfaces**, after the drain's glass and the ceiling's, it being far and away the nearest of the three — and with the very matrix the barrel was drawn with, recoil stroke and all, which is why both callers now take that pose into a local and hand it to both calls. One honest limit: from the overview camera the barrel hides its own muzzle end, so the open round reads only as the small ellipse of its cap at the top of the window, with the rest of the queue glazed behind it — which is exactly why the pane's darkening is what makes that ellipse tell. The oval in full shows in precise aim, whose lens rides over the barrel, and from any vantage above the tube (the Testbed's free camera, and the drop cinematic's swing), where the pane is seen near head-on and the step between the covered rounds and the open one is unmistakable. **That last claim was half wrong until #204**, and it is worth knowing which half: the oval read correctly from the ADS lens all along, and the *round standing open in it* did not — the notch was sized along the bore, and from the lens the sight line grazing its rim missed the front ball by 0.012 of a unit, so the ball was entirely behind glass on the one vantage that was supposed to show it best.

  **Its colour and alpha were the ceiling plate's until they were looked at, and they were the wrong two figures.** A pale tint at a low alpha subtracts about as much light as it adds back, so the four covered rounds came out faintly hazed and nothing else — a window nobody notices says nothing about which round fires next, which is the only reason the pane exists. The three figures the retune settled, and the order they matter in, are worth stating because each one is a different mechanism:

  - **The colour has to come down in every channel, the blue included.** The shader is handed the colour *premultiplied by the alpha* and decodes the product (`SrgbToLinear(DiffuseColor.rgb)`), so what the pane adds is that product, per channel, and roughly squared in the alpha. Deepening the blue while raising the alpha left the blue channel's product almost exactly where it began (0.85 × 0.4 against 0.50 × 0.62): the pane turned markedly bluer and barely darker, and measured on a glazed ball the blue channel moved four levels out of 173. The saturation lives in the **ratio** the channels keep, not in leaving one of them high.
  - **The alpha is the only thing that dims what is behind.** Under `BlendState.AlphaBlend` the transmission is exactly `1 - alpha` and the colour has no say in it at all. It is bounded above by the queue staying legible — the dark ball types bound it, being identified by their white gores alone — and it is bounded *hard* by a fact the notch hides: drawn opaque for a moment as a test, the pane fills the **whole** slot from the game camera. The barrel hides its own muzzle end, so the open round shows only as the small ellipse of its cap at the top of the window and the rest of the queue is read *through* the glass. The alpha therefore dims the entire queue to buy contrast on one ellipse, which is why the answer is a pane that is dark and **clear** rather than one that is merely thick.
  - **The sky reflection had to come down with them, and it is written as a product with the alpha.** The shader multiplies the reflected environment by the material alpha too, so raising the alpha would have brightened the reflection by the same factor and put the veil straight back at exactly the grazing angle the darkening was meant to clear. Worse, from the game camera this reflection is the *largest* term the pane contributes — larger there than its whole diffuse body — and being a reflection of the sky it is achromatic and pale. That is what the pane used to look like: not glass but **haze**, balls slightly out of focus rather than balls seen through something. The tint can only show once that wash is down, so the darkening and the cut are one change and not two.
- **`GameObjects.Magazine`** — the queue of loaded colours, the glide that carries it forward after a shot, and where each loaded ball sits in the bore: `SIZE`, `SPACING`, the ease constant, `Peek`/`Advance`/`Recolour`/`Refill`/`Settle`/`Step`, and the `BorePose` a frame's placement comes back as.
- **`GameCameraFit`** — where the camera stands, how high it aims, how far out the gun orbits and how far the player may walk it from there, solved together: `CAMERA_HEIGHT`, `FIT_MARGIN`, `CANNON_CAMERA_STANDOFF`, `CANNON_FIELD_CLEARANCE`, `CANNON_MAX_REST_ELEVATION`, `CANNON_DRAIN_CLEARANCE` (the rest radius and the walk's near end both stay this far outside the drain's mouth, so the wheels never roll off the stone onto the glass — the figure is set by the gold bead's proud bulge and by how far the inner wheel swings inside the stand's radius at full traverse) and `CANNON_ADVANCE_STROKE` (the walk's range in the `CameraFit` result — a fixed stroke either way so the walk feels the same on every map, its near end held off the footprint *and* drain clearances; the elevation bound is deliberately *not* applied to the range, because walking in past it and losing the highest near cells to the clamp is the player's own reversible trade). The solve is dish-aware: the gun's height is re-derived per candidate radius (`CannonRig.TrunnionHeightAt`), which makes the rest-elevation bound self-referential through the dish's profile — the alternation resolves that coupling the same way it resolves the lens–gun one. `CameraPosition` is both the pose the fit searches over and the pose each executable puts its overview lens at every frame, so the one expression has one home — and its height is **floored** at the arris-stance lens height (`LENS_FLOOR_Y`): a lens riding `CAMERA_HEIGHT` below a dish-sunken gun sat below the arris itself, and from out past the island's edge the coping swallowed the bottom half of the frame (measured), so the overview holds the height it was always tuned at and the walk does not bob the camera.
- **`PreciseAim`** — the lean over the barrel: every dial (`BACK`, `RISE`, `FOV`, `FLOOR_CLEARANCE`, `CONVERGE_MIN`/`CONVERGE_MAX`, `BLEND_TAU`, `TRIGGER_THRESHOLD`), the one reversible `Blend`, `ButtonHeld`, and the `AimPose` `BlendedPose` hands back.
- **`Cannon`'s own "The barrel's pose" region** — `AimDirection`, `StandBearing`, `OrbitCenterGround`, `MuzzlePosition`, `BarrelOrientation`, `BarrelWorld` and now `CarriageWorld` (seated on the stone under the trunnions — its up is the dish's own normal, so the carriage pitches with the *ground* it stands on and never with the *aim*: the tube elevates in the cradle), which each executable had kept as a private helper apiece. It belongs on the gun: all of it is read off the pose and none of it is stored. The advance walk's state (`Advance`, `SetAdvanceRange`, `RollTravel`/`SlideTravel`, the rubber `ADVANCE_EASE_ZONE`) is the gun's too, wired to W/S by each executable. **So is the recoil stroke, since #115** — it was the one piece of the gun still kept by a caller (the Game), and it moved onto `Cannon` because two parts of the gun answer the one shot off one clock: the tube slides `BarrelRecoilBack` in its cradle, and the undercarriage takes `CarriageRecoilBack`'s smaller, later shove (the hump `4s(1−s)` over the tube's normalized stroke — zero at the shot, peaking ~0.07 s in), with the wheels rolling by `WheelTravel` and the queue hanging off `DrawnMuzzlePosition`. The executables keep only the ticks (`KickRecoil` where they fire — the Testbed's game mode included, and deliberately not its free-mode camera shots or test rains — and `StepRecoil` beside the magazine's glide); the true pose (`AimDirection`, `MuzzlePosition`) takes none of it, so the recoil stays drawing-only by construction.
- **The walk's two travel signals** — `Cannon.RollTravel` (along the carriage's heading, what the wheel bodies roll by) and `Cannon.SlideTravel` (along its axle, what the rollers spin by), both since #129. **Neither walk owns an axis.** The design's first cut had the advance (W/S) feed the roll and the orbit (A/D) feed the slide, on the reasoning that the axle is the orbit's tangent — which holds only while the gun points along its stance. The carriage is **yawed with the aim** and the walk is not, so slewed 45° over, an advance is half a roll and half a slide; reported from play as the animation not matching the movement once the gun was aimed off-centre. `Cannon.AccumulateWalk` resolves **each step** into the carriage's own axes instead — vectorially, off the axes read out of the very matrix the carriage is drawn with, because a trigonometric decomposition needs two sign conventions right at once and neither is checkable from the code; and per step, because the traverse moves while the gun walks. Both measure the walk rather than the pose, so `OrbitToFace` and the `OrbitRadius` setter leave them alone, and so does traversing on the spot — a gun slewed in place scrubs its wheels, which is what a real one does. `WheelTravel` is `RollTravel` plus the recoil's shove, which belongs to that axis alone.
- **The wheel is an OMNIDIRECTIONAL one** since #129 (`OmniWheelMesh` + `OmniRollerMesh`), not the spoked wagon wheel it was — which was half of what read as a historical gun carriage, and could only answer one of the walk's two axes. Two rows of eight barrel rollers ring a pair of dark plates: the **body** spins off `WheelTravel` for the advance and the **rollers** spin off `SlideTravel` for the sideways half, so the gun no longer crabs sideways on wheels that stand still. A roller's profile is not a cylinder and cannot be — `ρ(t) = R − √(a² + t²)` is what keeps the wheel's envelope a circle, and a cylindrical roller would make it polygonal and bump as it rolled. `OmniWheelMesh.RollerSeats` throws at load if a retune ever grows the rollers through each other, in a row or across the rows. They are their **own instanced draw** (32 of them, against the bodies' 2) because a roller has to turn about its own axis while the body turns about the axle and the per-instance `Vector4` is the ball technique's dither — and the two draws buy the wheel's two tones for free, which is what keeps it legible standing still. The rollers are **fluted, and helically** — a smooth surface of revolution turning about its own axis is visually invariant, so their spin was correct and invisible until they were cut (reported from play; the spoked wheel’s own note and #231 had both recorded that lesson already, and a straight flute would say the roller turns but not which way). **Measured at nothing**: 130.0 FPS fluted against 129.1 smooth and 129.4 with the roller draw skipped entirely, all 7.7 ms and the bands overlapping (desktop 6900 XT, Testbed, fixed camera on the gun, 1600×900 ssaa 4, `fpscap=150`).

`AimReachability` came out of the Testbed alone (see the aim testing below).

**What deliberately stayed with the callers**, every one of them a real difference rather than a tidy-up not yet done: the simulation's stepping policy and what culls a ball (see "Physics in the game" in `docs/game-session.md`); the ceiling's height, which the Testbed derives from the map's level count and the Game from a plate that slides down as a level is played; the field's vertical placement, which goes into `Solve` as the two Y arguments — the Testbed's lattice frame *is* the world frame (floor y = 0, no death line), while the Game hangs its field per level so its bottom clears the death line (see "Levels in the game" in `docs/game-session.md`); where in the frame the barrel is drawn; the camera type and its set order (below); the field of view, which each executable owns, animates and lerps, so the fit is handed the very FOV the camera is rendering with rather than a second copy of the figure; the field's footprint, which both take off `CeilingPlate.FootprintFor` because those corners *are* the drawn plate's; the Game's transmute cross-fade and its next-colour policy; and the `[camera]` and `[aimcheck]` log lines. (The recoil stroke used to be on this list — "since only the Game animates one" — and #115 moved it onto `Cannon`: the carriage's response needed the tube's clock, and the Testbed fires the same stroke in game mode now.)

What reconciling the copies turned up:

- **The fit no longer parks the gun mid-solve.** Both copies assigned `Cannon.OrbitRadius` *inside* the alternation, and that setter runs `MoveToOrbitAngle()`, which slides `Position` — which the camera's half of the solve then read. So the gun stood at three intermediate guesses on every load, and the pair that came out was one round out of step. `GameCameraFit.Solve` computes the gun's pose at a candidate radius instead and returns the radius in its result, for **one** assignment by the caller after the solve; no `Cannon` is written, and none goes into the alternation at all.
- **Every recorded fit figure reproduced exactly at the hoist**, measured before and after it: the built-in 9×9×16 fallback → 27.6 out, aim Y −0.2, orbit 13.5; `One.json` (10×10×15) → 28.0, aim Y 0.0, orbit 13.5; 20×20×20 → 32.9, aim Y 1.5, orbit 18.0. Nothing the fit outputs changed to one decimal on any level. (The Game's *inputs* have since moved for deep fields — its field-floor rule raises any field that would reach past the death line — so the fallback and `One.json` still printed those very figures while `Colossus.json` and 20×20×20 printed new ones — and later the *solver* moved too, when the gun came down onto the island's dish: the drain clearance, the dish-derived trunnion height and the overview lens's floor all enter the solve now, so none of the figures in this paragraph reproduce today. They are kept as what the hoist measured; the current set is in "Levels in the game" in `docs/game-session.md`.)
- **The alternation does not converge on the first round, and both copies' comments claimed it did.** Two of the solve's sub-0.1 residuals moved, from round one now being seeded off `Cannon.OrbitRadius` rather than off the caller's last stand-off — the orbit radius (`Colossus.json` printed 14.2 where it had printed 14.1 — before the Game's field-floor rule raised that level; it prints 16.0 now) and the gun-to-lens gap (the Testbed's `Full.json` prints 15.0 where it printed 14.9, while 20×20×20 printed 14.9 where it had printed 15.0). The residual goes in **both** directions, so it is where three rounds of alternation land rather than a bias; `CONVERGENCE_ROUNDS` is 3 because a sub-0.1 survives to the third.
- **`CannonOrbitRadius()`'s `sqrt` was dead** in both copies, which #72 suspected and this confirms: it recomputed exactly `Cannon.OrbitRadius`, because the only two places that ever write `Position` both leave the horizontal distance at exactly the orbit radius. The solve reads the property and the helper is gone.
- **The magazine's three-arrays-in-step invariant is enforced now rather than commented.** `Advance` owns the queue's shift and reports every move through two hooks handed over once at construction — `slotCarried(destination, source)` and `slotLoaded(slot, type)` — so the Game's transmute arrays cannot fall out of step with the colours (see "A ball already in the barrel…" in `docs/game-session.md`). `Recolour` deliberately does **not** fire `slotLoaded`: a re-coloured ball is precisely the one whose old colour the cross-fade has to keep. The queue array never escapes the type, and a next-colour policy that answers `default(BallType)` throws instead of quietly loading a ball that draws as nothing at all.
- **`PreciseAim` hands back a pose and touches no camera, and that is load-bearing rather than tidy.** The Testbed drives a `BasicCamera3D` whose `FieldOfView → Position → Target` set order is mandatory (the `Target` setter rebuilds the view last, with world up), while the Game writes a base pose onto a `RecoilCamera` and goes on lerping the drop cinematic *over* the pose that comes back. Neither could be served by a component that assigned to a camera itself. The focus gate is the same rule by two routes for the same reason: the Testbed rebuilds its held flag with an `IsActive` term every frame, the Game simply does not run its aim update while inactive and clears the flag in that branch.
- **`CannonRig` disposes its mesh *and* its renderer.** The Testbed disposed only the mesh and leaked the instance buffer; the Game already did both.
- **The magazine's collection lost a per-ball 4×4 multiply.** `CollectMagazineBalls` passes the world matrix `BorePose.SlotWorld` built — the barrel's own basis with the translation written straight into its fourth row — instead of an orientation it then multiplied a translation into (BestPractices.md §6). The Game's collector already did it that way.
- **`AimReachability` answers with facts, not strings.** The check is a pure function of a map and the gun's orbit geometry — no simulation, no graphics device, no live `Cannon` — so the map editor can ask it on a save path rather than a script having to read a console line. The Testbed goes on formatting its three `[aimcheck]` lines from the result struct (in `Diagnostics/AimShootDriver` since #73), and their wording is unchanged on purpose: `.claude/skills/verify` documents those exact strings.

## The rest of the hardware, in one copy

The gun was the first half of #76. The second is everything else both executables had stood up twice around it, and it went the same way — one copy each, with the policy that is genuinely per-executable named here rather than left to be discovered:

- **`Prazsky.BS3D.Physics.PhysicsWorld`** — the physics session's *hardware*: the worker pool, the buffer pool everything in the simulation is allocated from, the `Simulation`, the `ContactEvents` stream wired into its narrow phase, the body description every shot is stamped from, and the one order all of it is built and torn down in. **The stepping policy stays with each caller by measured decision**, and the type is shaped so that it cannot quietly stop doing so: `Step` takes *one* step of exactly the length it is handed and nothing in it accumulates, clamps or counts, so the Testbed goes on taking one `Timestep(min(frameTime, 1/60))` per rendered frame with F9's slow motion applied at the call site while the Game goes on spending its frame in whole 1/120 s steps under a per-frame cap — the divergence "Physics in the game" in `docs/game-session.md` records as a decision rather than a drift. There is deliberately **no** accumulating overload: it would put one executable's policy inside the shared type and hand the other an accumulator its stop-the-world debug keys fight, and two entry points would read as a menu of interchangeable options when what is recorded is that one of them is worse. What the component *does* own is the order **inside** a step — `Timestep` → `ContactEvents.Flush` → that step's contact work — and the work goes in as a **parameter**, so there is no way to take a step without handing over what belongs inside it. Both copies had that order right and both spelled it out in a comment beside it; it is not a comment now. The `ThreadDispatcher` is private for the same reason: it was the one remaining path to a step taken behind `Step`'s back, which would skip the flush and process a queue of contacts describing a world that has already moved on. `RetireBall` is the unregister-**then**-remove primitive under every removal path in both, a listener being keyed on a collidable reference Bepu is free to hand to the next body added.
- **`BallRenderSet`** (`Prazsky.BS3D`) with **`ClusterCollector`** (`Prazsky.BS3D.Physics`) — everything it takes to draw balls, and the one walk that fills it: the three procedural sphere LODs, the three `InstancedModelRenderer`s with every figure of the balls' look, the (type × LOD) instance buckets each of which becomes exactly one `DrawInstancedPrimitives` call, and the walk over the `PhysicsBall[,,]` plus the shot and falling lists. It stood in all three executables, the bucket bookkeeping written out a fourth time inside `Testbed.cs` alone — and the editor's copy is why that program's balls had drifted (see "The map editor's render pipeline" in `docs/formats-and-tools.md`). **The invariant it exists to protect is that every ball is visited exactly once a frame**: the occlusion ease, the attach glide and the ripple all advance state that lives on the `PhysicsBall`, so a second visit runs all three at double speed while the buckets still look perfectly correct, and a missed visit freezes them — neither fails loudly. `BeginFrame` hands back a `BallDrawFrame`, and that it is a **`readonly ref struct`** is what makes the discipline structural rather than documented: it cannot be stored in a field, so a collection cannot leak across frames into last frame's camera, and it is the only thing that can put an instance into a bucket at all. It throws if a second frame is opened before the first is drawn, which is the exact shape of the double-advance bug. The heartbeat's clock is `Draw`'s argument rather than a property, so a caller cannot end up with balls that do not breathe by never having set it; and a caller with **no physics** is first-class — the map editor hands its `BallsMap` to `BallDrawFrame.AddMap` and passes its own scene clock, which is the whole reason that editor can shade a cluster the way the played one shades.
- **`MouseAim`** — the aim off a captured cursor and off the pad's right stick, with the three load-bearing things about it that had only ever been written down once: the delta is divided by the frame time, which cancels exactly against the frame time `Cannon.Aim` multiplies back in (`MouseAim.SENSITIVITY`, unchanged at 2.0); the viewport centre is read **live** every frame and never cached; and the first captured frame is skipped (`MouseAim.Initialized`, dropped through `Invalidate`). The steps are exposed separately rather than as one routine because the two callers interleave their own work between them and always did — the Game reads its shot edge and handles a running drop cinematic between applying the delta and re-centring, the Testbed applies, re-centres, then adds the pad. One method would have forced one of those orders onto the other.
- **`Prazsky.Core.Render.LaunchSmears`** and **`Prazsky.Core.Render.Crosshair`** — the muzzle streak and the four bars at screen centre, both drawn by both executables now. The streak is the section below. The crosshair is four rectangles struck from a 1×1 white texel the component makes itself, and the Testbed draws those instead of loading, stretching and re-centring `Bitmaps/Aimer.png`: the asset and its `.mgcb` stanza are **deleted** (nothing else in any of the three content projects referenced it), which leaves the Testbed's `Bitmaps` directory empty and the executable with one less thing to load, and the Game's own white pixel went with them, the crosshair having been its only consumer. It takes one opacity scalar rather than a flag — the Testbed passes a plain 1 in free mode, where the lens *is* the shot, both pass `PreciseAim.Blend` in game mode, and `Draw` skips itself below a hundredth of an opacity, so neither caller needs a visibility test of its own *for the fade* — the Game has since gained one for a different question, the level being over, whose blend is frozen under the result page (#259; see `docs/game-session.md`).

What reconciling these copies turned up:

- **Four divergences in the ball draw, each resolved rather than picked.** The **ambient-occlusion direction** is a sum of unit vectors and has to be divided by the occluder maximum before the shader sees it; the Testbed divided and the Game did not, and it cost the cluster its whole look (see the ambient-occlusion bullet in `docs/game-session.md`). `BallRenderSet.OcclusionTarget` is the only code path that can build that vector now, and it divides. The **occlusion ease** was exponential in the Testbed and a linear ramp in the Game: the exponential survives, because framed in seconds it does not change with the frame rate *and* `exp(0)` is 1 — so it is already right on a zero-length frame, without the special case the Game's copy needed. The **attach glide's convention was inverted** between them: the Testbed's scalar was the fraction *travelled* and the Game's the fraction *retained*, which is harmless until a frame reports zero elapsed time, where the travelled form correctly leaves the offset alone while the retained form, as the Game guarded it, zeroed the glide outright. The *retained* form is the one kept, because it needs neither a complement nor a guard. And only the Game **clamped the occluder count**, where the clamp can never bind: `BallsMap.CountOccupiedNeighbors` examines exactly the twelve cells the divisor counts and no more, so what it returns cannot exceed it — and a clamp that cannot bind reads as a warning that the counter is not to be trusted, which invites the next reader to adjust the divisor instead. The bound is the counter's own documented contract now, stated once beside the divisor it pairs with.
- **The Testbed initialised its `ContactEvents` twice**, which #73 suspected and this confirms at source: `Simulation.Create` already runs `Simu.NarrowPhaseCallbacks.Initialize`, which *is* what initialises the stream, so the second call hooked its `BeforeCollisionDetection` handler onto the timestepper a second time — doubling the freshness pass on every step — **and** orphaned the first `CollidableProperty`'s buffers. It never crashed and never visibly misbehaved; it silently cost a second walk of every listener's previous collisions per step. There is one `Initialize` in the program now and `PhysicsWorld`'s constructor owns it.
- **Three leaks, all of them surfaced by giving each thing one owner.** The Testbed disposed the cannon's mesh but not its renderer (above); it never disposed its `ContactEvents` at all, leaving the stream's two index sets and its `CollidableProperty` returned to nobody and its hook on a disposed timestepper; and it never disposed its three sphere meshes or their instance buffers. All three were harmless only because the Testbed tears down at process exit and nowhere else — which is why the Game, which tears a session down per level, is the copy that had them right.
- **The two vector types were already crossing silently.** MonoGame 3.8.5 declares an implicit conversion from `System.Numerics.Vector3`, so every one of those crossings compiled without a cast — which is precisely the objection. The named `ToXna()` (`Prazsky.Core.Tools.NumericsExtensions`, mirroring the framework's own `ToNumerics()`) is kept **deliberately** rather than simplified away: with two vector types in one file and only their namespaces telling them apart, a crossing that is invisible at the call site is how a value ends up in the wrong frame with nothing on the line to say so, and CLAUDE.md's convention is that the boundary be visible where it is crossed. The reasoning is in the file so the next reader does not remove it, and the hand-rolled copies of the conversion — one of them in a library — are gone with it.

## Shooting flow (Testbed)

Contact detection uses `BS3DLibs/Prazsky.BS3D.Physics/ContactEvents.cs` (adapted from the Bepu demo, and shared with the Game since the port that gave it a simulation); Bepu callbacks fire on worker threads, so contact events are queued and processed on the main thread, in the `Timestep` → `Flush` → process order `PhysicsWorld.Step` now owns. When a shot ball hits the structure, it is snapped into the nearest free neighboring cell (`BallsMap.PutBallAtClosestEmptyPositionNextTo`) and then wired into the physics structure with `AttachBallToStructure`. What does that snapping is `Testbed/Physics/BallContactEventHandler.cs` since #73 — it was a second public top-level type nested in `Testbed.cs`, and it is still nearly the Game's copy written again, which is **#68**'s to close and not the split's. The two differ in more than layout, which is why: the Game's listens on `OnTouching` rather than `OnContactAdded`, so it never attaches off a *speculative* contact (measured there: 23 of 23 attaches fired on a negative depth, placing the ball a worst 3.79 units from the contact that chose the cell, in a lattice 1.0 across), and it asks `ShotPlacement` which cell a shot lands in so its aim preview cannot disagree with the outcome. Converging them is a gameplay change to verify by hand in both executables, not a file move.

## The launch smear

A ball leaves the cannon at `SHOOT_MULTIPLIER` (200 u/s) — several ball diameters a frame — so a colour streak is drawn on firing to sell the launch (`Shaders/ShotTrail.fx`, modelled on `Flame.fx`). It is **anchored at the muzzle, not following the ball**: at 200 u/s the ball attaches in ~0.075 s, far too brief to read, so instead `ShootBall` hands `LaunchSmears.Add` the muzzle, the shot direction and the type colour, and the smear lives its own `LIFETIME` (0.45 s) and fades — held near-full for most of that (a `1 - t²` curve, not `(1 - t)²`, so it does not dim the instant it appears and get missed), then the ball is crisp. `Draw` puts out one camera-facing billboard per live smear, stretched `LENGTH` (7) along the shot; the trap learned here is that the **bright, wide end must be the leading (far) end, not the muzzle** — the muzzle end is hidden behind the barrel, so a muzzle-bright streak shows only its faint tapering tip and reads as a thin thread. `Add` therefore takes a muzzle and a direction and derives *both* ends itself, so the inversion cannot come back through a call site. It is drawn additively and depth-read like the campfire flame (so the cluster/cannon in front still hide it), in linear radiance boosted over 1 (`BRIGHTNESS`) so it glows and blooms through the glare. The colour is the ball type's diffuse tint decoded to linear, its hue kept but its peak lifted to `COLOR_FLOOR` so even the near-black 8-ball leaves a faint grey smear — decoded, floored and boosted inside the component, so the one thing a caller can still get wrong is which ball type it asked about.

**All of it is `Prazsky.Core.Render.LaunchSmears` since #76 and both executables construct one**, so a dial changed here changes the shipping product's shot as well; the six dials, the billboard quad and the `Smear` struct are private inside it. The map editor has none of this only because it never shoots. What each caller keeps is *when* to age: the Testbed calls `Update` inside its `if (_simulate)` block, so a paused sim holds its smears where they are, while the Game ages them every frame it updates. **That asymmetry has a cost the Game had to pay (#93), and any future caller inherits it**: ageing in `Update` while drawing in `Draw` means a screen that stops updating but goes on being drawn underneath a page — which is what a pause and the result screen both are — freezes every live smear at a fixed alpha and keeps drawing it, while the page's own camera turns around it. A pause is honest about that (the whole frame is frozen, and it resumes), but the result screen's is not: its camera moves, and there is nothing to resume into. So `ShowResultScreen` calls `Clear()` — a level that has ended has no shot worth still showing. It is deliberately *not* the `LaserGrid` treatment (wall-clock stamps evaluated in `Draw`), which would be the fix if a smear mid-flight still had something to say once the page is up; it does not. **And this is the one hoist that paid in per-frame work rather than in lines.** The Testbed looked **five** effect parameters up by name every frame — two of them compile-time constants it re-sent for nothing, and BestPractices.md §1 names trail widths as its own example of exactly that — plus four more *per smear* inside the loop, and walked `CurrentTechnique.Passes[0]` per smear: `4n + 5` string scans of the effect's parameter collection per frame, on the draw path. The seven handles and the one pass are cached at construction now, the two widths set once there, and each smear's far end is derived when it is added rather than per smear per frame. The GPU-state restore is the other half: both copies hard-coded on the way out the ordinary translucent baseline the glass drawn immediately after them needs — the drain's funnel, then the ceiling plate — which was an implicit contract between two pieces of the frame. The component saves the three states it changes and puts back exactly what it found, and on a frame with no live smear it returns before touching any of them, which is most frames; so that baseline can never have been the smear's restore to begin with. Image-identical, and now stated where it belongs, once before the scene.

## The cannon (Testbed)

The cannon is procedural now (`Prazsky.Core.Render.CannonMesh`, built and owned by `CannonRig` since #76) — the last modeled asset, `Cilinder.dae`, and its `CannonMetal`/`CannonMetalNormal` textures are gone from the content project. It is a **profiled**, thick-walled steel tube along the barrel axis, on `MeshBuilder` since the breech reshape, running the classic gun silhouette: a muzzle swell sweeping into the slim chase, a girdle ring standing ahead of the cheeks, the reinforce taper thickening into the base ring, and a **slot** along the top (`CannonRig.SLOT_HALF_ANGLE`, ~57°) whose cut edges are closed by rim faces following that profile, so the wall never reads as paper-thin. The muzzle is open — the shot leaves through it. The **breech is closed**: it used to show the player's camera the same open hole the muzzle has, and it wears a dome carrying a cascabel knob now. The slot no longer runs the whole length either — it stops `CannonRig.CHAMBER_DEPTH` (a ball radius) ahead of the breech face, leaving a closed hood, and the dome behind that face hides a chamber cavity of the same depth, where the freshest round waits out the post-shot glide (next section). It still has to stay a tube — a barrel — with only a slit on top, or it reads as an open trough; the balls nest in the bore and only a strip of each shows through the slit, which is enough to see its colour. The slot's width is not just a look, it is how much of the magazine reads: the balls sit **entirely inside** the bore (centres on the axis, radius 0.5 against a bore of 0.6), so nothing protrudes and the near rim occludes them as soon as the eye is off the slot's own axis. At the original ~41° the queue was invisible from anywhere but straight above; the last slot's ball shows only its front half at rest — the hood covers the rest — which is enough to read its colour. No UVs, so no detail texture — plain steel whose sheen is the specular ambient reflecting the sky.

The point of the slot is the **magazine**: the cannon loads a queue of `Magazine.SIZE` (5) balls in a row inside the barrel, and they show through the slit so the player can see the colour that will fire and the ones queued behind it — you cannot aim a shot whose colour you cannot see. The queue is the shared `Magazine`'s and never leaves it: `ShootBall` fires `_magazine.Peek()` (the ball at the muzzle) and `Advance` shifts the queue forward and deals a fresh type into the back, so it never empties. The Testbed's next-colour policy, handed in at construction, is `RandomBallType` — uniform over all thirteen, because its cluster is whatever map was dropped on it (the Game injects a different one). The loaded balls are drawn as **real balls** — added to the shared ball buckets through `BallDrawFrame.Add` (`CollectMagazineBalls`, into the frame the ball draw already opened) at positions along the aim axis (`BorePose.SlotPosition`, `Magazine.SPACING` apart, slot 0 at the muzzle = the spawn point), so they get the same pattern, emission and sky lighting as every other ball. The advance is **animated**, not a snap: `Advance` arms `Magazine.Slide` at 1 (each ball drawn one slot back, so the muzzle slot is momentarily empty where the fired ball left) and `Magazine.Step` eases it to 0 off the wall clock, so the queue glides forward into the freed slot — every ball but the freshest. The full displacement would hang the tail round a whole slot **behind** the tube, which the once-open breech used to absorb (the fresh ball popped into the air behind the gun and slid in through the hole) and the dome that closed it would have the ball materialise through steel. So `BorePose.SlotPosition` clamps the last slot's share of the slide to `CannonRig.CHAMBER_DEPTH`: the round waits **parked in the breech chamber**, back hemisphere nested in the dome's cavity, front hidden under the hood, and pulls out into the slit only as the ball ahead glides clear of its slot. The park depth, the hood's length and the cavity's depth are one constant, which is what makes the handoff seamless — and the interpenetration while both balls are under the hood invisible.

**The round that fires next is MARKED, because the window alone could not say which one it was (#175).** Two testers, independently, read a colour off the wrong ball while playing and fired expecting a match that could not happen — and the premise the paragraph above rests on ("you cannot aim a shot whose colour you cannot see") is exactly what failed. The cause is geometry: from the stance the game is played from, and from precise aim which is that stance leant in, the barrel **hides its own muzzle end**, so of the front ball only the small ellipse of its cap is open to the air and the rest of it — like the whole queue behind it — is read through the pane. Two big domes under glass, told apart by one small open cap. So `GameplayScreen`'s collector (the **Game's**; the Testbed's own is untouched) feeds slot 0 a `ModelInstance.Ripple` amount that breathes — `MUZZLE_MARK_BASE` 0.20 ± `MUZZLE_MARK_SWING` 0.10 at `MUZZLE_MARK_HZ` 1.6, on the wall clock — while the queue behind it carries none.

- **The glass was asked to do it after all, and #204 is where that was reversed.** This bullet said the notch's reach was "already a ball radius, which lands exactly on the seam where the front ball parts from the next, and reaching further back would begin uncovering the *second* ball, which is the opposite of the signal wanted". Both halves were true and the conclusion still did not hold, because the reach was measured **along the bore** and nobody looks along the bore. From the precise-aim lens — `PreciseAim.RISE` (2) above and `BACK` (6) behind the front ball's centre, that centre being what `Cannon.MuzzlePosition` returns — the sight line grazing the old rim passed the front ball at a closest approach of **0.512** against its radius of **0.5**. It missed the ball by 0.012: none of the round about to fire was seen through open air, all of it through the pane. So the reach is `3 × BALL_RADIUS` now, bounded on both sides rather than picked — the front ball's upper silhouette crosses the pane's outer radius at z = −1.456, so the rim has to sit behind that, and the **queue** limits it from the other side, the same lens's line tangent to the second round's crown crossing the outer radius at z = −0.567, past which nothing further can be uncovered because that ball is already in the way. Uncovering the second round is therefore both unavoidable and licensed by the issue. The balls still touch by construction (`Magazine.SPACING` is one diameter, so the queue reads as full rather than gappy), so there is no strip of open bore between them to widen.
- **The channel was already wired end to end** — the cluster's landing ripple — and the Game already switches it on (`BallRenderSet`'s `ripples`), so this is a CPU-side draw argument and no shader change. A *positive* ripple adds mostly-white light (the shader's own note explains why white and not the ball's hue); the negative half of that channel is the ceiling alarm's colour replacement and is not what this uses.
- **Measured, A/B on one build with the mark toggled and the queue forced to a single colour** so nothing but the mark could differ — mean luma over the same three bands of the window: slot 0 **121.5 → 134.3**, slot 1 126.0 → 127.2, slot 2 131.8 → 132.3 (the ±1 on the two behind it is the balls' own breath at a different phase between two runs, i.e. the noise floor). The defect is in that first column as much as the fix is: **unmarked, the round about to fire was the dimmest of the three**, sitting deepest in the tube; marked, it is the brightest, and nothing else in the queue moved.
- **The amount is bounded by the thing the mark exists for.** At 0.9 the wiring was proved (the front ball blazes and the queue does not) and it also proved the ceiling: the lift is mostly white, so a strong mark washes a red ball to pale pink — it would cost the player the very colour they are reading. It also stays well under the value at which a ball blooms through the glare, so the marked round does not halo through the pane.
- **Its rate is its own**: the balls breathe at `BallRenderSet`'s 1.1 Hz and the landing ghost blinks at 2.2, so 1.6 sits between them and on neither's harmonic — a marker that beat with the cluster would read as part of it. And it is **gated on `_previewBeamVisible`**, i.e. on "would a shot leave the barrel this instant", which is the same answer the ghost and the aim beam are drawn on and is refused on the same three things `Shoot` refuses on. A marked round over a spent budget or a decided level would be the broken promise the ghost was taken out of the frozen frame for.

The cannon is drawn with its own look-at matrix (`Cannon.BarrelWorld`) rather than `Cannon.World`: the mesh is modelled with its muzzle towards local -Z and its window towards local +Y, which `CreateWorld` maps to the aim direction and the up vector. `Cannon` keeps the pose and nothing else (orbit, aim, `Position`, `AimTarget`, and since #76 the barrel's own draw matrix, orientation and muzzle); its `Object3D` model slot is unused, the inherited `World` it still builds is used by neither executable, and its constructor no longer takes a `Model`.

That up vector is **world up**: `Cannon.BarrelOrientation()` points the barrel down the aim and pins the slot (local +Y) to world up, so the slit stays on the barrel's upper face and never rolls about the bore. An earlier version rolled the slot to face the **camera** so the loaded queue was always readable, but the roll looked wrong in motion — the gun is to sit on a stand that only **elevates and traverses**, and a barrel that spins about its own axis to track the eye reads as unreal. The cost is accepted: from the low game camera the player sees the barrel's underside and not always the queue (precise aim, whose camera rides over the barrel, still looks into the slot). `CreateWorld` orthogonalises world up against the aim, so the slit stays on top as the barrel elevates; the bore is clamped well off vertical (`Cannon`'s elevation clamp), so world up and the aim are never parallel and it never degenerates — and it no longer depends on the camera at all. The magazine balls take **the same basis**, which stops them skewing: drawn unrotated they would hold a fixed world orientation while the barrel tilts around them. They lie in the bore, so they are carried by it.

`Cannon.Position` is the **trunnions** — the pins a carriage holds a real gun by, at the barrel's point of balance — and not the muzzle. Aiming leaves `Position` alone and only moves `AimTarget`, so whatever `Position` means is what the barrel turns about: with it at the muzzle the whole tube and its loaded queue swung from the tip, which is the one place a gun does not pivot. The mesh is therefore modelled **about the tube's midpoint** (`CannonRig` lays the muzzle and breech faces symmetrically around `CannonRig.PivotToFrontBall`, half the queue's length, which it derives from `Magazine.SIZE` and `SPACING`; the dome and cascabel then reach a further `CannonMesh.PoleZ` behind the breech face, so the breech side outreaches the muzzle — `CannonRig.BarrelReach`, which is the box the camera fit frames the gun as, upwards and sideways; downwards it frames only to the wheels, see #135 there), so the world matrix's translation is the pivot. The muzzle becomes derived — `Cannon.MuzzlePosition(pivotToFrontBall)`, that same distance ahead of the pivot along the aim — and is what both the magazine layout and `ShootBall`'s spawn point hang off, so the shot leaves from the ball the player was watching rather than from the middle of the barrel. The aim direction is unchanged by this (the muzzle lies on the pivot→`AimTarget` line), so nothing about where a shot goes moved. The constructor consequently takes no height at all any more: the gun stands on the island's dished stone, so `Cannon` re-seats `Position.Y` off its own orbit radius on every move — `CannonRig.TrunnionHeightAt`, the local floor (`ArenaIsland.FloorHeightAt`) plus the `AXLE_DROP + WHEEL_RADIUS` stack the carriage hangs below the pins — and the wheels sit on the stone wherever the walk stands, **by construction** rather than by two literals agreeing with a comment.

## The game-mode camera (Testbed)

Third-person, behind the gun and **below** its trunnions, near the arena floor. The game is picking a cell out of a cluster hanging overhead and putting a ball of that colour into it, so the frame has one job: show the whole map, from underneath, square enough to read the layout — the gun is furniture in the foreground.

- `Cannon.StandBearing` is **flattened to the horizontal**. Taken straight from `Position - OrbitCenter` it tilts down by however far the gun stands below the cluster (~30° here), so half of the camera's back-off went downwards and cancelled its height, putting the camera on the barrel's own axis. Flat, `GameCameraFit.CAMERA_HEIGHT` is the only thing setting the camera's height, which is the point of it.
- **How much of the angle on the map is actually the camera's to give is small, and worth knowing before tuning it.** It is `atan((clusterY - cameraY) / horizontal distance)`, and a camera behind the gun is always further out horizontally than the gun itself, so it always sees the cluster *flatter* than the ~30° the barrel has. On the floor it is ~25°; a true perpendicular from-below view would need the camera at y = -20, far under the world. What dropping it buys is 5° (edge-on, the map a strip at the top of the frame) to ~22°, which is the whole difference between reading the layout and not — but 40°+ is not on the table without moving the camera out from behind the gun or shrinking the orbit radius.
- **The view does not ride the aim.** `GetCannonOffsettedTarget()` is the field centre. The controls split cleanly: orbiting carries the camera around the field, aiming turns the barrel inside a frame that stays put. An earlier version aimed the view along the barrel, which swings the board the player is reading and, at full traverse or depression, swings it off the screen.
- `GAME_FOV` is **narrow** (`Pi/4.2`, ~43°) and that follows from the drop. From up behind the gun the barrel and the cluster were 57° apart and the FOV had to be wide enough to hold both, leaving the map a small patch in a very wide frame; from down here they are ~14° apart, so the frame can close in on the map.
- **The stand-off and the aim height are solved, not tuned** (`GameCameraFit.Solve`, run on map load and on resize). Both inputs move under a fixed number: the field is sized per map, and the frustum per display. It bisects for the smallest camera distance at which the field's eight corners, the top of the glass ceiling and the cannon all land inside both half-angles, then bisects that angular range to get the aim height. The gun is a box of `CannonRig.BarrelReach` about its trunnions **upwards and sideways** — the tube really can point there — but **downwards only to its wheels** (`ArenaIsland.FloorHeightAt` of its orbit radius, which is `CannonRig.TrunnionHeightAt` read the other way). It was a symmetric box until #135, and the point a whole barrel's length under the trunnions is a pose the tube cannot strike: it framed 1.14 units of nothing on the Game's Onion, and since the Game caps the frame's top (`FRAMED_LEVELS`) it was that reservation rather than the field deciding how little of a tall cluster fitted. Measured, re-measured after the breech dome grew the box and again after #135 shrank its underside: `Full.json` (10×10×16) settles at **35.2** and `Dense20x10x15` at **34.6**, `20x20x20` pulls back to **42.0** — 38.6, 37.9 and 47.2 respectively while the box was symmetric. Hand-tuned constants framed `Full.json` and cut the top clean off `20x20x20` — a fixed frame can only ever fit one field size.
- **The cannon is placed relative to the camera, not to the field** (`GameCameraFit.CANNON_CAMERA_STANDOFF`, 15 units in front of the lens). The queue showing through the barrel's slot is what the player reads the next colour off, so it is really a HUD element and has to keep its size on screen; anchoring the gun to the field instead lets a large map push the camera back and shrink the gun with it. Two lower bounds override the stand-off and **which one binds changes with the map**: clearing the field's corner (`CANNON_FIELD_CLEARANCE`, or the gun stands under the cluster) and staying far enough out that the resting aim sits comfortably inside `Cannon`'s elevation clamp (`CANNON_MAX_REST_ELEVATION`, ~40° against a clamp that reaches ~80° — see the clamp rework below). `Cannon.OrbitRadius` is settable for this and slides the gun along its current orbit angle, which is why the solve computes candidate poses instead of assigning it (see "The gun's hardware, in one copy" above).
- The two solves are **mutually dependent** — the camera frames the gun, the gun is placed off the camera — so `GameCameraFit.Solve` alternates them (`CONVERGENCE_ROUNDS`, 3), and `FitCannonAndGameCameraToMap` makes the one assignment the result implies afterwards. It very nearly settles on the first round, because at a fixed distance from the lens the gun's angular footprint is the same whatever the radius — but not exactly: a sub-0.1 residual survives to the third round, in both directions, which the section above measures.
- **Moving the cannon closer to the field does not close the empty ground between the gun and the map**, which is worth knowing before trying it again. It was tried: because the camera stands off from the *field centre*, a cannon closer to the field is a cannon *further from the camera* (20.3 units against 15.0 on `Full.json`), and since the camera sits only 1.5 below the trunnions the gun is near the horizon from it — pushing it away moves it *towards* 0°, i.e. down, not up. Its elevation went from 5.75° to 4.23° and it lost a quarter of its size. The gap is set by the vertical drop from the hanging map to the gun, and only moving one of those in Y changes it.

## Precise aim (ADS) (Testbed)

The complement to the overview above, and the deliberate inverse of its "the view does not ride the aim" rule: a hold-to-aim sub-mode of game mode that *does* ride the aim, the way a shooter's iron sights do. Held with the **right mouse button** (or the gamepad **left trigger**), it leans the camera in over the barrel and looks straight down the aim, so the whole map reads and the shot goes where a screen-centre crosshair points; releasing eases back to the overview. It only runs in game mode (free mode still shoots from the fly camera). The overview's "how much angle is the camera's to give is small (~25°)" limit is exactly what this dissolves: a camera that looks *along* the aim sees whatever the barrel points at, head-on.

- **The pose is an over-the-barrel scope.** `PreciseAim.LensPosition` sits the lens `BACK` (6) behind the muzzle along `-aim` and `RISE` (2) above the bore, so the barrel is a small sliver along the bottom of the frame — grounding, not obstruction — and `LensTarget` looks at a point **on the shot ray** (`muzzle + aim·d`), so screen centre marks where the shot is directed (the shot leaves the muzzle along `aim`, so this is honest before gravity). `d` is the cluster centre projected onto the aim, clamped to `[CONVERGE_MIN, CONVERGE_MAX]` = `[6, 90]`; since the crosshair is on the ray at *any* `d`, this only *centres* the small over-the-barrel parallax over the depth range the impact face sweeps. That centre is the **caller's** to supply (`Testbed.ClusterCentre` derives the field's vertical midpoint off the loaded map, the Game reads a figure it solved once for the level), so the shared component never learns what a map is. **Aiming steeply up, `-aim` points down, so the set-back drops the lens below the stone island** and it showed the disc from underneath — an artefact the widened elevation clamp (up to ~80°) exposed. `LensPosition` therefore floors the lens Y `PreciseAim.FLOOR_CLEARANCE` (1) over the stone directly under it — `ArenaIsland.FloorHeightAt` at the lens's own footprint, because since the gun stands on the island's **dish** no single fixed floor serves: one high enough for the arris sat *above* the trunnions of a gun standing at the drain and pinned the lean, one low enough for the drain let a lens near the arris sink into the higher stone there. At every clamped-steep aim the frame bottom still looks upwards, so the island stays out of frame and the lens never sinks through it. (Only the ADS camera rides the aim; the overview camera holds a fixed pose, so it never needed this.)
- **Two different ups, on purpose.** The lens offset uses `PreciseAim.LensUp` — world up made perpendicular to the bore (`Up - aim·dot(Up,aim)`) — so the lift is straight over the barrel at every pitch and yaw and the tube stays a *bottom-centre* sliver. The **view** up is plain world up, got for free by setting `_camera.Target` **last**: `BasicCamera3D`'s `Target` setter rebuilds the view with its fixed `Vector3.Up`, giving a level, roll-free horizon. Both are well-conditioned across `Cannon.EnsureAimInBounds`'s elevation clamp (`Cannon.MinElevation`/`MaxElevation`, ≈ `[-5.7°, +80°]` — see the clamp rework below): at the ~80° ceiling the bore is still ~10° off vertical, so `LensUp`'s `up` keeps `|up|² ≈ 0.03`, far above the 1e-4 fallback threshold (which only trips within ~0.6° of straight up); the horizontal-perpendicular fallback stays dead code unless the clamp is pushed almost to vertical.
- **Modest zoom, not a tunnel.** `PreciseAim.FOV` = π/5 (36°) against `GAME_FOV` π/4.2 (43°) — a 1.19× lean-in. It is the *vertical* FOV (`CreatePerspectiveFieldOfView`), so the sliver position and every parallax angle are aspect-independent; nothing here needs per-map or per-aspect solving (unlike the overview), because precise aim magnifies the aim region rather than framing the whole field — the overview owns full-field context.
- **One reversible blend scalar.** `PreciseAim.Blend` eases 0→1 while held with the same `MathF.Exp(-dt/τ)` idiom as `Magazine.Slide` (`BLEND_TAU` 0.08 s — the magazine's is where the idiom came from), and `BlendedPose` returns `Lerp(overview, leaned, Blend)` for FOV, position and target together. At `Blend == 0` the Lerps return the overview pose **bit-for-bit**, so disengaging re-asserts today's game mode exactly. It is C1-continuous through an interrupted hold/release (no state machine, no snap). `Step` is called on **unheld frames too** — that is how the lean eases back out, and it is what makes losing focus a fade rather than a drop. The pose comes back as a value and this file applies it, because the set order **FOV → Position → Target is mandatory** — the `Target` setter rebuilds the view last, with world up, from the freshest values; the FOV setter's own `Recalculate()` is a throwaway.
- **The mouse aims the cannon throughout game mode** — in the overview as well as in precise aim (the arrow keys are retired). The cursor is captured the whole time you play: hidden and recentred every frame off the **live** `GraphicsDevice.Viewport` centre (**not** `CameraInputHelper`'s cached `_widthHalf/_heightHalf`, which go stale after a resize). The pixel delta is divided by the frame time, which cancels *exactly* against the frame time `Aim` multiplies back in, so aim moves a fixed `0.001·MouseAim.SENSITIVITY` radians per pixel at any frame rate; `MouseAim.Initialized` skips the first captured frame so grabbing the cursor never yanks the aim, and `MouseAim.Invalidate()` is what drops that baseline whenever the cursor is about to arrive somewhere unrelated to where the player left it. Non-inverted (mouse up = aim up, mouse left = yaw left); the gamepad right stick aims too, fed in as a rate (no `1/dt`). Precise aim changes nothing about the aiming itself — it only leans the camera in over the barrel (below).
- **The aim persists within a game-mode session; only the mouse moves it.** There is no auto-return to rest and no recentre-on-orbit — the whole aim-parking mechanism (`_aimParkingStarted`, `HoldAim`, `ReturnAimToRest`) was removed from `Cannon`. Releasing precise aim keeps the aim (it is just a zoom-out, so you stay pointed where you were), and orbiting with A/D turns the carriage without dragging the barrel to centre — like a turret keeping its aim as the base rotates. An earlier build returned the barrel to rest on precise-aim release and recentred it on orbit; both were dropped once the mouse became the aim everywhere in game mode, where they would have discarded the player's aim on a zoom-out or a reposition. **Leaving game mode does reset it**, though: `SwitchGameMode(false)` calls `Cannon.ResetAim()`, which *eases* the aim back to the rest direction over ~1 s (`Vector2.SmoothStep`, the same smooth return the old orbit parking had; orbit position left alone) — the gun swings back rather than snapping, and each game-mode session starts neutral. `Cannon.Update` advances the ease every frame regardless of mode (the cannon is a prop in free mode), and a mouse `Aim` interrupts it.
- **Cannon controls (game mode).** Aiming (elevation/traverse) is the **mouse**; firing is **LMB or Space**. Orbiting the gun around the field is on **A/D** (A left, D right) and **walking it towards the field and back on W/S** — standing nearer steepens the shot up into the cluster's underside, standing further flattens it — all game-mode only: in the free fly camera the mouse and all four keys belong to the fly camera instead. The walk is `Cannon.Advance`, the same held-±1 protocol and ramp as the orbit; its range is solved per level (`GameCameraFit.CANNON_ADVANCE_STROKE` around the rest radius, the near end held off the field's footprint clearance *and* the drain's — `CANNON_DRAIN_CLEARANCE` keeps the wheels on stone, never out over the glass funnel) and its **ends are rubber, not stops**: over the last `Cannon.ADVANCE_EASE_ZONE` units the speed scales down linearly with the room left, so the gun converges on an end exponentially — it eases on asymptotically, never strikes, and reverses out at full speed with no dead travel. The walk also rides the island's dish: walking in carries the whole carriage downhill toward the drain and walking out back up (`CannonRig.TrunnionHeightAt`), which steepens the resting aim a second way beyond the shrinking radius. The camera deliberately does not follow the walk — not even in height, its lens being floored at the arris-stance height (`GameCameraFit`'s `LENS_FLOOR_Y`) — so the gun visibly advances and sinks in a steady frame (the magazine's on-screen size is bounded by the stroke cap). The arrow-key aiming and the old NumPad4/6 orbit are both retired.
- **The elevation clamp is strongly up-biased** (`Cannon.MinElevation`/`MaxElevation`, ≈ `[-5.7°, +80°]`; traverse `MaxTraverse`, ±45°). The whole target cluster hangs overhead, so aiming down only wastes shots into the ground. The old near-symmetric range (`[-28.6°, +45°]`) did both wrong: it let the gun plunge into the ground, yet **could not lift onto a large map's top cells** — the clean shot at a cell is from the orbit angle that *faces* it (the ball rises over open ground; the opposite angle is shallower but fires across the cluster and is obstructed), and that facing elevation runs ~50-65° on the big maps, so a third of a wide map was unreachable and the level could not be finished. ~80° up covers the top corners of every supported map with margin, kept off vertical for the ADS up-vector; ~-6° down is a hair of feel with no more ground shots. `Cannon.CanAimAt`/`AimAt` aim the barrel at a world point within the clamp (used by the test tooling and any future auto-aim); `OrbitToFace` stands the carriage facing a target.
- **Testing the aim/shoot gameplay** (it is otherwise mouse-driven and hard to automate): `aimcheck` logs, per loaded map, the steepest *facing* elevation any cell needs against the clamp and a PASS/FAIL (`Diagnostics/AimShootDriver.LogReachability`, formatting the facts `AimReachability.Check` returns — static and separate from the sweep, since `aimcheck` runs without `aimshoot`); `aimshoot` (implies `aimcheck`) auto-enters game mode and fires a scan up the field's centre column then at its four top corners (orbiting to face each via `Cannon.OrbitToFace`, aiming via `AimAt`), logging the elevation each shot wanted vs what the clamp gave — a shot held short reads `CLAMPED SHORT`. Both run headless in a background window (the mouse aim is gated off under `aimshoot`).
- **LMB fires in game mode**, completing the hold-RMB-to-aim / click-to-shoot idiom (Space still fires). No shooting change was needed: `ShootBall` in game mode already spawns from `Cannon.MuzzlePosition` towards `_cannon.AimTarget`, i.e. along `aim`, which is the very ray the crosshair converges on.
- **Two wiring fixes are load-bearing.** `CameraInputHelper.CameraMovement` gained an `allowMouseLook` argument, passed **false** in game mode, so its whole mouse region is gated off there — otherwise the right button would *also* toggle the fly camera's rotate/pan and call the stale-centre `CenterMouse`. And leaving game mode straight from ADS (F10 while holding) must not teleport: `SwitchGameMode(false)` captures the leaned pose and sets `_freeExitFromAds`, so the free-mode exit animation eases **position, target and FOV** together from the ADS close-up to the overview pose (a plain overview→free exit leaves the flag false and only widens the FOV, byte-identical to before).
- **Focus and edge-input hygiene.** The held flag handed to `PreciseAim.Step` is gated on `IsActive`, so a held **gamepad left trigger** — which XInput reports even when the window is unfocused — does not keep an alt-tabbed window leaned in; losing focus eases ADS out and restores the cursor. And because the LMB now fires in game mode, edge-driven input (the button actions and the LMB shot) is skipped for one frame after focus returns (`_wasActive`): the input state is not registered while inactive, so the very click that refocuses a windowed game would otherwise read as a fresh press against a stale "released" and fire an unintended shot.
- **The honest limit is parallax.** Because the lens sits `PreciseAim.RISE` above the shot ray, the crosshair is pixel-exact only at the convergence depth `d`; a nearer impact reads slightly low, a farther one slightly high — worst ~1.6° on the biggest map, and consistently *slightly low* since balls attach at the near face. It is fundamental to over-the-barrel framing; if pixel-perfect first-contact aiming is ever wanted, replace the `clusterCentre` dot-projection in `PreciseAim.LensTarget` with a Bepu raycast of `(muzzle, aim)` against the ball bodies and set `d` to the hit distance, at the cost of one raycast per frame — and note that it would have to arrive as another argument, since the component sees no simulation.
